## 0. 文档目的
本文件是阶段4唯一工程执行手册，目标是把 AgentMem 从“可运行”提升到“可归因、可学习、可验证、可维护”。

## 1. 阶段4目标、边界与基线

## 1.1 目标（必须同时满足）
1. 让 with_mem 对 no_mem 的收益可复现，而不是一次性波动。
2. 让记忆干预可解释：能回答“哪条经验在何时注入、为什么注入、是否有效”。
3. 让系统可维护：模块独立、接口稳定、故障定位可收敛到单模块。

## 1.2 非目标（阶段4不做）
1. 不做模型参数训练或微调。
2. 不引入复杂外部编排系统替换当前主链。
3. 不追求一次性功能膨胀，优先收口质量闭环。

## 1.3 当前实验基线（first50 unlimited）
1. no_mem：32/50（64%）
2. with_mem：34/50（68%）
3. 绝对提升：+4%（+2实例）
4. `tool_failed_actions`：91 -> 66（-27.47%）
5. `instances_with_tool_failures`：31 -> 26（-16.13%）
6. `total_cost`：6.094 -> 5.792（-4.96%）

## 1.4 术语定义（本文件内固定语义）
1. `only_no`：仅 no_mem 成功、with_mem 失败的实例集合。
2. `only_with`：仅 with_mem 成功、no_mem 失败的实例集合。
3. 高风险样本：满足任一条件的样本：
- 连续失败次数 >= 2；
- 出现 `action_error` 且错误阶段为 `execution/test`；
- 同一 `action_family` 在同一实例内重复失败 >= 2 次。
4. 稳定正增益：在至少 2 次独立复跑中同时满足 solved rate 正向且统计口径达标（见 2.3）。

## 2. 阶段4验收口径（统一，避免重复定义）

## 2.1 硬门槛（全部必须满足）
1. `KGWriter` 的 `emb_tool_output`、`emb_diff_summary` 不再使用占位输入。
2. with_mem/no_mem 运行都可稳定产出事件日志，且日志可用于注入链路归因。
3. `pytest PDDL_work_mem/source_code/sweagent_external_tools -q` 全绿。
4. 实验产物（manifest/metrics/divergence）可追溯到代码版本、配置、运行窗口。
5. ProblemFile 升级到 V2，且旧数据可读取（向后兼容）。
6. RCA 输出必须包含：`root_cause_nodes`、`propagation_chain`、`error_module`、`evidence_refs`。
7. unresolved 样本自动产出 `failure_card_v2` 并绑定证据引用。

## 2.2 改进门槛（至少满足2项）
1. solved rate 相对 no_mem 稳定正增益。
2. `tool_failed_actions` 持续下降。
3. `total_cost` 或 `mean_steps` 至少一项持续下降。
4. `only_no` 回退实例数量下降。

## 2.3 统计口径与判定规则（强制）
1. 复跑要求：
- 至少 2 次独立复跑；
- 每次使用同一数据切片与同一评测脚本；
- 每次产出 manifest、metrics、divergence 三件套。
2. solved rate 稳定增益判定：
- `delta_solved_rate = solved_rate(with_mem) - solved_rate(no_mem)`；
- 两次复跑都要求 `delta_solved_rate > 0`；
- 合并样本后 bootstrap 95% 置信区间下界 `>= 0`。
3. 效率指标改善判定：
- `tool_failed_actions` 或 `mean_steps` 或 `total_cost` 至少 1 项在两次复跑中同向改善；
- 建议最小改善幅度：相对变化绝对值 `>= 3%`。
4. 失败回退控制判定：
- `only_no` 数量不高于基线，且最好下降；
- 若 `only_no` 上升，则必须提交实例级原因分析与回滚建议。

## 3. 模块化改造总则（阶段4强制）

## 3.1 模块化目标
1. 少接口：模块之间只通过标准对象交换，禁止内部状态互相读取。
2. 高独立：每个模块单一职责，可单独测试与替换。
3. 易定位：异常必须能映射到单模块边界和对应输入输出。

## 3.2 模块边界强约束
1. 禁止跨模块直接依赖对方内部实现文件，只能依赖接口契约与标准对象。
2. 禁止重复定义 schema（ProblemFile/FailureCard 等只允许单源定义）。
3. 所有跨模块对象必须有 `schema_version`、`trace_id`。
4. 每个模块至少保留一个“纯输入 -> 纯输出”的回放接口。

## 3.3 统一交换对象（跨模块唯一）
1. `NormalizedEvent`：标准化事件对象。
2. `ProblemFileV2`：节点事实对象。
3. `RetrievalPack`：检索返回包。
4. `RCAReport`：根因归因结果。
5. `FailureCardV2`：失败经验卡。
6. `BeliefDelta`：信念更新增量。
7. `MetricsSnapshot`：运行与对比指标快照。

对象格式约束：
1. JSON 可序列化。
2. 字段命名固定，不允许同义字段并存。
3. 支持落盘与回放。

## 3.4 `trace_id` 生命周期规范（强制）
1. 生成点：
- `trace_id` 由模块A在 `normalize_event` 首次生成；
- 生成规则建议：`{run_id}:{instance_id}:{step_index}:{event_seq}`。
2. 透传点：
- 模块B~G 严禁重建 `trace_id`，只能透传与追加衍生字段；
- `intervention_id` 必须绑定所属 `trace_id`。
3. 校验点：
- 任何跨模块对象入参都要校验 `trace_id` 非空；
- 若缺失，进入降级路径并记录 `trace_id_missing=true`。
4. 降级策略：
- 允许执行但标记为“不可归因样本”；
- 该样本不得进入 `effective_interventions` 统计。

## 4. 模块划分与接口契约（函数级）

## 4.1 模块A：Event Gateway（在线入口）
职责：Hook 事件规范化、校验、追踪绑定。  
输入：`raw_event: dict`  
输出：`NormalizedEvent`

核心接口：
1. `normalize_event(raw_event) -> NormalizedEvent`
2. `validate_event_schema(event) -> ValidationResult`
3. `emit_event(event) -> EventEnvelope`

交换信息类型：
1. 追踪：`instance_id/run_id/agent_name/source_event/step_index/trace_id`
2. 载荷：`thought/action/tool_calls/error_message`

## 4.2 模块B：Context Builder（ProblemFileV2）
职责：把事件上下文构造成可归因、可检索的节点事实。  
输入：`NormalizedEvent`、`TaskState`  
输出：`ProblemFileV2`

核心接口：
1. `build_problem_file(event, state) -> ProblemFileV2`
2. `serialize_problem_file(problem_file) -> dict`
3. `from_dict(data) -> ProblemFileV2`

交换信息类型：
1. 追踪字段：`instance_id/run_id/source_event/step_index`
2. 语义字段：`intent_text/action_text/action_family`
3. 统计字段：`execution_stats/test_stats/patch_stats`
4. 失败字段：`failure_signature.error_stage/exit_code/is_timeout/nonzero_exit`

## 4.3 模块C：Retrieval & Injection（在线检索注入）
职责：按场景检索历史经验并生成受预算约束的注入提示。  
输入：`ProblemFileV2`、`QueryContext`、`BudgetPolicy`  
输出：`RetrievalPack`、`InjectionHints`

核心接口：
1. `retrieve_for_planning(query) -> RetrievalPack`
2. `retrieve_for_repair(query) -> RetrievalPack`
3. `compose_injection(retrieval_pack, budget) -> InjectionHints`

交换信息类型：
1. 建议：`recommendations`
2. 证据：`evidence_refs`
3. 置信与解释：`confidence/assumptions/failure_mode_if_wrong`

## 4.4 模块D：RCA Engine（异步归因）
职责：步骤级归因、最小根因集合提取、传播链重建。  
输入：`TaskSnapshot`、`FailureTerminal`  
输出：`RCAReport`

核心接口：
1. `score_decisive_steps(snapshot) -> list[DecisiveStep]`
2. `extract_root_causes(decisive_steps) -> RootCauseSet`
3. `build_propagation_chain(root_causes, terminal) -> list[str]`
4. `analyze_failure(snapshot) -> RCAReport`

交换信息类型：
1. 归因：`root_cause_nodes/propagation_chain/error_module/error_type`
2. 纠偏：`corrective_actions/preventive_checks`
3. 解释：`confidence/evidence_refs`

## 4.5 模块E：Experience Distiller（经验提炼）
职责：把轨迹+RCA提炼为可复用经验对象。  
输入：`RCAReport`、`TaskSnapshot`、`OutcomeSummary`  
输出：`FailureCardV2`、`RepairPatternV2`、`PreventiveRuleV2`

核心接口：
1. `build_failure_card(report, snapshot) -> FailureCardV2`
2. `build_repair_pattern(history_slice) -> list[RepairPatternV2]`
3. `build_preventive_rule(history_slice) -> list[PreventiveRuleV2]`

交换信息类型：
1. 失败卡：`error_signature/candidate_fixes/verification_commands/evidence_refs`
2. 修复模式：`trigger_signature/fix_action_template/expected_verification`
3. 预防规则：`when/should_check/support`

## 4.6 模块F：Belief & Policy（信念与策略）
职责：经验统计、信念更新、偏好策略编译与冲突消解。  
输入：`FailureCardV2`、`RepairPatternV2`、`RunOutcome`  
输出：`BeliefDelta`、`PreferenceSet`

核心接口：
1. `update_beliefs(experiences, outcome) -> BeliefDelta`
2. `compile_preferences(beliefs) -> PreferenceSet`
3. `resolve_conflicts(belief_candidates) -> ConflictResolutionResult`

交换信息类型：
1. 统计：`support/uplift/confidence/severity`
2. 策略：`preference_rules/constraint_candidates`

## 4.7 模块G：Metrics & Audit（评测与审计）
职责：指标汇总、干预追踪、with_mem/no_mem 差异分析。  
输入：`RunArtifacts`、`InterventionTrace`  
输出：`MetricsSnapshot`、`DivergenceReport`

核心接口：
1. `record_intervention_trace(event, hints, outcome) -> TraceRecord`
2. `collect_metrics(run_dir) -> MetricsSnapshot`
3. `compare_runs(with_mem_run, no_mem_run) -> DivergenceReport`

交换信息类型：
1. 成本与成功率指标
2. 注入有效性指标
3. 差异字段：`detour_reduction/mem_unique_failures/effective_interventions`

## 5. 阶段4实施路线（按顺序执行）

## Phase A：基础稳定（先让系统可开发、可复现）

### A1. 依赖与运行基线统一 ✅
目标：本地环境可复现一致结果。  
重点：固定 `sentence-transformers`、移除随机 embedding 回退、修复旧断言。

### A2. 事件日志落盘硬校验 ✅
目标：杜绝“有结果无日志”。  
重点：with_mem 运行后必须存在 `with_mem_tool_events_window_*.jsonl`，否则失败退出。

### A3. ProblemFile Schema 单源治理 ✅
目标：消除 schema 分裂。  
重点：`core/problem_file.py` 作为唯一规范来源；`from_dict` 保持向后兼容。

---

## Phase B：记忆质量与归因核心改造

### B0. ProblemFile V2 节点升级（P0） ✅
目标：节点可归因、可比较、可学习。  
重点字段：`instance_id/run_id/source_event/step_index/action_text/action_family/patch_stats/test_stats/execution_stats`。

### B1. 去占位 embedding（P0） ✅
目标：`emb_tool_output`、`emb_diff_summary` 使用真实证据内容。  
重点：读取失败显式打标，不允许静默置空。

### B2. failure_card_v2（P1） ✅
目标：unresolved 样本沉淀为结构化可执行经验。  
重点：`error_signature/action_trace_snippet/candidate_fix_actions/verification_commands/evidence_refs`。  
执行约束：B2 分两步实施。
1. B2-Base：先产出基础 failure card（不依赖 RCA 深度字段）。
2. B2-RCA：在 B4 完成后回填 `root_cause_nodes/propagation_chain/error_module`。

### B3. 检索分型升级（P1） ✅
目标：按问题类型检索，不再单一 planning/repair。  
分型：`planning`、`error_recovery`、`test_failure_fix`、`regression_guard`。

### B4. RCA V2 升级（P0） ✅
目标：从末端错误归类升级为步骤级决定性归因。  
关键机制：
1. 候选关键步回溯 + `decisive_score`
2. 同分按最早决定性步骤优先
3. 输出最小根因集合 + 传播链 + 模块分类 + 纠偏建议
执行顺序约束：
1. B4 完成后，必须触发 B2-RCA 回填任务。
2. 未完成回填前，failure card 不得作为高优先经验注入。

## 7. 阶段4完成后的预期工作流程（三段式）

## 7.1 在线链路（Online Path）
1. Hook 事件进入 Event Gateway -> 生成 `NormalizedEvent`。
2. Context Builder 生成 `ProblemFileV2` 并写入事实层。
3. Retrieval & Injection 按场景检索并生成提示。
4. 注入提示带 `intervention_id + evidence_refs` 写回 agent。
5. Metrics & Audit 记录即时干预结果。

## 7.2 异步链路（Async Path）
1. 任务完成后生成 `TaskSnapshot`。
2. RCA Engine 对 unresolved/高风险样本做步骤级归因。
3. Experience Distiller 生成 failure/repair/preventive 三类经验对象。
4. Belief & Policy 更新统计并编译偏好策略。
5. Metrics & Audit 汇总异步产物质量。

## 7.3 回流链路（Feedback Loop）
1. 对齐 with_mem/no_mem 同实例轨迹。
2. 抽取 `effective_interventions` 并提升检索优先级。
3. 抽取 `mem_unique_failures` 并更新黑名单/降权规则。
4. 低价值经验降权或停用，保持经验库收敛。
5. 按同口径复跑下一轮实验。

## 9. 风险与回滚

## 9.1 主要风险
1. 注入过强导致 token 膨胀和路径偏航。
2. failure_card 噪声过高反向污染检索。
3. 分型检索和 RCA 引入开销导致性能回退。
4. schema 扩展引发历史数据读取失败。

## 9.2 回滚策略
1. 注入总开关：`SWE_AGENT_MEM_INJECT_ENABLED=0`
2. 降级检索：切回 legacy/hybrid 路径。
3. 仅保留在线链路，关闭异步 RCA 与提炼。
4. schema 写路径降级为 V1，读路径保持双版本兼容。
5. 依赖固定 manifest 复跑，对照回滚前后差异。

## 11. 本文档的工程决策（固定）
1. 阶段4采用 7 个一级模块；RCA 必须独立为异步模块。

5. 模块级代码测试文件统一放在阶段4目录下的 `tests/` 子目录。
