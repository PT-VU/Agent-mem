# 阶段五经验提取升级

> 目标：在现有 AgentMem 链路上，引入“LLM 辅助经验提取”，提升经验质量、可复用性与对最终 solved_rate 的贡献。  
> 参考依据：`PDDL_work_mem/00_project_context/resources/papers/归因.pdf`（AgentErrorTaxonomy + AgentDebug 方法）。

---

## 1. 现状问题（升级动机）

结合阶段四/阶段五实验复盘，当前经验提取的主要问题是：

1. 提取覆盖率低，`plan_generated -> 可写经验` 转化损耗高。  
2. 提取结果偏模板化，容易被 fingerprint 合并为少量泛化经验。  
3. 失败案例未稳定沉淀为可执行修复经验（failure card / repair pattern 质量不足）。  
4. 注入内容常是“流程建议”，缺少“根因-修复动作-验证方式”的闭环。  
5. 经验是否有效缺少精细归因，导致难以持续迭代。

根因：当前提取以规则聚合为主，缺少“逐 step 分析 + 最早关键错误定位 + 可执行反馈生成”。

---

## 2. 升级目标（Definition of Done）

本次升级后，经验提取应满足以下可验收标准：

1. 不新增“归因报告”作为最终产物，最终产物格式保持现有模板。  
2. 对失败 attempt，必须稳定产出可执行经验（修复建议 + 验证命令），并映射到现有经验模板。  
3. 抽象经验不再长期收敛到 1~2 条模板，经验多样性显著提升。  
4. 注入经验可解释：能回答“为什么注入、注入后行为是否变化、是否有收益”。  
5. 在官方评测口径上，with_mem 相对 no_mem 的 solved_rate 或效率指标有稳定净增益。

---

## 3. 设计原则

1. 根因优先，不做“全错全修”：优先定位最早、最关键、可改变结局的错误。  
2. LLM 做辅助，规则做落盘：LLM 只辅助发现更真实、更丰富的经验；最终写入仍由既有模板约束。  
3. 在线轻量，离线重分析：不让 LLM 分析阻塞主求解链路。  
4. 模板兼容优先：LLM 不得改变最终经验对象的格式模板与字段语义。  
5. 增益可验证：每条经验都要绑定来源事件和后续效果。

---

## 4. 升级总体架构（参考 AgentDebug 三阶段思路）

### 4.1 阶段 A：细粒度错误分析（Map to Taxonomy）

输入：

1. 单次 attempt 的完整轨迹（step、thought、action、observation、tool result）。  
2. 当前错误分类体系（可先采用 Memory/Reflection/Planning/Action/System 五模块）。  

处理：

1. 对每个 step 的每个模块进行错误判定。  
2. 输出模块级错误标签、证据、理由、置信度。  

输出对象（中间态，不作为最终落盘产物）：

1. `StepModuleAssessment[]`（结构化错误剖面）。

### 4.2 阶段 B：关键根因错误定位（Critical Error Detection）

输入：

1. 阶段 A 的全轨迹错误剖面。  
2. 任务结果（submitted/resolved/unresolved/incomplete）。  

处理：

1. 让 LLM 从全局视角定位最早关键错误（critical step）。  
2. 给出错误类型、根因解释、级联影响链。  

输出对象（中间态，不作为最终落盘产物）：

1. `CriticalSignal`（关键错误信号，用于后续经验提炼）。

### 4.3 阶段 C：经验合成与可执行反馈生成

输入：

1. `CriticalSignal`。  
2. 原始轨迹中相关证据片段。  

处理：

1. 生成可复用经验（可跨实例）。  
2. 生成针对当前类型问题的修复动作模板。  
3. 生成验证命令（最小验证闭环）。  

输出对象（最终仍映射到既有模板）：

1. `abstract_experience`（现有模板）。  
2. `failure_card_v2`（现有模板）。  
3. `repair_pattern_v2`（现有模板）。

---

## 5. LLM 在经验提取中的辅助角色（本次新增）

LLM 在提取链路承担 4 个辅助角色：

1. 错误检测器：判断 step/module 是否命中 taxonomy 错误，并输出证据。  
2. 根因定位器：识别最早 critical error，避免只修表面错误。  
3. 经验蒸馏器：把轨迹转为更可复用的经验候选，而非纯文本复述。  
4. 反馈优化器：当第一次建议无效时，迭代细化修复策略。

约束：LLM 只提供中间分析与建议，不直接定义最终存储格式。

---

## 6. 数据契约（中间态 + 最终态）

### 6.1 LLM 中间输出（仅运行时使用，不落盘为新模板）

#### 6.1.1 StepModuleAssessment

```json
{
  "attempt_id": "string",
  "step_index": 12,
  "module": "memory|reflection|planning|action|system",
  "error_detected": true,
  "error_type": "constraint_ignorance",
  "evidence": "quote/span",
  "reasoning": "why",
  "confidence": 0.78
}
```

#### 6.1.2 CriticalSignal

```json
{
  "attempt_id": "string",
  "critical_step": 12,
  "critical_module": "planning",
  "error_type": "constraint_ignorance",
  "root_cause": "...",
  "cascading_effects": [
    {"step": 13, "impact": "..."},
    {"step": 16, "impact": "..."}
  ],
  "correction_guidance": "...",
  "confidence": 0.81
}
```

### 6.2 最终落盘模板（保持不变）

1. `abstract_experience`（含 `pattern_type/abstracted_intent/success_conditions/failure_avoidance`）。  
2. `failure_card_v2`（含 `error_signature/candidate_fix_actions/verification_commands/evidence_refs`）。  
3. `repair_pattern_v2`（含 `trigger_signature/fix_action_template/expected_verification/evidence_refs`）。  

### 6.3 映射规则（LLM 输出 -> 既有模板）

1. `CriticalSignal.error_type` -> `failure_card_v2.error_signature.error_type`。  
2. `CriticalSignal.correction_guidance` -> `repair_pattern_v2.fix_action_template`。  
3. `StepModuleAssessment.evidence` -> `*_v2.evidence_refs`（经清洗/去重）。  
4. LLM 不得新增落盘类型，不得修改既有模板字段名与语义。

---

## 7. 触发策略（何时调用 LLM 提取）

### 7.1 必触发

1. `run_done` 且 `resolved=false`（失败样本）。  
2. `run_done` 且 `resolved=true` 且存在明显 recovery 轨迹（用于提炼成功修复经验）。  

### 7.2 条件触发

1. 同类错误在单 attempt 内重复出现 >= 2 次。  
2. 发生高成本退出（高 token/高步数但 unresolved）。  
3. action_error 高频爆发（用于快速补失败经验）。

### 7.3 不触发

1. 轨迹信息不足（例如极端截断，仅 1~2 步）。  
2. 仅有空洞模板内容且无执行证据。

## 8. 与现有代码的集成方案

### 8.1 新增模块建议

1. `agent_mem/processing/llm_extractor.py`  
职责：调用 LLM 执行阶段 A/B/C，输出结构化 JSON。

2. `agent_mem/processing/taxonomy.py`  
职责：维护错误分类定义与版本。

3. `agent_mem/processing/extraction_orchestrator.py`  
职责：组织事件、调度 LLM 提取、写入 graph_store。

### 8.2 现有模块改造点

1. `sweagent_adapter.py`  
在 `handle_run_done` 触发异步提取任务，不阻塞主流程。

2. `graph_store.py`  
不新增新的最终经验模板集合；仅将中间分析映射写入既有模板集合。

3. `memory_agent.py`  
检索优先级改造：优先召回“critical-error 对齐”的经验，再回退通用经验。

### 8.3 运行策略

1. 在线：只读取已提炼经验，不做重 LLM 分析。  
2. 异步：run_done 后执行 LLM 辅助提取，映射写回既有经验库。  
3. 定时：批量重评分低质量经验并降权。

---

## 9. 质量门禁与去噪策略

1. JSON 严格校验：schema 不合法直接丢弃。  
2. 证据完整性：无 evidence 不入库。  
3. 置信度门槛：`item_confidence < 阈值` 进入候选池，不直接注入。  
4. 去重：fingerprint + semantic similarity 双重去重。  
5. 反模板污染：连续重复通用语句自动降权。  
6. 回流降权：注入后无效次数累计后下调优先级。

---

## 10. 评估方案（验证“LLM 提取是否真的更有用”）

### 10.1 过程指标

1. 提取覆盖率：`有有效经验写入的attempt / 总attempt`。  
2. 关键根因有效率：修复 critical error 后是否减少重复失败。  
3. 经验可执行率：经验是否包含可执行修复动作与验证命令。  
4. 注入命中率：注入后 N 步内是否出现建议动作执行。  

### 10.2 结果指标

1. 官方 `resolved_rate`（planned 口径）。  
2. 平均步数与 token 成本。  
3. incomplete 控制（不得明显劣化）。  
4. only_with / only_no 的实例级差异。

### 10.3 对照实验

1. A 组：现有规则提取（baseline）。  
2. B 组：规则 + LLM 辅助提取（本方案）。  
3. C 组：仅 LLM 提取（用于评估规则约束价值，不建议生产）。

---

## 11. 分阶段实施（工程落地顺序）

1. 第 1 步：定义 taxonomy 与 JSON schema，先实现离线抽取脚本。  
2. 第 2 步：接入 `run_done` 异步提取，不影响线上主链路。  
3. 第 3 步：把 LLM 中间结果映射入既有经验模板并可检索。  
4. 第 4 步：改造注入排序逻辑（critical-error 对齐优先）。  
5. 第 5 步：加入质量门禁和回流降权机制。  
6. 第 6 步：跑 first50 对照实验，按官方口径验收。

---

## 12. 风险与缓解

1. 风险：LLM 成本上升。  
缓解：仅对高价值失败样本触发，异步批处理。

2. 风险：LLM 输出不稳定。  
缓解：低温度、严格 schema 校验、多次采样一致性检查。

3. 风险：错误归因“看起来合理但不可执行”。  
缓解：强制输出修复动作 + 验证命令；无验证计划不入库。

4. 风险：引入过多噪声经验。  
缓解：质量门禁、反模板污染、回流降权、周期清理。

---

## 13. 本文档对应的直接开发结论

1. 阶段五应把“经验提取”从规则聚合升级为“LLM 辅助 + 结构化经验合成”。  
2. 重点不是增加经验数量，而是提升“高真实性经验”的命中和可执行性。  
3. 实施上必须坚持“在线不阻塞、离线重提炼、结果可回流”的架构。  
4. LLM 只做提取辅助，不改变最终经验格式模板。  
5. 验收必须用官方评测口径，不以 submitted 代替 resolved。
