## 第二部分：经验提取/经验存储/经验复用的做得好与做得不好

### 2.1 经验提取（Extraction）
#### 做得好
1. 在线提取链路可跑通：`plan_generated -> external_tool_response -> buffered -> injected` 在日志中可见。
2. 检索过程有结构化调试字段（候选数、子图数、query_type），具备基础可审计性。

#### 做得不好
1. 提取覆盖偏低：`external_tool_response(769) / plan_generated(5211) ≈ 14.8%`。
2. 错误提取基本失效：
   - 50/50 实例都出现 error-like observation（总计约 971 步）
   - 但实例日志中 `event_handled="action_error"` 为 0。
3. 超时问题明显：`External tool_a timed out` 高频出现，导致大量可提取信息未进入后续链路。

### 2.2 经验存储（Storage）
#### 做得好
1. 持久化存储链路正常：`observation_kg / belief_graph / abstract_experiences` 文件存在并持续写入。
2. 可以保存结构化经验对象（belief、abstract_experience）的基础框架已建成。

#### 做得不好
1. 存储内容与运行规模不匹配：
   - `metadata.json` 显示 `total_actions=856`，`total_beliefs=1`，`total_abstract_experiences=2`。
2. 失败经验未形成闭环：`failure_cards_v2=0`，`repair_patterns_v2=0`。
3. 语义多样性不足：建议文本高度重复，推荐语句几乎集中为 3 条模板（例如 `Consider: Generate plan for task...`）。

### 2.3 经验复用（Reuse）
#### 做得好
1. 在最终结果上出现净正收益：官方 planned solved rate +2pp。
2. 个别难例存在有效干预迹象：`astropy__astropy-12962` 有多次注入并成为 only_with 成功实例。

#### 做得不好
1. 注入覆盖不足：仅 16/50 实例被注入，34/50 完全无注入。
2. 触发与注入脱节：触发器很多，但注入少，说明触发后链路损耗严重。
3. 注入内容可执行性弱：多为通用流程建议，缺少具体问题-具体修复策略。
4. 注入与效果关联不稳定：
   - 有注入实例 solved 比例未显著高于无注入实例
   - 注入更像“高复杂场景伴生信号”，而非稳定增益因子。

## 第三部分：对照阶段四预期的偏差、未预料问题、以及设计遗漏

### 3.1 未达到阶段四预期的行为（对照阶段四工程指导文件）
> 对照文档：`PDDL_work_mem/02_task_management/phase_history/阶段4/阶段4工程开发指导文件_2026-02-28.md`

1. 预期“可解释干预闭环”未达成。
- 预期：回答“哪条经验在何时注入、为什么注入、是否有效”。
- 实际：注入事件存在，但实例级归因链路不完整（事件 `instance_id` 基本为 `main`），难以稳定追踪“注入 -> 后续行为 -> 成败”。

2. 预期“query_type 分型检索”未达成。
- 预期：`planning/error_recovery/test_failure_fix/regression_guard`。
- 实际：几乎只有 `planning`；`action_error` 路径在本次实例日志中几乎未被有效触发。

3. 预期“失败样本产出 failure_card_v2”未达成。
- 预期：unresolved 自动沉淀 failure card。
- 实际：`failure_cards_v2=0`，说明失败经验没有形成高质量可复用资产。

4. 预期“RCA 深度参与经验提炼”未达成。
- 预期：RCA 输出应进入经验提炼与回流。
- 实际：本批数据里未体现出 RCA 对失败学习的实质贡献（失败经验资产几乎为空）。

### 3.2 本次暴露的未预料问题与错误
1. 外部工具调用稳定性问题被低估。
- 高频超时导致提取链路在最前端即大量丢包。

2. 任务映射粒度问题被低估。
- 事件层缺乏稳定 instance 级标识，导致跨文件对账困难，评估可信度受限。

3. 存储污染风险被低估。
- `run_done` 成功摘要与“Generate plan for task”类模板被反复强化，容易形成低信息密度经验，稀释真正可执行经验。

4. 指标表象与真实效用存在偏差。
- solved_rate 有小幅提升，但 incomplete 大幅上升，说明“提升”与“稳定性”未同时达标。

### 3.3 阶段四设计未完全覆盖与遗漏点
1. 缺少“提取覆盖率门禁”。
- 仅看最终 solved_rate 不足，应增加：
  - `external_tool_response / plan_generated` 最低覆盖阈值
  - `action_error` 提取覆盖阈值

2. 缺少“注入必要性判定 + 注入后验证”闭环。
- 当前触发多、注入少，且注入后效果评估薄弱，应补：
  - 注入触发命中率
  - 注入后 N 步 recovery/regression 指标

3. 缺少“经验质量去重与降噪策略”强约束。
- 需要限制模板化建议重复写入，增加最小信息增益阈值。

4. 缺少“失败资产硬产出”门槛。
- unresolved 样本应强制产出 `failure_card_v2`（即使是低置信版本），否则失败无法被学习。

5. 缺少“评测口径一致性保护”。
- 应同时追踪 planned/submitted 两口径，并将 incomplete 纳入核心验收门禁。

### 3.4 总结判断（阶段四效果）
1. 阶段四实现了“可运行”的 AgentMem，但尚未实现“稳定有效”的跨实例经验复用。
2. 当前最关键短板不在“是否有记忆模块”，而在“失败信息能否稳定提取并沉淀为高质量经验”。
3. 若不先修复提取覆盖与失败学习链路，后续扩大实验规模会继续放大噪声，难以验证体系真实增益。

## 第四部分：修改建议（新增）

### 4.1 “注入实例成功率”直接回答
1. 按本报告正文口径（注入覆盖 16/50）计算：注入实例中官方 resolved 为 4 个，成功率为 `4/16 = 25.0%`。
2. 对应 resolved 实例为：
- `astropy__astropy-12825`
- `astropy__astropy-12962`
- `astropy__astropy-13032`
- `astropy__astropy-13306`
3. 说明：按当前落盘 `*.info.log` 复算可见“发生过注入”的实例为 17 个，则为 `4/17 = 23.5%`。该差异来自统计口径与补跑覆盖差异，不影响“注入组成功率未显著领先”的结论。

### 4.2 为什么只有 16 个实例有注入，而其余实例无注入
1. 注入链路是串联硬条件，不是“触发即注入”：
- 先有 `plan_generated` 事件。
- Tool A 在超时前返回可解析结果。
- 返回结果里有可用建议，且通过置信度阈值。
- 建议被写入 `pending hint buffer`。
- 下一次 `on_model_query` 到来时才会真正注入。
2. 本次数据中链路损耗很大：
- `plan_generated=5211`
- `external_tool_response=769`
- `memory_hint_buffered=21`
- `memory_injected=21`
3. 另一个核心问题是 Tool A 稳定性不足：
- 50/50 实例都出现 `External tool_a timed out`。
- 全量 `*.info.log` 中该超时日志出现约 4601 次。
4. 当前 HOOK 事件中的 `instance_id` 基本是 `main`，实例级可追踪性弱，导致“注入-效果”归因困难，进一步放大统计误差。

### 4.3 对“提取覆盖偏低 + Tool A 大量出错”的修复思路
1. P0 稳定性修复（先做）
- 将 Tool A 超时阈值从 8 秒提升到分层阈值（建议 `8s/20s` 双档：快速路径 8s，失败后重试 20s）。
- 为 Tool A 增加熔断与降级：连续超时时进入“轻检索模式”，仅返回 cached top-k，避免阻塞主链路。
- 将 Tool A 调用从主执行路径拆为异步请求 + 同步读取最近成功结果（主流程不被单次超时拖死）。

2. P0 覆盖率修复（同时做）
- 强制补齐 `action_error` 与 `run_done` 的提取分支，不能只依赖 `plan_generated`。
- 为提取链路增加门禁指标并在实验脚本里 hard fail：
- `external_tool_response / plan_generated >= 0.35`
- `memory_hint_buffered >= 0.15 * external_tool_response`
- `action_error` 覆盖率（error-like observation 命中）>= 0.60

3. P1 质量修复（第二阶段）
- 引入建议去重与最小信息增益阈值，抑制模板化建议反复写入。
- 强制产出失败资产：每个 unresolved 至少产出 1 条 `failure_card_v2`（低置信也要产出）。
- 检索分型从“几乎全 planning”扩展到 `error_recovery/test_failure_fix/regression_guard`，并在日志中独立计数。

4. P1 可观测性修复（必须补）
- 将真实实例 ID（`problem_statement.id`）注入 HOOK payload，替换当前 `main` 伪标识。
- 为每次注入写入 `intervention_id`，并在后续 N 步记录“是否触发恢复动作/是否最终 resolved”，形成可解释干预闭环。

### 4.4 可执行的短期目标（下一轮实验前）
1. 先把 Tool A 超时与 instance_id 追踪修好，再重跑 Full First50 with_mem。
2. 新一轮验收必须同时满足：
- `incomplete_instances` 不高于 no_mem 对照组 +2。
- 注入覆盖率至少达到 30/50。
- 注入组 solved_rate 不低于非注入组 solved_rate。
3. 若以上不满足，暂停扩大样本规模，先回到链路稳定性与失败经验沉淀能力修复。

## 第五部分：Smoke10 经验链路专项归档（提取-保存-注入）

> 目标：把本轮问答中的关键诊断完整归档，作为后续阶段升级的事实基础。  
> 主要证据来源：  
> 1) `PDDL_work_mem/04_testing/reports/withmem_vs_nomem_full50_and_smoke10_deep_report_20260303.md`  
> 2) `PDDL_work_mem/04_testing/reports/smoke10_full_analysis_20260303.json`  
> 3) `PDDL_work_mem/06_artificial_intelligence/experiments/multi-try_experiment/with_mem/smoke_test_plan5_20260303/*`

### 5.1 四个核心问题的直接结论

#### 5.1.1 为什么提取经验这么稀疏
1. 本轮 smoke 配置是强截断轨迹：`PER_INSTANCE_CALL_LIMIT=1`。每次在 2 次 API 调用即 `exit_cost`，几乎没有真实“修复动作链”被执行。  
2. 每个 attempt 在经验图里几乎只沉淀 1 个 `plan_generated` action，导致 run_done 阶段缺少失败动作上下文，抽象与失败卡只能退化为通用模板。  
3. 抽象经验采用 fingerprint 合并，5 次尝试被合并为 1 条 abstract experience（`support_count=5`），看起来更“稀疏”。  
4. 注入端有显式上限，每次最多注入 3 条 hint，进一步压缩可见多样性。

#### 5.1.2 是否每轮都完整执行了经验提取流程
1. 不是“完整全流程”，而是“部分流程执行”。  
2. 在线链路（`plan_generated -> 检索 -> buffer -> inject`）在 attempt2~5 可见。  
3. `action_error` 分支基本未发生（主要退出原因为 cost limit，不是动作执行错误）。  
4. `run_done` 存在 timeout+重试，重试响应常见 `no_active_task`。  
5. 同时，持久化里确实新增了 task/failure_card，说明 run_done 提取逻辑至少执行过一次（可见新增时间戳连续递增）。

#### 5.1.3 能否看到 smoke 里每次读写了哪些经验
可以，且本轮 5 次 with_mem 读取的核心三条经验 ID 基本固定：
1. `failure_card_v2`: `86e2db1d-1bd6-4d51-a75e-6dfb37c9ce01`  
2. `abstract_experience`: `5a18ee01-0429-4d52-96c0-e14b964747d7`  
3. `belief_tip`: `5ac37f66-3ac8-4217-84a1-dcf8703fc831`

#### 5.1.4 是否限制了单案例可提取经验数量
是，且有多处限制：
1. 注入上限：`max_hints=3`。  
2. 抽象经验构建：每任务最多“任务级 1 条 + 错误特化最多 1 条”。  
3. 规划检索最终子图上限为 3。  
4. planning 查询下 failure card 返回上限为 1。  
5. 抽象经验按 fingerprint 合并，天然压缩条目数量。

### 5.2 Smoke10（with_mem）逐 attempt 经验读写台账

| Attempt | 读取经验（用于注入） | 新增经验（持久化） | 结果 |
|---|---|---|---|
| 1 | 无（冷启动） | `failure_card=86e2...`、`abstract=5a18...`、`belief=5ac3...` | `exit_cost` |
| 2 | `86e2...` + `5a18...` + `5ac3...` | `failure_card=e08f...` | `exit_cost` |
| 3 | `86e2...` + `5a18...` + `5ac3...` | `failure_card=e4c2...` | `exit_cost` |
| 4 | `86e2...` + `5a18...` + `5ac3...` | `failure_card=9252...` | `exit_cost` |
| 5 | `86e2...` + `5a18...` + `5ac3...` | `failure_card=4c25...` | `exit_cost` |

补充事实：
1. 注入 hint 文本在 attempt2~5 基本相同，缺乏增量信息。  
2. `failure_cards_v2` 总数是 5（每次 1 条），但内容同质化严重（error_type=unknown，action_trace 长度极短）。  
3. `abstract_experiences` 总数是 1，`support_count=5`，说明 5 次被合并到同一模式。

### 5.3 提取-保存-注入全流程失败机理（系统性解释）

#### 5.3.1 输入侧退化（提取原料不足）
1. 每次轨迹太短，动作多样性与失败上下文不足。  
2. 结果是“可被提取”的信息主要只有计划动作与退出摘要，几乎没有真实 repair 证据。

#### 5.3.2 提取侧退化（高质量经验难产）
1. failure card 从极短轨迹构建，error signature 长期 `unknown`。  
2. abstract 通过合并机制不断吸收同质样本，最终收敛为单一 generic pattern。  
3. belief 统计在全失败条件下变为负 uplift，但仍被读取并注入（质量门控不足）。

#### 5.3.3 存储侧退化（数量有增长、信息增益不足）
1. 文件层面“看起来在增长”（5 张 failure card、5 次 attempt belief），但语义信息几乎不增长。  
2. 存储产物与运行规模不匹配：动作大量发生时仍仅形成极少可复用高质量经验。

#### 5.3.4 注入侧退化（重复注入，无策略演化）
1. 每次最多注 3 条，且多数来自同一 card/abstract/belief 组合。  
2. 注入内容可执行性弱，偏“通用提示”而非“针对当前错误的修复策略”。  
3. 因此出现“链路触发了，但效果不变”的症状：attempt2~5 成功率、步数、API 调用均无改善。

#### 5.3.5 观测侧偏差（导致“看起来流程没跑全”）
1. `tool_b` 每次都有超时重试，拉低 run_done 稳定性。  
2. run_done 响应频繁出现 `no_active_task`，使外部观察误以为提取未执行。  
3. 但持久化中确有新增经验条目，说明“执行发生过，但可观测性与响应时序不稳定”。

### 5.4 本轮 smoke 的关键偏差归因总结（用于升级决策）
1. 主问题不是“有没有记忆模块”，而是“提取输入被实验配置截断后，记忆模块只能产出低信息经验”。  
2. 主问题不是“注入没触发”，而是“注入内容重复且低可执行性，无法转化为行为改进”。  
3. 主问题不是“完全没保存”，而是“保存的是低质量同质经验，导致跨轮次学习失败”。  
4. 当前 smoke 更接近“链路连通性测试”，不具备评估 AgentMem 学习增益的条件。

### 5.5 后续升级的归档要求（防信息丢失）
1. 每次实验必须同时归档：
- 事件日志（含 `memory_hint_buffered/memory_injected`）  
- 持久化快照（`observation_kg/belief_graph/abstract_experiences/failure_cards_v2`）  
- 逐 attempt 读写映射（读取了哪些 ID，新增了哪些 ID）  
2. 每次实验报告必须区分三层结论：
- 链路是否触发（connectivity）  
- 经验是否增量（memory quality growth）  
- 性能是否提升（task outcome）  
3. 后续“增益验证”实验不得使用会截断主轨迹的信息预算设置（否则只验证链路，不验证学习）。

## 第六部分：经验机制升级建议（新增）

### 6.1 升级目标（系统视角）
1. 提升“可提取经验密度”：让每轮运行产生可复用、可执行、可区分的经验对象，而非单一模板。
2. 提升“跨轮学习增量”：确保 attempt 越往后，读取到的经验结构和策略有真实变化。
3. 提升“注入有效性”：注入内容要能改变后续行为路径，而不仅仅是提示存在。
4. 提升“链路可解释性”：能回答哪条经验在何时注入、为什么注入、注入后是否带来收益。

### 6.2 用户指定四项改动（主线）

#### 6.2.1 解决抽象经验过度合并问题
1. 改动建议：
- 现有“单 fingerprint 强合并”改为“分层合并”。
- 同任务内强合并，跨任务弱合并；弱合并保留多条候选并记录来源差异。
2. 预期收益：
- 避免 5 次尝试被压成 1 条 generic pattern。
- 提升经验多样性，减少注入内容长期重复。
3. 主要风险：
- 存储增长更快，噪声经验也会增加。
4. 风险控制：
- 增加最小信息增益阈值（无新增字段/无新增证据不允许新建）。
- 增加过期与降权策略（长期无收益经验自动降权）。

#### 6.2.2 去掉单任务抽象经验条数上限
1. 改动建议：
- 去掉“任务级 1 条 + 错误特化最多 1 条”的硬上限。
- 改为“按质量排序保留 Top-K”（K 可配置）。
2. 预期收益：
- 同一任务内可保留不同阶段策略（探索、修复、验证）。
- 提升后续检索命中具体步骤经验的概率。
3. 主要风险：
- 容易写入重复或低质量抽象。
4. 风险控制：
- 质量打分至少包含 evidence 数量、可执行字段覆盖、与已有经验差异度。

#### 6.2.3 解决检索返回上限问题
1. 改动建议：
- 放宽 planning 下 `failure_card` 与 `selected_subgraph` 返回上限。
- 放宽后必须做 rerank 和冲突消解，不直接原样注入。
2. 预期收益：
- 减少“永远只读到同三条”的现象。
- 提升复杂实例下的候选覆盖率。
3. 主要风险：
- 候选过多导致检索噪声提升、注入内容互相冲突。
4. 风险控制：
- 保留“多检索、少注入”原则，返回可增多，但最终注入仍由质量门控筛选。

#### 6.2.4 去掉注入上限
1. 改动建议：
- 去掉固定 `max_hints=3` 的硬限制，改为动态预算模型。
- 动态预算由任务复杂度、当前上下文剩余空间、候选质量共同决定。
2. 预期收益：
- 在高复杂度实例中不再因硬截断丢失关键经验。
- 提升后续步骤策略调整空间。
3. 主要风险：
- token 成本上升、提示过载、模型注意力分散。
4. 风险控制：
- 按“高质量优先”注入，低质量候选只留检索日志不入 prompt。
- 设置 token 预算上限与分段注入策略（本轮注策略、下轮补证据）。

### 6.3 除数量限制外的关键阻塞（必须同步修复）
1. 上游轨迹截断问题：`PER_INSTANCE_CALL_LIMIT` 或成本限制过紧，会让经验提取原料先天不足。  
2. `action_error` 覆盖不足：失败修复链路未充分触发，导致 error_recovery 经验沉淀不足。  
3. `run_done` 稳定性问题：tool_b 超时与 `no_active_task` 响应影响提取闭环可观测性。  
4. query_type 失衡问题：检索长期偏 `planning`，修复类经验入口不足。  
5. instance 级追踪问题：事件标识粒度不足，注入效果难归因。  
6. 质量门控一致性问题：整体 confidence 与条目 confidence 混用，导致低价值经验进入注入。

### 6.4 推荐执行顺序（流程视角）
1. 第一阶段（先保原料）：
- 放宽实验截断配置，提升 `action_error` 与真实修复轨迹覆盖。
- 修复 run_done 超时与任务上下文清理时序问题。
2. 第二阶段（再扩容量）：
- 先做“去过度合并 + 去单任务条数硬上限”。
- 同步上线质量评分与信息增益门槛。
3. 第三阶段（后扩注入）：
- 放宽检索返回上限，启用 rerank。
- 用动态预算替代注入上限，避免 token 失控。

### 6.5 阶段验收门槛（建议）
1. 提取覆盖：
- `external_tool_response / plan_generated` 达到目标阈值。
- `action_error` 链路在失败实例中有稳定覆盖。
2. 经验增量：
- 同实例多次 attempt 后，`abstract_experiences` 条目数与语义多样性显著提升。
3. 注入有效性：
- 注入内容不再固定重复，且注入后 N 步内重复失败率下降。
4. 结果约束：
- 在 solved_rate 提升的同时，`incomplete` 不可显著恶化。
