# 阶段8 AgentMem 升级初步展望与计划

## 总目标

整体上，这个 AgentMem 框架要能够存储过去行为经验的探索空间，以及具体经验。帮助 Agent 拥有在实践中更强的解题能力。注入时，我们希望在尽量压缩 token 的同时给出有帮助的过往经验。

## 1. 当前阶段结论

基于阶段7正式同题测试、本地分析和云端评估，当前 AgentMem v2.1 的定位已经比较清楚：

- 它已经是一个真实工作的记忆系统，不是“开了开关但没生效”。
- 它当前最稳定的价值，是 `搜索纪律控制`、`失败路径回避`、`验证纪律强化`、`repro path 复用` 和 `晚期收敛辅助`。
- 它还不是一个稳定的 `成功语义记忆系统`。
- 它会把 agent 拉回较好的 patch family，但还不会稳定地把“为什么这个 patch 会成功”压成高置信、可早期复用的成功知识。

换句话说，当前系统已经具备：

- `path-level reuse`
- `workflow-level reuse`

但还没有稳定具备：

- `bug-specific semantic reuse`
- `early-success acceleration`

## 2. 当前升级方向的核心判断

阶段8不应该继续简单做“对象加法”。  
真正值得做的是把当前已经存在但还不够闭合的链路，压缩成更有效、更低噪、更偏成功语义的系统。

当前最值得抓的不是：

- 再加更多长期对象
- 再加更多分析层
- 再加更多编译卡类型

而是三件更硬的事：

1. **把成功路径压成强成功卡**
2. **让 gate 真正过滤低质量 candidate**
3. **让注入从“纪律提示”升级成“高价值最小提示”**

## 3. 阶段8升级目标

阶段8建议明确收敛到以下 4 个升级目标。

### 3.1 目标 A：从失败记忆偏置，升级到成功语义偏置

当前系统最强的是失败经验：

- unresolved 风险
- validation gap
- broad patch / over-exploration
- closure guard

但真正想要的升级方向是：

- 当系统已经见过 resolved patch family 后
- 后续尝试应该更早拿到“该题正确修法的核心不变量”

也就是说，阶段8要把记忆重点从：

- `避免犯错`

逐步升级为：

- `更早逼近正确解`

### 3.2 目标 B：把 candidate 长期层升级为 promotion 驱动的长期层

当前系统已经能生成：

- failure cards
- repair patterns
- compiler cards
- projected subtask / edge candidates

但这些对象多数仍停留在：

- `candidate`

阶段8需要提升的是：

- 哪些对象能 promotion
- promotion 后怎么更稳定地进入注入层
- 哪些对象必须 suppression / deprecate

否则会出现：

- 记忆对象越来越多
- 注入越来越活跃
- 但收益没有同步提升

### 3.3 目标 C：让注入真正 token-efficient

当前实验已经说明：

- 记忆注入是真实发生的
- 但主流内容仍然偏纪律型、说明型

阶段8的目标不是让注入更多，而是让注入更短、更硬、更值。

理想方向是：

- 更少条数
- 更短文本
- 更高命中率
- 更强针对性

目标不是：

- “尽量多提醒”

而是：

- “最小 token 下给出最有帮助的历史经验”

### 3.4 目标 D：让同题和跨题的收益都可测

阶段7已经把实验目标拆成两条：

- 同题收益
- 跨题收益

阶段8升级必须继续服务这两个评价面：

1. 同题：
   - 是否更早成功
   - 是否减少无效探索
   - 是否能更稳定复用成功路径

2. 跨题：
   - 是否能把相近题型的经验迁移过去
   - 是否减少 harmful transfer
   - 是否在保持 token 压缩的同时真正提升成功率

## 4. 当前系统的关键瓶颈

### 4.1 成功事实很多，但成功语义很弱

当前热路径 / 冷路径 / official eval 已经能把不少事实写下来。  
问题不是“没有 success truth”，而是：

- success truth 还没有被稳定编译成高价值 success card

目前系统更擅长保留：

- failure traces
- validation failures
- retry guidance

但不擅长保留：

- 解决这个 bug 的关键结构性规律

### 4.2 Gate 评估存在，但过滤职责太弱

当前同题分析已经说明：

- `external_ratio` 通常能过
- `buffer_ratio` 常常不过
- `action_error_coverage` 常常不过
- `passed` 往往是 `false`

但因为：

- `hard_fail_enabled = false`

结果就是：

- 低质量对象继续留在候选池里
- compiler 还会继续消费它们
- 注入层因此持续有噪声

### 4.3 注入内容偏纪律型，不够语义型

当前被高频注入的内容主要是：

- avoid repeat failed strategy
- validation gap
- reproduce before patch
- verification plan
- closure guard

这些都不是没用，相反它们已经带来稳定收益。  
但问题是它们对“更早找到正确解”的推动力有限。

### 4.4 成功卡 promotion 还不够强

当前系统在 attempt resolved 后，仍缺少一个更果断的机制，把：

- 成功 patch family
- 成功验证路径
- 成功代码不变量

压缩成：

- 短小、强约束、可复用的 success card

## 5. 阶段8建议的升级主线

阶段8建议围绕 3 条主线推进。

### 主线 1：SuccessPathCard / BugInvariantCard

#### 目标

把 resolved attempt 的成功路径和关键代码不变量，压缩成更高价值的成功知识对象。

#### 最小设计方向

建议先不要发散成太多新对象，先只引入一个最小 success family：

- `SuccessPathCard`

它至少应该包含：

- `instance_id / task family`
- `winning_patch_family`
- `repro_path`
- `target_validation_path`
- `bug_invariant_summary`
- `confidence`
- `promotion_state`

如果后续确认 bug invariant 足够稳定，再把其中一部分升格成更抽象的：

- `BugInvariantCard`

#### 原则

- 先做最小对象
- 先服务已验证场景
- 不一开始就扩成通用论文型 ontology

### 主线 2：Promotion-first Governance

#### 目标

让治理层真正控制：

- 什么能继续存在
- 什么能进入 compiler
- 什么能进入默认注入

#### 建议收敛

阶段8里，治理层至少要强化 4 条规则：

1. resolved-driven promotion  
2. unresolved-driven suppression  
3. repeated low-value candidate deprecate  
4. compiler 输入白名单更严格

#### 结果预期

治理层不再只是“记录状态”，而是真正决定：

- 哪些知识继续活
- 哪些知识不再污染 prompt

### 主线 3：Token-aware Injection

#### 目标

让注入从“多条纪律提示”升级为“少量高价值提示”。

#### 建议策略

阶段8建议同时强化：

1. `family dedupe`
2. `success-first ranking`
3. `strict card budget`
4. `trigger-specific card selection`

#### 核心思路

不同 trigger 不应该拿同一桶记忆：

- `plan_generated` 更适合 plan hint / success path hint
- `before_test_run` 更适合 validation hint
- `over_exploration` 更适合 closure / stop signal
- `before_submit` 更适合 minimal verification checklist

## 6. 阶段8初步升级计划

### Phase 8A：成功知识最小闭环

#### 目标

先打通“resolved -> success card -> next attempt 注入”的最小链路。

#### 任务

1. 定义 `SuccessPathCard` 最小 schema
2. 在 `official_eval_feedback` 后生成 success candidate
3. 对 resolved attempt 的 patch family / repro path / validation path 做最小摘要
4. 把 success candidate 接进 compiler 白名单
5. 给 success card 单独预算，避免被纪律卡淹没

#### 验收标准

- resolved attempt 后确实能生成 success card
- 下一个同题 attempt 能检索到 success card
- 注入 token 不显著上升

### Phase 8B：治理层强化

#### 目标

让 candidate 不再无限堆积。

#### 任务

1. 开启更严格的 gate
2. 把 `passed=false` 的长期 candidate 降权或清退
3. 增加 repeated low-value candidate suppression
4. 限制 compiler 对未 promotion 对象的消费

#### 验收标准

- compiler card 总量增长变慢
- 注入重复率下降
- 低质量 candidate 的长期残留减少

### Phase 8C：注入预算与排序优化

#### 目标

把当前“注入很多但不够锋利”的状态压成更精炼的注入层。

#### 任务

1. trigger-specific ranking
2. success-first rerank
3. family-level dedupe
4. card budget per trigger

#### 验收标准

- 每次注入的卡更少
- 平均 token 更低
- 注入命中率更高

### Phase 8D：正式验证

#### 目标

重新验证：

- 同题 15 instance * 10 repeats
- 跨题两个大 repo 的 carry-over

#### 核心指标

同题：

- first success index
- success count
- pre-success path diversity
- mean tokens to first success

跨题：

- resolved rate delta vs fresh
- first-attempt success rate
- harmful transfer rate
- token cost per resolved

## 7. 建议的工程优先级

如果阶段8只能先做一小部分，我建议优先级如下：

1. `SuccessPathCard` 最小闭环
2. resolved-driven promotion
3. compiler 白名单收紧
4. trigger-specific 注入预算
5. 再做更抽象的 BugInvariantCard

原因很简单：

- 当前最大缺口不是“对象太少”
- 而是“成功知识太弱，候选噪声太多”

## 8. 阶段8的最稳预期

阶段8不应该追求一步到位把 AgentMem 变成“成熟成功语义记忆系统”。  
更现实、也更好的目标是：

1. 让系统开始稳定保留成功路径知识
2. 让注入从纪律型提示向成功型提示倾斜
3. 让治理层真正降低噪声
4. 在同题和跨题实验中看到更稳定的正向信号

## 9. 一句话总结

阶段8的核心任务不是“继续把记忆系统做大”，而是把它做“更硬、更准、更省 token”。  
也就是：

> **从会复盘失败、会约束发散，升级到能更早复用成功路径，并逐步提炼出 bug-specific 成功语义。**
