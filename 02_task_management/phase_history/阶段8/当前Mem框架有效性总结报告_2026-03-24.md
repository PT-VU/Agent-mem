# 当前 Mem 框架有效性总结报告（基于前 13 案例 / 130 个 completed WithMem trials）

## 1. 报告目标

本文不再重复“前 13 案例 NoMem vs WithMem 阶段性对比”的原始表格，而是基于那份结果，回到这 `130` 个已完成的 `WithMem trials` 本身，回答下面两个更关键的问题：

1. 当前 mem 系统到底**起了什么作用**？
2. 当前 mem 系统**本来应该实现、但实际上还没有实现**的能力是什么？

本报告的判断范围严格限定为：

- same-only 实验前 `13` 个实例
- `NoMem = 130 attempts`
- `WithMem = 130 attempts`
- 对照基线文档：
  [前13案例_NoMem_vs_WithMem阶段性对比_2026-03-24.md](/home/pt/SWE-bench/PDDL_work_mem/02_task_management/phase_history/阶段8/前13案例_NoMem_vs_WithMem阶段性对比_2026-03-24.md)

---

## 2. 一句话结论

当前 mem 框架**不是无效**，也不是“没有介入”。

它已经明显具备下面这类能力：

- 持续积累 failure / repair / compiler / episode 类经验对象
- 在运行中主动检索并注入经验
- 压低 incomplete，提升 attempt 的流程稳定性
- 在部分题上复用已知 repro path、避免重复失败策略
- 在 agent 发散时进行 closure/validation 导向的纠偏

但它**还没有形成我们真正想要的那种“提升解题能力的记忆系统”**。

目前更准确的定位是：

> 当前 mem 更像一个“搜索纪律控制器 + 失败经验规避器 + 局部复盘助手”，而不是一个“稳定提高 solved rate 的成功语义记忆系统”。

## 3. 数据基线：先看结果，不先讲故事

### 3.1 前 13 案例总体结果

- `NoMem`: `73 resolved / 130 = 56.15%`
- `WithMem`: `70 resolved / 130 = 53.85%`

- `NoMem`: `21 incomplete / 130 = 16.15%`
- `WithMem`: `6 incomplete / 130 = 4.62%`

直接解释：

- 现阶段，`WithMem` **没有带来更高的总 resolved 数**
- 但 `WithMem` **明显减少了 incomplete**

这两个结论必须同时成立，不能只说其中一半。

### 3.2 attempt 1~4 的对比

在前 13 个实例上，`attempt_01 ~ attempt_04` 的 resolved 率如下：

| attempt | NoMem resolve率 | WithMem resolve率 |
|---|---:|---:|
| 1 | 53.85% | 53.85% |
| 2 | 61.54% | 61.54% |
| 3 | 61.54% | 61.54% |
| 4 | 53.85% | 53.85% |

而 incomplete 率如下：

| attempt | NoMem incomplete率 | WithMem incomplete率 |
|---|---:|---:|
| 1 | 15.38% | 0.00% |
| 2 | 15.38% | 0.00% |
| 3 | 15.38% | 0.00% |
| 4 | 15.38% | 7.69% |

这个结果非常关键，因为它说明：

- 当前 mem **没有把前几次尝试的成功率抬高**
- 但它**明显降低了前几次尝试的“空跑 / 半途挂掉 / 无法收口”**

换句话说，当前 mem 的主要收益不是“更早解出来”，而是“更稳地把尝试跑完”。

## 4. 当前 mem 系统“确实在工作”的证据

这是这份报告最重要的部分之一。我们不能因为 solved 没抬高，就误判成“mem 没工作”。

### 4.1 记忆对象确实被持续写出

在多个实例目录下，都能看到这几类持久化对象：

- `graph_store/compiler_cards_v21.json`
- `graph_store/failure_cards_v2.json`
- `graph_store/repair_patterns_v2.json`
- `sidecar_store/compiler_cards.jsonl`
- `sidecar_store/episode_ledger.jsonl`
- `sidecar_store/subtask_edges.jsonl`
- `sidecar_store/subtask_instances.jsonl`

例如下面这些实例都存在这些对象：

- `django__django-11620`
- `scikit-learn__scikit-learn-13439`
- `django__django-15320`

这说明：

- 当前 mem 不是“只在 prompt 里做几句提示”
- 它已经具备了“把运行历史写成长期对象”的框架能力

### 4.2 在 130 个 completed WithMem trials 中，检索/注入是高频发生的

对前 13 个实例的 `130` 个 completed WithMem trials 的 `jsonl` 日志统计结果：

- `memory_hint_buffered`: `652` 次，覆盖 `117/130` 个 attempts
- `memory_injected`: `827` 次，覆盖 `130/130` 个 attempts
- `proactive_trigger`: `8868` 次，覆盖 `130/130` 个 attempts
- `memory_intervention_feedback`: `1555` 次，覆盖 `130/130` 个 attempts
- `memory_gate_evaluation`: `127` 次，覆盖 `127/130` 个 attempts

这组数字说明：

- 当前 mem 系统不是偶尔工作，而是**全程高频参与**
- 尤其是 `memory_injected` 已经做到 `130/130 attempts`
- 所以“mem 当前没用”的说法是不成立的

### 4.3 它最常介入的时机，是搜索纪律和收口节点

`proactive_trigger` 的高频时机分布：

- `over_exploration`: `4735`
- `first_file_access`: `2316`
- `before_submit`: `1252`
- `before_test_run`: `564`
- `first_failure`: `1`

这说明当前系统的介入重心是：

1. 刚进入代码路径时提醒
2. 发散过多时提醒
3. 提交前提醒
4. 测试前提醒

这非常像一个**过程控制器**，而不是一个“直接告诉你 bug 核心不变量”的系统。

### 4.4 它注入的内容，主要是纪律类 / 失败规避类 / closure 类

注入频率最高的 family id 包括：

- `closure_signal:over_exploration_after_key_signal` `132`
- `workflow_step:consider: generate plan for task...` `105`
- `negative_strategy__official_eval_unresolved__avoid_repeat_failed_strategy` `69`
- `direct_success_flow__missing_validation__run_done_exit_status_submitted_has_submission_true_submission_success_true_evaluation_success_unknown_generate_plan` `65`
- `validation_gap__missing_validation__add_local_validation` `63`
- `patch_risk__official_eval_unresolved__avoid_repeat_failed_strategy` `61`
- `failure_card:evaluation_unresolved:reproduce_the_failing_path_with_target_validation_before_next_patch` `60`

此外还有不少 case-local family：

- `attempt_summary:django__django-11620`
- `plan_hint__django_django_11620__reuse_confirmed_repro_path`
- `attempt_summary:scikit-learn__scikit-learn-13439`
- `plan_hint__scikit_learn_scikit_learn_13439__run_target_validation_before_broad_tests`

这说明当前 mem 的有效部分主要在：

- 控制 agent 不要无边界发散
- 强化验证和 repro
- 提醒避免重复踩已经失败过的策略
- 在少数 case 上复用已知 repro path

## 5. 当前 mem 系统“真正有用”的地方

### 5.1 它显著提升了运行稳定性

最硬的证据就是 incomplete：

- `NoMem incomplete = 21`
- `WithMem incomplete = 6`

这说明 mem 的一个现实收益已经成立：

> 它能把更多 attempts 从“没收住 / 没跑完 / 空结果”推到“至少给出一个可判定结果”。

尤其在前四次尝试中，这个差异非常明显。

### 5.2 它对“极难题”的收益，主要是把 incomplete 变成 unresolved

典型例子：

- `sympy__sympy-15308`
  - `NoMem`: `0 resolved / 10 incomplete`
  - `WithMem`: `0 resolved / 10 unresolved`

- `sympy__sympy-11897`
  - `NoMem`: `0 resolved / 10 incomplete`
  - `WithMem`: `0 resolved / 7 unresolved / 3 incomplete`

这类题并没有被解决，但 mem 的作用是把它们从“流程崩掉”拉回到“可评测失败”。

这不是 solved 提升，但它是工程上真实可见的价值：

- 更少空跑
- 更少丢结果
- 更可分析
- 后续复盘基础更完整

### 5.3 它能在个别题上帮助改进路径选择

最清楚的例子是：

- `django__django-15320`
  - `NoMem resolved = 4`
  - `WithMem resolved = 6`

这个实例说明 mem 不是完全没有提升 solved 能力；它在**个别实例**上已经能帮助 agent 更少走错路，或者更快复用有效路径。

但问题是：

- 这个能力还不够稳定
- 还不能推广成全局收益

### 5.4 它已经具备“局部案例经验复用”能力

从注入内容看，当前 mem 不是只有全局 generic hint，它已经出现了明显的 case-local 经验：

- `attempt_summary:<instance>`
- `plan_hint__<instance>__reuse_confirmed_repro_path`
- case-local `closure_guard`

这说明系统已经有了：

- 把同题先前 attempts 沉淀为摘要
- 在后续 attempts 中再取回并注入

这正是我们最初希望同题记忆具备的基本雏形。

## 6. 当前 mem 系统“没有实现”的能力

这部分才是下一阶段真正该修的核心。

### 6.1 它没有把 solved rate 拉上去

最硬的事实仍然是：

- `NoMem = 73 / 130`
- `WithMem = 70 / 130`

如果只问“当前 mem 是否已经让前 13 案例的 solved 更高”，答案就是：

> **没有。**

所以现在不能把这套系统描述成“已经显著提高解题正确率”。

### 6.2 它没有提高早期 attempts 的成功率

`attempt 1~4` 的 resolved 率完全一样，这个事实非常强：

- 说明当前 mem 还没有帮助 agent 在更早阶段更快撞上正确路径
- 也说明它尚未把“过去成功经验”变成足以改变早期搜索方向的高价值知识

这正是当前系统最核心的未达成目标之一。

### 6.3 它还没有把“成功经验”压缩成强语义、强约束的记忆

当前高频注入内容，主流仍然是：

- `workflow_step`
- `validation_gap`
- `negative_strategy`
- `closure_signal`
- `failure_card`

这些内容的共同特点是：

- 对流程有帮助
- 对纪律有帮助
- 对避免重复失败有帮助

但它们**不等于 bug-specific success invariant**。

现在缺失的是这种能力：

> 当某题已经出现过成功 patch family 时，系统应能把“为什么这条路径有效”的核心语义，压缩成更短、更硬、更高权重的 success memory，并在下一次尝试中优先注入。

这件事当前没有稳定发生。

### 6.4 它的 governance / gate 现在基本没有形成强约束

在前 13 案例的 130 个 completed WithMem trials 里：

- `memory_gate_evaluation` 出现了 `127` 次
- 但 `passed = false` 也是 `127` 次
- 同时 `hard_fail_enabled = false` 也是 `127` 次

这说明：

- gate 不是没跑
- 它在跑
- 但它几乎没有起到“强过滤 / 强阻断”作用

更直接地说：

> 当前治理层更像“记录一下我本来该拦”，而不是“真的把低价值干预拦住”。

### 6.5 它的自我反馈几乎没有区分度

`memory_intervention_feedback` 统计为：

- `1555` 次
- `local_effective = true` 也是 `1555` 次

这很可能说明一件事：

> 当前反馈闭环还不能有效区分“真的有效”和“只是发生过干预”。

如果所有反馈几乎都被标成有效，那这套反馈就难以驱动真正的 memory ranking / promotion / pruning。

这也是当前 mem 框架还没有实现的关键能力。

### 6.6 成功热路径写入存在，但远远不够强

对 gate 事件里的热路径指标做聚合后：

- `success_fact_hotpath_written = 1495`
- `success_fact_hotpath_skipped = 10724`

并且按 attempts 口径看：

- 至少写过一次 success hotpath 的 attempts：`34`
- 至少出现过 success hotpath skipped 的 attempts：`115`

这说明：

- 成功经验写入不是完全没有
- 但大量成功事实仍然被跳过或没有进入足够强的热路径

所以现在系统仍然更像：

- 会写一些成功痕迹
- 但还不擅长把这些痕迹升级成强复用资产

## 7. 面向“mem 框架有效性”的精确定性

### 7.1 当前已经成立的有效性

如果把“有效性”拆细，当前成立的是：

1. **流程稳定性有效**
   - incomplete 大幅下降

2. **失败规避有效**
   - 会反复注入 negative strategy / patch risk / failure card

3. **探索收口有效**
   - `over_exploration` 是最高频 trigger
   - closure 类 family 被高频选择

4. **局部经验复用有效**
   - case-local `attempt_summary` 和 `plan_hint` 已经真实存在

5. **记忆基础设施有效**
   - graph store / sidecar store / compiler cards / repair patterns 都在落盘

### 7.2 当前尚未成立的有效性

如果我们对 mem 框架的目标是：

> “存储过去行为经验的探索空间，以及具体经验，帮助 Agent 在实践中拥有更强的解题能力，并在尽量压缩 token 的同时注入真正有帮助的过往经验。”

那么当前**尚未成立**的部分是：

1. **更强的解题能力**
   - 目前总 solved 没有超过 NoMem

2. **更快找到正确路径**
   - 早期 attempts 成功率没有提升

3. **成功经验的高质量压缩**
   - 现在注入主流还是 generic workflow / validation / failure avoidance

4. **高质量治理**
   - gate 在跑，但没有形成强约束

5. **有效性的可信自评**
   - feedback 几乎全是 `local_effective=true`

6. **对困难题的语义突破**
   - 比如 `sympy__sympy-15308`、`matplotlib__matplotlib-18869`、`django__django-15996`
   - 当前 mem 主要降低 incomplete，但还没有形成突破性 solved 提升

## 8. 对当前框架的最终评价

### 8.1 当前评价

如果必须给一句不绕弯子的评价：

> 当前 mem 框架已经是“有用的工程系统”，但还不是“有效的解题增强系统”。

更细一点说：

- 它已经不是空架子
- 也不是“完全没起作用”
- 它对稳定性、收口、失败规避、局部复盘都有效

但它离我们真正想要的目标还差关键一步：

> **它还没有把过去 trials 中的成功经验，稳定地转化为未来 trials 的更高 solved rate。**

### 8.2 当前最准确的架构定位

当前最准确的产品/架构定位是：

- 不是“成功经验驱动器”
- 而是“运行纪律增强器 + 失败复用器 + 同题复盘助手”

这个定位并不低级，但它不等于我们的终极目标。

## 9. 下一阶段最值得做的 5 个改进点

### 9.1 把成功路径 promotion 提到最高优先级

现在最缺的不是再造更多 failure card，而是：

- 当某条 patch family 被官方 eval 证实为 resolved 时
- 立刻产出 success card / success invariant / success hotpath
- 并在后续 attempts 中提高它的权重，优先注入

### 9.2 压缩 generic workflow 提示，减少“看起来有用但信息密度低”的注入

当前高频 family 中有太多这类内容：

- `workflow_step`
- 泛化 `validation_gap`
- 泛化 `repair_pattern` 长文本

这些内容会让系统很忙，但未必真正改变 solved。

### 9.3 让 gate 真正承担治理职责

现在 `memory_gate_evaluation` 本质上没有形成 runtime 约束。  
下一阶段应该让它至少做到一件事：

- 对低价值、重复、长而泛的记忆进行硬过滤或降权

### 9.4 让 feedback 具备区分度

如果 `local_effective` 几乎永远是 `true`，那这条反馈链就不够有用。  
下一阶段应该让反馈能区分：

- 真的改变了结果
- 只是陪跑
- 反而造成发散

### 9.5 从“流程知识”转向“问题语义知识”

当前系统最擅长的是告诉 agent：

- 要规划
- 要验证
- 不要重复失败

下一阶段更重要的是告诉 agent：

- 这个 bug 的核心不变量是什么
- 上一次成功 patch 真正解决的是哪条 semantic path
- 下一次应该如何最短路径回到这条语义正确路径

---

## 10. 最终结论

如果只问一句：

> 当前 mem 框架有没有用？

答案是：

> **有用，但用途比我们原先期待的更窄。**

它当前最确定的价值是：

- 降低 incomplete
- 提升流程稳定性
- 在同题中复用局部经验
- 对发散进行纠偏

它当前最明显的不足是：

- 没有把 solved rate 真正拉高
- 没有更早地把正确路径找出来
- 没有把成功经验压成强语义、强治理、低 token 的高价值记忆

所以对当前 mem 框架的最准确总结不是“无效”，也不是“已经成功”，而是：

> **它已经完成了“从 0 到 1 的工作基础设施建设”，但还没有完成“从 1 到 N 的解题能力提升”。**
