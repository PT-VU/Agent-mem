# 阶段8 成功路径复用与超时治理框架方案

日期：2026-04-19  
阶段：Phase 8  
范围：基于 `phase8_same_only_kimi_formal_lite_001_005_splitprep_v2` 单题 same-only 实验结果，对 AgentMem 框架做“成功路径复用 + 超时治理”方向的结构化收敛。

---

## 1. 核心目标

这份文档只服务两个目标：

1. **尽量稳定复用成功 attempt 的路径**
   - 不只是“把过去成功尝试存下来”
   - 而是要让后续 attempt 更稳定地回到同一个成功 patch family、repro path、validation path

2. **尽量稳定防止超时**
   - 不只是事后记录 “这次 timeout 了”
   - 而是要从过往超时里提取能稳定限制后续行为的经验，并在运行时真正起治理作用

如果一句话概括本阶段真正要做的事：

> 把当前的 mem 从“提示型经验注入器”，升级成“成功路径复用器 + 超时治理器”。

## 2. 这次单题实验已经证明了什么

本次分析基于：

- run root  
  `/home/pt/SWE-bench/PDDL_work_mem/06_artificial_intelligence/experiments/final_validation/phase8/phase8_same_only_kimi_formal_lite_001_005_splitprep_v2`

关键事实如下。

### 2.1 成功路径确实被记住了

`WithMem attempt_01` 和 `attempt_02` 成功提交了同一个一行 patch。  
这说明当前系统已经具备：

- 同题局部经验积累
- 成功路径再次检索
- 成功路径再次注入

这不是“mem 完全无效”。

### 2.2 超时失败也确实被抽成了更细的经验

在后续 `attempt_03 ~ attempt_08` 里，系统已经抽出了两类有价值的负向经验：

1. **过度探索/重复 repro 经验**
   - `abs_2_1776584454`
   - 核心意图：
     - repeated reproduction 或 ad-hoc validation 如果迟迟没有 patch，就不要继续扩 scope
     - 优先复用已确认 repro path
     - 更早提升 minimal fix candidate
     - 避免在 repro 已确认后继续创建新脚本

2. **验证缺口经验**
   - `abs_3_1776597057`
   - 核心意图：
     - 没有 target validation 的提交是高风险
     - 应该在 submission 前做 target validation
     - 不要无 target validation 就提交

这说明当前框架已经不只是记住“失败了”，而是已经开始记住：

- 哪类行为应该继续
- 哪类行为应该避免
- 下一步更应该做什么

### 2.3 但这些经验还没有形成真正的运行时约束

后续日志显示，这些经验已经被检索和注入，包括：

- `reuse_confirmed_repro_path`
- `avoid_create_new_repro_script_after_repro_confirmed`
- `promote_minimal_fix_candidate_earlier`
- `run_target_validation_before_submission`

但最终后续 attempt 仍然大面积 `timeout_no_prediction` 或 `missing_prediction`。

这说明当前问题不是：

- 没有记忆
- 没有提取经验
- 没有注入经验

而是：

> 这些经验目前主要还是 advisory hints，而不是能够稳定改变行为的治理约束。

## 3. 当前框架的真实缺口

### 3.1 成功经验没有被压缩成“强成功卡”

当前系统能记住成功路径，但还没有把成功路径压成一个稳定、短小、强语义、低 token 的对象，例如：

- 这个 bug 的最小 patch family 是什么
- 最小 repro path 是什么
- 最小 target validation 是什么
- 在什么信号出现后应当优先提交

当前 success memory 更像：

- “过去成功过”
- “可复用这条路”

而不是：

- “这就是高置信最小闭环，优先走它，偏离它需要额外理由”

### 3.2 超时经验已经有了方向，但没有预算

当前负向经验已经能表达：

- 不要继续 ad-hoc repro script loop
- 不要继续 broad test without patch
- 不要无 target validation 就提交

但它还没有细化成预算型规则，比如：

- repro 已确认后，最多允许再写 0 个新 repro script
- 没有 patch candidate 时，不允许做 broad regression
- 同一 failing path 最多做 1 次 target validation retry
- 连续 N 个 step 没有 patch/edit 进展就必须收口

也就是说，当前系统已经学会了**方向**，但还没有学会**预算**。

### 3.3 提示被看见了，但没有形成行为闭环

当前链路是：

`memory extraction -> memory storage -> retrieval -> prompt injection`

缺的那一层是：

`runtime governance`

也就是：

- 什么时候只是提醒
- 什么时候应当强偏置
- 什么时候必须禁止某类动作
- 什么时候应该结束探索并提交/退出

如果这一层不存在，那么经验就只能“影响思考”，无法“约束行为”。

## 4. 建议的目标架构

阶段8建议把记忆体系收敛成四类对象。

### 4.1 SuccessPathCard

作用：稳定复用成功 attempt 的最小闭环。

建议最小 schema：

```json
{
  "card_type": "SuccessPathCard",
  "instance_scope": "same-case",
  "patch_family": "...",
  "repro_path": ["..."],
  "target_validation": ["..."],
  "submit_preconditions": ["..."],
  "confidence": 0.0,
  "support_count": 0
}
```

最关键的是让它包含：

- `patch_family`
- `repro_path`
- `target_validation`
- `submit_preconditions`

而不是只记录“这个 attempt 曾 resolved”。

### 4.2 TimeoutGovernanceCard

作用：把超时失败抽成可执行的行为限制。

建议最小 schema：

```json
{
  "card_type": "TimeoutGovernanceCard",
  "failure_family": "ad_hoc_repro_script_loop",
  "trigger_scope": "same-case",
  "prefer_actions": ["reuse_confirmed_repro_path"],
  "avoid_actions": ["create_new_repro_script_after_repro_confirmed"],
  "budget_hints": {
    "max_new_repro_scripts_after_repro_confirmed": 0,
    "max_broad_tests_before_patch": 0,
    "max_target_validation_retries_without_patch_upgrade": 1
  },
  "confidence": 0.0,
  "support_count": 0
}
```

重点不是“记录失败类型”，而是要把它变成可执行预算。

### 4.3 ConstraintCandidate

作用：让记忆提取模型输出“约束候选”，但不直接生效。

建议 schema：

```json
{
  "constraint_id": "...",
  "source_memory_ids": ["..."],
  "trigger": "plan_generated | before_test_run | before_submit | over_exploration",
  "hardness": "soft | strong | guardrail | hard_stop",
  "action": "prefer | avoid | forbid | require",
  "target": "...",
  "justification": "...",
  "confidence": 0.0,
  "support_count": 0,
  "expires_after_attempt": null
}
```

### 4.4 RuntimeGuard

作用：运行时治理器。

它不是再注入一段提示词，而是根据 `ConstraintCandidate + policy rules` 决定：

- 本次只提示
- 本次强偏置
- 本次直接阻止某类动作
- 本次必须收口到 submit / abort

## 5. 为两个核心目标分别设计最小闭环

## 5.1 目标一：稳定复用成功 attempt 路径

### 当前缺口

成功经验存在，但没有被升级成强成功卡。

### 建议闭环

1. `resolved` attempt 结束后
2. 提取：
   - 最小 patch family
   - 最小 repro path
   - 最小 target validation
   - submission 前关键证据
3. 生成 `SuccessPathCard`
4. 进入 compiler 白名单
5. 在后续同题 attempt 的 `plan_generated` 和 `before_submit` 两个 trigger 优先注入
6. 如果运行中发现行为偏离 success path，则给出强偏置或 guardrail

### 预期效果

后续 attempt 不再只是“想起以前成功过”，而是：

- 优先走同一 patch family
- 优先复用同一 repro path
- 优先跑同一 target validation
- 偏离时需要更强证据

---

## 5.2 目标二：稳定防止超时

### 当前缺口

当前系统已经知道：

- 不要继续写新的 repro script
- 不要在没 patch 时做 broad test
- 不要无 target validation 就提交

但这些仍主要是 advice，不是治理。

### 建议闭环

1. 连续 unresolved / timeout attempt 结束后
2. 提取失败 family
3. 为该 family 生成 `TimeoutGovernanceCard`
4. 从自然语言经验中再抽出预算型 hint
5. 运行时用 `RuntimeGuard` 执行

### 示例预算

针对当前 case，可以先用最小规则：

- `repro_confirmed -> max_new_repro_scripts_after_repro_confirmed = 0`
- `no_patch_candidate -> max_broad_tests_before_patch = 0`
- `target_validation_passed -> prefer_submit_or_small_revision`
- `N steps without patch/update -> trigger closure guard`

### 预期效果

不再只是“知道不要过度探索”，而是：

- 到某个阈值后，系统不再允许继续扩散
- 让 agent 更稳定地进入收口动作

## 6. 你提出的新可能性：让记忆提取模型参与决定“硬性程度”

这是一个值得认真做，但必须加边界的方向。

核心问题不是：

> 能不能让模型参与？

而是：

> 模型参与到哪一层，权力边界放在哪里？

### 6.1 三种方案

#### 方案 A：模型只提取经验，不决定硬性程度

特点：

- 继续维持当前模式
- 模型只负责抽取 card / hint
- 运行时全靠固定规则

优点：

- 最稳
- 最容易解释
- 风险最低

缺点：

- 约束强度不够灵活
- 对 case-specific 行为控制不够细

#### 方案 B：模型提出“约束候选”，规则层决定是否执行

特点：

- 模型输出 `ConstraintCandidate`
- 包括：
  - 建议硬性程度
  - 适用 trigger
  - 目标动作
  - 信心
  - 支持证据
- 最终是否启用、启用到什么层级，由 deterministic policy 决定

优点：

- 能保留 case-specific 灵活性
- 能利用模型对“当前经验是否足够形成约束”的语义判断
- 风险可控

缺点：

- 系统更复杂
- 需要定义清晰的 policy gate

#### 方案 C：模型直接决定并施加硬约束

特点：

- 提取模型直接输出“禁止/必须”类指令
- 运行时直接信任执行

优点：

- 最灵活
- 理论上最快实现强约束

缺点：

- 风险最高
- 容易 hallucinate
- 难解释
- 难调试
- 可能把错误经验放大成错误治理

### 6.2 这种做法的主要优点

如果采用方案 B，主要收益是：

1. **约束强度可以 case-specific**
   - 不是所有 bug 都适合同一套硬规则

2. **可以利用 richer context**
   - 模型能同时看到：
     - success path
     - timeout pattern
     - validation history
     - current trigger

3. **更容易把自然语言经验转成运行时策略**
   - 尤其适合从“经验句子”过渡到“治理候选”

### 6.3 这种做法的主要风险

风险主要有五类。

#### 风险 1：把错误经验硬化

如果模型错误判断：

- 当前成功路径其实只是偶然
- 当前 timeout 只是环境污染

却把它升级成 hard constraint，后续会被强误导。

#### 风险 2：过拟合同题局部噪音

同题 repeat10 很容易学到“这轮局部偶然性”。

如果没有 support threshold，模型可能把一次偶然失败抽成强规则。

#### 风险 3：提示注入和运行时治理相互冲突

如果 prompt 里说“优先提交”，治理层又说“必须先验证”，模型和 runtime 就会出现双重控制、难以解释。

#### 风险 4：错误不可观测

如果模型直接决定硬性程度，而没有结构化落盘：

- 事后很难知道为什么这次被限制
- 很难回溯是经验错了、模型错了、还是 gate 错了

#### 风险 5：策略漂移

如果硬约束过多依赖模型临场判断，系统行为会漂，难以稳定复现。

### 6.4 最终建议

**建议采用方案 B，不建议采用方案 C。**

也就是：

> 让记忆提取模型参与“提出约束候选”，但不要让它直接拥有“最终硬约束执行权”。

理由很简单：

- 纯规则层太死，吸收不了 case-specific 经验
- 纯模型层太危险，容易把错经验变成硬约束
- 模型提议 + 规则裁决，才是风险和收益最平衡的结构

## 7. 推荐的硬性程度分层

建议把约束分成四层，而不是简单的“软/硬”二元。

### L0：Advisory

只注入提示，不影响工具调用。

适用：

- support 低
- confidence 一般
- 首次出现的经验

### L1：Strong Preference

在 prompt 和 action ranking 中强偏置，但允许偏离。

适用：

- 成功 path 已出现 1~2 次
- 负向经验已有一定支持，但污染风险还没完全排除

### L2：Guardrail

限制某类动作发生，例如：

- repro 已确认后不再允许新建 repro script
- 无 patch candidate 时不允许 broad regression

适用：

- 同一失败 family 重复出现
- support count 达阈值
- 环境污染概率低

### L3：Hard Stop

满足条件后必须 submit / abort / switch mode。

适用：

- 只有在 deterministic signal 很强时才启用
- 不应由模型直接决定

## 8. 我建议的最终落地方案

### 8.1 短期建议

先做最小闭环，不要一上来把系统改得太复杂。

优先级如下：

1. **SuccessPathCard 最小闭环**
   - 把 resolved attempt 压成强成功卡

2. **TimeoutGovernanceCard 最小闭环**
   - 把 `ad_hoc_repro_script_loop` 和 `broad_test_without_patch` 变成预算规则

3. **RuntimeGuard 最小闭环**
   - 先支持 2 条硬治理：
     - repro confirmed 后禁止再建新 repro script
     - no patch candidate 时禁止 broad tests

4. **ConstraintCandidate 原型**
   - 让记忆提取模型先输出候选，不直接执行

### 8.2 中期建议

中期再把预算经验做细：

- `max_new_repro_scripts_after_repro_confirmed`
- `max_target_validation_retries_without_patch_upgrade`
- `max_steps_without_edit_or_patch_progress`
- `submit_trigger_after_validated_minimal_patch`

### 8.3 不建议现在就做的事

不建议马上做：

- 完全由模型直接决定 hard stop
- 大量新增复杂 card 类型
- 在没有治理日志的情况下直接启用强动作限制

这会让系统过快变复杂，而且调试成本很高。

## 9. 验收标准

如果阶段8把这条主线做对，至少应当看到以下现象：

### 成功路径复用

- 同题后续 attempt 能稳定检索到 success path card
- success path card 能进入高优先级注入
- 后续 attempt 的 patch family 重复率上升
- 后续 attempt 的首次有效 patch step 更早

### 超时治理

- `ad_hoc_repro_script_loop` 出现次数下降
- `broad_test_without_patch` 出现次数下降
- `timeout_no_prediction` 占比下降
- “已有有效 patch 但没 submit” 的情况减少

### 约束模型介入

- 每条强约束都有结构化来源、置信度、support_count 和 fallback
- 不出现“模型一句话直接把系统带偏”的情况

---

## 10. 最终判断

这次单题实验已经足够清楚地说明：

1. 当前框架已经能积累比“泛泛教训”更细的经验  
2. 这些经验已经能够被后续 attempt 检索和注入  
3. 但它们还没有被升级成稳定、可执行、可预算的治理机制

所以阶段8接下来最值得做的，不是再继续加更多记忆对象，而是：

> 把“成功路径”压成强成功卡，把“超时失败”压成预算治理卡，再用受控的 runtime guard 去真正改变行为。

关于“让记忆提取模型参与决定硬性程度”这件事，我的最终建议是：

> **可以介入，但只能做 constraint candidate proposer，不能直接做 hard constraint final authority。**

最稳的结构是：

`memory extraction model 提议 -> governance policy 审批 -> runtime guard 执行`

这条路线最符合我们当前真正的目标：

- 稳定复用成功路径
- 稳定抑制超时
- 不把错误经验硬化成系统级错误行为
