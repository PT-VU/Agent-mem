# 阶段9 成功路径复用与超时治理实现说明

日期：2026-04-20  
对应设计文档：`阶段8_成功路径复用与超时治理框架方案_2026-04-19.md`

---

## 1. 本次实现目标

本次实现只做最小但真实可运行的闭环，不做大而全重构。

核心目标：

1. 让 `resolved attempt` 能被压缩成可复用的强成功卡，而不只是留下零散 trail
2. 让 `timeout / incomplete attempt` 能被压缩成可执行的超时治理卡，而不只是留下事后总结
3. 让治理卡不只停留在 prompt hint，而是能进入运行时约束

---

## 2. 本次实际落地内容

### 2.1 新增 SuccessPathCard

在 official eval 返回 `resolved` 后，框架现在会直接生成 `SuccessPathCard`，并写入 `compiler_cards_v21`。

当前最小字段包括：

- `patch_family`
- `repro_path`
- `target_validation`
- `submit_preconditions`
- `prefer_actions`
- `governance_hardness=strong`

当前语义：

- 后续同题 attempt 在 planning 阶段更容易优先检索到该卡
- 该卡会推动 agent 回到已验证成功的 patch family 和 target validation 路径
- 该卡目前主要提供 **强偏置**，还不是 hard stop

### 2.2 新增 TimeoutGovernanceCard

在 official eval 返回 `incomplete`，且表现出“长时间探索但没有形成有效 patch”时，框架现在会生成 `TimeoutGovernanceCard`。

当前最小字段包括：

- `failure_family=ad_hoc_repro_script_loop`
- `prefer_actions`
- `avoid_actions`
- `budget_hints`
- `governance_hardness=guardrail`

当前最小预算包括：

- `max_new_repro_scripts_after_repro_confirmed = 0`
- `max_broad_tests_before_patch = 0`
- `max_target_validation_retries_without_patch_upgrade = 1`

当前语义：

- 这类卡不只是建议“别再过度探索”
- 而是会把部分 avoid action 传入运行时治理层

### 2.3 运行时桥接层开始消费治理卡

`bridge_hook` 现在不再只从 `attempt_summary_v1` 读取 `avoid_actions`。

现在它也会从满足以下条件的 recommendation 中读取运行时约束：

- `type=compiler_card`
- `card_type=TimeoutGovernanceCard / ClosureGuardCard`
- 或 `governance_hardness in {guardrail, hard_stop}`

当前会真正进入运行时阻断的动作包括：

- `create_new_repro_script_after_repro_confirmed`
- `run_broad_regression_before_patch_candidate_exists`
- 以及已有的其他 closure guard pattern

这意味着当前记忆框架已经从：

`经验抽取 -> 注入提示`

前进到了：

`经验抽取 -> 治理卡 -> 运行时约束`

### 2.4 检索层开始显式偏置新卡

为了让新卡真正被用到，检索层做了两类增强：

1. `GraphStore.query_compiler_cards_v21`
   - `SuccessPathCard` 在 `planning` 查询里获得额外加分
   - `TimeoutGovernanceCard` 在 `planning / error_recovery / test_failure_fix / regression_guard` 中获得额外加分

2. `MemoryAgent._retrieve_compiler_cards`
   - 现在会把以下结构化字段带回上层：
     - `support_count`
     - `subproblem_type`
     - `strategy_label`
     - `prefer_actions`
     - `avoid_actions`
     - `budget_hints`
     - `governance_hardness`

也就是说，新卡现在不是只以一句自然语言 hint 被看见，而是带着治理元数据一起进入桥接层。

## 4. 这次实现已经解决了什么

本次实现已经解决的是真问题，不是纸面设计：

1. `resolved` 不再只是“promote 旧对象”
   - 现在会落成明确的 `SuccessPathCard`

2. `incomplete timeout` 不再只是“写一条 negative abstract experience”
   - 现在会额外落成 `TimeoutGovernanceCard`

3. 运行时约束不再只依赖 `attempt_summary_v1`
   - 现在治理卡也能真正限制行为

4. 新卡不再只是存储对象
   - 检索层已经能优先把它们拿回来

## 5. 这次实现仍然故意没有做的事

为了保持 good taste，这次没有一次性把系统做得过重。

以下内容仍然是下一阶段事项，而不是这次补丁的一部分：

### 5.1 还没有完整实现 ConstraintCandidate + policy gate

当前没有引入独立的：

- `ConstraintCandidate`
- `deterministic policy gate`
- `RuntimeGuard policy engine`

这次是直接把最关键的治理元数据压进 compiler card，再由 bridge hook 消费。

这样做的好处是：

- 先把最短闭环做通
- 不把系统复杂度一次性抬高

### 5.2 还没有实现真正的 step-budget / hard-stop 计数器

文档里说的更强预算，比如：

- `N steps without patch -> force closure`
- `1 次 target validation retry 后必须 submit/abort`

目前仍然还没有直接绑定到 step counter 或 action counter。

现在已有的是：

- 动作级 avoid rule
- 治理卡预算提示
- 运行时 block pattern

还没有做到：

- 真正的 deterministic hard stop

### 5.3 还没有让模型直接决定硬性程度

本次实现保持了保守边界：

- 模型/提取链负责生成 card
- 运行时桥接层只消费显式治理字段

没有让模型直接临场决定：

- 当前该不该 hard stop
- 当前该不该 forbid 某类动作

这符合之前设计文档里的结论：

> 先做“模型提出结构化治理信息”，不要直接让模型拥有最终硬约束执行权。

## 6. 当前版本的工程判断

### 这是一个真实改进

因为它已经让框架具备：

- 成功路径卡化
- 超时治理卡化
- 运行时 guard 接治理卡

这不是只改文档，也不是只改 prompt。

### 但这还不是最终形态

当前版本更准确地说是：

> 从“提示型经验注入器”向“成功路径复用器 + 超时治理器”迈出的第一步

它已经补上了闭环，但还没有补上全部治理层。

---

## 7. 下一步建议

建议按下面顺序继续推进，而不是同时全做：

1. **先观察新卡在后续 single-case repeat 实验里的真实效果**
   - 是否更容易复用成功 patch family
   - 是否更少出现新的 repro script 扩散
   - 是否更少在无 patch 情况下跑 broad regression

2. **再补 deterministic budget guard**
   - `N steps without patch/edit`
   - `target validation pass -> submit_or_small_revision`

3. **最后再考虑引入 ConstraintCandidate + policy gate**
   - 让模型参与“提出治理候选”
   - 但不要直接掌握硬约束执行权

---

## 8. 一句话总结

这次实现把阶段8文档里的关键设计，落成了一个最小但真实可运行的闭环：

> `resolved -> SuccessPathCard -> planning bias`  
> `timeout/incomplete -> TimeoutGovernanceCard -> runtime guard`

这就是当前阶段最值得先做、也最符合 good taste 的落地方式。
