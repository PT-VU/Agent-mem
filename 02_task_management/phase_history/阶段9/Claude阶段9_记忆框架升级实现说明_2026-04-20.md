## 1. 本次升级的背景与目的

本次升级基于对 Phase 8 实验数据（前 13 案例、130 个 WithMem attempts）的深入分析，识别出六大核心缺口：

| 缺口 | 现象 | 影响 |
|---|---|---|
| 成功知识提取太浅 | `success_fact_hotpath_skipped = 10724`，跳过率 88% | 后续 attempt 只知"上次成功了"，不知"为什么成功" |
| 超时治理无确定性预算 | `TimeoutGovernanceCard.budget_hints` 是建议非计数器 | 过度探索仍然发生 |
| Gate 治理失效 | `passed=false=127, hard_fail_enabled=false=127` | 低价值注入持续流入 |
| 反馈信号无区分度 | `local_effective=true` = 1555/1555（100%） | promotion/suppression 缺乏驱动 |
| 注入内容信息密度低 | `workflow_step`、`validation_gap` 占主流 | bug-specific 经验被稀释 |
| 跨题经验迁移缺失 | 治理卡仅在 same-case scope 有效 | 同类 bug 跨题无法复用 |

**核心目标**：把记忆框架从"搜索纪律控制器"推进到"成功语义记忆系统"。

#### 3.2.2 `_write_bug_invariant_card` 方法

从 diff 文本规则化提取 bug 语义信息，生成 BugInvariantCard：

```python
def _write_bug_invariant_card(self, *, instance_id, eval_ref, patch_text, summary,
                               validation_summary, task_summary, run_id, attempt_id, trace_id):
    # 前置检查：没有 patch 就不生成
    changed_files = [...]
    if not patch_text.strip() and not changed_files:
        return None
    
    # 规则化提取 bug 语义
    change_type = self._infer_change_type(patch_text)        # 改动类型
    key_lines = self._extract_key_added_lines(patch_text)    # 关键新增行
    target_function = self._extract_target_function(patch_text)  # 目标函数/类
    validation_invariant = self._extract_validation_invariant(validation_summary)  # 验证命令
    bug_semantic = self._build_bug_semantic(...)             # 语义摘要
    
    # 生成 ≤300 字符的短格式 hint
    hint = f"[BugInvariant] Fix: {bug_semantic}. Key change: {key_line_hint[:80]}. Validate: {validation_invariant}."
    
    # 写入 compiler_cards_v21，confidence=0.95，governance_hardness="strong"
    return self._upsert_compiler_card_with_support({...})
```

**Card schema 的核心字段**：
```json
{
  "card_type": "BugInvariantCard",
  "bug_semantic": "condition_fix in Field() at __init__.py",
  "minimal_patch_signature": {
    "files_touched": ["django/db/models/fields/__init__.py"],
    "change_type": "condition_fix",
    "key_lines": ["if not isinstance(value, (list, tuple)):"]
  },
  "validation_invariant": "pytest tests/test_field.py -q",
  "governance_hardness": "strong",
  "confidence": 0.95
}
```

#### 3.2.3 四个静态辅助方法

| 方法 | 功能 | 实现逻辑 |
|---|---|---|
| `_infer_change_type(patch_text)` | 推断改动类型 | 正则匹配新增行：`if/elif`→condition_fix，`raise/assert`→missing_check，`return`→wrong_return，`def/class`→new_function_or_class，其他→code_change |
| `_extract_key_added_lines(patch_text)` | 提取关键新增行 | 过滤 `+` 开头行，去掉注释和空行，取前 3 条长度 >5 的行 |
| `_extract_target_function(patch_text)` | 提取目标函数/类名 | 优先从 `@@ ... @@ <context>` 提取 def/class 名；fallback 到新增行中的 def |
| `_build_bug_semantic(target_function, change_type, changed_files)` | 组装语义摘要 | `f"{change_type} in {target_function}() at {file_hint}"` |

**示例输出**（对 django 一行修复 patch）：
```
[BugInvariant] Fix: condition_fix in Field() at __init__.py.
Key change: if not isinstance(value, (list, tuple)):.
Validate: pytest tests/ -q.
```

### 3.4 `bridge_hook.py` — 四项增强

#### 3.4.1 确定性步骤预算守卫

**`__init__` 中新增状态**：
```python
self._step_budget_state: dict[str, int] = {
    "steps_since_last_edit": 0,    # 距上次代码编辑的步数
    "steps_since_last_patch": 0,   # 距上次 patch 进展的步数
    "total_steps": 0,               # 总步数
    "extra_repro_budget": 0,        # repro 确认后的额外预算
}
self._patch_candidate_exists = False   # 是否已产生 patch 候选
self._step_budget_guardrail_steps = 15  # L1 阈值（可配置）
self._step_budget_strong_steps = 25     # L2 阈值（可配置）
self._step_budget_hard_stop = 50        # L3 阈值（可配置）
```

**支持环境变量覆盖**：
- `AGENT_MEM_STEP_GUARDRAIL_NO_EDIT`（默认 15）
- `AGENT_MEM_STEP_STRONG_NO_PATCH`（默认 25）
- `AGENT_MEM_STEP_HARD_STOP_TOTAL`（默认 50）

**新增静态方法**：
```python
@staticmethod
def _is_code_edit_action(action_text: str) -> bool:
    # 检测: str_replace_editor / edit_file / apply_patch / str_replace / create_file / write_file

@staticmethod
def _is_patch_submission(action_text: str) -> bool:
    # 检测: submit / <submit> / final answer / final patch
```

**新增 `_update_step_budget(action_text)` 方法**：
- 每步递增 `total_steps`、`steps_since_last_edit`、`steps_since_last_patch`
- 检测到代码编辑 → 重置 `steps_since_last_edit = 0`，设置 `_patch_candidate_exists = True`
- 检测到提交 → 重置 `steps_since_last_patch = 0`
- 检测到 repro 确认信号 → 设置 `extra_repro_budget = 5`（最多叠加 5 步缓冲）

**新增 `_check_step_budget_triggers()` 方法**（三档触发）：

| 档位 | 触发条件 | 动作 | 硬性程度 |
|---|---|---|---|
| L1 Guardrail | `steps_since_last_edit ≥ 15`，每 5 步触发一次 | 注入强偏置提示："必须生成 patch 或提交" | Guardrail |
| L2 Strong | `steps_since_last_patch ≥ 25` 且无 patch 候选，每 10 步触发一次 | 将 `run_broad_regression_before_patch_candidate_exists` 加入 blocked_action_patterns + 注入提示 | Strong |
| L3 HardStop | `total_steps ≥ 50` 且无 patch 候选 | 注入最高优先级提示："立即提交或退出" | Hard Stop |

**调用位置**：`on_actions_generated` 方法中，在 `_scan_proactive_triggers` 之前：
```python

self._check_step_budget_triggers()
self._scan_proactive_triggers(step.action)
```

**`_select_hints_for_injection` 中的配套改动**：

|---|---|---|---|
| 1 | BugInvariantCard / SuccessPathCard | 各 1 条 | 否（豁免预算） |
| 2 | closure_signal / step_budget | 1 条 | 是 |
| 3 | repair / failure_card | 1 条 | 是 |
| 4 | validation | 1 条 | 是 |

#### 3.4.3 Gate 硬规则——非 semantic 卡注入上限

**改动位置**：`_buffer_memory_hints` 方法，在 fingerprint 去重之前

**改动内容**：
```python
card_type = item.get("card_type") if isinstance(item, dict) else None
is_semantic_card = card_type in {"BugInvariantCard", "SuccessPathCard"}
# 非 semantic 卡：同一 family_id 本次 attempt 已注入 ≥ 3 次 → 直接跳过缓冲
if not is_semantic_card and family_id and self._hint_family_injected_count.get(family_id, 0) >= 3:
    continue
```

**设计意图**：
- 防止低价值 generic hint 反复进入注入缓冲池（原来的 `max_hints_per_family_per_attempt=1` 仅控制单步注入，不控制累计缓冲）
- BugInvariantCard/SuccessPathCard 永远不被限制，因为它们随 attempt 增加而更新

**`step_budget:` 前缀触发**：步骤预算守卫产生的 system hint 被识别到 `closure_signal` 桶中：
```python
if family_id.startswith("step_budget:"):
    return "closure"
```

#### 3.4.4 反馈信号区分度修复

**改动位置**：`_advance_interventions` 方法的 feedback 日志输出

**原代码**（永远为 true）：
```python
"local_effective": int(row.get("success_events", 0)) > 0 and int(row.get("error_events", 0)) == 0,
```

**新代码**（真正有区分度）：
```python
success_count = int(row.get("success_events", 0))
error_count = int(row.get("error_events", 0))
# 有效 = 至少 1 个成功事件，且成功次数 ≥ 错误次数
local_effective = success_count > 0 and success_count >= error_count
```

**区分逻辑说明**：
- `action_executed` → `success_events += 1`
- `action_error` → `error_events += 1`
- 如果注入后下一步就报错了 → `error_events > success_events` → `local_effective = False`
- 如果注入后多步成功 → `success_events ≥ error_events` → `local_effective = True`

这使 `memory_intervention_feedback` 能真正区分"陪跑注入"与"有效干预"，为未来的 promotion/suppression 机制提供可信信号。

## 6. 本次升级仍然故意没有做的事

为保持系统可测试性和可解释性，以下内容不在本次范围内：

### 6.1 跨题经验迁移（AtomicBelief Cross-case Promotion）

同类型 bug 在不同 repo 出现时，BugInvariantCard 尚未自动聚合为跨题 AtomicBelief。这需要：
- embedding cosine similarity 相似度匹配（阈值 0.85）
- support_n ≥ 3 才 promote to preference

**下一阶段工作**：在 `object_governance_policy.py` 和 `belief_graph.py` 中增加 cross-case promotion 逻辑。

### 6.2 ConstraintCandidate + PolicyGate（完整治理链）

当前 governance 链路是：`card → bridge_hook 直接消费`。  
完整设计中应有独立的 `ConstraintCandidate` 对象和 `deterministic policy gate`，但本次为最小闭环优先实现。

### 6.3 真正的 step counter Hard Stop（强制 exit）

当前 L3 Hard Stop 只注入最高优先级提示词，不强制修改 action。真正的强制退出需要在 `on_actions_generated` 中修改 `step.action`，类似现有的 `_soft_block_runtime_guard_pattern`。暂缓是因为需要更多实验数据确认阈值再硬化。

### 6.4 短卡片格式规范（compact_render）

`card_compiler.py` 中尚未增加统一的 `compact_render` 方法。目前 BugInvariantCard 的 hint 已在生成时控制在 ≤300 字符。统一格式规范留作后续。

## 8. 一句话总结

本次升级把记忆框架在以下四个维度做了真实的代码级强化：

> **语义化**（BugInvariantCard）+ **确定性**（Step Budget Guard）+ **密度**（Semantic 注入桶 + Gate 过滤）+ **可信**（反馈区分度）

这四项改动相互配合：BugInvariantCard 提供最高密度的语义注入内容，Step Budget Guard 确保不会在无 patch 情况下继续漫游，Gate 过滤防止低价值 hint 稀释高价值信号，反馈区分度为未来的 promotion/suppression 提供可信信号。
