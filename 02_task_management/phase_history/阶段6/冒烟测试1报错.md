## 1.1 本次测试的检查重点修正

本次是单例闭环冒烟测试，不是统计实验。

因此本次的主要检查目标应该是：
- submit 后是否真的触发了 official evaluate；
- official evaluate 的结果是否真的进入了 `official_eval_feedback`；
- `official_eval_feedback` 是否进一步影响了经验提取/写入/回流；
- 在线记忆链路是否至少在结构上跑通。

不应该把“单例样本里注入有没有显著提升最终 solved rate”当成硬性验收标准。这个问题只能通过多实例或重复尝试实验来判断。

## 3. 哪些部分明显不按预期

### 3.1 运行时注入基本没有发挥作用

`memory_behavior` 的关键结果：
- `unique_families_injected = 0`
- `total_family_injections = 0`
- `repeated_family_injections = 0`

这说明：
- 虽然 Tool A 检索一直在工作，事件日志里有大量 `plan_generated -> external_tool_response`；
- 但最终没有形成有效注入统计；
- 也就是说，“检索到候选”并没有真正变成“帮助主模型收敛的可追踪注入”。

这是当前最大问题之一：
**在线记忆链路在跑，但没有真正进入主求解回路。**

### 3.2 检索严重偏向 workflow/planning 垃圾经验

事件日志显示：
- Tool A 在大量 step 上持续返回同一个 family：`workflow_step:consider: generate plan for task...`
- `candidate_count_before_filter` 从 0 一直涨到 52
- 但几乎所有候选都来自当前任务本身累积出来的 planning 轨迹

对应后果：
- 记忆系统没有把 agent 往“最小修复”方向拉；
- 反而持续强化了“继续计划、继续读代码、继续做额外验证”的行为。

这说明当前的 retrieval/rerank 仍然有结构性问题：
- 对当前任务自己刚写出来的 planning 痕迹过拟合；
- 对低价值 workflow family 的压制仍然不够；
- 对真正高价值的 negative strategy / patch risk / stop signal 还不够强。

### 3.3 停止条件明显失效

这次轨迹里，agent 很早就已经拿到了关键事实：
- `all_world2pix(quiet=True)` 返回 best solution；
- `world_to_pixel_values()` 当前不传 `quiet=True`，因此仍抛异常；
- 这已经足够支持一个“最小修复”候选。

但之后 agent 没有收敛，而是继续做了大量无效扩展：
- 检查 WCS API 其他实现；
- 写额外脚本 `test_quiet.py`；
- 写额外脚本 `test_scalar_vs_array.py`；
- 继续追 wrapper/base/sliced_wcs 等非关键路径；
- 继续讨论接口兼容性、多版本迁移、context manager 等超出当前任务的设计问题。

最终轨迹推进到约 `step 128` 才结束。

这说明当前系统缺少一类很关键的经验/控制：
- **“已拿到足够决策证据后，停止扩展搜索”的 stop/closure 经验。**

### 3.4 单实例 20 分钟上限没有按预期生效

运行日志明确显示：
- `Overall Progress ... 0:53:49`

也就是说：
- 当前这个“每实例 20min”的约束，在这次 closed-loop smoke 中没有真正把实例裁停；
- 即便 `--agent.tools.total_execution_timeout 1200` 已传入，整体实例运行时间仍然远超 20 分钟。

这是流程层面的严重问题，因为它会直接污染后续评估：
- 你以为是在比较“20min budget 下的能力”；
- 实际跑出来的是“远超预算后的能力/行为”。

### 3.6 official eval 回流虽然触发了，但 candidate 关联失败

这说明：

这非常重要。

## 4. 为什么这次最终 unresolved

从 patch 和回流结果看，根因不是“完全没理解问题”，而是以下组合：

### 4.1 patch 方向发生了泛化和过度设计

最终 patch 不是最小修复，而是把 `world_to_pixel_values` 改成了一个 80 多行的大逻辑：
- 新增 `quiet` 参数
- 默认 `quiet=False`
- 捕获 `NoConvergence`
- 发 warning
- 手工组装 `best_solution`
- 手工处理 scalar/array/broadcast/NaN

这种 patch 风格的问题是：
- 复杂度太高；
- 语义改变过大；
- 容易偏离任务真正需要的最小行为修复；
- 风险显著高于“在确切调用点做最小修正”。

### 4.2 轨迹中出现了大量“自造验证任务”

agent 在主问题已经足够清楚时，又额外制造了多个验证脚本：
- `reproduce_error.py`
- `test_quiet.py`
- `test_scalar_vs_array.py`
- `test_wcsapi_basic.py`

其中一部分脚本一开始还是错的，例如最早的 reproduction 脚本本身就因为 matplotlib 用法错误而失败。这个噪声会带来两个直接坏处：
- 消耗大量 step / token / wall time；
- 给经验提取系统喂入大量“与真正 issue 不完全对齐”的局部信号。

### 4.3 评测后系统正确判定为 unresolved，但还没有足够强地反推“为什么这个 patch 风险高”

`official_eval_feedback` 已经识别出：
- `outcome = unresolved`
- `risk_flags = [quiet_flag]`

这说明系统已经开始具备“这类 patch 有风险”的意识。问题在于：
- 这种风险意识还没有前置到在线阶段；
- 只在事后回流；
- 且没有成功 suppress 本轮 candidate。

## 8. 总结

这次样本最重要的价值不在于 patch 成功，而在于它第一次完整证明了下面这件事：

**我们的阶段6闭环已经能把一次真实的 submitted-but-unresolved 运行，走完整个 `trial -> official eval -> official_eval_feedback -> memory behavior` 链条。**

但它同时也明确暴露出：

**当前系统更像是“能在事后记住失败”，还不是“能在运行中有效阻止失败”。**

这是下一轮升级的核心方向。


## 9. 异常清单对应解决方案

### 9.1 运行时间异常：标称 20min，实际约 53m49s

问题：
- 当前 `--agent.tools.total_execution_timeout 1200` 没有真正把单实例总运行时长限制在 20 分钟内。

解决方案：
- 增加**外层 wall-clock 超时**，不要只依赖 agent 内部工具超时。
- 在 closed-loop runner 里用外层 watchdog 包住单实例执行，例如对 `sweagent run-batch --instances.slice i:i+1` 施加硬超时。
- 超时后统一标记为 `incomplete_timeout`，并把该 outcome 进入 `official_eval_feedback`/failure card。
- 将“工具超时”和“实例总时长超时”分开记录，避免语义混淆。

### 9.2 注入异常：retrieval 有候选，但 `total_family_injections = 0`

问题：
- 在线检索在工作，但没有形成有效、可追踪的主模型注入。

解决方案：
- 先修正注入事件统计，区分：
  - `retrieved_candidate_count`
  - `buffered_hint_count`
  - `model_prompt_injected_count`
  - `accepted_hint_count`
- 在 `bridge_hook` 中显式记录“为什么没注入”：budget/cooldown/duplication/fallback suppression。
- 对 `memory_hint_buffered -> memory_injected` 断点加结构化日志，不再只依赖最终 summary。
- 单例测试阶段，不以“注入后 solved 提升”为验收，而以“注入链是否可追踪”作为验收。

### 9.3 停止条件异常：拿到关键结论后仍继续扩展搜索

问题：
- agent 在核心技术结论已足够的情况下继续扩展分析、写额外脚本、读非关键文件。

解决方案：
- 增加 `closure_signal`/`stop_signal` 经验类型。
- 当满足以下条件时，强制提升 stop 类经验优先级：
  - 已验证核心假设；
  - 已形成最小 patch 候选；
  - 后续动作只是在做接口外延探索。
- 增加“连续 N 次没有产生新高价值证据”的 stop heuristic。
- 将“重复验证同一结论”“继续扩大接口讨论”写成 negative strategy memory。

### 9.4 检索异常：持续返回低价值 `workflow_step` family

问题：
- retrieval 被当前任务自身的 planning 轨迹污染，持续返回低价值 workflow 提示。

解决方案：
- 进一步下调 `workflow_step/belief_tip/planning_rule` 的排序权重。
- 对“当前任务自身最近若干 step 生成的 planning 痕迹”加入更强去重和时间衰减。
- 提高以下 bucket 的排序优先级：
  - `negative_strategy`
  - `patch_risk`
  - `validation_gap`
  - `closure_signal`
- 增加“相同 family 在同一实例中出现超过阈值后直接静音”的策略。

### 9.5 回流关联异常：`related_candidate_count = 0`

问题：
- official eval 已返回 unresolved，但没有回连到本轮 candidate 对象。

解决方案：
- 给 `run_done` 阶段生成的 candidate 经验统一附加稳定的 `instance_id/run_id/attempt_id/patch_fingerprint`。
- `official_eval_feedback` 先按 `instance_id + run_id` 查，再按 `patch_fingerprint` 精确匹配。
- 对未能匹配的 unresolved 结果单独告警，不能静默接受。
- 在 graph store 里增加“candidate lineage”字段，保证 promote/suppress 有明确目标。

### 9.6 提取时机问题：official eval 前仍产生较多 candidate 经验

问题：
- submit 后、评测前，系统还是会写入不少正向/中性经验，语义偏乐观。

解决方案：
- 把 `run_done` 阶段写入的经验默认标记为 `promotion_state=candidate`、`evidence_stage=submission`。
- official eval 之前，不允许这些 candidate 进入高优先级检索。
- 只有 `resolved` 后才 promote；`unresolved` 直接 suppress 或转负经验。
- 对 `submission_pending_official_eval` 状态下的抽取预算收紧，减少 abstract 经验数量。

### 9.7 在线可解释性不足：`read_ids` 基本为空

问题：
- retrieval/注入发生了，但在线链路没有稳定记录“模型到底读了哪些经验”。

解决方案：
- 在 `memory_hint_buffered` 时记录 candidate `read_ids`；
- 在真正拼入 prompt 时记录 `prompt_injected_read_ids`；
- 在后续 action/feedback 上把这些 read_ids 带过去，形成最小可追踪链。
- 没有 read_ids 的 retrieval 结果不应进入“经验有效性分析”，避免伪解释。

### 9.8 patch 过大与过度设计

问题：
- 最终 patch 不是最小修复，而是 80 多行的接口扩张式修改。

解决方案：
- 在 patch risk 中增加结构化风险标签：
  - `large_patch`
  - `interface_expansion`
  - `behavior_change_default`
  - `quiet_flag`
- 当 patch risk 达到阈值时，向模型注入“优先最小修复”的约束提示。
- 对“单文件改动行数过大 + 新增参数 + 自定义 fallback 逻辑”设为高风险组合。

### 9.9 自造验证脚本过多

问题：
- agent 在同一问题上连续创建多个辅助脚本，且部分脚本本身是错误的。

解决方案：
- 将“在同一实例中创建过多一次性测试脚本”定义为 negative strategy pattern。
- 对复现实验脚本数量设置软阈值，超过阈值后触发 stop/closure 提示。
- 对脚本失败原因进行分类：
  - 目标 bug 复现失败
  - 脚本自身错误
  - 环境噪声
- 只有第一类才允许进入高权重经验。

## 10. 对本次测试口径的最终修正

本次是**单例闭环冒烟测试**，因此：
- 不应把“注入是否显著提升最终 solved rate”作为硬性验收标准；
- 本次真正应该检查的是：
  1. submit 后是否真的 evaluate；
  2. evaluate 的结果是否进入 feedback；
  3. feedback 是否真正参与后续经验写入与状态修正；
  4. 在线链路是否至少可追踪、可解释。
