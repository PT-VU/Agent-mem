# 阶段6：经验注入总结3

## 1. 本文目标

本文不是单纯描述“当前 AgentMem 有哪些字段”，而是要回答更关键的问题：

1. 当前经验条目里到底存了什么信息，这些信息够不够支撑后续求解。
2. 为什么仅仅知道“上一次全局失败了”并不能提升下一次表现。
3. 我们应该如何把一次长轨迹切分成可分析、可归因、可写经验的子块。
4. 经验必须具体到什么粒度，才能真正改变后续 agent 的行为。
5. 下一阶段要补哪些结构，才能让经验从“抽象提示”升级成“可执行约束”。

这份文档的核心结论是：

**未来的经验提取，不能只围绕最终 resolved / unresolved 结果做粗粒度总结，而必须先对整条 trial 做整体理解，再对其中的子块进行因果分析，最后把经验落到具体 action 或 action 链级别。**

---

## 2. 当前经验条目里到底有什么信息

### 2.1 抽象经验并不只有一句建议

当前系统中的 `abstract_experience` 已经不只是自然语言建议。它至少包含：

- `experience_id`：经验唯一标识。
- `pattern_type`：原始模式类型，例如 `negative_strategy_timeout_after_overexploration`。
- `normalized_pattern_type`：归一化后的模式族，例如 `negative_strategy`、`failure_recovery`、`validation_gap`。
- `family_id`：family 级聚合键，用来把相似经验归并到同一族。
- `source_instance_id`：经验最初来自哪个 instance。
- `support_count`：该经验 family 被重复支持了多少次。
- `metadata.experience_polarity`：正向 / 负向 / 中性。
- `metadata.promotion_state`：candidate / promoted / suppressed。
- `metadata.official_eval_refs`：和哪些 official eval 结果绑定过。

因此，当前系统已经知道：
- 这条经验是什么；
- 它来自哪里；
- 它是否被重复观察到；
- 它是否已经被官方反馈确认；
- 它当前是待定、已确认还是被压制。

这说明当前经验系统并不是完全“无上下文”的。

### 2.2 当前还有三类更具体的经验对象

除了 `abstract_experience`，当前系统还有三类更具体的对象。

#### 1. `failure_card_v2`

它最接近“问题卡片”，字段包括：

- `task_id`
- `action_id`
- `instance_id`
- `run_id`
- `source_event`
- `step_index`
- `trace_id`
- `error_signature`
- `action_trace_snippet`
- `candidate_fix_actions`
- `verification_commands`
- `root_cause_nodes`
- `propagation_chain`
- `error_module`
- `failure_class`
- `status`

也就是说，它已经能表达：
- 错误发生在哪；
- 是在什么 action 上触发的；
- 当时做了什么；
- 推荐优先做哪些修复动作；
- 应该用什么验证命令检查。

#### 2. `repair_pattern_v2`

它最接近“遇到某种触发条件时优先尝试什么”的经验。字段包括：

- `trigger_signature`
- `fix_action_template`
- `expected_verification`
- `support`
- `confidence`

它的价值在于：能把“触发条件 -> 修复动作 -> 验证方式”表达成一条结构化模式。

#### 3. `preventive_rule_v2`

它最接近“在什么条件下先检查什么，避免浪费时间”的规则。字段包括：

- `when`
- `should_check`
- `support`
- `confidence`

它的价值在于：可以表达预防性规则，而不是事后总结。

### 2.3 当前已经有的条件信息是什么

如果严格一点看，当前系统已经有一部分条件信息：

- `error_signature`
- `trigger_signature`
- `verification_commands`
- `source_event`
- `instance_id / run_id / attempt_id / trace_id`
- `pattern_type / normalized_pattern_type / family_id`
- `failure_class`
- `official_eval_refs`

因此问题不是“完全没有条件信息”，而是：

**这些条件信息还没有被整理成一个明确的“适用范围 + 作用对象 + 行为建议”的结构。**

---

## 3. 当前系统的根本问题：全局失败信息太粗，不能直接指导下一次求解

### 3.1 仅仅知道全局失败状态没有用

仅仅知道：
- 上一次 `unresolved`
- 上一次 `incomplete`
- 上一次 `over_exploration`

对下一次求解的帮助非常有限。

原因很简单：
- 它告诉你“这次整体没成功”；
- 但它没有告诉你“为什么没成功”；
- 更没有告诉你“是在哪一段、哪一个子问题、哪一种动作路径上没成功”。

而真正能帮助后续求解的，不是全局失败标签，而是：

- 上一次全局失败的**原因**；
- 这个原因出现在哪个**子块**；
- 在这个子块里使用了哪条**路径**；
- 这条路径为什么失败；
- 它以后该如何被避免。

### 3.2 “over exploration”必须被具体化

如果我们判断某次失败的原因是 `over_exploration`，那么这句话本身还不够。

必须继续回答：

- 是在 **什么方向** 上发生了 over-exploration？
- 是在 `reproduce_issue` 上反复写 ad-hoc 脚本？
- 是在 `localize_fix` 阶段扩大到了无关模块？
- 是在已有关键信号后仍然继续 broad search？
- 是在 `validation` 阶段反复跑不直接相关的测试链？

如果只停留在“over exploration”这个标签上，那经验还是太粗。

### 3.3 每条经验必须能指向 action 或 action 链

这是当前最需要强化的一点：

**每一条经验都必须尽可能具体地指向某个 action，或者一段 action 链。**

因为只有这样，后续读取经验时才能知道：
- 在什么条件下，这个 action 是正确的；
- 在什么条件下，这个 action 是错误的；
- 哪些 action 组合起来会把问题带偏；
- 哪些 action 组合起来更接近成功。

否则，经验就只会变成“抽象的信息传递”，而不是“可执行的经验条”。

---

## 4. 经验提取之前，必须先对整条 trial 做整体理解

这是本轮讨论里最关键的新要求。

在做具体经验提取之前，我们必须先对上一次的 trial 有一个整体理解，至少回答以下问题：

- 这次尝试想解决什么问题？
- 最初的 plan 认为应该怎样解决？
- 计划里的关键任务链条是什么？
- 实际执行的链条和最初计划是否一致？
- 哪些地方执行成功了，哪些地方偏离了？
- 最终结果是什么？
- 偏差来自 plan 层，还是执行层？

也就是说，经验提取前，应该先做一次 **attempt-level overall understanding**。

如果没有这个整体理解，后面的经验提取就很容易变成：
- 看到某个失败动作就抽一条经验；
- 看到某个错误就抽一条经验；
- 看到某个超时就抽一条经验；

这样做的问题是：
- 丢失全局上下文；
- 容易把局部噪声误判成关键原因；
- 容易得到碎片化经验，而不是能指导后续求解的高价值经验。

## 5. 我们应该如何切分 trial：子块分析（Sub-block Analysis）

你这里说的“子块”，本质上和文档里提到的“子问题”是同一类概念。只是“子块”更强调它是从整体任务链里切出来的一段完整片段。

建议在经验提取前，先把整条 trial 切成若干个子块。每个子块至少要包含：

- 子块目标是什么；
- 它在整体计划中承担什么作用；
- 它是否必要；
- 实际是怎么执行的；
- 它对最终结果的贡献是正面还是负面；
- 如果是负面的，问题出在 plan 还是执行。

### 5.1 子块的来源

子块不能只按 step 数量机械切分，而应该按语义切分。建议初始切分来源包括：

- plan 中原本定义的阶段性目标；
- 轨迹中明显切换任务意图的地方；
- 从一个验证路径切换到另一个路径的地方；
- 从“定位问题”切换到“尝试修复”的地方；
- 从“修复”切换到“验证”的地方。

### 5.2 子块分析的两个层面

#### A. Plan 层分析

对每个子块，先看它在计划层的角色：

1. 这个子块最初的目标是什么？
2. 这个目标对整体成功是否必要？
3. 这个子块是否真的完成了它原本的目标？
4. 如果没有完成，后续有没有用其他方式继续尝试该目标？
5. 还是说系统直接绕过了这个子目标？

这里的重点不是动作本身，而是：

**这个子块在整个任务计划里的位置是否合理、目标是否必要、目标是否被真正完成。**

#### B. 执行层分析

再看这个子块在执行层是怎么完成的：

1. 为了实现当前子块的目标，使用了什么方法？
2. 这些方法是否有效？
3. 有没有更短、更直接的实现方式？
4. 有没有犯明显错误？
5. 这些错误能不能被归纳成可复用经验？
6. 这些方法对应的是哪一类 action 或 action 链？

这里的重点不是任务目标，而是：

**为了实现这个目标，实际走了什么路径，这条路径是否值得复用或避免。**

### 5.3 子块分析的输出

做完子块分析后，每个子块都应该有一个结构化输出，至少包括：

- `subproblem_type` / `subblock_type`
- `goal`
- `is_goal_necessary`
- `plan_role`
- `plan_success`
- `execution_path_labels`
- `key_actions`
- `positive_contribution`
- `negative_contribution`
- `failure_source`（plan / execution / mixed）
- `preferred_actions`
- `avoid_actions`

只有做完这一步，后续的经验提取才会有坚实的基础。

## 6. 未来的经验必须长成什么样

### 6.1 经验必须从“抽象建议”升级为“可执行经验条”

未来的经验不能只是一句：
- “不要过度探索”
- “优先验证最小修复”

这种表达太抽象，无法真正指导 agent。

经验应该尽量是这样的结构：

- 在 `subproblem_type = reproduce_issue` 且已经有 `error_signature = X` 的情况下；
- 如果已经创建过 `reproduce_issue.py` 并成功复现一次；
- 那么不要继续新建第二个 `test_*.py`；
- 优先执行 `action Y`；
- 避免执行 `action Z`；
- 如果一定要继续验证，先跑 `command C`。

也就是说，一条高质量经验应该显式包含：

- **触发条件**
- **适用范围**
- **推荐动作**
- **避免动作**
- **验证方式**
- **来源 action / action 链**

### 6.2 每条经验最好要有 action-level grounding

未来每条经验最好都能回答：

- 这条经验主要来自哪一个 action？
- 或者来自哪一段 action 链？
- 哪些 action 是关键正贡献？
- 哪些 action 是关键负贡献？

否则，经验再抽象也很难真正改变行为。

### 6.3 应增加显式的适用范围字段

建议未来在经验对象中补以下字段：

- `subproblem_type`
- `strategy_label`
- `applicability_scope`
- `applicability_signals`
- `prefer_actions`
- `avoid_actions`
- `source_action_ids`
- `source_action_chain`
- `plan_goal`
- `plan_role`
- `failure_source`

这样经验就不再只是“总结”，而是带着条件和动作建议的策略条目。

## 7. 稀疏奖励问题应该如何处理

### 7.1 不能直接把最终 reward 粗暴分摊给整条轨迹

如果只拿最终 `resolved / unresolved / incomplete` 做经验提取，就会出现两个问题：

1. 整条轨迹太长，不知道哪一段真正导致了失败；
2. 很多中间有效探索会被整体失败掩盖。

所以正确方法不是：
- 看到最终 unresolved，就把整条链都视为失败。

而是：
- 先整体理解 trial；
- 再切分子块；
- 再判断每个子块对结果的贡献；
- 最后才提经验。

### 7.2 子块级贡献判断是稀疏奖励的解法之一

在子块级别，至少可以判断：

- 该子块是否提供了关键正信号；
- 该子块是否浪费了大量时间；
- 该子块是否只是中性探索；
- 该子块的负面来自 plan 还是 execution；
- 该子块后续是否被更好的路径替代。

这样我们就能把最终稀疏 reward，转成一系列更细粒度的中间判断。

---

## 8. 对“把前一个 attempt 的 plan 或行为链压缩交给下一个 attempt”的评价

这个方向不仅可行，而且我认为应该做。但前提是：

**必须是结构化压缩，而不是把原始行为链直接交给下一个 attempt。**

如果直接传原始链，会有几个严重问题：

- 噪声太大；
- 错误尝试会被一起带过去；
- prompt 负担迅速膨胀；
- 后续 attempt 难以抓住重点。

正确做法是生成一个高密度的 `attempt_summary_v1`，例如包含：

- `problem_goal`
- `initial_plan_outline`
- `plan_success`
- `actual_execution_outline`
- `confirmed_signals`
- `subblocks`
- `tried_strategies`
- `failed_strategies`
- `best_partial_progress`
- `unverified_hypotheses`
- `next_best_actions`

这个对象的作用是：

- 不替代现有经验对象；
- 而是作为下一轮 attempt 的高层入口；
- 帮助下一轮先理解“上一次到底发生了什么”。

## 9. 我们现在能做到什么，做不到什么

### 9.1 现在已经能做到的

当前框架已经能做到：

1. 在 attempt 结束后，把最终失败沉淀成负经验；
2. 在后续 attempt 中真正读取到这条负经验；
3. 把多次重复出现的同类失败聚合进同一个 family；
4. 通过 `support_count` 表达“这类失败重复出现过多次”；
5. 通过 `promotion_state` 和 `official_eval_refs` 管理经验状态；
6. 通过 `failure_card_v2 / repair_pattern_v2 / preventive_rule_v2` 表达部分更具体的经验对象。

### 9.2 现在还做不到的

当前框架还做不到：

1. 精确定位某个子块上的失败路径 A；
2. 在后续相似子块里稳定避免路径 A；
3. 把 plan 偏差和 execution 偏差明确区分开；
4. 给每条经验提供清晰的适用范围和动作边界；
5. 把前一个 attempt 的高层理解压缩后交给下一个 attempt；
6. 让读取到的负经验足够强地改变 agent 的行为。

换句话说：

**当前系统已经具备粗粒度失败记忆，但还不具备“子块级策略学习 + 可执行经验条”能力。**

---

## 10. 下一阶段最值得优先做的升级

如果按收益排序，我认为最值得优先做的是：

### 10.1 `trial_overview + subblock_analysis`

在正式提经验之前，先形成对整条 trial 的整体理解，并切出子块。

### 10.2 `subproblem_type + strategy_label`

给每个子块明确类型，给其中的关键路径明确标签。

### 10.3 `action-grounded experience`

让每条经验都尽量绑定具体 action / action 链，而不是只保留抽象建议。

### 10.4 `attempt_summary_v1`

把上一轮的高密度信息压缩给下一轮，而不是只传碎片经验。

### 10.5 `prefer_actions / avoid_actions`

让经验真正带有可执行性。后续读取经验时，不只是告诉 agent：
- 发生过什么，

而是告诉 agent：
- 现在优先做什么；
- 不要再做什么。

---

## 11. 结论

当前经验系统已经具备：
- 经验提取；
- 经验聚合；
- 跨 attempt 继承；
- 官方反馈回流；
- 粗粒度负经验注入。

但它还不具备：
- 子块级失败路径归纳；
- plan 层与 execution 层分离分析；
- 面向 action 的可执行经验条；
- 基于整体 trial 理解的 attempt 压缩摘要。

因此，下一阶段最重要的不是继续重复做更多实验，而是：

1. 让经验提取前先有整体理解；
2. 让子块分析先于具体经验提取；
3. 让每条经验都尽量指向具体 action 或 action 链；
4. 让经验表达里包含 prefer/avoid 这类可执行约束；
5. 让上一轮 attempt 的整体认识以压缩摘要的方式进入下一轮。

只有这样，AgentMem 才有可能从“记住失败”升级为“避免重复失败，并更快走向有效路径”。
