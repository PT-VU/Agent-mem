## 缺陷提示

我们应该改变当前的测试流程。更合理的流程应该是：先跑单个 instance，再立刻跑官方 resolved 评估，然后带着评估结果做经验提取。

此前的所有测试里，经验提取基本都是在没有得到外界反馈的情况下完成的。系统看到的只是 trial 内部的局部成功、局部验证和 `submitted` 状态，看不到官方评测中的 `resolved / unresolved` 结果。因此，当前提取出来的很多经验本质上是“自我感觉成功后的总结”，而不是“经过外部验收后的真实经验”。这会直接导致经验质量偏高估、负经验缺失、错误 patch 路线无法被及时沉淀为失败经验，从而影响后续注入效果。

### 1.2 通过阅读 trial，可以明确看到的共同问题

#### 问题 A：模型把大量时间花在“计划”上，而不是尽快建立与题目等价的验证闭环

四个已提交实例的 trace 都显示出非常重的 planning 主导：

- `astropy__astropy-12318` 的 `critical_signal` 也是 planning/system stuck loop
- `astropy__astropy-12825` 的 `critical_signal.error_type = repetitive_planning`

这不是偶发现象，而是这次 smoke 的主失败模式。

更重要的是：这些 planning loop 最后仍然产出了 patch，并被系统视为 `task_success`，但官方评测全部 unresolved。说明现在的 agent 很擅长“在长 planning 后提交一个自认为合理的 patch”，但不擅长“尽快用正确的 target validation 证明 patch 真解决了题目”。

#### 问题 B：模型做了不少“看起来合理”的局部验证，但这些验证与 benchmark 的真实验收并不等价

从 trace 可以看到，模型在多个实例里都偏好：

- 自建 `reproduce_*.py`
- 自建 `test_*.py`
- 手动跑少量自定义检查
- 再提交 patch

这类操作有价值，但当前最大的缺点是：

- 它验证的是模型自己构造的假设
- 不是题目真实失败条件
- 不是仓库已有的最相关回归测试
- 也没有把“自定义验证是否覆盖题目核心约束”作为门禁

结果就是：trial 内部看起来“成功”，官方 resolved 却是 0。

#### 问题 C：patch 形态暴露出“问题理解偏移”和“改动范围失控”

下面是基于 patch 内容的工程推断，不是官方失败断言，但足够支持经验总结。

##### `astropy__astropy-11693`

patch 是：

```diff
-        pixel = self.all_world2pix(*world_arrays, 0)
+        pixel = self.all_world2pix(*world_arrays, 0, quiet=True)
```

这个改动的风险非常高：

- 它更像“压错误/静默失败”，不是确认算法语义修复
- 如果真实问题是收敛逻辑或异常传播策略错误，`quiet=True` 可能只是在掩盖问题
- 当前系统没有提取出“不要用 silence/suppression 代替真实修复”这类负经验

##### `astropy__astropy-12057`

patch 在 `nduncertainty.py` 里引入了一整套 `to()`、`_get_converter()`、`convert_uncertainty()` 框架，改动范围非常大，而且直接扩展了 public API。

这里暴露出的错误模式是：

- 题目如果是一个局部转换或行为 bug，模型却选择了“设计一套新框架”
- 这是典型的过度解决（over-solve）
- 当前系统没有提取出“局部 bug 不要优先扩 API / 不要大面积引入新抽象”这类经验

##### `astropy__astropy-12318`

patch 修改 `BlackBody` 中 scale 的单位处理逻辑，引入多分支 dimensionless 路径。

它的问题是：

- 这是一个多分支语义修改
- 缺少与原问题 failing assertion 的强绑定
- 这类 patch 很容易在局部例子上合理、在真实测试矩阵上错误

当前系统没有提取出“如果没有题目对应断言，不要改多个语义分支”这类经验。

##### `astropy__astropy-12825`

patch 新增：

```python
except AttributeError:
    warnings.warn(...)
    continue
```

这是典型的“吞异常解决法”：

- 它可能让程序继续跑
- 但没有证明异常本身是允许被吞掉的
- 很可能只是把错误转成 warning，规避症状，而不是修复根因

当前系统没有提取出“不要把未知 AttributeError 直接吞掉；先确认 capability check 或类型边界”这类经验。

### 1.3 有哪些经验其实应该被提取出来，但当前没有被提取

这是本次最关键的部分。

#### 应提取但未提取经验 1：错误 patch 类型经验

当前系统提取到了大量“planning loop”经验，但没有提取下面这些更直接影响 resolved 的经验：

- **不要用 `quiet=True` / broad warning / broad exception swallowing 来掩盖真实 bug**
- **局部 bug 优先做最小改动，不要一上来引入新 API 或整套转换框架**
- **如果验证依赖自建脚本，而不是仓库已有 target tests，这类 patch 风险极高**
- **如果 patch 改了多个语义分支，但没有对应失败断言，说明问题定位还不够准**

为什么没有提取：

- 当前提取主入口是 `run_done`
- `run_done` 时这 4 个实例被判为 `success=True`，因为 `exit_status=submitted has_submission=True`
- 因此 `failure_card_v2.generated = false`
- 提取系统主要围绕“高 cost 成功但存在 planning 问题”做抽象，而不是“提交了错误 patch”
- 官方 unresolved 结果没有回流到记忆系统，所以“错误 patch 经验”根本没有被写出来

这不是模型没看见问题，而是架构上根本没有把“提交但 unresolved”当作失败信号。

#### 应提取但未提取经验 2：负策略经验（negative strategy memory）

这次几个实例都出现了相似模式：

- 长时间 planning
- 自建复现脚本
- 自建验证脚本
- patch 提交
- 官方 unresolved

这本质上已经构成了一类可复用负经验：

- **当某个子任务签名下，策略 S 走到“自建验证通过 + 官方 unresolved”时，应记录该策略不可靠**

但当前系统没有这样的经验对象。

现有对象主要是：

- `abstract_experience`
- `repair_pattern_v2`
- `failure_card_v2`
- `preventive_rule_v2`

这里面最接近负经验的是 `failure_avoidance`，但它是从 critical signal 的模板化字段派生出来的，不是从“实际走过的错误策略链”归纳出来的。因此它太泛，不足以表达：

- “方法 1 在 task/subtask X 上已经试过且失败”
- “后续不要再走相同思路”

#### 应提取但未提取经验 3：验证缺口经验

当前系统抽到了一个 `validation_guard`，这是进步。但它还不够具体。

真正应该提取的是：

- **先跑最接近题目的原仓库测试，再写 patch**
- **如果只能自建脚本，必须证明这个脚本覆盖题目里的核心失败条件**
- **没有 target regression 的 patch，不应进入提交态**

为什么没提取：

- LLM 提取 prompt 里没有原始 issue 文本、没有 diff 语义、没有目标测试信息
- 它只能看到压缩后的 trajectory 摘要，因此能看出“缺验证”，但看不出“缺的是哪种验证、为什么这种验证缺口会导致 unresolved”

### 1.4 本次都尝试了哪些方法，但没有效果

从 trail 里可以看到几类反复出现、但没有带来 resolved 的方法：

1. 反复浏览代码 + 反复生成计划
2. 自建复现脚本验证局部假设
3. 自建综合测试脚本验证自己修改后的局部行为
4. 通过 broad workaround 让程序不报错
5. 通过扩大 patch 范围来“覆盖更多可能情况”

这些方法为什么没效果：

- 它们验证的是“模型当前猜测是否自洽”，不是“题目是否真正被解决”
- 它们没有优先绑定 benchmark 的真实断言或回归路径
- 一旦第一次 patch 方向错了，后续仍然围绕错误假设做增量补丁
- 记忆系统注入的大多也是“planning/validation 抽象建议”，没有足够强的 domain-specific repair guidance 去打断错误路线

### 1.5 为什么这几次都没能解决问题

我认为原因不是单一的，而是三层叠加：

#### 第 1 层：agent 本体的问题理解和验证策略有偏差

- 过早进入 patch 阶段
- 没有先拿到最贴题的 regression 验证
- 经常用自建脚本代替题目真实失败条件
- 对 patch 风险的判断不足，容易做 suppression patch 或 over-engineered patch

#### 第 2 层：记忆系统注入的内容偏“元建议”，不够“任务约束化”

本次注入的 family 主要是：

- `repair_pattern:*`
- `direct_success_flow__missing_validation__...`
- `belief_tip:workflow:generate plan for task -> ...`
- `workflow_step:consider: generate plan for task...`
- `validation_gap__missing_validation__add_local_validation`
- `planning_loop__missing_validation__bound_planning_iterations`

这里真正可能直接帮到题目修复的，主要是 repair/validation 两类；但很多注入仍然是 workflow/belief/planning 风格的高层建议。

这些建议对“减少无意义 planning”有帮助，但对“当前 patch 在 astropy 的哪个函数语义上错了”帮助很弱。

#### 第 3 层：反馈闭环本身是失真的

事件日志里很多 `memory_intervention_feedback` 被记为 `effective=true`，原因只是：

- hint 注入后，后面 5 个 action 都是 `action_success`

但这并不意味着：

- patch 方向正确
- 验证更贴题
- 最终任务 resolved

事实恰恰相反：

- 本次 4 个 submitted 全部 unresolved
- 但很多 hint 在局部反馈里被记成 effective

这说明当前 feedback 语义过于局部，容易把“后续动作执行成功”误判成“记忆帮助了解题”。

### 1.6 当前模型做错了哪些部分，应该如何做

当前模型最明显做错了 5 件事：

1. **把 planning 当成主要工作，而不是前置环节**
   - 应该在很早阶段就强制形成“问题假设 -> target validation -> patch -> target validation”的闭环

2. **把自建验证当成题目验证**
   - 应优先跑仓库已有最贴题测试或最小 regression
   - 自建脚本只能是辅助，不应替代 target validation

3. **对 patch 风险没有内置约束**
   - 应在提交前检查：是否扩大 public API、是否吞异常、是否只是 suppress error、是否改了多个语义分支

4. **没有显式记录“这条路已经试过且没用”**
   - 应该有 negative strategy memory
   - 同类 task/subtask 下重复策略要被抑制

5. **没有把 benchmark 真正失败回流成记忆**
   - 应该把 official unresolved 或本地 target regression fail 写回 failure memory
   - 否则系统只会积累“自以为成功”的经验

## 2. 结合当前经验框架，对系统结构的判断

### 2.1 我们当前是不是只有 micro 的局部经验，没有对过去试错的总结

结论：**基本是的，当前系统主要还是 micro 经验，缺少真正的“试错总结经验”。**

更准确地说：

- 不是完全没有 abstract layer
- 但当前 abstract layer 主要是从单次 attempt 的 `critical_signal` 提炼出来的“错误类型 -> 修正建议”
- 它还不是“策略层总结”

当前系统已经有：

- `abstract_experience`
- `repair_pattern_v2`
- `validation_guard`
- belief tip / workflow step

但它缺少：

- `failed_strategy_memory`
- `subtask_strategy_blacklist`
- `patch_risk_pattern`
- `validation_gap_memory` 的细粒度版本
- `submitted_but_unresolved` 的专门记忆对象

所以现在系统更像：

- “我看到了一个局部错误信号，于是给出一个局部建议”

而不是：

- “对于 task/subtask A，方法 1 已经在过去失败过，所以本次应该禁用或显著降权”

### 2.2 当前提取、注入、写入、反馈架构里还有哪些明显可提升点

#### 提升点 1：`run_done=submitted` 不应该自动视为 success

这是本次最关键的结构缺陷。

当前行为是：

- 只要 `has_submission=True`
- `failure_card_v2` 就不生成，理由是 `task_success`

这会直接导致：

- 错误 patch 不被视为失败
- 负经验不写入
- 后续 retrieval 看不到“这个策略在真实评测里失败”

应该改成两阶段：

- `submission_success`
- `evaluation_success`

只有第二阶段成功，才能算真正的 success memory。

#### 提升点 2：把 official eval / target test 结果回流进 memory

当前系统只看 trial 内部发生的事，不看后验评测。这样会丢掉最有价值的信号：

- patch 是否真的解决了 benchmark 问题

应该在评测后补一条异步回流链路：

- `submitted + unresolved` -> 生成 failure card / negative strategy memory / patch risk memory
- `submitted + resolved` -> 提升对应经验权重

#### 提升点 3：当前反馈机制过于局部，容易误报 effective

现在的 `memory_intervention_feedback` 只看注入后的一小段动作是否成功。

这会把：

- “命令跑通了”
- “文件打开了”
- “脚本执行了”

误判成记忆有效。

应该改成至少三级反馈：

- 短期：动作是否顺利执行
- 中期：是否发生 strategy shift / 是否引入更贴题验证
- 长期：是否 resolved / 是否至少让 target regression 从 fail 变 pass

#### 提升点 4：当前 retrieval 仍然被 planning/workflow family 污染

这次 `selected_family_ids` 反复出现：

- `belief_tip:workflow:generate plan for task -> ...`
- `workflow_step:consider: generate plan for task...`

它们对减少 resolved error 没有足够直接的帮助，却持续占注入预算。

应该进一步降权或只在 cold-start 时注入一次。

#### 提升点 5：当前 traceability 还有一个细节问题

虽然这次 `read_ids` 实际已经落盘了（`experience_rw_map.jsonl` 中 380 条里 280 条非空），但很多对象里 `source_instance_id` 仍然是 `main`，而不是真实 benchmark instance id。

这会让后续做跨 instance 统计、失败归因、经验 lineage 追踪变得麻烦。

### 2.3 对“先尽可能多地抽取经验，然后在后续过程中逐个排除”的评价

这个建议**方向是对的，但不能直接落成“全写入 + 全注入”**。

我赞成的版本是：

#### 方案：两层记忆池

1. **候选经验池（raw candidate reservoir）**
   - 尽量多抽
   - 可以包含低置信度、负策略、验证缺口、patch 风险、loop 提示等
   - 不直接进入主检索池

2. **正式经验池（promoted canonical memory）**
   - 只有通过质量门和后验反馈的经验才升级进来
   - 进入常规检索和注入

如果直接把“尽量多抽取”的结果全部写进当前主检索池，会有 3 个风险：

- 检索噪声爆炸
- planning/workflow 类泛经验占满预算
- 同一个问题被大量近义建议淹没

所以我支持你的建议，但要改成：

- **尽量多抽取到候选层，再逐步晋升/淘汰，而不是尽量多抽取后直接参与注入。**

这其实也是当前系统最缺的一层：

- 候选经验层
- 负策略层
- 评测后回流晋升层

### 3.2 当前 prompt 的核心问题

#### 问题 1：prompt 没有看到“题目本身”

LLM 没看到：

- 原始 issue / problem statement
- 目标文件与题意约束
- patch diff 语义
- 官方评测结果
- 真实失败断言

它只能看到压缩后的行动轨迹。

因此它很容易总结出：

- planning 太多
- 验证不够
- 系统卡住

但很难总结出：

- quiet=True 是错误修复方向
- broad exception swallowing 风险高
- 这个 patch 虽然内部验证通过，但与题目断言不等价

#### 问题 2：trajectory 压缩过度

当前 LLM 看到的每一步只有：

- action_type
- action_family
- outcome
- intent_text 截断 240 字
- failure_type

它看不到很多真正关键的信息：

- 实际 diff 改了什么
- 具体跑了什么测试命令
- stdout/stderr 的关键信号
- patch 是否扩大 public API
- touched files 的精细语义

#### 问题 3：只看前 80 步

当高价值错误出现在第 80 步以后，LLM assessment 会漏掉它。

这次几个实例步数在 77 到 114 之间，已经逼近或超过这个阈值。说明当前 prompt 设计对长轨迹不稳。

#### 问题 4：它输出的是“critical signal”，不是“策略总结”

即使 LLM 分析得对，后续也会被压缩成：

- `critical_signal`
- `abstract_experience`
- `repair_pattern_v2`

这一步会丢失很多上下文。尤其是：

- 哪种 patch 风格错了
- 哪种验证方法不可靠
- 哪种思路在特定子任务下已经失败

### 3.3 LLM 生成的信息是如何被处理后变成经验的

当前链路如下：

1. `ExtractionOrchestrator.process_attempt()` 在 `run_done` 被触发。
2. `LLMExperienceExtractor.analyze_steps()` 先做 step assessment。
3. `detect_critical_signals()` 合并 rule-based rows 与 LLM rows，选出 `critical_signal`。
4. 再调用 `_call_llm_for_critical()`，把选中的 signal 精炼成：
   - `root_cause`
   - `correction_guidance`
   - `confidence`
5. `ExtractionOrchestrator._map_to_existing_templates()` 把这份 critical signal 映射成 3 类现有对象：
   - `abstract_experience`
   - `failure_card_patch`
   - `repair_pattern_v2`
6. `_rebalance_abstract_experiences()` 做 bucket 限流：
   - `planning_rule: 1`
   - `execution_tip: 1`
   - `failure_recovery: 2`
   - `validation_guard: 1`
7. `_dedup_repair_patterns()` 以 `(error_type, stage, module, fix_action_template)` 去重。
8. `_apply_quality_gate()` 只检查两件事：
   - `evidence_refs` 非空
   - `confidence >= min_item_confidence`
9. 通过后，由 adapter 写入：
   - `abstract_experiences.json`
   - `repair_patterns_v2.json`
   - `experience_rw_map.jsonl`

### 3.4 这一处理链的最大问题

#### 问题 A：LLM 输出被过早压成“单个 critical signal”

一个 attempt 里可能同时包含：

- 问题理解错误
- 验证方式错误
- patch 风格错误
- 提交策略错误

但现在最终只围绕 1~N 个 `critical_signal` 来建模，且主信号通常是 planning/system 级。这会导致：

- domain-specific 失败模式被压扁
- patch-level 失败被 planning-level 元错误覆盖

#### 问题 B：quality gate 太弱，不判断“是否泛化过头”

现在 quality gate 只看：

- 有没有 evidence
- confidence 高不高

它不看：

- guidance 是否过泛
- 是否与题目约束绑定
- 是否只是 workflow 建议
- 是否是已经重复出现的 generic planning hint

#### 问题 C：没有把 LLM 输出转化成“负策略记忆”

现在 LLM 输出主要变成：

- abstract guidance
- repair patterns

没有变成：

- `do_not_repeat_strategy`
- `failed_validation_pattern`
- `patch_risk_pattern`
- `submitted_but_unresolved`

### 3.5 prompt 可以怎么改进

我建议至少做 4 个方向的增强：

1. **把 issue / task summary / changed files / patch diff / key test signals 一并给 LLM**
2. **不只让 LLM 找 error，还让它找“错误策略”和“缺失验证”**
3. **把输出 schema 扩成两层**
   - `critical_signal`
   - `strategy_observations` / `validation_gaps` / `patch_risks`
4. **长轨迹不要硬截前 80 步，而是做阶段摘要后再交给 LLM**

## 4. 顺着上述问题继续思考，哪些升级能切实提升 resolved rate

下面这些方向，我认为是“对 resolved rate 真有帮助”的，而不是只让系统看起来更复杂。

### 4.1 把“submitted but unresolved”正式纳入经验闭环

这是优先级最高的一条。

应增加异步回流链路：

- official eval unresolved
- 本地 target regression fail
- patch apply fail

都应该生成正式负记忆，例如：

- `submitted_unresolved_failure_card`
- `failed_strategy_memory`
- `validation_gap_memory`
- `patch_risk_memory`

没有这条链路，系统会持续积累“自认为成功”的经验，越跑越偏。

### 4.2 新增“策略失败记忆”对象，而不是只存 repair pattern

建议新增一类对象，例如：

- `failed_strategy_v1`

字段至少包括：

- `task_signature`
- `subtask_signature`
- `strategy_family`
- `why_failed`
- `evidence_refs`
- `negative_confidence`
- `block_until_new_evidence`

这样后续相似任务就可以做：

- 同 subtask 下，如果策略 family 命中过去失败经验，则降权或禁止

### 4.3 在注入层引入“负经验优先级”

现在注入主要是“怎么做”。

后续应增加“不要怎么做”：

- 不要用 broad exception swallowing
- 不要只靠 quiet=True / warning continue 解决
- 不要在没有 target test 的情况下提交
- 不要在局部 bug 上扩 public API

这种负经验往往比正经验更能立刻减少错误尝试。

### 4.4 把注入门从“动作成功”改成“验证质量提升”

当前 feedback 之所以失真，是因为判定太浅。

更合理的判定应该看：

- 注入后是否更早跑了 target validation
- 注入后是否减少了 planning 连续重复
- 注入后是否减少了 broad patch / broad catch
- 注入后是否产生了更接近题目约束的验证命令
- 最终是否 resolved

### 4.5 强制建立“最小验证闭环”作为提交前门禁

对当前 agent 来说，真正缺的不是更多 planning，而是更早进入正确闭环。

提交前应强制满足至少一条：

- 跑过最贴题仓库测试
- 跑过与 issue 直接等价的最小 regression
- 如果两者都没有，禁止提交或显著降置信提交

这条如果落地，resolved rate 很可能比继续增加 planning 提示更有用。

### 4.6 提升检索排序：强压 workflow/belief family，提升 task-grounded family

这次注入里仍有较多：

- `belief_tip:*`
- `workflow_step:*`

这些可以保留，但不该占高价值注入预算。建议：

- workflow/belief 只在冷启动或第一次注入时允许出现
- 一旦已有 repair/validation/task-grounded hints，可直接压制 workflow/belief

### 4.7 把 patch diff 也纳入提取对象

当前提取只基于 trajectory 和 critical signal。建议额外加入：

- patch 类型分类（minimal fix / suppressive fix / broad API extension / exception swallowing / semantic branch expansion）

这会让系统能真正学到：

- “哪类 patch 风格在 astropy 这类仓库里经常是错的”

### 4.8 为长 planning 增加真正的执行中断机制，而不是只存经验

当前系统已经能识别 planning loop，但主要处理方式仍然是：

- 抽经验
- 注提示

这不够。还需要 agent runtime 级的 policy：

- 连续 N 次 planning 且 touched files / validation plan 没变化 -> 强制切换到执行或验证
- 否则直接中断当前策略并要求重定向

这个对降低 token/time 浪费很有效，也更符合 AgentMem 的目标。

## 5. 本次阶段6 smoke 的总判断

### 5.1 这次系统做得好的地方

1. 已经不是完全没有提取、没有注入、没有落盘的阶段了
2. `read_ids` 已经真实记录了大部分读取关系
3. `write_ids` 已经记录了 4 次 `run_done` 写入
4. family 化、去重、聚合是实打实在工作的
5. 能稳定把 planning loop / validation gap 抽出来
6. 能在事件流中追踪注入与反馈

### 5.2 这次系统最关键的失败点

1. 把 `submitted` 错当作 `success`
2. 没有把 `official unresolved` 写回记忆
3. 提取主轴仍偏 planning 元问题，而不是 patch/validation 失败
4. 没有负策略记忆
5. 注入反馈局部化，导致误判 effective
6. prompt 看不到题目、diff、目标测试，因此抽不到真正影响 resolved 的经验

### 5.3 一句话结论

当前经验系统已经具备“记录和注入局部经验”的能力，但还没有形成“基于真实试错结果纠正后续策略”的能力。

换句话说：

- 它已经能告诉 agent：你在 planning 上浪费太多了。
- 但它还不能稳定告诉 agent：你这条修复路线本身是错的，不要再走了；你必须换验证方式、换 patch 风格、换子任务策略。

而后者，才是真正决定 resolved rate 的东西。
