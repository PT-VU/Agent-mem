# 阶段6 AgentMem 核心功能测试计划

## 1. 目标

本测试计划的目标不是只回答“最后有没有 solved”，而是严格区分并验证 AgentMem 的四类核心能力：

1. 经验提取是否发生，且是否提取出有用而不是空泛的经验。
2. 经验存储是否一致，是否能被后续 attempt 稳定读取。
3. 经验消费是否真正改变后续行为，而不是只在日志里留下 `read_ids`。
4. 实验环境是否稳定，能否支撑串行/并行实验，而不会被 Docker/runtime 问题污染结果。

## 2. 测试原则

### 2.1 双轨测试

后续测试必须分成两条线，不能混在一起：

1. 稳定性测试线  
目的是验证 runner、Docker、resume、cleanup、official eval feedback 是否稳定。  
这条线可以限时，避免无限消耗资源。

2. 能力验证测试线  
目的是验证 AgentMem 是否能通过跨 attempt 经验积累改善解题轨迹，甚至最终解决问题。  
这条线不应该用严格总时限把实验裁成一堆 `incomplete`，否则无法观察“多轮学习”是否真的有提升。

### 2.2 结果口径

所有实验结果必须分开记录四个层次：

1. `process_status`  
进程是否正常结束，是否有环境层失败。

2. `submission_status`  
是否形成 patch / pred / submitted。

3. `official_eval_status`  
resolved / unresolved / incomplete / infra_failure。

4. `memory_effect_status`  
经验是否被提取、存储、读取、消费，是否导致后续行为变化。

不能再把 `submitted` 当成 solved，也不能把 `read_ids` 的出现当成“记忆已经有效”。

## 3. 核心测试对象

### 3.1 提取层

必须验证：

1. `abstract_experience`
2. `attempt_summary_v1`
3. `official_eval_feedback` 写回
4. `experience_rw_map.jsonl`

### 3.2 消费层

必须验证：

1. `attempt_summary_v1` 是否被后续 attempt 读取。
2. `avoid_actions` 是否进入 runtime guard。
3. `subproblem_type / strategy_label` 是否参与 planning retrieval。
4. 读取经验后，后续轨迹是否出现可观测变化。

### 3.3 环境层

必须验证：

1. Docker preflight
2. image resolve
3. runtime 启动
4. cleanup 是否真删除容器
5. resume 前经验完整性校验

### 4.2 集成测试

目标：验证主链能串起来，不在 very-early 阶段退出。

必须覆盖：

1. 单实例 `with_mem` closed-loop smoke
2. `official_eval -> apply_feedback -> memory_behavior`
3. `resume-check` 是否拒绝不完整经验
4. cleanup 是否真删掉残留容器

验收标准：

1. 能完成 `run -> eval -> feedback -> cleanup`
2. 没有残留目标容器
3. summary 和 feedback 文件生成

### 4.3 稳定性 smoke 线

目标：验证环境层稳定，不要让 Docker/runner 污染后续结果。

配置建议：

1. 单实例
2. 单 worker
3. `INSTANCE_TOTAL_EXEC_TIMEOUT_SEC=1200`
4. `MAX_ACTIVE_RUN_BATCHES=1`
5. `RUNTIME_PREWARM=0`

检查项：

1. 是否越过 `preflight / resolve_image / launch_sweagent`
2. 是否出现 `runtime did not start within timeout`
3. 是否出现残留容器
4. 是否完成 feedback 后处理

### 4.4 能力验证主线

目标：验证跨 attempt 的经验积累能否改善轨迹，甚至最终解决问题。

配置建议：

1. 同一 instance
2. `repeat5`
3. 共享记忆
4. 每次 attempt 后做 `official_eval + feedback`
5. 不设总时限，或只保留非常宽松的超长 watchdog

关键验收指标：

1. `attempt_summary_v1` 是否在 attempt2+ 被读取
2. `avoid_actions` 是否导致 runtime guard block
3. `plan_generated` 密度是否下降
4. ad-hoc 脚本数量是否下降
5. 是否更快形成 patch / pred / submitted
6. official eval outcome 是否改善

## 5. 观测指标

### 5.1 必看指标

1. `summary_count`
2. `feedback_count`
3. `abstract_experience_count`
4. `repair_pattern_count`
5. `failure_card_count`
6. `read_ids` / `write_ids`
7. `plan_generated` 总数
8. ad-hoc 脚本相关 action 次数
9. runtime guard block 次数
10. `submitted / resolved / incomplete`

### 5.2 行为改变量指标

这些指标比 solved rate 更适合早期判断 AgentMem 是否在工作：

1. `time_to_first_patch`
2. `time_to_first_validation`
3. `plan_loop_density`
4. `subpath_reuse_rate`
5. `avoid_action_trigger_rate`

## 6. 通过标准

### 6.1 稳定性通过标准

满足以下全部条件，才算环境层稳定：

1. 单实例 smoke 连续 3 次不出现 runtime 启动失败
2. 实验结束后无残留目标容器
3. early failure 时能完整留下诊断证据
4. `resume-check` 能正确拒绝不完整经验，正确放行完整经验

### 6.2 能力通过标准

满足以下至少 3 条，才可以认为 AgentMem 核心能力出现了真实进展：

1. attempt2+ 能稳定读取 `attempt_summary_v1`
2. `avoid_actions` 至少触发一次 runtime guard block
3. 后续 attempt 的 `plan_generated` 总数明显下降
4. 后续 attempt 的 ad-hoc 脚本数下降
5. 后续 attempt 更快形成 patch / pred
6. official eval outcome 出现正向改善
