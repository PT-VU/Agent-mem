下面给你一份可直接发给工程组的 **工程 PRD 版**。
它已经融合了你新增的 29 个实例分析结果，目标不是“继续扩 memory”，而是**解决当前已经暴露出来的三个真实工程瓶颈：经验同质化、注入重复化、评估污染**。这些判断直接来自你现有代码闭环和前 29 个实例的运行证据：系统已经能在线记录、检索、注入并在 `run_done` 后抽取经验，但成功样本中 memory 明显被 planning-loop 类经验垄断，而 16 个 incomplete 主要是主链路 LLM 余额与 Docker 故障，不能算 memory 失效。 
从 benchmark 角度看，SWE-bench 衡量的是 agent 是否能基于 issue 和代码仓库生成通过测试的 patch，所以 memory 最应提升的是**定位、验证、恢复**三类行为，而不是反复强化宏观 planning 建议。([SWE-bench][1])
从学术角度看，Reflexion、ExpeL 和 memory survey 的共同启示也是：training-free 的经验学习是可行的，但效果主要取决于**经验表示、经验选择和使用时机**，而不是单纯“写进更多反思文本”。([arXiv][2])

# AgentMem 升级工程 PRD（基于当前代码与前 29 个实例复盘）

## 1. 文档目标

* 为工程组提供一版可直接落地的 AgentMem 升级方案。
* 本轮升级只解决已经被证据确认的问题，不做大规模架构重写。
* 目标是在 **不明显增加系统复杂度** 的前提下，提高：

  * 有效 memory 的信息密度
  * 注入的非重复性与实际干预价值
  * SWE-bench 上可归因于 memory 的真实收益
  * 重复尝试场景下的经验累积效果

---

## 2. 背景与问题定义

### 2.1 当前系统状态

* 当前 AgentMem 已经具备完整在线闭环：

  * Hook 捕获 `plan_generated / action_error / run_done`
  * Adapter 写入 action 与图结构
  * MemoryAgent 做检索
  * Hook 在 `on_model_query` 时注入 hints
  * `run_done` 后做 RCA、抽象经验提取、failure card、repair pattern 写库。

### 2.2 前 29 个实例复盘后的关键结论

* 成功实例中 memory 确实工作了，但**学到的经验高度集中在 planning loop / inefficient planning / lack of progression**。
* 最后一次被选中的注入内容高度重复，常见为：

  * state machine / progress tracker
  * plan termination / loop limit
  * Generate plan -> Generate plan -> Generate plan 的 workflow belief。
* 前 29 个里有 16 个 incomplete，但其共同特征是：

  * `tool_a_calls=0`
  * `DeepSeekException: Insufficient Balance`
  * 个别叠加 Docker 故障
    这类 case 没有形成真实 action 序列，因此不能用来评价 memory 本身。

### 2.3 当前最核心的问题

* 经验提取已经能跑，但**经验池正在同质化**。
* 检索已经能命中，但**注入结果缺少增量信息**。
* 评估已经能出数字，但**infra failure 与 memory failure 混在一起**。

---

## 3. 产品目标

### 3.1 本轮必须达成的目标

* 降低 planning 类经验的重复写入与重复注入
* 提高 recovery / validation 类经验在记忆池中的占比
* 让每次注入都尽量提供“新的、可执行的下一步”
* 把 infra failure 从 memory 评估中剥离

### 3.2 本轮明确不做

* 不改模型权重
* 不引入复杂 RL 或长链监督
* 不重写 `bridge_hook -> adapter -> orchestrator -> graph_store` 主链路
* 不引入独立向量数据库作为必要前提

---

## 4. 本轮范围

### 4.1 In Scope

* 经验对象规范化与去同质化
* 注入门控与去重
* 新增 validation_guard 经验类型
* action_error 侧轻量 micro-extraction
* infra failure 分类出库
* 评估口径修正
* 指标与日志补齐

### 4.2 Out of Scope

* PDDL3 硬约束编译
* 复杂自动晋升策略
* 多 agent memory sharing
* 大规模 UI 或可视化平台

---

## 5. 成功标准

### 5.1 系统层成功标准

* planning 类经验新增速度明显下降
* recovery / validation 类经验占比提升
* 相同 family 的重复注入率显著下降
* Top 注入结果中重复语义建议显著减少

### 5.2 评估层成功标准

* 实验报告中必须单列：

  * overall solved rate
  * infra-excluded solved rate
  * memory-eligible solved rate
* repeated attempts 实验中，memory 组曲线相较 baseline 随尝试次数上升更明显

---

## 6. 现状问题拆解

### 6.1 问题一：经验提取同质化

**现象**
成功样本中大部分提取结果都在重复表达“planning loop / excessive planning / lack of transition / missing verification”。

**后果**

* `abstract_experiences.json` 快速堆积近义对象
* retrieval 命中很多语义重复经验
* 注入时浪费预算
* 难以积累更贴近 patch success 的 execution / recovery knowledge

---

### 6.2 问题二：注入内容重复，增量不足

**现象**
多个实例最后一次 Tool A 返回的注入建议高度相似，常是同一簇 planning-loop 建议加一个 workflow belief。

**后果**

* memory 实际上没有持续带来新信息
* 模型收到的提示更像重复提醒，而不是具体纠偏
* 注入频率高，但有效干预率不一定高

---

### 6.3 问题三：memory 评估被基础设施故障污染

**现象**
16 个 incomplete 主要由余额不足和 Docker 异常导致，且没有真实 actions。

**后果**

* solved rate 被错误拉低
* 无法判断 memory 是否真的没帮助
* fallback failure card 混入常规记忆池会增加噪声

---

## 7. 方案总览

本轮升级分 6 个模块：

* M1：经验 canonicalization 与 family 合并
* M2：经验提取预算重排，压 planning、扶 recovery/validation
* M3：注入去重与 novelty/diversity 排序
* M4：新增 validation_guard 与 action_error micro-extraction
* M5：infra failure 独立出库，不参与常规 retrieval
* M6：评估口径与 memory 健康度指标补齐

---

## 8. 模块设计

## M1. 经验 canonicalization 与 family 合并

### 目标

将表面不同、语义相近的 planning-loop 经验归并为少量 canonical families，避免 memory 池继续膨胀。

### 设计

在 `ExtractionOrchestrator.process_attempt()` 写库前新增 canonicalization 层。

### 新增字段

每条经验新增：

* `normalized_pattern_type`
* `normalized_trigger_family`
* `normalized_advice_family`
* `family_id`
* `support_count`
* `variant_texts`
* `source_attempt_ids`
* `evidence_refs`

### 典型 family 初始枚举

* `planning_loop_no_transition`
* `planning_loop_no_termination`
* `plan_missing_validation_step`
* `patch_without_local_verification`
* `test_failure_missing_localization`
* `repeated_broad_search_without_narrowing`

### 规则

* 若新经验与现有经验在 family 级别高相似，则：

  * 不新增独立经验对象
  * 只更新已有经验的 support / evidence / variants
* 仅当触发条件或建议动作明确不同，才新建对象

### 代码改动点

* `processing/extraction_orchestrator.py`
* `processing/abstract_experience_builder.py`
* `storage/graph_store.py` 的 upsert 逻辑

### 验收

* planning family 的 unique object 数量增长显著减缓
* `abstract_experiences.json` 中同类 planning-loop 建议不再大规模重复出现

---

## M2. 经验提取预算重排

### 目标

减少 planning 经验过度生产，把 memory 容量优先留给真正可能提升 SWE-bench patch 成功率的 recovery / validation 经验。

### 新预算

每次 `run_done` 最多写入：

* `planning_rule`: 0–1 条
* `execution_tip`: 0–1 条
* `failure_recovery`: 0–2 条
* `validation_guard`: 0–1 条

### 规则

* 如果本轮已命中 `planning_loop_no_transition` family，则禁止再次写入同 family planning 经验
* 对 evidence 薄弱、文本泛化的 planning 建议直接丢弃
* 对包含明确 error signature、明确下一步动作、明确验证方式的 recovery/validation 候选优先保留

### 代码改动点

* `processing/extraction_orchestrator.py`

### 验收

* planning 类型经验占新增经验比例下降
* recovery/validation 类型经验占比上升

---

## M3. 注入去重与 novelty/diversity 排序

### 目标

让注入从“相关即可”变成“相关且有新信息”。

### 设计一：family 冷却窗口

对每条候选 hint 增加：

* `family_id`
* `last_injected_step`
* `last_injected_attempt`

#### 规则

* 同一 `family_id` 在最近 N 步内禁止重复注入
* 同一 attempt 内同一 family 最多注入 1 次
* 若当前候选与最近注入文本相似度高于阈值，则 suppress

#### 默认参数

* `no_repeat_within_steps = 8`
* `max_same_family_per_attempt = 1`

### 设计二：注入排序加入 novelty

新排序分数：

* `score = relevance + helpfulness + novelty - redundancy`

其中：

* `relevance`：与当前 query / trigger 的匹配度
* `helpfulness`：历史注入后有效率
* `novelty`：是否提供新的下一步动作 / 新的验证方式 / 新的 error family
* `redundancy`：是否与当前上下文或最近提示重复

### 设计三：type diversification

最终注入最多 2 条时：

* 不能两条都属于同一 family 且表达同一意图
* 优先组合：

  * 1 条原则型规则
  * 1 条可执行恢复动作

### 代码改动点

* `retrieval/memory_agent.py`
* `bridge_hook.py` 中 `_pending_memory_hints` 的筛选与排序逻辑

### 验收

* 相同 planning-loop 建议不再频繁连续出现
* 注入结果中 recovery/validation 提示占比提升
* 单次注入的信息增量更明显

---

## M4. 新增 validation_guard 与 action_error micro-extraction

### 目标

把当前被塞在 planning 经验里的“必须验证”知识，独立提升为高价值记忆类型；同时让失败恢复经验从纯 run_done 总结，前移到 action_error 时的在线轻量学习。

### M4.1 新增 `validation_guard`

#### 含义

表达“在 edit / patch / test 前后，应该先做什么局部验证”。

#### 对象字段

* `trigger`
* `next_action`
* `verification`
* `scope`
* `evidence`
* `confidence`

#### 典型例子

* 修改前先定位 failing tests 对应模块
* patch 后优先跑局部 test，而非全量重跑
* 对某类 assertion mismatch，先补最小复现实验

#### 代码改动点

* `core/` 新增或扩展 type 定义
* `processing/extraction_orchestrator.py` 映射模板
* `retrieval/memory_agent.py` 检索类型支持

---

### M4.2 新增 `action_error` 侧 micro-extraction

#### 触发时机

在 `handle_action_error()` 后，对高价值错误做即时轻量提取。

#### 首批支持的 error family

* `test_failure`
* `import/module error`
* `assertion mismatch`
* `timeout/stuck`

#### 输出形式

写入短期缓存 `ephemeral memory`：

* `trigger`
* `next_action`
* `verification`

#### 生命周期

* 先不立刻写正式长期库
* 若本轮后续该建议有效，则在 `run_done` 时升级为正式 `failure_recovery`

### 价值

* 让最关键的恢复知识从“事后总结”变为“在线学习”
* 更符合 Reflexion / ExpeL 中“基于试错信号快速积累经验”的有效模式。([arXiv][2])

### 代码改动点

* `agent_mem/integration/sweagent_adapter.py`
* `processing/llm_extractor.py` 或新增轻量 rule extractor
* `bridge_hook.py` 的 hint buffer

### 验收

* `action_error` 后出现更多具体、短小、可执行的恢复提示
* recovery hints 不再完全依赖 `run_done`

---

## M5. infra failure 独立出库

### 目标

把根本没有进入有效 agent 行为链的失败，与真正的 agent/memory 失败分开。

### 设计

将 fallback failure card 拆为两类：

* `infra_failure_card`
* `agent_failure_card`

### 归类规则

以下错误进入 `infra_failure_card`：

* `llm_insufficient_balance`
* `docker_build_255`
* `docker_daemon_unavailable`
* `docker_pull_sigbus`

### 行为规则

* `infra_failure_card` 不进入常规 retrieval
* 只用于：

  * 实验过滤
  * 基础设施监控
  * run 质量审计

### 代码改动点

* `processing/failure_card_builder.py`
* `storage/graph_store.py`
* `run_done` fallback 分支

### 验收

* retrieval 不再命中 `no_actions / unknown` 类 failure card
* 实验表中可直接给出 infra failure 占比

---

## M6. 评估与日志补齐

### 目标

让后续所有实验能真正回答：“memory 是否有效”。

### 6.1 实验口径三分法

每个实例必须先分类为：

* `infra_failure`
* `agent_execution_failure`
* `resolved_or_submitted`

主表必须同时报告：

* overall solved rate
* infra-excluded solved rate
* memory-eligible solved rate

### 6.2 memory 健康度指标

新增指标：

* `memory_family_entropy`
* `duplicate_family_ratio`
* `same_family_reinjection_rate`
* `avg_unique_hints_per_attempt`
* `planning_family_share`
* `recovery_family_share`
* `validation_family_share`
* `helpful_injection_rate by family`

### 6.3 必做消融

* `No Memory`
* `Planning Memory Only`
* `Recovery + Validation Only`
* `Full Memory`
* `Full Memory + Dedup Gate`

### 6.4 关键问题

要证明的不是“上下文更长所以更好”，而是：

* structured experience 比 raw trajectory 更有用
* gated injection 比无门控注入更有用
* 去同质化后的 memory 池比原始 memory 池更有用

### 代码改动点

* `bridge_hook.py` 日志补齐
* `experience_rw_map.jsonl` 扩展字段
* 实验汇总脚本

### 验收

* 实验报告能清楚区分 infra 与 memory
* 能画出 repeated attempts 下不同 memory family 的效果曲线

## 10. 系统流程变更

### 10.1 `plan_generated`

* 保留现有链路
* 但 planning 注入只在以下条件满足时开放：

  * 连续 3 个 planning family action
  * 最近 5 步没有新增 evidence
  * 最近 2 次 plan 文本高度相似
  * 当前 plan 缺少 validation/test step

### 10.2 `action_error`

* 在现有 repair retrieval 之后增加 micro-extraction
* 优先写入 ephemeral recovery memory
* 下一次 `on_model_query` 可优先注入该短期恢复建议

### 10.3 `run_done`

* 先做 infra / agent failure 分流
* 再做 canonicalization
* 再按新预算产出长期经验
* 最后更新 family 级 support 与 helpfulness

## 12. 风险与规避

### 风险一：过度去重导致经验过粗

* 规避：只有 family 与建议动作同时高度相似时才合并

### 风险二：planning 注入减少后短期 recall 降低

* 规避：只减少低增量重复 planning hint，不移除高价值 planning 规则

### 风险三：micro-extraction 产生短期噪声

* 规避：先写 ephemeral memory，只有有效才 promote

### 风险四：实验脚本未同步，导致新旧口径混杂

* 规避：本轮 PR 必须包含日志 schema 和汇总脚本更新

## 14. 给工程负责人的一句话总结

* 现在不是 memory 不够多，而是 **planning memory 太多、太像、太重复**。
* 这一轮要做的事情很简单：**把重复 planning 经验压缩成少量 canonical rules，把真正能改变 SWE-bench 解题轨迹的 recovery/validation 经验扶起来，再把 infra failure 从评估里清出去。**

这份 PRD 的判断基础，一方面来自你当前 AgentMem 的已实现结构、事件链路、经验对象和注入机制。
另一方面，前 29 个实例已经明确证明：当前成功样本里的 memory 主要学到的是 planning-loop 避免策略，而非更细粒度的恢复经验；同时 16 个 incomplete 主要是主链路不可用，并不构成对 memory 机制本身的反证。
再结合 SWE-bench 的任务属性与 Reflexion、ExpeL、memory survey 的共识，这一轮升级最应该追求的是**更高质量的经验对象、更受控的注入、更干净的评估口径**。([SWE-bench][1])
