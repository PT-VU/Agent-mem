## 1. 直接回答：为什么 29 个里有 16 个 incomplete

- 前 29 个实例中，`13` 个产出了非空 patch，`16` 个 incomplete。
- 这 16 个 incomplete 的共同特征是：`tool_a_calls=0`、`tool_b_calls=1`、`extraction_pipeline.triggered=false`、`failure_card_v2.generated=true`。
- 主因不是经验系统没工作，而是主求解链路在进入有效施工前就失败了。具体统计如下：
  - `16/16` 都出现了 `DeepSeekException: Insufficient Balance`，即主 LLM 在第 1 步附近反复重试后失败。
  - `1/16` 还叠加了 `docker build ... exit status 255`（`astropy__astropy-13462`）。
  - `1/16` 还叠加了 `Cannot connect to the Docker daemon` 和 `docker pull ... SIGBUS`（`astropy__astropy-13465`）。
- 因为没有形成真实的 action 序列，Tool A 没有可检索/可注入的 planning 事件，Tool B 只能走 fallback：
  - 合成一个 `task_run_done_fallback_*` 任务；
  - 写入 1 张低置信度 failure card；
  - 不触发 LLM 抽象经验提取；
  - 不新增 repair pattern；
  - 不更新 belief 图中的有效经验。

## 2. 这 29 个实例里的 AgentMem 实际运行流程

### 2.1 事件捕获

- 入口是 `PDDL_work_mem/source_code/sweagent_external_tools/bridge_hook.py`。
- Hook 在 3 个时机工作：
  - `on_actions_generated`：每次模型给出 action 后，构造 `plan_generated` 事件，调用 Tool A。
  - `on_model_query`：如果 Tool A/Tool B 之前已经把 hint 放进 pending buffer，就把这些 hints 追加成一条用户消息注入给主模型。
  - `on_run_done`：任务结束时构造 `run_done` 事件，调用 Tool B 做收尾、提取、写库。
- Hook 会把事件序列化到环境变量 `SWE_AGENT_EXT_EVENT_JSON`，外部工具进程从这个 JSON 里读当前事件。

### 2.2 经验注入链路（Tool A）

- Tool A 的触发源是 `plan_generated`。
- Tool A 内部通过 `memory_agent.retrieve_for_query_type()` 做检索，核心输入是：
  - 当前 query 类型（这里几乎都是 `planning`）；
  - 当前 action / problem context；
  - 图存储中的抽象经验、repair pattern、belief。
- 检索结果会带 `retrieval_debug`，其中最关键的是：
  - `candidate_count_after_filter`：过滤后候选任务数；
  - `selected_subgraph_count`：最终选了几个任务子图；
  - `injection_selected_count`：最终有多少条建议进入注入候选。
- Hook 拿到 Tool A 返回后，不会直接改代码，而是先：
  - 从 `planning_tips/recommendations` 里提炼成 hint；
  - 放进 `_pending_memory_hints` buffer；
  - 在下一次 `on_model_query` 时，把这些 hints 拼成 `[AgentMem Hints]` 文本追加到主模型输入。
- 所以“注入发生的时间点”不是 Tool A 返回的那一刻，而是 Tool A 返回之后、下一次主模型 query 之前。

### 2.3 经验提取链路（Tool B）

- Tool B 在这 29 个实例里只在 `run_done` 时触发。
- `PDDL_work_mem/source_code/sweagent_external_tools/agent_mem/integration/sweagent_adapter.py` 在 `handle_run_done()` 里按顺序做 4 件事：
  1. `action_logger.end_task()` 结束当前任务并生成 `task_summary`。
  2. 若 task 有 action，则用 `memory_agent.update_beliefs()` 更新 belief。
  3. 用 `abstract_experience_builder.build_from_task()` 先生成一批基础 abstract experience。
  4. 调 `ExtractionOrchestrator.process_attempt()`，由 LLM 辅助做 step analysis、critical signal 检测，再映射成：
     - `abstract_experience`
     - `failure_card_v2` patch
     - `repair_pattern_v2`
- `ExtractionOrchestrator` 的触发条件来自 `extraction_orchestrator.py`：
  - `run_done_unresolved`：失败实例；
  - `run_done_success_with_recovery`：成功但中途出现 fail action；
  - `run_done_high_cost`：成功但 step 多、成本高（这里 13 个成功实例走的都是这个分支）。
- 在这 29 个实例里：
  - 13 个成功实例：`extraction_pipeline.triggered=true`，`llm_used=true`。
  - 16 个 incomplete：因为没有真实 actions，走 fallback，`triggered=false`，`llm_used=false`。

### 2.4 经验存放链路

- 存储位置都在：`/home/pt/SWE-bench/PDDL_work_mem/06_artificial_intelligence/experiments/03_run_outputs_full_first50_nomem_20min/with_mem/reruns/withmem_full50_20min_p1_online_20260307_194549/persistence/graph_store`
- 主要文件：
  - `abstract_experiences.json`：抽象经验。
  - `failure_cards_v2.json`：失败卡。
  - `repair_patterns_v2.json`：修复模式。
  - `belief_graph.json`：belief 图。
  - `observation_kg.json`：任务/action/evidence 子图。
  - `experience_rw_map.jsonl`：每次事件读了哪些 memory、写了哪些 memory。
- 这里要特别注意：`abstract_experience` 是 `upsert` 的，不是 append-only。
  - 这意味着同一个 `experience_id` 可能在多个实例里复用并被增量合并。
  - 因此报告里列出的 `experience_id` 表示“该实例写入/命中的对象 ID”；对象的当前内容可能已经被后续实例继续补充过。

## 4. 成功 13 例与 incomplete 16 例的共性结论

### 4.1 成功 13 例的共性

- 都发生了大量 Tool A 调用，说明 AgentMem 确实在持续参与 planning 阶段。
- 都在 run_done 时触发了 LLM 辅助提取。
- 提取出来的经验主题高度集中在：
  - planning loop / repetitive planning
  - inefficient planning
  - system stagnation / timeout_or_infinite_loop
- 这些经验最终被写成：
  - 1 组 direct success flow 经验
  - 多组 critical_* 类型 abstract experience
  - 多条 repair_pattern_v2
- belief 图里还沉淀出了一个共享 workflow belief（例如反复 “Generate plan for task” 的模式）。

### 4.2 incomplete 16 例的共性

- 没有 Tool A 调用，意味着没有进入“可注入经验”的正常 planning 循环。
- Tool B 只做了收尾 fallback：
  - `synthesized_task=true`
  - `failure_card_v2.generated=true`
  - `abstract_experience_updates.generated=0`
  - `extraction_pipeline.triggered=false`
  - `llm_used=false`
- 所以这 16 个实例不是“AgentMem 注入了错误经验导致失败”，而是“主求解链路在经验系统真正发挥作用前就中断了”。

## 6. 结论

- 对这 29 个实例，AgentMem 在前 13 个成功实例里是实打实运行起来了：持续检索、持续缓冲、持续注入，并在 run_done 时做了 LLM 辅助抽象提取和 repair pattern 写库。
- 这 13 个实例里，AgentMem 学到的主要不是“某个仓库的具体补丁”，而是“如何避免 planning 反复空转、如何尽快从 planning 进入 execution/validation”。
- 对后 16 个 incomplete 实例，失败主要发生在求解主链路：DeepSeek 余额耗尽，外加个别实例的 Docker 构建/拉镜像异常。由于没有真正产生 task actions，AgentMem 只能写 fallback failure card，无法完成正式经验提取。
- 因此，若要继续分析 AgentMem 对 solved rate 的真实增益，必须把“LLM 余额/运行环境故障”与“记忆机制本身的效果”严格分离；这 16 个 incomplete 不能拿来评价记忆检索质量。
