# 阶段6 First1 闭环冒烟测试最终总结（2026-03-09）

## 1. 测试对象与结论

本次测试对象：
- 数据集：SWE-bench full
- 范围：first1
- 模式：with memory
- 流程：单实例运行 -> 官方评测 -> official_eval_feedback 回流 -> memory behavior 汇总
- 运行目录：`PDDL_work_mem/06_artificial_intelligence/experiments/03_run_outputs_full_first50_nomem_20min/with_mem/smoke_runs/stage6_smoke_full_first1_withmem_nostandalone_rerun_20260309_111249`

最终结论：
- 闭环流程已经打通。
- 本次实例 `astropy__astropy-11693` 成功提交了 patch，但官方评测结果为 `unresolved`。
- 经验系统的“评测后回流”已经生效，但“运行时注入帮助 agent 收敛”这一层仍然基本没有发挥作用。
- 当前最主要的问题不是“完全没有提取经验”，而是：
  1. 注入没有真正作用到求解过程；

  4. 单实例 20 分钟上限没有按预期起效，实际运行耗时约 53 分 49 秒。

## 3. 哪些部分明显不按预期

### 3.1 运行时注入基本没有发挥作用

`memory_behavior` 的关键结果：
- `unique_families_injected = 0`
- `total_family_injections = 0`
- `repeated_family_injections = 0`

这说明：
- 虽然 Tool A 检索一直在工作，事件日志里有大量 `plan_generated -> external_tool_response`；
- 但最终没有形成有效注入统计；
- 也就是说，“检索到候选”并没有真正变成“帮助主模型收敛的可追踪注入”。

这是当前最大问题之一：
**在线记忆链路在跑，但没有真正进入主求解回路。**

### 3.2 检索严重偏向 workflow/planning 垃圾经验

事件日志显示：
- Tool A 在大量 step 上持续返回同一个 family：`workflow_step:consider: generate plan for task...`
- `candidate_count_before_filter` 从 0 一直涨到 52
- 但几乎所有候选都来自当前任务本身累积出来的 planning 轨迹

对应后果：
- 记忆系统没有把 agent 往“最小修复”方向拉；
- 反而持续强化了“继续计划、继续读代码、继续做额外验证”的行为。

这说明当前的 retrieval/rerank 仍然有结构性问题：
- 对当前任务自己刚写出来的 planning 痕迹过拟合；
- 对低价值 workflow family 的压制仍然不够；
- 对真正高价值的 negative strategy / patch risk / stop signal 还不够强。

### 3.3 停止条件明显失效

这次轨迹里，agent 很早就已经拿到了关键事实：
- `all_world2pix(quiet=True)` 返回 best solution；
- `world_to_pixel_values()` 当前不传 `quiet=True`，因此仍抛异常；
- 这已经足够支持一个“最小修复”候选。

但之后 agent 没有收敛，而是继续做了大量无效扩展：
- 检查 WCS API 其他实现；
- 写额外脚本 `test_quiet.py`；
- 写额外脚本 `test_scalar_vs_array.py`；
- 继续追 wrapper/base/sliced_wcs 等非关键路径；
- 继续讨论接口兼容性、多版本迁移、context manager 等超出当前任务的设计问题。

最终轨迹推进到约 `step 128` 才结束。

这说明当前系统缺少一类很关键的经验/控制：
- **“已拿到足够决策证据后，停止扩展搜索”的 stop/closure 经验。**

### 3.4 单实例 20 分钟上限没有按预期生效

运行日志明确显示：
- `Overall Progress ... 0:53:49`

也就是说：
- 当前这个“每实例 20min”的约束，在这次 closed-loop smoke 中没有真正把实例裁停；
- 即便 `--agent.tools.total_execution_timeout 1200` 已传入，整体实例运行时间仍然远超 20 分钟。

这是流程层面的严重问题，因为它会直接污染后续评估：
- 你以为是在比较“20min budget 下的能力”；
- 实际跑出来的是“远超预算后的能力/行为”。

### 3.5 submitted 阶段的提取仍然偏乐观

`run_done` 的 Tool B 输出显示：
- `submission_success = true`
- `resolved_like_success = false`
- `failure_card_v2.generated = false`
- `reason = submission_pending_official_eval`
- 同时仍然写入了 2 条 abstract experience 和 7 条 repair pattern

这本身不是完全错误，但问题在于：
- 在 official eval 还没回来之前，系统已经基于一个“已提交 patch”状态写入了不少正向/中性经验；
- 这会让记忆系统在评测前过早乐观。

### 3.6 official eval 回流虽然触发了，但 candidate 关联失败

`official_eval_feedback` 的结果里有一个非常关键的字段：
- `related_candidate_count = 0`
- `promoted_ids = []`
- `suppressed_ids = []`
- 只新增了新的写入：`written_ids = [abs_3_..., abs_4_..., failure_card...]`

这说明：
- unresolved 的官方回流事件已经来了；
- 但它没有把本轮 `run_done` 产生的 candidate 经验正确识别并压制/抑制；
- 也就是说，candidate -> official outcome 的关联链还是断的。

这非常重要。
如果这个关联不修，系统就只能“额外再写一些负经验”，但不能真正修正本轮运行时形成的错误候选经验。

### 3.7 读写映射基本没有记录实际读依赖

`experience_rw_map.jsonl` 显示：
- 大量 `plan_generated` 事件都是 `read_ids = []`
- `write_ids = []`
- 直到 `run_done` 才开始集中写入

这说明：
- 在线阶段虽然发生了 retrieval，但我们并没有把“这次模型到底读了哪些经验”稳定映射出来；
- 这会导致后续两件事都做不好：
  1. 无法做可靠的 intervention attribution；
  2. official eval 回流时无法回溯应该 suppress/promote 哪些候选。

## 4. 为什么这次最终 unresolved

从 patch 和回流结果看，根因不是“完全没理解问题”，而是以下组合：

### 4.1 patch 方向发生了泛化和过度设计

最终 patch 不是最小修复，而是把 `world_to_pixel_values` 改成了一个 80 多行的大逻辑：
- 新增 `quiet` 参数
- 默认 `quiet=False`
- 捕获 `NoConvergence`
- 发 warning
- 手工组装 `best_solution`
- 手工处理 scalar/array/broadcast/NaN

这种 patch 风格的问题是：
- 复杂度太高；
- 语义改变过大；
- 容易偏离任务真正需要的最小行为修复；
- 风险显著高于“在确切调用点做最小修正”。

### 4.2 轨迹中出现了大量“自造验证任务”

agent 在主问题已经足够清楚时，又额外制造了多个验证脚本：
- `reproduce_error.py`
- `test_quiet.py`
- `test_scalar_vs_array.py`
- `test_wcsapi_basic.py`

其中一部分脚本一开始还是错的，例如最早的 reproduction 脚本本身就因为 matplotlib 用法错误而失败。这个噪声会带来两个直接坏处：
- 消耗大量 step / token / wall time；
- 给经验提取系统喂入大量“与真正 issue 不完全对齐”的局部信号。

### 4.3 评测后系统正确判定为 unresolved，但还没有足够强地反推“为什么这个 patch 风险高”

`official_eval_feedback` 已经识别出：
- `outcome = unresolved`
- `risk_flags = [quiet_flag]`

这说明系统已经开始具备“这类 patch 有风险”的意识。问题在于：
- 这种风险意识还没有前置到在线阶段；
- 只在事后回流；
- 且没有成功 suppress 本轮 candidate。

## 5. 当前经验系统的真实状态

### 5.1 已经做到的

- 闭环打通了；
- official eval 回流打通了；
- unresolved 会写成新的 failure/abstract 经验；
- infra failure 没污染这次样本；
- `validation_guard` 类经验已经出现；
- `llm_assisted_extractor` 也确实在写 repair pattern。

### 5.2 仍然没有做到的

- 在线注入没有真正帮助 agent 收敛；
- workflow/planning 垃圾经验没有被及时压住；
- 读取到的经验没有稳定记录成 `read_ids`；
- official eval 回流没有关联回本轮 candidate；
- run_done 前的候选经验仍然偏乐观；
- stop/closure 类经验缺失；
- 20 分钟预算没有真正被 enforce。

## 6. 这次样本最值得保留的异常清单

1. **运行时间异常**：标称 20min，实际单实例跑了约 53m49s。
2. **注入异常**：retrieval 有大量候选，但 `family_injection_summary.total_family_injections = 0`。
3. **停止条件异常**：agent 已拿到关键结论仍继续扩展搜索到 120+ step。
4. **检索异常**：持续返回低价值 `workflow_step` family，且候选数一路膨胀到 52。
5. **回流关联异常**：`official_eval_feedback.related_candidate_count = 0`，没有 suppress/promote 到本轮 candidate。
6. **提取时机问题**：official eval 前仍产生较多 candidate 经验，语义偏乐观。
7. **在线可解释性不足**：`experience_rw_map` 里的 `read_ids` 基本为空，无法解释记忆到底有没有被真正用上。

## 7. 下一步最值得做的改动（按优先级）

### P0
1. 修 timeout 约束，确保“每实例 20min”真正生效。
2. 修 `official_eval_feedback` 与 `run_done candidate` 的关联逻辑，让 unresolved 能 suppress 本轮 candidate。
3. 修在线读写映射，把真正被检索/注入/采纳的经验写进 `read_ids`。

### P1
4. 给 retrieval 增加更强的 stop/closure/negative-strategy 优先级，进一步压低 workflow family。
5. 在 agent 已拿到关键技术结论时，增加“停止继续扩展验证”的触发条件。
6. 把“自造验证脚本过多”作为负经验模式显式提取。

### P2
7. 重新约束 run_done 前的 candidate 写入预算：official eval 前减少正向抽象经验，更多写成 provisional/candidate。
8. 在 patch risk 里增加“过大补丁、接口扩张、quiet_flag 扩散”之类结构化风险标签。

## 8. 总结

这次样本最重要的价值不在于 patch 成功，而在于它第一次完整证明了下面这件事：

**我们的阶段6闭环已经能把一次真实的 submitted-but-unresolved 运行，走完整个 `trial -> official eval -> official_eval_feedback -> memory behavior` 链条。**

但它同时也明确暴露出：

**当前系统更像是“能在事后记住失败”，还不是“能在运行中有效阻止失败”。**

这是下一轮升级的核心方向。
