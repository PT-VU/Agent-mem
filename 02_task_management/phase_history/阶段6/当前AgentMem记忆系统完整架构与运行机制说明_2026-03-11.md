> 参考文档：`阶段5/当前agent mem框架.md`、`00_project_context/resources/Agent-mem架构.md`

## 0. 先给结论：当前系统到底是什么

当前 AgentMem 不是一个“把所有执行动作完整写成长期记忆再统一学习”的系统；它在当前主链路里更准确的定义是：

1. `bridge_hook.py` 挂在 SWE-agent 生命周期上，监听少数关键事件。
2. 这些事件被序列化成 `SWE_AGENT_EXT_EVENT_JSON`，交给外部命令。
3. 外部命令通过 `dispatcher.py -> agent_mem_main.py -> SWEAgentAdapter` 进入 AgentMem 主处理链。
4. AgentMem 会：
   - 在 `plan_generated` 时检索规划经验；
   - 在 `action_error` 时检索修复经验，并即时写入微型修复模式；
   - 在 `run_done` 时做抽象经验提取、失败卡生成、RCA、Attempt 摘要生成；
   - 在官方评测结果回来后再决定“晋升/压制”哪些经验。
5. Hook 本身负责：
   - 缓冲 hints；
   - 决定什么时候注入；
   - 运行时软阻断明显低价值/重复性的动作；
   - 记录干预效果和门禁指标。

### 0.1 最重要的现状纠偏

这几点必须先讲清楚，否则后面的架构理解会偏：

1. 当前在线主链路**并没有把每个成功执行的 shell/tool action 都写进 KG**。  
   Hook 当前只主动调用外部工具处理：
   - `on_actions_generated`
   - `on_action_error`
   - `on_run_done`

2. `on_action_executed` 在当前代码里只做本地统计与干预效果跟踪，**不会调用 Adapter 写库**。  
   所以当前 Observation KG 的主来源其实是：
   - 规划时生成的 action 文本；
   - 出错时的失败 action 文本；
   - `run_done` 时基于这些历史节点做离线抽取。

3. `handle_action_success()` 这个 API 存在，但**没有接到当前 Hook 主链路**。  
   它只能通过别的脚本或手动 API 调用生效。

4. 当前长期记忆“晋升为可信经验”的关键门槛不在 `run_done`，而在后续 `official_eval_feedback`。  
   换句话说，`submitted` 只会把经验写成 candidate，不会当成最终正确经验。

## 1. 当前主链路和旁路链路总览

## 1.1 主链路

```text
SWE-agent 生命周期
  -> ExternalToolBridgeHook
      -> on_actions_generated / on_action_error / on_run_done
      -> 组装事件 JSON
      -> 调外部命令 (tool_a_cmd / tool_b_cmd)
          -> dispatcher.py
              -> agent_mem_main.py
                  -> SWEAgentAdapter
                      -> ActionLogger / KGWriter / MemoryAgent / RCA / Extractor / GraphStore
      -> 解析返回 JSON
      -> 缓冲 hints
      -> on_model_query 时做注入
      -> on_action_executed / on_run_done 时做效果跟踪和门禁统计
```

## 1.2 收尾学习链路

```text
run_done
  -> 关闭 active task
  -> 基于已记录 actions 取 task subgraph
  -> 更新 belief
  -> 生成 abstract experience candidate
  -> 未完成时生成 RCA + failure_card_v2 + repair_pattern_v2
  -> ExtractionOrchestrator 生成：
       attempt_summary_v1
       abstract_experience
       failure_card_patch
       repair_pattern_v2
```

## 1.3 官方评测反馈链路

```text
official_eval report / instance dir
  -> official_eval_bridge.py 构造 official_eval_feedback 事件
  -> SWEAgentAdapter.apply_evaluation_feedback()
  -> EvaluationFeedbackProcessor
      -> resolved: promote candidate experiences
      -> unresolved/incomplete: suppress old candidate + 写入 negative memories
      -> infra_failure: 写 infra failure card
```

## 1.4 仓内存在但不在当前主链路上的模块

这些模块存在，但当前主链路没有真正依赖它们：

1. `agent_mem/retrieval/retriever.py`
2. `agent_mem/retrieval/embedder.py`
3. `agent_mem/processing/error_handler.py`

当前真正生效的检索逻辑在 `agent_mem/retrieval/memory_agent.py`，真正生效的 embedding 生成逻辑在 `agent_mem/processing/kg_writer.py`。

## 2. 模块分层与职责

## 2.1 Hook 接入层

### `bridge_hook.py` / `ExternalToolBridgeHook`

职责：

1. 监听 SWE-agent 生命周期回调。
2. 组装事件 payload。
3. 调外部命令。
4. 解析外部命令返回 JSON。
5. 把可注入经验先放进 `_pending_memory_hints`。
6. 在 `on_model_query` 时根据预算、置信度、家族冷却、runtime guard 做选择性注入。
7. 记录干预效果、门禁统计、stale fallback、circuit breaker 状态。

它是整个系统的在线控制面。

## 2.2 路由入口层

### `dispatcher.py`

职责：

1. 判断 AgentMem 是否可导入。
2. 把 Tool A / Tool B 语义映射到统一入口 `agent_mem_main.py`。
3. 在普通事件模式下，先把原始 payload 记录到统一 JSONL 日志中。
4. 如果 AgentMem 不可用，则回退到旧版 `tools/tool_a.py` / `tools/tool_b.py`。

注意：

1. Tool A / Tool B 在当前实现里主要只是“事件语义标签”：
   - A 偏 `plan_generated`
   - B 偏 `action_error` / `run_done`
2. 真正处理逻辑已经统一到 Adapter。

## 2.3 主入口层

### `agent_mem_main.py`

职责：

1. 读取 `SWE_AGENT_EXT_EVENT_JSON`。
2. 加载配置。
3. 初始化 `SWEAgentAdapter`。
4. 根据 `event` 路由到：
   - `handle_plan_generated`
   - `handle_action_error`
   - `handle_run_done`
   - `apply_evaluation_feedback`
5. 把结果 JSON 打印到 stdout，供 Hook 回读。

额外模式：

1. `--stats`
2. `--export`

## 2.4 编排层

### `agent_mem/integration/sweagent_adapter.py` / `SWEAgentAdapter`

这是 AgentMem 的编排中心。它串起了：

1. `GraphStore`
2. `ActionLogger`
3. `KGWriter`
4. `MemoryAgent`
5. `AbstractExperienceBuilder`
6. `ExtractionOrchestrator`
7. `EvaluationFeedbackProcessor`
8. `FailureCardBuilder`
9. `RCAAgent`

它还负责两个非常关键的持久化文件：

1. `active_tasks.json`
2. `experience_rw_map.jsonl`

## 2.5 处理层

### `ActionLogger`

职责：

1. 根据事件创建 `ProblemFile`。
2. 保存 stderr/stdout/diff/test 输出证据。
3. 自动构造 `failure_signature`、`env_signature`、`patch_stats`、`test_stats`、`execution_stats`。
4. 把 ProblemFile 写进 Observation KG。
5. 根据 `last_action_id` 建边。

### `KGWriter`

职责：

1. 为 ProblemFile 生成多视角 embedding。
2. 把 embedding 回写到 ProblemFile 对象。

### `AbstractExperienceBuilder`

职责：

1. 基于 task actions 生成 task-level 抽象经验。
2. 为每个 error type 再生成 error-specific 抽象经验。
3. 归一化 pattern family / trigger family / advice family。

### `RCAAgent`

职责：

1. 找失败节点。
2. 识别根因候选。
3. 计算 decisive score。
4. 生成 root cause、propagation chain、corrective actions、preventive checks。

### `FailureCardBuilder`

职责：

1. 把 unresolved attempt 转成 `failure_card_v2`。
2. 生成候选修复动作和验证命令。
3. 识别 infra / agent failure class。

### `ExtractionOrchestrator`

职责：

1. 在 `run_done` 后触发“步骤级失败信号抽取”。
2. 调用 rule-based taxonomy 与可选 LLM extractor。
3. 生成：
   - `attempt_summary_v1`
   - `abstract_experience`
   - `failure_card_patch`
   - `repair_pattern_v2`
4. 执行质量门。

### `EvaluationFeedbackProcessor`

职责：

1. 把官方评测结果回写到记忆对象。
2. 决定 promote / suppress。
3. 写负向经验与 infra failure card。

## 2.6 检索层

### `MemoryAgent`

职责：

1. Query rewriting
2. 结构检索 + embedding 检索融合
3. abstract experience / failure card / repair pattern / belief / attempt summary 的组合召回
4. 去重、重排、打分
5. `run_done` 时更新 belief graph

## 2.7 存储层

### `GraphStore`

职责：

1. 持有 Observation KG、Belief Graph。
2. 读写 `abstract_experiences`、`attempt_summaries_v1`、`failure_cards_v2`、`repair_patterns_v2`、`preventive_rules_v2`。
3. 保存和加载 JSON 文件。
4. 提供 query / upsert / merge / statistics。

## 3. 当前在线状态机：Hook 内存态到底维护了什么

`ExternalToolBridgeHook` 在进程内维护了一组关键状态：

| 状态 | 作用 |
|---|---|
| `_pending_memory_hints` | 等待注入的 hints 队列 |
| `_recent_hint_fingerprints` | 对 hint 文本去重 |
| `_hint_family_last_injected_step` | 每个 family 上次注入步号 |
| `_hint_family_injected_count` | 每个 family 本次 attempt 已注入次数 |
| `_recent_triggers` | 最近触发过的主动触发器 |
| `_seen_files` | 已见过的文件名，用于 `first_file_access` |
| `_ad_hoc_script_names` | 已识别的 ad-hoc 脚本名 |
| `_closure_active` | 是否进入“该收口了”的状态 |
| `_blocked_action_patterns` | 来自 attempt summary 的需软阻断动作模式 |
| `_active_subproblem_type` | 当前锁定子问题类型 |
| `_active_strategy_label` | 当前锁定策略标签 |
| `_active_interventions` | 已注入 hints 的局部效果跟踪窗口 |
| `_consecutive_failures` | 连续失败计数 |
| `_step_index` | 当前步号，`on_actions_generated` 时递增 |
| `_tool_failure_streak` | 外部工具失败连击数 |
| `_tool_circuit_open_until` | circuit breaker 冷却截止时间 |
| `_last_success_payload_by_event` | 按 event 缓存最近一次成功响应，供 stale fallback |
| `_metrics` | 质量门指标计数器 |

这些状态决定：

1. hint 会不会进缓冲区；
2. 哪些 hint 会被注入；
3. 是否要阻断新建 repro script 或扩 scope；
4. 外部工具不可用时是否用 stale payload 顶上；
5. 最终门禁是否通过。

## 4. 事件协议：什么事件会触发记忆系统

## 4.1 统一输入协议

所有事件都通过环境变量 `SWE_AGENT_EXT_EVENT_JSON` 传入，格式是 JSON 字符串。

所有 payload 至少包含：

1. `version`
2. `event` / `event_type`
3. `source`
4. `agent`
5. `instance_id`
6. `run_id`
7. `attempt_id`
8. `step_index`
9. `timestamp`
10. `trace_id`

## 4.2 当前会被主链路主动触发的 Hook action

| Hook action | 触发条件 | 目的 | 外部工具 |
|---|---|---|---|
| `on_init` | Hook 被初始化 | 识别 `instance_id` | 无 |
| `on_actions_generated` | 模型产出下一步 action | 规划检索、更新 runtime guard | `tool_a_cmd` |
| `on_model_query` | 模型再次请求前 | 注入 hints | 无外部工具 |
| `on_action_error` | 动作执行异常 | 修复检索、写微型修复模式 | `tool_b_cmd` |
| `on_action_executed` | 动作执行完成 | 统计 error-like observation、推进 intervention 窗口 | 无外部工具 |
| `on_run_done` | 整个 run 结束 | 收尾学习、门禁输出 | `tool_b_cmd` 或回退 `tool_a_cmd` |

## 4.3 当前支持但不由 Hook 主链路直接发起的事件

| 事件 | 来源 |
|---|---|
| `official_eval_feedback` | 评测后处理脚本、`official_eval_bridge.py`、或外部调用 |
| `action_success` | Adapter API 有，但 Hook 当前不发 |

## 5. Hook 详细流程：每个 action 如何触发、触发后如何运行

## 5.1 `on_init`

触发时机：

1. Hook 被挂载到 agent 上时。

执行逻辑：

1. 读取 `SWE_AGENT_EXT_RUN_ID`、`SWE_AGENT_EXT_ATTEMPT_ID`。
2. 优先从 `SWE_AGENT_EXT_INSTANCE_ID` 取 instance。
3. 如果没有，则尝试从：
   - `agent._problem_statement.id`
   - `agent.problem_statement.id`
4. 如果都没有，退化为 `agent.name`。

运行结果：

1. 成功拿到实例 ID；
2. 拿不到则用 agent 名称代替。

## 5.2 `on_actions_generated`

这是规划时主入口。

### 5.2.1 触发前的 runtime guard 检查

在真正发事件前，Hook 会先检查是否要软阻断当前 action。

阻断来源有两类：

1. `_blocked_action_patterns` 命中
2. `_closure_active=True` 且检测到“又在新建 ad-hoc 脚本”

如果命中：

1. 不会丢弃这一步；
2. 会把 `step.action` 改写成一个 `printf` 提示语句；
3. 仍然继续进入后续流程；
4. 这意味着 agent 看到的是“被替换后的 action”，不是原始 action。

### 5.2.2 步号和指标更新

执行顺序：

1. `_step_index += 1`
2. `plan_generated` 指标 +1
3. 扫描 proactive trigger

### 5.2.3 proactive trigger 扫描

扫描的是 `step.action` 文本。

可能触发的 marker：

1. `before_test_run`
   - 命中 `pytest/unittest/tox/nox/nose/python -m pytest/make test`

2. `before_submit`
   - 命中 `submit/submission/create pr/open pr/final answer/final patch`

3. `first_file_access:<filename>`
   - 第一次看到某个文件名时触发

4. `over_exploration:<n>`
   - 命中两个及以上 `test_*.py` / `reproduce_*.py` / `debug_*.py`
   - 同时：
     - `_closure_active=True`
     - 追加一个系统生成 hint：
       `Stop expanding ad-hoc scripts. Validate the minimal fix against the target failing path, then either submit or terminate.`

### 5.2.4 事件 payload 构造

`plan_generated` payload 额外包含：

1. `thought`
2. `action`
3. `runtime_guard`

其中 `runtime_guard` 包括：

1. `closure_active`
2. `ad_hoc_script_count`
3. `recent_triggers`
4. `blocked_families`
5. `blocked_action_patterns`
6. `active_subproblem_type`
7. `active_strategy_label`

### 5.2.5 调外部命令 `_run_cmd`

如果配置了 `tool_a_cmd`，则执行外部命令。

主要控制逻辑：

1. 如果 circuit breaker 开启且未冷却完成：
   - 不执行命令；
   - 记录 `circuit_open`；
   - 尝试 stale fallback。

2. 否则执行 `subprocess.run(shell=True)`。

3. 尝试次数：
   - `attempts = max(1, max_retries + 1)`

4. 超时：
   - `tool_a` 默认超时：`max(45.0, timeout_sec * 3.0)`
   - retry 超时：`max(60.0, tool_a_timeout * 2.0, timeout_sec * 2.5)`

5. timeout 后：
   - 记 `tool_timeout_events`
   - failure streak +1
   - 若开了 adaptive timeout，则将该工具后续超时提升到 retry timeout

6. stdout 若能解析出 JSON：
   - 即使进程 return code 非 0，只要 JSON 合法，也会把它当作成功处理结果。

7. 全部失败后：
   - 若开 `enable_stale_fallback` 且之前有同事件成功 payload，则回放 stale payload；
   - 否则记 `failed`。

### 5.2.6 解析外部响应 `_handle_parsed_tool_payload`

当 stdout 里解析出 JSON 后，会做：

1. 记录最近一次成功 payload 到 `_last_success_payload_by_event`
2. 写 `external_tool_response` 日志
3. 根据 payload 更新 runtime guard
   - 只识别 `attempt_summary_v1` 类型 recommendation
   - 可写入：
     - `_active_subproblem_type`
     - `_active_strategy_label`
     - `_blocked_action_patterns`
4. 将响应中的 hints 放入 `_pending_memory_hints`

### 5.2.7 什么会被缓冲成 hint

会从这些字段里抽：

1. `planning_tips`
2. `repair_suggestions`
3. `next_step_fix`
4. `recommendations`

能抽成 hint 的文本来源：

1. 字符串 item 本身
2. dict item 的以下字段之一：
   - `recommendation`
   - `repair_action`
   - `next_step_fix`
   - `recommend`
   - `summary`

### 5.2.8 hint 缓冲规则

整批拦截规则：

1. 先算 batch confidence；
2. 如果整批 `confidence < SWE_AGENT_MEM_MIN_CONFIDENCE`，整批不进缓冲。

逐项拦截规则：

1. item confidence 低于 `SWE_AGENT_MEM_MIN_ITEM_CONFIDENCE` 跳过；
2. 相同 hint 文本指纹去重；
3. `workflow_step:` 且当前步号大于 3，直接跳过；
4. 超过最大 pending 上限时，从队头丢旧项。

pending 上限：

1. 如果 `SWE_AGENT_MEM_MAX_HINTS > 0`，soft cap = `max_hints`
2. 否则 soft cap = 25
3. `max_pending = max(20, soft_cap * 8)`

### 5.2.9 `on_actions_generated` 的运行结果分支

可能结果：

1. 命令未配置：事件结束，无响应。
2. 命令成功，返回规划建议：hint 被缓冲。
3. 命令成功，但返回空建议：只记日志，不缓冲。
4. 命令超时但 stale fallback 成功：使用旧 payload。
5. 命令失败且无 stale fallback：只记录失败日志。
6. action 被 runtime guard 改写：仍继续发送事件，但发送的是替换后的 action。

## 5.3 `on_model_query`

这是“真正注入”的时刻，不是计划或错误事件返回时立即注入。

### 5.3.1 触发前提

只有满足以下条件才会进入：

1. `SWE_AGENT_MEM_INJECT_ENABLED = true`
2. `_pending_memory_hints` 非空

### 5.3.2 hint 选择算法 `_select_hints_for_injection`

排序键：

1. bucket priority
2. `selection_score`
3. `item_confidence/batch_confidence`

bucket 优先级：

1. `closure`
2. `repair`
3. `validation`
4. `general`
5. `workflow`

bucket 判定规则：

1. `closure_signal` -> `closure`
2. `repair_pattern_v2` / `failure_card_v2` / `negative_strategy` / `patch_risk` -> `repair`
3. `validation_gap` / `validation_guard` -> `validation`
4. `belief_tip` / `workflow_step` / `planning_loop` -> `workflow`
5. 其他 -> `general`

选择约束：

1. `char_budget = max(max_hint_chars, hint_char_budget)`
2. 如果 `require_trigger_for_injection=true` 且近期没有 trigger：
   - 低于 `max(min_confidence, 0.7)` 的 hint 不会被选，只会继续留在 buffer
3. `workflow` hint 在以下情况直接丢弃：
   - `step_index > 3`
   - 最近触发过 `over_exploration`
4. 同 family 只允许一个进入本轮；
5. family 若达到 `max_hints_per_family_per_attempt`，本 attempt 不再注入；
6. family 若距离上次注入步数小于 `family_cooldown_steps`，本轮先不注入；
7. bucket 限额：
   - `closure/repair/validation/workflow`：每桶最多 1 条
   - `general`：最多 2 条
8. 若达 `max_hints` 或字符预算，则剩余项留 buffer。

### 5.3.3 注入格式

注入到 `messages` 的内容固定是：

```text
[AgentMem Hints]
Use these hints only when relevant to the current repository state.
1. ...
2. ...
```

如果超出 `max_hint_chars`，会截断。

### 5.3.4 注入后还会发生什么

1. 清空 `_recent_triggers`
2. 为每个 family 记录：
   - `last_injected_step`
   - `injected_count`
3. 注册 intervention 窗口：
   - 默认观察后续 5 步
4. 记录 `memory_injected` 日志

### 5.3.5 intervention 跟踪

每次注入都会注册 `intervention_id`，随后：

1. `on_action_error` -> `error_events +1`
2. `on_action_executed` -> `success_events +1`
3. 每次事件都会 `remaining_steps - 1`
4. 窗口耗尽或 `run_done` 时关闭

关闭时写 `memory_intervention_feedback`：

1. `local_effective = success_events > 0 and error_events == 0`
2. `evaluation_effective` 当前固定为 `None`

### 5.3.6 `on_model_query` 的运行结果分支

1. 无 hint：不注入。
2. 有 hint 但都被过滤：不注入。
3. 选出若干 hint：写入消息并开始 intervention 跟踪。

## 5.4 `on_action_error`

### 5.4.1 触发条件

SWE-agent 报告动作执行异常时触发。

### 5.4.2 本地状态变化

1. `_consecutive_failures += 1`
2. `action_error_events +1`
3. 推进 intervention 窗口
4. 根据失败次数写 trigger：
   - 第一次失败：`first_failure:<error_type>`
   - 第二次及以上：`consecutive_failures:<n>`

### 5.4.3 事件 payload

额外包含：

1. `error_type`
2. `error_message`
3. `thought`
4. `action`

### 5.4.4 外部工具执行

走 `tool_b_cmd`，执行逻辑与 `tool_a` 一样，只是超时默认更短：

1. `tool_b_timeout_sec` 默认等于 `timeout_sec`

### 5.4.5 结果分支

1. 命令成功返回修复建议：进入 hint buffer。
2. 返回空建议：只记日志。
3. 命令失败 / 超时 / stale fallback：同 `plan_generated`。

## 5.5 `on_action_executed`

这是当前最容易被误解的回调。

它**不会写库**，只做三件事：

1. 检查 `step.observation` 是否像 error
   - 命中 `error/exception/traceback/assert/failed/no such file/timed out/non-zero`
   - 则 `error_like_observation +1`
2. 如果 observation 不是 `"simulated command error"`：
   - 把 `_consecutive_failures` 清零
   - 若之前有失败，会记录 `after_success:<n>`
3. 推进 intervention 窗口，记为 `action_success`

这意味着：

1. 它影响 metrics；
2. 它影响 memory 干预效果判断；
3. 但它不生成新的 ProblemFile。

## 5.6 `on_run_done`

### 5.6.1 触发条件

agent run 结束时触发。

### 5.6.2 payload

包含：

1. `trajectory_steps`
2. `exit_status`
3. `has_submission`

### 5.6.3 调外部工具

优先用 `tool_b_cmd`，没有的话回退 `tool_a_cmd`。

### 5.6.4 后处理

1. 强制关闭所有 intervention；
2. 输出门禁评估；
3. 记录 `run_done` 日志。

### 5.6.5 门禁计算 `_emit_gate_evaluation`

三个核心比率：

1. `external_ratio = external_tool_response / max(1, plan_generated)`
2. `buffer_ratio = memory_hint_buffered / external_tool_response`
3. `action_error_coverage = action_error_events / error_like_observation`

默认阈值：

1. `external_ratio >= 0.35`
2. `buffer_ratio >= 0.15`
3. `action_error_coverage >= 0.60`

输出：

1. `memory_gate_evaluation`
2. 如果 `SWE_AGENT_MEM_GATE_HARD_FAIL=true` 且未通过，再额外输出 `memory_gate_hard_fail`

注意：

1. 当前所谓 `hard_fail` 只会写日志，**不会真正中断进程**。

## 6. Adapter 详细流程：进入 AgentMem 后每个事件怎么处理

## 6.1 task 绑定与 `active_tasks.json`

### 6.1.1 task key 生成

`_build_task_key()` 规则：

1. 优先使用：
   - `run_id`
   - `attempt_id`
   - `instance_id`
2. 值会做 sanitize，只保留 `[a-zA-Z0-9_.-]`

常见格式：

1. `run_id:attempt_id:instance_id`
2. 没有 attempt 时退化为 `run_id:instance_id`
3. 再退化为 `instance_id`

### 6.1.2 `_ensure_task_context()`

对 `plan_generated` 和 `action_error`：

1. 先读 `active_tasks.json`
2. 如果已有 task_id，则 resume
3. 否则新建 `task_YYYYMMDD_HHMMSS_agent`
4. 调 `ActionLogger.start_task(..., resume_from_existing=True)`

这保证同一个 run/attempt/instance 的在线事件会落到同一个 task。

## 6.2 `handle_plan_generated`

### 6.2.1 task_context

当前写法：

1. `instruction = thought or action`
2. `summary = action`
3. `env_signature` 只有：
   - `run_id`
   - `attempt_id`
   - `instance_id`

### 6.2.2 写 ProblemFile

`ActionLogger.log_action()` 的实际字段：

1. `action_type = TOOL_CALL`
2. `intent_text = "Generate plan for task"`
3. `action_text = action`
4. `action_family = "planning"`
5. `inputs = {"thought": thought, "action": action}`
6. `tool_calls = [{"type": "plan_generation", "content": action}]`
7. `outcome = SUCCESS`

当前主链路下，这个 planning 节点通常：

1. 没有 stdout/stderr
2. 没有 touched_files
3. 没有 diff/test evidence
4. 只有 action 文本和元数据

### 6.2.3 生成 embedding

如果 `AGENT_MEM_ENABLE_ONLINE_EMBEDDINGS=true`：

1. 生成 `emb_task_sem`
2. 生成 `emb_intent`
3. 其他向量只有在相应字段存在时才会生成

当前主链路里 planning 节点一般不会有：

1. `emb_file_scope`
2. `emb_error_sig`
3. `emb_tool_output`
4. `emb_diff_summary`

### 6.2.4 规划检索

调用：

`MemoryAgent.retrieve_for_query_type(query_type="planning", ...)`

返回：

1. `planning_tips`
2. `evidence_refs`
3. `confidence`
4. `retrieval_debug`

### 6.2.5 rw map 记录

会写一条 `experience_rw_map.jsonl`：

1. `event=plan_generated`
2. `read_ids=实际召回的经验 ID`
3. `write_ids=[]`

### 6.2.6 返回结果情况

1. 有 tips：Hook 会继续缓存。
2. 无 tips：返回空列表，Hook 不注入。

## 6.3 `handle_action_error`

### 6.3.1 task_context

1. `instruction = thought or action`
2. `summary = error_message[:240]`
3. `env_signature` 仍然只有 run/attempt/instance

### 6.3.2 写 ProblemFile

实际字段：

1. `action_type = TOOL_CALL`
2. `intent_text = thought`
3. `action_text = action`
4. `action_family = "error_recovery"`
5. `inputs = {"action": action, "error_type": error_type}`
6. `tool_calls = [{"type": "action_execution", "content": action}]`
7. `stderr = error_message`
8. `outcome = FAIL`

### 6.3.3 `failure_signature` 当前真实生成逻辑

不是直接使用 `event_data.error_type`，而是由 `ActionLogger._create_failure_signature()` 从 `stderr` 第一行粗略归一化：

1. 第一行含 `error` -> `error_type="error"`
2. 含 `exception` -> `error_type="exception"`
3. 含 `fail` -> `error_type="failure"`
4. 否则 `unknown`

这意味着：

1. ProblemFile 内部的 `failure_signature` 比事件里的 `error_type` 粗；
2. 但 MemoryAgent 检索时仍会使用 `event_data.error_type` 作为显式 query 条件。

### 6.3.4 修复 query 类型

规则：

1. `if "test" in error_type.lower()` -> `query_type = "test_failure_fix"`
2. 否则 -> `query_type = "error_recovery"`

### 6.3.5 修复检索

调用：

`MemoryAgent.retrieve_for_query_type(query_type=repair_query_type, ...)`

返回：

1. `repair_suggestions`
2. `next_step_fix`
3. `expected_outcome`
4. `retrieval_debug`

### 6.3.6 即时微型经验写入

除了返回 suggestions，本事件还会写两个轻量对象：

1. `repair_pattern_v2`
   - 条件：不是 infra 错误，且能提取到 `next_step_fix`

2. `preventive_rule_v2`
   - 条件：不是 infra 错误，且能提取到验证命令

注意：

1. `preventive_rule_v2` 当前主链路只写不读；
2. 它不会直接参与当前在线检索。

### 6.3.7 返回结果情况

1. 有修复建议，且微型经验写入成功；
2. 有修复建议，但不满足微提取条件；
3. 没有修复建议，`repair_suggestions=[]`；
4. infra 错误会跳过微型经验写入。

## 6.4 `handle_run_done`

这是最复杂的事件。

### 6.4.1 先清 active task

1. 从 `active_tasks.json` 删除当前 task key
2. 立即 `graph_store.save()`

### 6.4.2 synthesized task 分支

如果找不到当前 task key：

1. `synthesized_task = True`
2. 创建 fallback task_id：
   `task_run_done_fallback_<ts>_<instance>`

这保证即使 `active_tasks.json` 丢了，`run_done` 仍然可观察。

### 6.4.3 exit_status 分类

使用以下布尔量：

1. `has_submission = bool(event_data["has_submission"])`
2. `submission_success = has_submission or exit_status == "submitted"`
3. `resolved_like_success = exit_status in {"done", "success"} and not submission_success`
4. `task_closed_cleanly = submission_success or resolved_like_success`

### 6.4.4 task_summary

调用 `ActionLogger.end_task(task_closed_cleanly, summary=...)`

注意当前实现：

1. `total_actions` 固定为 `0`
2. 这是 `ActionLogger.end_task()` 里的 TODO，当前还没真实统计

### 6.4.5 读取 task actions

读取：

1. `subgraph = observation_kg.get_task_subgraph(task_id)`
2. `task_actions = graph_store.get_task_actions(task_id)`

如果前面在线没有写入 action，这里可能为空。

### 6.4.5.1 `run_done_context` 是怎么来的

`handle_run_done()` 会先调用 `_build_run_done_context()` 组装 extractor 的额外上下文，来源并不神秘，基本都是从已落库 `task_actions` 做启发式拼装：

1. `changed_files`
   - 从每个 action 的 `touched_files` 合并去重得到
   - 但当前 Hook 主链路很少填 `touched_files`，所以这里经常是空

2. `ad_hoc_script_names`
   - 从 `action_text` / `intent_text` 里用正则抓 `test_*.py` / `reproduce_*.py`

3. `validation_summary.commands`
   - 只有当某个 action 的 `action_type == RUN_TEST` 时才默认补 `pytest -q`
   - 当前主链路大部分 action 都是 `TOOL_CALL`，所以这一项也常常为空

4. `task_problem_excerpt`
   - 来自 `task_context["instruction"]` 或 `task_context["summary"]`

5. `patch_summary`
   - 只包含很粗的：
     - `changed_file_count`
     - `has_submission`
     - `exit_status`

这意味着 extractor 在很多真实运行里更多依赖：

1. `action_text`
2. `intent_text`
3. `stderr`
4. trace 结构

而不是高保真 diff/test/touched_files 证据。

### 6.4.6 belief update 分支

仅在以下条件执行：

1. `subgraph` 存在
2. `submission_success` 为假

分支：

1. `resolved_like_success` -> `outcome="success"`
2. 其他未 clean close -> `outcome="fail"`

如果 `submission_success=True`：

1. 不更新 belief
2. `belief_update["skipped_reason"] = "submission_pending_official_eval"`

### 6.4.7 abstract experience 基础提取

只要 `task_actions` 非空，就会调用 `AbstractExperienceBuilder.build_from_task()`

它会：

1. 生成 task-level pattern
2. 为每个失败 error type 生成 error-specific pattern

如果 `submission_success=True`，还会调用 `_trim_submission_candidate_experiences()`：

1. 尽量只保留 1 条非 planning/workflow 模式经验；
2. 没有的话退化为 1 条 fallback。

写入时 metadata 会打上：

1. `promotion_state = candidate`
2. `evidence_stage = submission/trial_local`
3. `experience_polarity = neutral/positive`
4. source instance / run / attempt / event id

### 6.4.8 unresolved 时的 RCA + failure card

如果 `task_closed_cleanly=False`：

1. `rca_report = RCAAgent.analyze_task_failure(task_id)`
2. `failure_card = FailureCardBuilder.build_from_unresolved(...)`
3. `graph_store.upsert_failure_card_v2(...)`
4. 如果 RCA 里有 corrective actions，再写成多个 `repair_pattern_v2`
5. 再把 repair pattern IDs 回链到 failure card metadata.links

### 6.4.9 `ExtractionOrchestrator.process_attempt()`

无论 task 是否 clean close，只要 `task_actions` 非空，都会进入 orchestrator。

它总是先生成：

1. `trial_overview`
2. `subblock_analysis`
3. `attempt_summary_v1`

然后根据 `_trigger_reason()` 决定是否继续做 critical-signal 提取：

触发条件：

1. `run_done_unresolved`
2. `run_done_success_with_recovery`
3. `run_done_high_cost`（成功但步数 >= 40）

如果未触发：

1. 仍然返回 `attempt_summary_v1`
2. 但不会生成 extra abstract / repair pattern / failure patch

### 6.4.10 extractor 结果如何回写

如果 extractor `triggered=True`：

1. `abstract_experiences` -> 逐条 `upsert_abstract_experience`
2. `failure_card_patch`
   - 如果前面已有 failure card：打 patch
   - 如果前面没有 failure card 且当前是不 clean close：直接新建一张 card
3. `repair_patterns` -> 逐条 upsert
4. 再把 repair pattern ids 写回 failure card links

### 6.4.11 attempt summary fallback

如果 extractor 没生成 attempt summary，或者根本没有触发：

1. 走 `_build_fallback_attempt_summary()`
2. 仍会生成 `attempt_summary_v1`

### 6.4.12 没有 task_actions 的 unresolved fallback

如果：

1. `task_actions` 为空
2. `task_closed_cleanly=False`

则仍会生成一个 fallback `failure_card_v2`，避免“失败 attempt 什么都没留下”。

### 6.4.13 rw_map 写出内容

`run_done` 最终会把这些 ID 视为 write_ids：

1. abstract experience ids
2. attempt summary id
3. failure card id
4. repair pattern ids

### 6.4.14 `handle_run_done` 的运行结果分支

完整分支可以归纳为：

1. `submission_success=True`
   - 不更新 belief
   - failure card 不生成
   - 抽象经验写成 candidate
   - 等待 official eval

2. `resolved_like_success=True`
   - 更新 belief 为 success
   - 不生成 failure card
   - 可能生成 positive candidate experience

3. `unresolved 且有 task_actions`
   - 更新 belief 为 fail
   - 生成 RCA
   - 生成 failure card
   - 生成 repair patterns
   - extractor 可能再补充 patch 和 abstracts

4. `unresolved 且没有 task_actions`
   - 生成 fallback failure card
   - 生成 fallback attempt summary

5. `active task 丢失`
   - `synthesized_task=True`
   - 仍继续收尾

## 6.5 `apply_evaluation_feedback`

### 6.5.1 触发条件

不是 Hook 自动触发，而是后处理脚本或外部调用触发。

### 6.5.2 输入要求

必须有：

1. `instance_id`

没有则直接返回：

1. `event_handled = official_eval_feedback`
2. `error = missing_instance_id`

### 6.5.3 attempt_id 推断

如果未显式给 `attempt_id`：

1. 尝试从 `run_id` 中匹配 `_attempt_<n>`
2. 转成 `attempt-<nn>`

### 6.5.4 patch_text 获取

优先级：

1. `event_data.patch_text`
2. `patch_path` 指向的文件内容

### 6.5.5 `EvaluationFeedbackProcessor.apply_feedback()` 分支

1. `resolved`
   - 找到 related candidate experiences
   - 全部 mark promoted

2. `infra_failure`
   - 新写一张 infra failure card
   - 不走 suppress/promote 负向经验流程

3. `unresolved` / `incomplete`
   - suppress 相关 candidate experiences
   - 基于 patch risk / validation gap / overexploration 写 negative experiences
   - `unresolved` 时额外写 failure card

### 6.5.6 attempt summary 回写 / 回填

先尝试：

1. `update_attempt_summary_outcome(instance_id, run_id, attempt_id, outcome, eval_ref)`

如果找不到现成 summary：

1. 先构造 fallback summary
2. upsert
3. 再 update outcome

因此官方评测反馈即使晚到、run_id 不一致，也能回填到 attempt summary。

## 7. 当前数据模型：每个对象到底存什么，哪些字段会在主链路里真正被填上

## 7.1 `ProblemFile`

核心字段：

1. `action_id`
2. `task_id`
3. `timestamp`
4. `instance_id / run_id / agent_name / source_event / step_index / trace_id`
5. `action_type / intent_text / action_text / action_family`
6. `inputs / tool_calls`
7. `stdout_ref / stderr_ref / diff_summary_ref / tests_ref / touched_files`
8. `outcome / failure_signature / env_signature`
9. `patch_stats / test_stats / execution_stats`
10. `evidence_index`
11. `embeddings`
12. `epistemic_tags`
13. `metadata`

## 7.2 当前 Hook 主链路里 ProblemFile 实际填充情况

| 字段 | `plan_generated` | `action_error` | 当前说明 |
|---|---|---|---|
| `action_type` | `tool_call` | `tool_call` | 当前主链路都不是细粒度 shell action 类型 |
| `intent_text` | 固定 `"Generate plan for task"` | `thought` | planning 的意图非常泛化 |
| `action_text` | `action` | `action` | 主要证据文本 |
| `action_family` | `planning` | `error_recovery` | 用于检索与 RCA |
| `stderr_ref` | 无 | 有 | action_error 才会保存错误文本 |
| `failure_signature` | 无 | 由 stderr 粗略归一化 | 不是原始 `error_type` 直写 |
| `touched_files` | 通常空 | 通常空 | 当前 Hook 不上传真实 touched files |
| `diff_summary_ref` | 空 | 空 | 当前主链路不采集 diff |
| `tests_ref` | 空 | 空 | 当前主链路不采集 test output |
| `env_signature` | 通常空 | 通常空 | 当前 Adapter 未传 env_info |
| `emb_task_sem` | 常有 | 常有 | 由 `intent_text` 生成 |
| `emb_intent` | 常有 | 常有 | 由 `intent_text` 生成 |
| `emb_error_sig` | 无 | 可能有 | 依赖 failure signature |
| `emb_file_scope` | 通常空 | 通常空 | touched files 为空时无 |
| `emb_tool_output` | 通常空 | 可能有 stderr 摘要 | 依赖证据文件可读 |

### 7.2.1 一个重要现实

当前系统在“代码粒度证据”上仍然偏弱，因为主链路缺少：

1. 真实 diff 写入；
2. 真实测试输出写入；
3. 真实 touched files；
4. 成功 action 的持续落库。

所以当前记忆系统更像：

1. “规划/失败事件记忆 + run_done 后抽象归纳”
2. 而不是“完整执行轨迹事实仓库”

## 7.3 Observation KG

数据结构：

1. `ObservationKG.task_subgraphs`
2. `TaskSubgraph.action_nodes`
3. `TaskSubgraph.edges`
4. `action_to_task`

边类型：

1. `success_next`
2. `fail_retry`

### 7.3.1 当前实现的边语义注意点

`ActionLogger.log_action()` 是按“当前节点 outcome”决定边类型的：

1. 当前 action 成功 -> `last_action -> current_action` 标为 `success_next`
2. 当前 action 失败 -> `last_action -> current_action` 标为 `fail_retry`

这和原始设计里的“失败节点 -> 重试节点”为 `fail_retry` 有偏差。  
所以当前 `fail_retry` 更准确地说是：

1. “前一节点指向当前失败节点”
2. 而不是“失败节点指向修复节点”

这会直接影响 repair chain 的语义解释。

## 7.4 Belief Graph

两类对象：

1. `AttemptBelief`
2. `AtomicBelief`

当前 `update_beliefs()` 的行为：

1. 每个 task 在 run_done 时写一个 `AttemptBelief`
2. 再基于：
   - 最后 action
   - 最新失败 action
   - success chain / retry chain
   生成或更新一个 `AtomicBelief`

类型：

1. success -> `WORKFLOW`
2. fail -> `PITFALL`

它不是复杂统计学习，只是一个轻量的可累计规则库。

## 7.5 `abstract_experience`

这是当前最重要的可复用知识对象之一。

关键字段：

1. `pattern_type`
2. `normalized_pattern_type`
3. `normalized_trigger_family`
4. `normalized_advice_family`
5. `family_id`
6. `abstracted_intent`
7. `success_conditions`
8. `failure_avoidance`
9. `evidence_refs`
10. `source_task_ids / source_event_ids / source_run_ids / source_attempt_ids`
11. `subproblem_type / strategy_label`
12. `prefer_actions / avoid_actions`
13. `applicability_scope`
14. `confidence / support_count`
15. `metadata.promotion_state / experience_polarity / evidence_stage`

## 7.6 `attempt_summary_v1`

用途：

1. 记录同一 instance 上一轮 attempt 的失败策略、最佳局部进展、下一步更优动作
2. 在下一轮 planning 前期注入

## 8. 检索与注入算法：经验为什么会被召回

## 8.1 Query Rewriter

### planning query

输出结构：

1. `query_type`
2. `task_semantic`
3. `context`
4. `env_cluster`
5. `file_scope`
6. `intent_patterns`

### repair query

输出结构：

1. `query_type`
2. `error_type`
3. `error_signature`
4. `current_action`
5. `env_cluster`
6. `action_type`

它当前是规则改写，不是 LLM 改写。

## 8.2 动态预算 `_dynamic_budget`

复杂度定义：

1. `complexity = len(words(current_action)) + len(words(error_message))`

base：

1. `error_recovery/test_failure_fix` -> 10
2. `regression_guard` -> 8
3. 其他 -> 7

bonus：

1. `min(6, complexity // 20)`

导出预算：

1. `subgraph_budget = base + bonus`
2. `recommendation_budget = max(6, min(18, subgraph_budget))`
3. `failure_card_budget = max(2, recommendation_budget // 4)`
4. `repair_pattern_budget = max(2, failure_card_budget)`

## 8.3 结构检索 `SubgraphSelector`

### planning relevance

分数组成：

1. 有 success chain -> `+0.3`
2. 文件范围匹配 -> `+0.3`
3. intent pattern 匹配 -> `+0.2`

### repair relevance

分数组成：

1. 有 failure chains -> `+0.2`
2. error type 匹配 -> `+0.3`
3. action type 匹配 -> `+0.3`

这部分是结构/规则分。

## 8.4 embedding 候选收集

调用 `GraphStore.find_similar_actions()`。

尝试的 view 顺序：

1. 请求 view
2. `emb_task_sem`
3. `emb_intent`
4. `emb_error_sig`
5. `emb_file_scope`

planning 默认最小相似度：

1. `0.28`

repair 默认最小相似度：

1. `0.24`

如果没有任何候选过阈值：

1. 退化为取最前面几条 raw candidates

## 8.5 结构分与 embedding 分融合

融合权重：

1. `structure = 0.55`
2. `embedding = 0.35`
3. `support = 0.10`

`support_score = min(1.0, len(subgraph.action_nodes) / 15.0)`

最终：

`fused = 0.55*structure + 0.35*embedding + 0.10*support`

## 8.6 recommendation 来源拼装顺序

### planning

当前顺序是：

1. `ExperienceDistiller.distill_planning_experience()`
2. `abstract_experience`
3. `failure_card_v2`
4. `repair_pattern_v2`
5. `attempt_summary_v1`
6. 如果前面都不够高价值，再补 1 条 `belief_tip`

### repair

当前顺序是：

1. `ExperienceDistiller.distill_repair_experience()`
2. `belief_repair_hint`
3. `abstract_experience`
4. `failure_card_v2`
5. `repair_pattern_v2`

## 8.6.1 GraphStore 内部 query 打分公式

除了 `MemoryAgent` 自己的融合与重排，底层 `GraphStore` 在查询不同对象时还有自己的评分公式。

### `query_abstract_experiences()`

基础分：

`0.45 * lexical + 0.35 * confidence + 0.20 * support + err_bonus + critical_bonus + state_bonus + context_bonus`

其中：

1. `lexical`
   - 查询文本与经验文本 token Jaccard
2. `support`
   - `min(1.0, support_count / 5.0)`
3. `err_bonus`
   - 查询 `error_type` 与 `failure_avoidance/pattern_type` 匹配时加分
4. `critical_bonus`
   - 与 `metadata.critical_signal` 对齐时加分
5. `state_bonus`
   - promoted / official_eval / positive polarity 会加分
   - candidate / submission 会减分
6. `context_bonus`
   - `subproblem_type` / `strategy_label` 精确匹配时加分

### `query_failure_cards_v2()`

基础分：

`0.45 * lexical + 0.35 * confidence + et_bonus + rca_bonus + critical_bonus`

其中：

1. `et_bonus`
   - 查询 `error_type` 与 card `error_signature.error_type` 对齐
2. `rca_bonus`
   - 有 `root_cause_nodes` 加 `0.1`
3. `critical_bonus`
   - 与 `metadata.critical_signal` 或 `critical_alignment` 对齐时额外加分

注意：

1. 默认 `include_infra=False`
2. 也就是当前主链路检索 failure card 时，默认不会把 infra failure card 注进来

### `query_repair_patterns_v2()`

基础分：

`0.45 * lexical + 0.35 * confidence + et_bonus + support_bonus + critical_bonus`

其中：

1. `support_bonus = min(0.2, support / 20.0)`
2. `critical_bonus` 由 `metadata.critical_alignment` 提供

## 8.7 recommendation 重排 `_dedup_and_rerank_recommendations`

会先按 runtime guard 做过滤：

1. `closure_active` 时压制 workflow / planning loop
2. 命中 blocked action patterns 的 recommendation 被丢掉
3. 如果当前已锁定子问题类型，和当前子问题不一致的 workflow/planning_loop 会被丢掉
4. 如果当前 strategy_label 与某 recommendation 相同且 recommendation 带 avoid_actions，则也可能被丢掉

然后计算：

1. `type_bias`
2. `confidence`
3. `critical_alignment_score`
4. `helpfulness_score`
5. `novelty_score`
6. `family_bonus`
7. `changed_file_overlap_bonus`

其中 type bias 大致偏向：

1. `attempt_summary_v1` +0.18
2. `repair_pattern_v2` +0.16
3. `failure_card_v2` +0.14
4. `abstract_pattern` +0.06
5. `belief_tip` -0.12
6. `legacy_experience` -0.08

高价值 family bonus 偏向：

1. `closure_signal`
2. `negative_strategy`
3. `patch_risk`
4. `validation_gap`

而对：

1. `belief_tip`
2. `workflow_step`
3. `planning_loop`

会施加负偏置。

## 8.8 Attempt Summary 的特殊作用

`_retrieve_attempt_summary()` 有三个关键限制：

1. 必须同 `instance_id`
2. 必须不是当前 `attempt_id`
3. 当前步号必须 `<= 2`

它的目的不是持续注入，而是：

1. 在新 attempt 的 very early stage 提醒“上一轮失败在哪里”
2. 同时把 avoid_actions 写进 Hook runtime guard

这也是阶段6最重要的闭环之一。

## 9. `run_done` 后的学习算法：怎么从一次 attempt 里长出新记忆

## 9.1 `AbstractExperienceBuilder`

### task-level pattern

根据 action 序列推导：

1. `pattern_type`
   - `recover_from_failure`
   - `validate_then_submit`
   - `direct_success_flow`
   - `failure_dominant_attempt`
   - `generic_attempt`

2. `abstracted_intent`
3. `success_conditions`
4. `failure_avoidance`
5. `confidence`
6. `metadata.error_signature/tool_sequence/changed_file_pattern/test_signal`

### error-specific pattern

每种失败 error type 再额外生成一条：

1. `pattern_type = repair_<error_type>`
2. `abstracted_intent = repair_<error_type>_by_narrowing_context_then_retrying_with_adjustment`

## 9.2 `RCAAgent`

处理流程：

1. 找出 outcome=`fail` 的节点
2. 对每个失败节点：
   - classify error type
   - 找 root cause candidates
   - 给每个 candidate 打 decisive score
   - 取前 2 个作为 root causes
   - 构造 propagation chain
   - 生成 corrective_actions 与 preventive_checks
   - 估算 confidence

### decisive score 组成

1. 同 error type -> `+0.45`
2. candidate 自己也是 fail -> `+0.2`
3. touched_files 有交集 -> `+0.2`
4. candidate 发生在 failure 前 -> `+0.1`
5. graph ancestor -> `+0.15`

### 当前限制

1. propagation chain 目前是简化版，不是真实最短路径分析
2. corrective_actions 是模板库 + root cause review

## 9.3 `FailureCardBuilder`

对 unresolved task：

1. 取最后一个失败 action 作为 pivot
2. 生成：
   - `error_signature`
   - `action_trace_snippet`
   - `candidate_fix_actions`
   - `verification_commands`
   - `evidence_refs`
3. 如果有 RCA，就补：
   - `root_cause_nodes`
   - `propagation_chain`
   - `error_module`

### failure class

会尝试判定：

1. `infra_failure_card`
2. `agent_failure_card`

## 9.4 `ExtractionOrchestrator`

### 9.4.1 触发理由

`_trigger_reason()`：

1. 未成功 -> `run_done_unresolved`
2. 成功但中间有失败 -> `run_done_success_with_recovery`
3. 成功且步数 >= 40 -> `run_done_high_cost`
4. 否则不触发 deep extraction

### 9.4.2 规则分析器 `taxonomy.py`

按 step 生成 `StepSignal`：

1. `action/system`
   - 有明确失败 action

2. `planning`
   - planning step 没有验证/test/check 意图

3. `reflection`
   - 连续两步失败且 action 文本完全相同

4. `memory`
   - previous action metadata 里存在 memory_hint_count，但下一步还失败

### 9.4.3 LLM extractor

只有满足这两个条件才启用：

1. `AGENT_MEM_LLM_EXTRACT_MODE` 不是 `off/heuristic`
2. 同时配置了：
   - `AGENT_MEM_LLM_API_URL`
   - `AGENT_MEM_LLM_API_KEY`

LLM 作用：

1. 给 assessments 做补充
2. 优化 critical signal 的 root_cause / correction_guidance

LLM 不是最终 schema writer，只是分析增强器。

### 9.4.4 critical signal

每个 critical signal 包含：

1. `critical_step`
2. `critical_module`
3. `error_type`
4. `root_cause`
5. `cascading_effects`
6. `correction_guidance`
7. `confidence`

如果完全没有 assessments 且本轮失败：

1. 会退化成一条 `unclassified_failure` critical signal

### 9.4.5 模板映射

每个 critical signal 会映射成：

1. 1 条 `abstract_experience`
2. 1 个 `failure_card_patch`
3. 多条 `repair_pattern_v2`

此外 strategy observations 还能再额外映射出：

1. `negative_strategy_*`
2. `closure_signal_*`
3. `validation_gap_*`
4. `patch_risk_*`

### 9.4.6 strategy observations 的来源

两部分：

1. LLM 输出的 `strategy_observations`
2. 规则启发式 `_heuristic_strategy_observations()`

启发式触发条件包括：

1. 步数很高且 validation 次数多 -> `closure_signal_over_exploration`
2. ad-hoc 脚本数 >= 2 -> `negative_strategy_ad_hoc_script_sprawl`
3. target path 已定位却扩到别的 module
4. 一直在验证但没有 code edit

### 9.4.7 质量门 `_apply_quality_gate()`

拒绝条件：

1. 没有 `evidence_refs`
2. `confidence < AGENT_MEM_EXTRACT_MIN_CONFIDENCE`
3. official eval unresolved 但不是 negative polarity 的 abstract
4. planning_rule 过于泛化

通过后才真正回写。

## 14. 当前实现的关键限制与偏差

这部分不是设计愿景，而是当前代码现状。

### 14.1 在线主链路不是完整动作采集

当前主链路只稳定采集：

1. `plan_generated`
2. `action_error`
3. `run_done`

所以它更像“事件级记忆系统”，不是“全执行轨迹事实系统”。

### 14.2 成功动作没有持续写库

`handle_action_success()` 存在，但 Hook 不调用。  
因此：

1. success_next 边只来自部分 planning 节点；
2. 真实成功执行动作在当前主链路里大多缺席。

### 14.3 `fail_retry` 边语义和设计稿不完全一致

当前实现按“当前节点 outcome”决定边类型，导致 `fail_retry` 不是标准的“失败节点 -> 修复节点”。

### 14.4 当前主链路里 file/diff/test 证据偏少

因为 Hook 没把真实 diff/test output/touched_files 传给 Adapter。

### 14.5 `preventive_rules_v2` 当前只写不读

它能被 action_error 微提取生成，但在线检索链没有查询它。

### 14.6 `ActionLogger.end_task()` 的 `total_actions` 还是 TODO

当前 `task_summary.total_actions` 固定是 `0`。

### 14.7 failure signature 比较粗

`action_error` 的 `event_data.error_type` 不会直接写进 `ProblemFile.failure_signature.error_type`，而是被 stderr 第一行重新粗归一化。

### 14.8 `gate_hard_fail` 目前只是日志，不是硬中断

即使门禁失败，也只会写 `memory_gate_hard_fail`，不会强制终止运行。

### 14.9 部分仓内模块是旧实现或旁路实现

当前主链路没直接用：

1. `retrieval/retriever.py`
2. `retrieval/embedder.py`
3. `processing/error_handler.py`

### 14.10 存在字段级实现偏差风险

例如：

1. `FailureCardBuilder` 的某些分支会尝试读取当前 `FailureSignature` schema 中并未正式定义的字段；
2. 这说明部分代码仍处于阶段性演化状态，文档和实现要持续对齐。

## 15. 对“当前 AgentMem 到底学到了什么”的最终归纳

基于当前代码，AgentMem 真正稳定学到并能闭环复用的，不是“每个代码动作的完整回放”，而是以下四类对象：

1. **Attempt Summary**
   - 给下一轮同实例尝试提供“上一轮失败策略”和 runtime guard

2. **Abstract Experience**
   - 提供可跨任务检索的抽象经验

3. **Failure Card**
   - 沉淀未解决失败、错误签名、候选修复和验证命令

4. **Repair Pattern**
   - 给 error 阶段提供更直接的 fix template

Hook 再把这些对象转成“少量、高价值、限预算、带冷却”的 hints 注入给当前 agent。  
阶段6真正新增和强化的，是：

1. attempt_summary 驱动的 runtime guard
2. negative/closure/validation 类型经验的优先注入
3. official eval 后 promote/suppress 的闭环
