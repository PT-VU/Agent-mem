# 阶段6综合代码升级建议（基于经验注入总结2与当前代码现状）

## 0. 目标

这份建议的目标不是“再加更多功能”，而是把当前 AgentMem 从“能记录一些经验”推进到“能基于真实外部反馈积累高质量经验，并减少错误 patch 路线复用”的状态。

核心目标只有 4 个：

1. **把 `submitted` 和 `resolved` 彻底分开**，不再把提交 patch 当成真正成功。
2. **把官方评测结果回流进经验系统**，让错误 patch 也能变成经验，而不是只积累“自我感觉成功”的经验。
3. **压制泛化过头的 planning / workflow 提示**，让注入更偏向 task-grounded repair / validation / negative strategy。
4. **用最少的代码改动实现这些能力**，尽量复用现有对象和链路，避免新造一套系统。

---

## 1. 设计原则

### 1.1 先解决真问题，不扩散复杂度

从 `经验注入总结2.md` 和当前 smoke 结果看，真问题不是：

- 没有 LLM
- 没有图存储
- 没有提取
- 没有注入

真问题是：

- 提取发生得太早，且没有外界反馈
- 错误 patch 没被当成失败经验
- 注入内容里有太多泛 workflow 提示
- 反馈闭环把“动作执行成功”误当成“经验有效”

因此升级建议必须围绕这 4 个点，而不是再堆更多中间层。

### 1.2 能复用现有 schema 就不要再加新 schema

当前已有对象：

- `abstract_experience`
- `repair_pattern_v2`
- `failure_card_v2`
- `preventive_rule_v2`
- `belief_graph`
- `experience_rw_map.jsonl`

建议：

- **不要再新造一整套“经验数据库”或“新图结构”**
- 只在现有 schema 上增加最少量字段和状态
- 真正需要新增的，只新增一个轻量的“评测回流处理模块”

### 1.3 在线链路只做轻量帮助，重经验提取放到评测后

建议把系统分成两条链：

#### 在线链路（求解时）

只做：

- 检索
- 去重
- 少量注入
- 轻量 feedback

#### 离线链路（评测后）

做：

- official resolved / unresolved 回流
- 失败 patch 经验提取
- 负策略经验沉淀
- 经验升权/降权

这样流程更干净，也更符合“经验要基于真实反馈”这个目标。

## 2. 当前代码的主要结构性缺陷

### 2.1 `run_done submitted` 被当成 success，导致错误 patch 不会沉淀为失败经验

当前 trace 已经证明：

- 4 个 instance 都 `submitted`
- 官方 `resolved = 0`
- 但 `failure_card_v2.generated = false`，理由是 `task_success`

这会直接导致：

- 错误 patch 路线不写入失败经验
- 后续任务仍可能继续复用相似错误思路

这是当前最优先要改的点。

### 2.2 提取 prompt 没看到 issue / diff / target test / official eval

当前 `llm_extractor.py` 的 prompt 主要只看压缩 trajectory：

- `step_index`
- `action_type`
- `action_family`
- `outcome`
- `intent_text`
- `failure_type`

它没看到：

- 原始问题描述
- patch diff 语义
- 变更文件模式
- 目标测试或回归验证结果
- 官方 resolved / unresolved 结果

所以它很容易抽出：

- planning loop
- validation gap
- generic correction guidance

但很难抽出：

- 这是一类 suppression patch
- 这是 broad exception swallowing
- 这是 over-engineered patch
- 这是“自建脚本验证通过但官方 unresolved”的失败策略

### 2.3 当前反馈机制的“effective=true”语义不可靠

现在 `memory_intervention_feedback` 的有效性主要看：

- 注入后几步是否 `action_success`

这太局部，会误判：

- 命令跑通
- 文件打开
- 脚本执行成功

为“经验真的帮助解决了问题”。

但本次 smoke 已经证明：

- 多个 intervention 被标记为 `effective=true`
- 最终官方 `resolved=0`

所以这条反馈链现在不能作为经验升权的主依据。

### 2.4 当前注入仍被 workflow / belief / planning family 污染

当前 `selected_family_ids` 中反复出现：

- `belief_tip:*`
- `workflow_step:*`
- `planning_loop:*`

这些可以作为辅助提示，但不应占用主注入预算。

当前更需要被优先注入的是：

- task-specific repair pattern
- validation guard
- negative strategy
- patch risk warning

### 2.5 当前系统缺少真正的负策略经验

当前系统有 `failure_avoidance`，但它仍然偏模板化。

系统缺少的是：

- 对某类 task / subtask / patch style 的失败总结
- 这种总结不是一句抽象警告，而是“这个思路已经在真实评测里失败过”的结构化记忆

这是 resolved rate 提升的关键能力之一。

---

## 3. 总体升级方向：只做一条简单而正确的主链

建议的目标主链如下：

### 3.1 在线求解链路

`retrieve -> dedup -> inject -> solve -> submit`

要求：

- 只注入少量高价值记忆
- 不在在线链路里做重抽取
- 不把局部 success 当成长期 success

### 3.2 评测后回流链路

`official_eval -> classify outcome -> extract experience -> update memory`

要求：

- `resolved` 写正经验
- `unresolved` 写负经验 / patch 风险 / 验证缺口经验
- `incomplete / infra failure` 单独归档，不污染主记忆池

### 3.3 经验写入后的状态机

建议引入最小状态，而不是加新 schema：

在现有经验对象 `metadata` 中增加：

- `evidence_stage`: `trial_local | submission | official_eval`
- `experience_polarity`: `positive | negative | neutral`
- `promotion_state`: `candidate | promoted | suppressed`

这样可以不新增新对象类型，只通过 metadata 控制经验是否参与主检索。

---

## 4. 具体代码升级建议（按模块）

## 4.1 `agent_mem/integration/sweagent_adapter.py`

### 目标

把 `run_done submitted` 和“真正成功”分离，停止在 trial 结束时把 `submitted` 当成最终成功。

### 当前问题

- `task_success` 语义过早
- `failure_card_v2` 在 `submitted` 情况下被跳过
- 结果是错误 patch 不产出失败经验

### 建议改法

#### 改动 1：把当前 `success` 语义拆成两层

在 adapter 内部引入两个明确概念：

- `submission_success = (exit_status == 'submitted' and has_submission == True)`
- `evaluation_success = unknown`（trial 阶段默认未知）

不要在 `run_done` 里直接把 `submission_success` 当成最终 success。

#### 改动 2：`run_done` 只写“候选经验”，不写最终成功经验

具体做法：

- `run_done` 生成的 `abstract_experience / repair_pattern` 默认标记：
  - `metadata.evidence_stage = 'submission'`
  - `metadata.promotion_state = 'candidate'`
- 不再用 `task_success` 跳过 failure 语义
- 对高风险 patch，即使 submitted，也允许生成 `failure_card_v2` 候选卡

#### 改动 3：加入“评测后回流入口”

在 adapter 层增加一个轻量方法，例如：

- `apply_evaluation_feedback(instance_id, eval_result, patch_path, summary)`

它不参与在线求解，只用于实验后处理。

### 为什么这样最简洁

- 不需要推翻现有 adapter
- 不需要重写 hook
- 只是把 success 语义拆开，并为离线评测回流留一个接口

---

## 4.2 新增 `agent_mem/processing/evaluation_feedback.py`

### 目标

把官方评测结果转成经验写回，而不是让评测和记忆系统完全脱钩。

### 为什么需要新增这个模块

这是当前唯一值得新增的模块，因为它解决的是架构断点：

- 现在 memory 系统不知道 official unresolved
- 所以需要一个最小的新入口去做“评测结果 -> 经验写回”

### 模块职责

输入：

- `instance_id`
- `resolved / unresolved / incomplete / infra_failure`
- patch diff
- target test result（如果有）
- task summary
- 现有 graph_store 句柄

输出：

- 更新后的 `abstract_experience`
- 必要时新增 `failure_card_v2`
- 必要时新增 `repair_pattern_v2`
- 对已有 candidate memory 做 promotion / suppression

### 简化原则

不要做复杂流水线，只做 3 件事：

1. `resolved`
   - 给相关经验升权
   - `promotion_state -> promoted`
2. `unresolved`
   - 写一条负经验
   - 写一条 patch risk / validation gap 经验
3. `infra_failure`
   - 只归档，不参与主检索

### 最小输出建议

无需新增 schema，优先复用：

- `abstract_experience`：写负策略或验证缺口总结
- `failure_card_v2`：写 unresolved failure card
- `repair_pattern_v2`：仅保留高价值修复动作模板

---

## 4.3 `agent_mem/processing/llm_extractor.py`

### 目标

让 LLM 不只看到“行动摘要”，而能看到足够多的信息去判断：

- patch 风格是否危险
- 验证是否失真
- 哪类思路已经失败

### 当前问题

- prompt 没看到 issue / diff / test / eval
- 只看 `actions[:80]`
- 输出只聚焦 `critical_signal`

### 建议改法

#### 改动 1：扩展输入，但不要扩成一大坨

新增到 `user_prompt` 的字段：

- `task_problem_excerpt`
- `changed_files`
- `patch_summary`
- `validation_summary`
- `submission_status`
- `official_eval_status`（在评测后回流路径中）

不要把完整 diff 全塞进去，先做一个简短 `patch_summary`：

- 是否扩大 API
- 是否 broad catch exception
- 是否 add quiet / suppress
- 是否改多个语义分支

#### 改动 2：把输出从“只找 critical signal”改成“两层输出”

建议让 LLM 输出：

- `critical_signals`
- `strategy_observations`

其中 `strategy_observations` 最少包含：

- `strategy_type`
- `why_failed_or_risky`
- `evidence`
- `recommended_avoidance`
- `confidence`

#### 改动 3：去掉硬编码只看前 80 步

保留简洁做法：

- 不用全量轨迹
- 改成“头部关键步 + 中间异常步 + 尾部提交步”的摘要拼接

例如：

- first 15
- error-related 20
- last 15

这样比单纯 `[:80]` 更稳，也不需要引入复杂摘要器。

---

## 4.4 `agent_mem/processing/extraction_orchestrator.py`

### 目标

让提取结果从“planning 元经验主导”转向“task-grounded repair / validation / negative strategy 主导”。

### 当前问题

- 当前 bucket 仍然容易保留 planning_rule
- `quality_gate` 太弱，只看 evidence 和 confidence
- 没有 patch risk / strategy failure 的映射

### 建议改法

#### 改动 1：新增 3 个 bucket，但仍复用现有对象

在 `_classify_abstract_bucket()` 中新增：

- `negative_strategy`
- `patch_risk`
- `validation_gap`

但不要新建 schema，只体现在：

- `pattern_type`
- `normalized_pattern_type`
- `metadata.experience_polarity`

#### 改动 2：进一步压 planning_rule

当前策略已经比以前好，但还不够。建议：

- `planning_rule` 默认最多 0~1 条
- 若同 attempt 已有 `negative_strategy` 或 `validation_gap`，则 planning_rule 直接不写

#### 改动 3：加强 quality gate

增加以下拒收条件：

- guidance 仅包含 workflow/plan 字样且没有 task-specific evidence
- patch 风格被识别为 suppressive 或 broad catch，但没有 target validation
- `submission_success=True` 且 `official_eval_status=unresolved` 时，不能当正经验写入

#### 改动 4：把“错误 patch 经验”写成 abstract experience

例如：

- `pattern_type = negative_strategy_suppressive_fix`
- `failure_avoidance = ['do_not_use_quiet_true_as_primary_fix']`

这是比新造 schema 更简单的做法。

## 4.5 `agent_mem/retrieval/memory_agent.py`

### 目标

让注入真正服务于 solved，而不是继续给 agent 喂太多 workflow 提示。

### 当前问题

- `belief_tip:*` / `workflow_step:*` 仍在占注入预算
- retrieval 排序里 task-grounded 与 workflow 风格没有足够拉开差距

### 建议改法

#### 改动 1：新增 family 黑名单/冷启动白名单

最简单做法：

- 默认不注入 `belief_tip:*` 和 `workflow_step:*`
- 只在“当前任务没有任何 repair/validation/negative strategy 命中”时，允许注入 1 条 workflow 提示

#### 改动 2：提升以下 family 的优先级

- `repair_pattern:*`
- `validation_gap:*`
- `negative_strategy:*`
- `patch_risk:*`

#### 改动 3：加入 changed-file / module overlap 加权

优先给和当前 touched files 或当前 module 更接近的经验更高权重。

这一步不需要复杂 embedding 变更，只要在现有排序上加一个 overlap bonus 即可。

---

## 4.6 `bridge_hook.py`

### 目标

保持 hook 简洁，只负责注入编排，不负责复杂策略判断。

### 当前问题

- hook 现在已经做了很多 gate / cooldown / selection 工作
- 再继续在 hook 里加复杂逻辑会变脏

### 建议改法

hook 层只保留：

1. family cooldown
2. 每 family 每 attempt 注入上限
3. 注入预算分配

建议的最小预算策略：

- 每次最多注入 3 条
- 注入顺序固定为：
  1. 1 条 repair/negative strategy
  2. 1 条 validation gap
  3. 若还空，再补 1 条 workflow

不要在 hook 里继续堆复杂评分器。评分逻辑留在 retrieval。

---

## 4.7 `agent_mem/storage/graph_store.py`

### 目标

最小代价支持候选/正式经验、正/负经验、评测后晋升/压制。

### 建议改法

在现有对象 metadata 上增加字段，不新增新表：

- `experience_polarity`
- `promotion_state`
- `evidence_stage`
- `official_eval_refs`

然后新增最小几个辅助方法：

- `mark_experience_promoted(experience_id, eval_ref)`
- `mark_experience_suppressed(experience_id, eval_ref, reason)`
- `append_official_eval_ref(experience_id, eval_ref)`

这样就够了，不需要重写 graph_store。

---

## 4.8 `experiments/common/*` 与实验脚本

### 目标

把测试流程改成正确顺序：

`run single instance -> official eval -> extract/update memory -> next run`

### 当前问题

现在的流程是：

- 先跑很多 instance
- trial 结束就提经验
- 之后才知道 resolved/unresolved

这导致经验系统先学到的是“自我感觉成功”，不是“外部确认后的结果”。

### 建议改法

#### 单实例评测流程脚本

新增或改造一个简单脚本：

- `run_one_withmem_then_eval_then_extract.sh`

流程：

1. 跑 1 个 instance
2. 立刻跑官方 eval
3. 调 `evaluation_feedback.py`
4. 更新 graph_store
5. 再开始下一个 instance

#### 小批量流程脚本

full50 正式跑时也建议保留窗口，但窗口内按 instance 串行反馈：

- 窗口仍是 25
- 镜像预下载/清理逻辑保留
- 但经验提取不要只在窗口末尾做，要在每个 instance 的官方评测后做

这样虽然略慢一点，但这是目前最有价值的慢。

---

## 5. 应该删除或降级的冗余部分

### 5.1 降级 `belief_tip:*` 和 `workflow_step:*` 的主注入地位

它们可以留在存储里，但不该继续占主预算。

### 5.2 停止把局部 `action_success` 当作长期有效反馈

可以保留为短期信号，但不能再作为主升权依据。

### 5.3 不要再扩更多“计划类经验”模板

当前 planning 类经验已经很多，继续增加只会污染检索。

### 5.4 不新增第二套存储系统

不要为了“候选经验池”再造新数据库。用：

- 现有 `abstract_experience`
- 加 `promotion_state`

就足够了。

### 5.5 不在 hook 中继续堆复杂业务判断

hook 只保留调度、预算、冷却。复杂判断留给 retrieval 和 post-eval。

## 6. 推荐的最小施工顺序

## WP-1：修正 success 语义

目标：

- `submitted != resolved`

改动：

- `sweagent_adapter.py`
- `graph_store.py`

- `run_done` 后生成的是 candidate 经验，不是最终成功经验

## WP-2：接入 official eval 回流

目标：

- unresolved 能写入失败经验

改动：

- 新增 `evaluation_feedback.py`
- 改实验脚本

验收：

- 一个 `submitted but unresolved` 实例会在 graph_store 中新增负经验或 failure card

## WP-3：升级 LLM prompt

目标：

- prompt 能看到 issue/diff/test/eval 摘要

改动：

- `llm_extractor.py`
- `extraction_orchestrator.py`

验收：

- 提取结果里出现 task-grounded negative strategy / patch risk / validation gap，而不只是 planning loop

## WP-4：压制 workflow/belief 注入

目标：

- 主预算只给高价值经验

改动：

- `memory_agent.py`
- `bridge_hook.py`

验收：

- `selected_family_ids` 中 workflow/belief 比例显著下降

## WP-5：重构 feedback 语义

目标：

- 不再把局部动作成功当成长期有效

改动：

- `bridge_hook.py`

验收：

- feedback 区分 short-term / eval-backed

## 7. 测试建议

## 7.1 单元测试

### `llm_extractor.py`

- 给定 issue + patch_summary + validation_summary，能输出 `strategy_observations`
- 长轨迹摘要逻辑不丢关键尾部步骤

### `extraction_orchestrator.py`

- `submitted unresolved` 不会被写成正经验
- `negative_strategy` / `validation_gap` / `patch_risk` 可以映射为 abstract experience
- planning_rule 在高价值 bucket 存在时被压制

### `memory_agent.py`

- workflow/belief family 默认降权
- repair/validation/negative strategy family 提权

### `graph_store.py`

- `promotion_state` / `experience_polarity` / `evidence_stage` 读写正确

## 7.2 集成测试

### 单实例闭环测试

跑 1 个 instance：

1. with_mem 求解
2. 官方 eval
3. 回流提取
4. 检查 graph_store 中是否新增：
   - unresolved failure card 或 negative strategy memory

### 二次尝试测试

同一个 instance 跑两次：

- 第一次 unresolved 后
- 第二次检索是否能读到对应负经验
- 是否减少相同 patch 风格或相同验证缺口

## 7.3 指标验收

至少增加以下指标：

- `submitted_unresolved_instances`
- `negative_strategy_written`
- `official_eval_backed_memory_count`
- `workflow_family_injection_ratio`
- `validation_family_injection_ratio`
- `patch_risk_memory_count`

真正要看的不是“经验条数更多”，而是：

- 重复错误思路是否减少
- target validation 是否更早出现
- workflow 注入占比是否下降
- resolved rate 是否提升

---



这些事做完，系统就会从：

- “只会从 trial 内部局部成功里学”

变成：

- “开始能从真实失败里学，并减少错误路线复用”

这才是当前最有希望直接提升 resolved rate 的升级方向。
