0. 对SWE-bench/PDDL_work_mem/02_task_management/phase_history/阶段7/AgentMem_v2_framework_design.md的评论：
这份评审很到位，而且比我前面的判断更“工程落地化”。

我读完后的结论是：

1. 它抓住了 v2 现在最关键的问题

不是“方向错”，而是设计稿把未来形态写得太完整，和当前代码基线之间还差 3 个硬前提：

subtask 边界契约

高保真事实采集链

可落地的存储迁移方案

这三个点，基本就是从“论文式架构”到“能上线跑”的真实断层。评审原文说得很清楚：v2 可行，但必须改写成**“分层投影 + 旁路增量”**，而不是直接拿新语义替换旧主链路。

2. 它对当前系统的判断，和 repeat-10 证据是闭合的

评审的核心诊断是：

当前系统确实能改行为，也确实能带来局部成功

但成功路径没有“粘住”

长期增长主要是 repair_patterns_v2 和 workflow/checklist 类对象

preventive_rules_v2 基本没进入主读取闭环

这个判断和 repeat-10 分析完全对齐。repeat-10 里两次成功都更像“重新解出来”，而不是“复用了已存的代码级不变量”；成功后的检索反而更吵、更泛，且没有学到 data.start_line / header_rows 这类决定性修复语义。

3. 它给的“最佳融合姿势”我基本赞同

评审最有价值的一点，是把融合路线收敛到了一个非常稳的方案：

保留阶段6主链路

新增 sidecar 长期层

让阶段6对象先充当 v2 的过渡语义层

消费层继续走现有 on_model_query 注入点

它甚至把映射关系写得很清楚：Runtime Controller、Attempt Summary 保留；Subtask Instance 先由 run_done 投影生成；Episode Ledger 先做 append-only JSONL；Compiler Cards 出来后仍走现有注入路径。这个方案比“直接上显式 subtask turn 协议”要稳得多。

4. 它最重要的纠偏，是把“planner 显式 subtask”从前提降成了目标

这点我觉得非常对。

你主设计文档里把“每个子任务由 planning 显式创建、每个子任务一个独立 dialog turn”写成了核心机制。这个从研究设计上很干净，但从当前工程现实看，评审指出：

现在并没有这个契约

现有主链路核心事件还是 plan_generated / action_error / run_done / official_eval_feedback

如果强推 subtask_start / subtask_end / abort / recheck，会破坏低侵入性、延迟预算和数据兼容性

所以它建议：先支持 projected_subtask，再考虑 declared_subtask。我认为这是对的，也是你现在最应该吸收进 v2 设计稿的改写。

5. 它比我之前的建议更进一步的一点：明确要求“热路径 / 冷路径”分离

这个非常重要。

评审直接指出，不能把 subtask_end 提取、失败归因、冲突分析都塞进热路径，否则在线性能会先崩；因此应该拆成：

subtask_end_hotpath：只记事实、只做轻量 tagging

subtask_end_coldpath：异步或 run_done 后统一做 LLM 归因

这比单纯说“在线/离线分层”更可执行。

6. 它对主设计文档的最大修正意见，也很准确

你的主设计文档本身是好的，特别是：

把 v2 定位成“长期 episodic search graph + 短期 runtime controller”

明确保留 on_model_query、runtime guard、official eval gating

明确了长期层/短期层/信用层分工

这些方向没问题。

但评审指出一个关键问题：它现在更像“理想架构文档”，还不是“工程架构文档”。尤其缺：

事实层证据怎么来

新对象放哪里

attempt 级 official eval 怎么分摊到 subtask/path/prototype

compiler 的缓存/失效

subtask 粒度实验怎么切

这些批评都成立。

7. 我会怎么吸收这份评审

我会把它当成对 v2 设计稿的“工程降噪版”，核心改动有 4 条：

第一，把 v2 的默认路线改成：

Phase A：补事实层

Phase B：run_done 投影出 Episode Ledger + Subtask Instance

Phase C：把旧对象先编译成 PlanHintCard / SubtaskRiskCard / RetryHintCard / ClosureGuardCard

这其实就是评审给的推荐实施顺序。

第三，把 “Episode Ledger / 新对象存储” 默认落到 sidecar JSONL，先别侵入现有 GraphStore/ObservationKG。

第四，把 v2 的最小 DoD 收窄到评审给的那 7 条，不再一开始就追求完整 prototype/compiler 体系。

我的最终判断

这份本地 codex 评审是高质量的，而且应该被你吸收到主设计文档里，作为“工程融合修订版”的主线。

一句话概括它的价值：

你的 v2 设计稿解决了“要去哪里”，
这份评审解决了“怎么从现在这套代码走过去而不把主链路搞崩”。

# 一、可以直接移除或停用，而且大概率**不影响当前有效果**的部分

## 1. `preventive_rules_v2` 这条生成链，当前可以先停掉

这是我认为最明确的一项。

原因很直接：

* 评审明确写了，`preventive_rules_v2` **仍然基本不进入主读取闭环**，并且建议“不要先强化生成，先把已有对象真正接入读取”。
* 当前架构说明也明确说了，`preventive_rules_v2` **当前只写不读**。
* repeat-10 里最终统计也是 **0 preventive rules**，说明它既没形成稳定压缩对象，也没成为有效的主消费对象；反而系统主要在堆 `repair_patterns_v2`。

**建议**：
把 `preventive_rules_v2` 从当前主生成链里直接停掉，或者至少默认关闭，只保留一个离线实验开关。
这不会伤到你当前已经证明有效的部分，因为当前有效部分主要来自：

* attempt summary
* failure cards
* repair patterns
* runtime guard / closure / injection

而不是 preventive rules。

---

## 2. 旧的、未进主链路的检索/处理旁路模块，可以先清理出主工程关注面

当前架构说明已经明确指出，主链路**没直接用**这些模块：

* `retrieval/retriever.py`
* `retrieval/embedder.py`
* `processing/error_handler.py` 

如果这些模块现在既不参与主读取闭环，也不是你接下来 v2 sidecar 方案的必需件，那它们至少应该：

* 从“主架构叙事”里移除
* 从默认运行路径里排除
* 从测试矩阵里降级

**注意**：我这里说的是“从主工程复杂度里移除”，不是一定删文件。
最稳妥的做法是先把它们标为 **legacy / dormant**，不要让它们继续污染你对系统真实结构的判断。

---

## 3. `gate_hard_fail` 如果一直只是日志，可以先别把它当正式模块维护

当前文档明确说：`gate_hard_fail` **目前只是日志，不是硬中断**。

这类模块最容易制造复杂度幻觉：

* 设计里看起来有一层“强门禁”
* 实际上对 agent 行为没形成真实控制

如果它现在只是记日志，没有进入决策闭环，那就不该继续占据架构心智负担。
建议两种二选一：

* **要么真正做成 hard stop / strong gate**
* **要么暂时降级成纯 telemetry，不再算方法模块**

# 二、可以保留底座，但应当**停止继续扩张**的部分

## 4. `repair_patterns_v2` 的继续扩张，应该马上收缩

repeat-10 的证据已经很明确：

* 一次 case 跑完后，`repair_patterns_v2` 长到了 **61**
* `preventive_rules_v2` 还是 **0**
* 这说明系统在积累很多低支撑 repair 建议，但没有压缩成稳定策略。

而且评审也已经指出：

* 当前系统的长期增长主要体现在 `repair_patterns_v2` 和 workflow/checklist 类对象
* 不是 bug-specific invariant。

这意味着 `repair_patterns_v2` 不是该删光，而是要**停止无节制增长**。
你可以保留它作为过渡语义层，但不应该再继续把它当“默认最重要的长期经验对象”去扩展。

**建议**：

* 保留读取
* 缩减生成
* 做聚类/近重复合并
* 把它收敛成 compiler card 的输入材料，而不是长期终态对象

这也和评审建议一致：旧对象先映射成 `PlanHintCard / SubtaskRiskCard / RetryHintCard / ClosureGuardCard`，而不是继续无限长。

---

## 5. `failure_card_v2` 的“重复写入近似同义卡”应尽快停掉

repeat-10 里很明确：

* unresolved attempt 基本都会再写一个 failure card
* 很多卡本质上重复在说同一件事：
  `evaluation_unresolved` / `reproduce_the_failing_path_with_target_validation_before_next_patch`
* 这种重复负反馈增加了噪声，但没有更深层 patch variant explanation。

所以 `failure_card_v2` 不是没用，但**重复写近同义 failure card** 这条链要收缩。
这是低风险减复杂度点。

**建议**：

* 保留 failure card 类型
* 删除“每次 unresolved 都默认新建一张近似卡”的策略
* 改成：

  * merge/update existing cluster
  * 或只写 delta failure

这样能明显减噪。

---

## 6. “success-like flow” 这类污染性抽象，建议直接移除

repeat-10 明确点名了一个危险对象：

* `direct_success_flow`
* 它把 `run_done submitted` 这种 **official eval unknown** 的状态抽成了 success-like experience
* 后续还被标为 `template_polluted: true`、`suppression_reason: official_eval_unresolved`。

这种对象是高复杂度、低可信度、强污染源。
我会直接建议：

**把所有“官方评测未确认前的成功抽象”从主经验生成里移除。**

repeat-10 的结论也明确建议：
**不要把 `run_done submitted` 当 success-like。**

# 三、可以延后，不该现在进入主工程复杂度的部分

## 7. `Path Segment / Prototype / Skill Compiler` 现在都不该进入主实现复杂度

这一点评审已经说得非常直白：

* 最简单有工程价值的做法不是直接上完整 `Subtask Graph + Path Segment + Prototype + Compiler`
* 而是先补事实层，再升格现有对象，再最后做这些。

并且评审明确要求：

* `Prototype / Skill Compiler` **必须后置**
* 否则只是把噪声压缩成更难排查的噪声。

所以从“本地工程里哪些可以先移除复杂度”的角度：

* **Path Segment**
* **Prototype**
* **完整 Skill Compiler**

都不应该现在作为正式主模块推进。
它们可以保留在设计文档里，但不该进入当前工程的默认复杂度预算。

---

## 8. 显式 `subtask_start / subtask_end / subtask_abort / subtask_recheck` 在线协议，当前不要上

评审已经明确指出：

* 当前主链路只有 `plan_generated / action_error / run_done / official_eval_feedback`
* `subtask_*` 事件协议还不存在
* 把它作为默认前提会破坏低侵入性和延迟预算。

因此，这部分不只是“延后”，而是**当前应该从默认实施计划里移除**。
先用 `run_done` 投影 `subtask_instance`，而不是强推 planner 显式 subtask 协议。

---

## 9. 在线 `subtask_end` LLM 归因，不该放进热路径

评审的建议非常明确：

* `subtask_end_hotpath`：只记事实，轻量 tagging
* `subtask_end_coldpath`：异步或 run_done 后做 LLM 归因。

所以如果你问“哪些部分可以去掉而不影响效果”，
这里更准确地说是：

**把“在线逐子任务 LLM 深分析”从当前工程计划里移除，不会伤到当前有效果，反而能降低性能风险和复杂度。**

评审明确建议继续把它作为最近一轮 briefing card 保留。

这是你整个系统里最靠谱的信用分配锚点，不能动。

2.那除此之外，本地有哪些机制可以为我们的新设计提供帮助的？也就是新的v2设计里的新模块有没有可以从现有框架复用的功能，模块和部分？




有，而且其实不少。
如果目标是让 **v2 新模块尽量“旁路增量”地长出来**，而不是重写当前系统，那么现有框架里最值得复用的是三类能力：

1. **在线控制面**
2. **事件编排与收尾学习面**
3. **过渡语义对象与存储/检索底座**

下面我按 **“v2 新模块 → 现有可复用部分 → 为什么值得复用 → 复用时注意什么”** 来讲。

---

## 一、最该复用的是在线控制面，不要重写

### 1. Runtime Controller 整体能力，v2 应直接继承

当前系统已经不是单纯检索器，而是一个在线提示器、运行时防发散控制器、`run_done` 学习器和 official-eval 反馈编译器。它已经有：

* hook 接入 SWE-agent 生命周期
* hint 缓冲
* `on_model_query` 统一注入
* runtime guard
* cooldown / closure
* intervention 跟踪
* stale fallback / circuit breaker

这些能力正是评审里建议保留的“阶段6在线控制层”。 

**对应到 v2：**

* `Runtime Controller` 不该重写
* v2 新出的 `PlanHintCard / SubtaskRiskCard / RetryHintCard / ClosureGuardCard` 都应该继续走现有 `on_model_query` 注入点
* 新的长期层只负责“产出更好的 card”，不负责重做注入器

### 2. `_pending_memory_hints` + 选择性注入算法，直接复用

当前 hook 不是拿到经验就立刻注，而是先缓存，再在 `on_model_query` 里按：

* bucket priority
* confidence
* family cooldown
* per-bucket quota
* char budget
* trigger gating

统一筛选后注入。这个机制已经很成熟，完全可以作为 v2 的 **统一消费口**。

**对 v2 的价值：**

* 你不需要重新设计“怎么把长期图谱结果安全地送给 agent”
* 只需要把新长期层编译出来的对象，映射成现有 hint/card 格式
* 这样可以最大化复用已有实验结论和门禁逻辑

### 3. runtime guard / closure / blocked patterns，v2 继续复用

当前系统里真正立竿见影的一部分收益，来自：

* `attempt_summary` 驱动的 `_blocked_action_patterns`
* `_closure_active`
* 软阻断重复/低价值动作
* 限制 ad-hoc script 扩张

这些逻辑已经被证明能影响行为。当前架构文档也明确说，阶段6真正强化的是 attempt_summary 驱动的 runtime guard、negative/closure/validation 经验优先注入，以及 official eval 后的 promote/suppress。

**对 v2 的价值：**

* 新的长期层不需要直接控制 agent
* 只要给控制层提供更高质量的 `avoid_actions / startup cautions / retry guidance`
* 控制层继续执行“什么时候拦、什么时候收口、什么时候降噪”

## 二、事件编排主链也值得复用，不要推倒

### 4. `bridge_hook -> dispatcher -> agent_mem_main -> SWEAgentAdapter` 主骨架，直接保留

当前主骨架已经明确、稳定，而且评审也明确建议 **不要动这条主骨架**。最好的工程融合方式就是：保留阶段6主链路，在旁边 sidecar 增量长出长期层。 

**对 v2 的价值：**

* 新模块可以挂在 Adapter 后面
* 也可以在 `run_done` 或 `official_eval_feedback` 后旁路写 sidecar
* 不必改动在线回路的基本协议

### 5. 现有四类核心事件，仍然是 v2 的最佳起点

当前真正稳定的主事件就是：

* `plan_generated`
* `action_error`
* `run_done`
* `official_eval_feedback`

评审明确指出，现阶段不要把 `subtask_start / subtask_end / abort / recheck` 当默认工程前提，而应该先用当前事件做 **projected_subtask**。

**对 v2 的价值：**

* `Episode Ledger` 可以先直接记录这四类事件
* `Subtask Instance` 可以先由 `run_done` 投影生成
* 这让你可以在不改 planner 契约的前提下先跑起来

### 6. `active_tasks.json` / task key 机制，很适合当 v2 的 episode 绑定底座

当前 Adapter 已经有：

* `run_id + attempt_id + instance_id` 的 task key
* `active_tasks.json`
* 同一 run/attempt/instance 的事件会自动 resume 到同一 task

这其实已经是一个简化版的 **episode binding** 机制。

**对 v2 的价值：**

* `Episode Ledger` 可以直接沿用这个 task 绑定语义
* 你不需要重新发明 session/attempt 归属规则
* 只需要把 sidecar 存储和这个 task key 对齐

---

## 三、收尾学习面有很多“半成品”，可以升格复用

### 7. `run_done` 是最好的 v2 投影点

当前系统最复杂、也最有信息聚合能力的地方，就是 `run_done`：

* 关闭 active task
* 读取 task actions / subgraph
* 生成 attempt summary
* 生成 abstract experience
* unresolved 时做 RCA / failure card / repair pattern
* 等 official eval 再 promote/suppress

评审也明确建议：`Subtask Instance` 先由 `run_done` 投影生成，而不是强推在线显式 subtask 事件。 

**对 v2 的价值：**

* `SubtaskProjector` 最适合挂在 `run_done`
* `Episode Ledger -> Subtask Instance -> Subtask Edge` 第一版都可以从这里生成
* 在线延迟最小，工程风险最低

### 8. `ExtractionOrchestrator` 可以直接升级成 v2 的冷路径抽取器

当前 `ExtractionOrchestrator` 已经会在 `run_done` 后做：

* rule-based taxonomy
* 可选 LLM extractor
* 生成 attempt_summary / abstract_experience / failure_card_patch / repair_pattern

评审也强调，v2 要把昂贵分析留在冷路径，而不是塞进热路径。 

**对 v2 的价值：**

* 它很适合继续承担：

  * `projected_subtask` 抽取
  * 子任务级失败归因
  * 冲突经验分析
  * prototype 候选摘要
* 也就是：不用新写一个全新的“子任务分析器”，而是升级现有 orchestrator

### 9. `RCAAgent` 很适合直接成为 v2 的失败归因内核

你自己已经说过，失败归因协议想借鉴 RCA，并且希望和解题 agent 用同底座 LLM。
当前系统里其实已经有 `RCAAgent`，它会做：

* 根因候选
* decisive score
* propagation chain
* corrective actions
* preventive checks

这正是 v2 里 **Plan Failure / Execution Failure / Tool Strategy Failure / Validation Failure / Informative Failure** 这套归因 taxonomy 的最好起点。

**对 v2 的价值：**

* 失败归因协议不需要从零做
* 可以先把现有 RCA 输出映射到新 taxonomy
* 后续再逐步细化

---

## 四、现有长期对象虽然不够强，但很适合当“过渡语义层”

### 10. `attempt_summary_v1` 最值得直接升格

评审明确说：`attempt_summary_v1` 已经是最接近 compiler card 的对象之一，应该继续保留，先升格成 “最近一轮 briefing 卡”。

当前系统里它还能驱动：

* `_blocked_action_patterns`
* `subproblem_type`
* `strategy_label`
* runtime guard

**对 v2 的价值：**

* 第一版 `RetryHintCard / ClosureGuardCard` 基本可以直接从 attempt summary 映射
* 在长期层尚未成型前，它就是最好的过渡 compiler object

### 11. `failure_card_v2` 适合映射成 `SubtaskRiskCard`

当前 unresolved attempt 会产出：

* 错误签名
* 候选修复
* 验证命令
* failure class

这类对象虽然现在噪声偏大，但语义方向很适合做 v2 的风险卡。

**对 v2 的价值：**

* 先别追求完美 `Subtask Prototype`
* 可以先把已有 failure card 转成 `SubtaskRiskCard`
* 用来支持执行层的 local retry / caution / validation guidance

### 12. `repair_pattern_v2` 适合映射成 `RetryHintCard`

当前 error 阶段如果拿到了 `next_step_fix`，会即时生成 `repair_pattern_v2`。
虽然评审指出它现在增长过快、偏 workflow 噪声，但作为 **局部 retry guidance 的过渡对象** 仍然是有价值的。 

**对 v2 的价值：**

* 不适合直接当最终长期原型
* 但很适合先编译成小型 retry 卡，在执行层继续消费

### 13. `abstract_experience` 适合做 prototype 候选，不适合直接等价 prototype

评审明确说：未来 `Subtask Prototype` 不应直接等价于当前 `abstract_experience`。
但 `abstract_experience` 依然有用，因为它已经是跨任务抽象层的来源之一。

**对 v2 的价值：**

* 它可以作为 `PrototypeCompiler` 的输入材料之一
* 但不要直接拿它当最终原型
* 应该和 projected subtasks、path segments、official eval 结果一起再编译

---

## 五、检索和存储底座也能复用一部分

### 14. `MemoryAgent` 可以直接复用成 v2 的检索编排器

当前真正生效的检索逻辑已经在 `memory_agent.py`，它负责：

* query rewriting
* 结构检索 + embedding 检索融合
* 多种对象组合召回
* 去重、重排、打分

评审也建议：新系统的消费层仍然可以继续让 `MemoryAgent` 读取 compiler cards。 

**对 v2 的价值：**

* 不需要全新写一套 retrieval orchestration
* 可以先给 `MemoryAgent` 增加新 source：

  * `episode_ledger.jsonl`
  * `subtask_instances.jsonl`
  * `subtask_edges.jsonl`
  * compiler cards
* 然后让它继续输出当前 hook 能吃的 payload

### 15. `GraphStore` 可继续作为旧对象仓，但新对象先别强塞进去

评审很明确：
新对象先 sidecar 落地，不要一上来侵入 ObservationKG。

**对 v2 的价值：**

* `GraphStore` 继续保存：

  * observation_kg
  * belief_graph
  * attempt_summary / failure / repair / abstract
* 新的：

  * `episode_ledger.jsonl`
  * `subtask_instances.jsonl`
  * `subtask_edges.jsonl`
    先放 sidecar
* 这样保住现有系统兼容性

### 16. `experience_rw_map.jsonl` / metrics / intervention feedback，很适合做 v2 实验观测层

当前系统已经会记录：

* 读了哪些经验
* 写了哪些经验
* 注入过哪些 hints
* intervention 是否局部有效
* gate_evaluation 指标

这些虽然现在还不等于最终科研指标，但很适合当 v2 的实验 telemetry。

**对 v2 的价值：**

* 可直接拿来做：

  * 注入噪声分析
  * post-success retrieval sharpness
  * retry consistency
  * 不同 card family 的局部效用统计

---

## 六、哪些“现有缺点”其实也能变成 v2 的利用点

### 17. `run_done` 当前“投影式学习”虽然不完美，但正好适合 v2 第一阶段

当前系统一个现实是：

* 没有稳定 success action 主链路写库
* 主来源是 planning 文本、error 文本、run_done 后离线抽取

这本来是缺点。
但从 v2 角度看，它正好支持评审建议的 **projected_subtask first** 路线。 

也就是：

* 先承认现在没有 declared subtask
* 用现有 run_done 聚合和 subblock_analysis 先投影
* 等数据质量足够，再实验 planner 显式 subtasks

### 18. `subproblem_type / strategy_label / avoid_actions` 已经是 proto-subtask 语义

评审明确指出，这些已经落到了：

* 抽取
* 存储
* 检索
* 注入
* runtime guard

也就是说，你已经有了非常像“子任务原型标签”的雏形。

**对 v2 的价值：**

* `Subtask Instance` 第一版完全可以把这些字段当作过渡 schema
* `PrototypeCompiler` 第一版也可以先围绕这些字段聚类/归并
* 不必等真正完整的 subtask schema 一次到位

---

## 七、我会怎么定义“v2 里最值得复用的现有资产”

如果只给一个最实用版本，我会说这 8 项最值钱：

1. **`bridge_hook` 整套在线控制逻辑**
2. **`on_model_query` 延迟注入点**
3. **runtime guard / closure / cooldown / blocked patterns**
4. **`run_done` 收尾学习入口**
5. **`official_eval_feedback` promote/suppress 闭环**
6. **`ExtractionOrchestrator + RCAAgent` 作为冷路径抽取/归因器**
7. **`MemoryAgent` 作为统一检索编排器**
8. **`attempt_summary_v1 / failure_card_v2 / repair_pattern_v2` 作为过渡 compiler 输入材料**

这些都是当前框架里已经存在、并且对 v2 真有帮助的部分。对应地，评审也明确建议：
v2 最好的融合方式不是重写，而是“**sidecar 长期层 + 复用现有控制层**”。

---

## 最后一条最重要的意见

**v2 最应该复用的，不是当前系统里那些“名字好听的对象”，而是已经形成闭环的机制。**

也就是优先复用：

* 会影响行为的机制
* 会被 official eval 纠偏的机制
* 已经进入主读取链的机制

而不是优先复用那些：

* 只写不读的对象
* 还没形成闭环的半成品
* 只是“未来也许会有用”的名词层模块

这也是为什么我会把重点放在 **controller、run_done、official-eval、MemoryAgent、attempt-summary** 这些东西上，而不是放在 `preventive_rules_v2` 这类当前还没闭环的对象上。 

如果你愿意，我下一条可以继续把这些内容收敛成一张 **“v2 模块复用映射表”**：
列成 `v2模块 | 复用现有模块 | 复用方式 | 先做/后做 | 风险点`。
