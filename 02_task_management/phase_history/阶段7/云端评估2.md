这份**最终框架**我给的总体评价是：

**方向正确，工程分层明显成熟，已经从“方法提案”进入“可实施架构”；但离“低风险上线并稳定提升目标指标”还差 3 个关键闭环：成功事实采集、层级信用分配、热/冷路径资源预算。** 你这版最大的进步，是把 v2 明确收敛成五层：**Control Loop / Fact Plane / Projection Plane / Compiler Plane / Governance Plane**，并且明确坚持三条原则：**保留阶段6在线主链路、长期层 sidecar 增量生长、旧对象只作为过渡语义层而非终态。** 这三点让它在工程上是可落地的，不再是“推倒重来”的理想架构。

下面我主要从 **工程架构** 和 **目标实现** 两个角度评估。

---

## 一、工程架构评价

## 1. 架构主思路是对的，而且比前几版稳很多

这版最重要的工程判断是：

* **在线控制面不重写**，继续复用 `ExternalToolBridgeHook -> dispatcher.py -> agent_mem_main.py -> SWEAgentAdapter` 这条已稳定工作的主骨架；
* **长期记忆不侵入 GraphStore 主语义**，而是通过 `EpisodeLedgerStore / subtask_instances.jsonl / subtask_edges.jsonl` 以 sidecar 方式增量接入；
* **所有新长期对象最终都必须经过 CardCompiler / MemoryAgent，再走 `on_model_query` 统一注入**，而不是各层各自直接往 prompt 里塞东西。 

这是一个很好的工程选择，因为它避免了两种常见失败：

1. **重写在线控制链，导致行为回归**
2. **让长期层直接侵入在线决策点，导致延迟、噪声和调试难度同时爆炸**

而且它和 SWE-agent 本身的扩展方式也是一致的：SWE-agent 官方文档明确支持通过模板配置来控制 `system_template`、`instance_template`、`next_step_template`、`strategy_template` 等消息结构，并在 agent 生命周期中对 per-turn 输入进行稳定控制，因此你把 v2 的统一消费口放在 `on_model_query` 这一类现有注入点上，是符合宿主框架演化方向的。([swe-agent.com][1])

---

## 2. 分层边界比以前清楚很多，这是这版最强的一点

这版文档最大的工程优点，不是模块多，而是**边界第一次相对清楚了**：

* **Layer 0 Control Loop**：只负责在线监听、缓冲、注入、runtime guard、intervention tracking。
* **Layer 1 Fact Plane**：负责动作、证据、环境、diff/test/touched_files 等事实记录。
* **Layer 2 Projection Plane**：负责 run_done 冷路径里从一次 attempt 投影出 Episode / Subtask / Edge。
* **Layer 3 Compiler Plane**：负责把旧对象和新对象都编译成统一可注入的 cards。
* **Layer 4 Governance Plane**：负责去重、收缩、污染控制、official-eval 状态治理。

这意味着你已经不再把“经验对象生成”“在线注入”“长期学习”“对象治理”混成一团。
从工程架构角度，这已经跨过了最危险的一步。

---

## 3. 模块复用策略是合理的，没有重复造轮子

这版没有犯一个很常见的问题：为了做 v2，重写 v1 所有东西。
相反，它明确把下列现有模块当作**稳定底座**继续复用：

* `ExternalToolBridgeHook`
* `dispatcher.py`
* `agent_mem_main.py`
* `SWEAgentAdapter`
* `ActionLogger`
* `KGWriter`
* `GraphStore`
* `ExtractionOrchestrator`
* `RCAAgent`
* `FailureCardBuilder`
* `EvaluationFeedbackProcessor`
* `MemoryAgent`

这个复用策略和上一份“可行性与融合评审”的建议完全一致：
**保留阶段6主链路，新增 sidecar 长期层，并让阶段6对象先充当 v2 的过渡语义层。**

这很重要，因为当前阶段6真实有效的部分，本来就不是“完整动作事实仓库”，而是：

* 在线提示器
* runtime 防发散控制器
* run_done 学习器
* official-eval 反馈编译器。

v2 沿着这个现实基线往前长，而不是否认它，这是正确的。

---

## 4. 这版文档已经有“工程落地说明书”的样子，但还没完全到“无歧义实现规范”

这版比前几版强的地方是，它已经不仅讲“为什么这样设计”，还写了：

* 启动前置条件
* 启动时序
* planning 触发链
* 模型查询前注入链
* action_error 链
* 成功观察链
* run_done 冷路径学习链
* 去冗余规则
* 新工程师的二次开发入口。

这已经非常接近工程说明书了。
但如果你问我“能不能直接交给一个新同学，完全无歧义开工”，我的答案还是：

**还差一点。**

最缺的不是理念，而是下面两类“接口规范级细节”：

### 第一类：字段与对象映射表还不够死

比如：

* `attempt_summary_v1` 的哪些字段进入 `PlanHintCard`，哪些进入 `ClosureGuardCard`
* `failure_card_v2` 如何变成 `SubtaskRiskCard`
* `repair_pattern_v2` 如何变成 `RetryHintCard`
* `official_eval_feedback` 如何从 attempt 级回写到 `SubtaskInstance.status` / `SubtaskEdge.effectiveness` / `CompilerCard.promotion_state`。

### 第二类：热路径 / 冷路径资源预算还没完全量化

文档已经意识到：

* `on_action_executed` 目前主要做统计，不稳定写库
* success fact capture 是 v2 第一优先级之一
* projected subtask 应该优先于 declared subtask。

但还没有彻底写成：

* 哪些步骤同步执行
* 哪些允许异步
* 超时上限是多少
* Sidecar 写入失败怎么降级
* 冷路径失败时在线控制是否完全不受影响

这会是工程落地阶段最容易卡的地方。

---

# 二、从目标实现角度评估

你现在的目标，我理解主要有两个：

1. **跨 session 探索真正积累起来，不再重复踩坑**
2. **当前系统能学到更稳的成功路径，而不只是 workflow 级提醒**

从这两个目标看，这版框架是明显前进的，但还不是“天然就会成功”。

## 1. 对“跨 session 探索”的支持，已经比阶段6强很多

阶段6 的真实问题不是没有记忆，而是它主要学到了：

* attempt summary
* abstract experience
* failure card
* repair pattern

以及这些对象驱动的 runtime guard 和 negative/closure/validation 优先注入。

问题在于，这些对象更像：

* 失败策略摘要
* 局部修复模板
* workflow/validation/anti-over-exploration 提醒

而不是“跨 attempt 的结构化路径”。
这也是可行性评审里点明的核心问题：**系统有用，但学到的对象层次不对，导致成功路径难以稳定复用。**

v2 通过：

* `EpisodeLedgerEvent`
* `SubtaskInstance`
* `SubtaskEdge`
* `PRECEDES / RETRY_OF / ALTERNATIVE_TO`

第一次把“过去到底试过什么路径”从对象语义上明确了出来。

所以从目标实现角度看：

**这版第一次真正有机会解决“重复重跑但不收敛”的问题。**

---

## 2. 对“成功路径粘住”的支持，方向对，但还依赖一个前提：成功事实必须真的采进来

这是我认为整版框架里最大的成败点。

文档自己也承认：

* 当前 `on_action_executed()` 主要做统计和 intervention 推进，没有稳定写库；
* 如果成功动作不进入事实层，长期层就会一直更擅长记失败，不擅长记成功路径。

所以 v2 提出的两个方案：

* `on_action_executed()` 在线轻量写 success fact
* 或 `run_done()` 回放补写 success fact

都非常关键。

如果这一步做成了，v2 才有可能真正学到：

* 成功修改涉及哪些文件
* 哪种验证闭环真正有用
* 哪些 path segment 是“通向正确修复”的而不是“看起来合理但无贡献”的

**如果这一步做不成，v2 很可能仍然只是一个更复杂的失败经验系统。**

这也是为什么上一份评审把“事实层不足”列为 v2 最大硬前提之一。

---

## 3. 对“目标实现”的最大风险：信用分配还没有完全闭合

这版框架已经意识到 `official_eval_feedback` 是最终裁决层，并让 `EvaluationFeedbackProcessor` 未来回写：

* `SubtaskInstance.status`
* `SubtaskEdge.effectiveness`
* `CompilerCard.promotion_state`。

这方向是对的。
但从目标实现角度看，真正难点在于：

> **官方评测是 attempt 级结果，而你想奖励或惩罚的是 subtask / edge / card 级对象。**

这中间天然存在“过归因”风险。
上一份评审也明确指出，这是当前工程上还没有闭合的部分之一。

所以我会说：

* 这版已经把问题认对了
* 但还没有完全解决它

也就是说，它离“能解释为什么成功/失败并把信用正确分到局部路径”还有一段距离。

---

# 三、我认为这版框架最强的地方

我会给它三个高分点。

## 1. 真正做到了“保守增量”

不是推倒旧系统，而是明确：

* 旧在线控制层保留
* GraphStore 保留
* 新长期层走 sidecar
* 旧对象做 compiler 输入材料。

这使得它可以边实验边回退，工程风险低很多。

## 2. 把“知识对象”统一收敛到了 CompilerCard

这非常关键。
如果没有 `CardCompiler`，你的系统会再次陷入“对象很多、消费混乱、每层都想直接注入”的老问题。
现在它明确规定：**长期层直接返回原始 SubtaskGraph 节点是不允许的，控制面只理解低 token、强行动性的 card。**

这个设计非常对。

## 3. 去冗余规则写得很清楚

这版第一次明确写出：

* `preventive_rules_v2` 不是未来核心对象
* pre-eval success-like abstraction 是污染源
* `gate_hard_fail` 只是 telemetry
* legacy retrieval/processing 模块不在真实主链路
* `PathSegmentMiner / PrototypeCompiler / 显式 subtask_* 在线协议` 都是延后模块。

这很重要，因为它阻止工程继续膨胀。

---

# 四、我认为这版框架最大的几个风险点

## 1. 成功事实采集如果迟迟落不了地，整个 v2 会失焦

这是第一风险。
没有 success fact capture，Projection Plane 产出的 subtasks 和 edges 还是会偏失败路径和 workflow 标签，成功路径仍然“粘不住”。

## 2. Compiler Plane 可能变成新的噪声放大器

如果 `CardCompiler` 只是机械地把旧对象和 projected subtasks 重新包装成 card，而没有更强的治理/去重/状态机，那么你只是把噪声从对象层转移到了 card 层。
所以 `ObjectGovernancePolicy` 实际上不是附属优化，而是方法正确性的核心部分。

## 3. `projected_subtask` 的稳定性仍未证明

这版已经很正确地把 `declared_subtask` 降成未来条件，而优先走 `projected_subtask`。
但新的问题是：
**你仍然需要证明 projected subtask 真的足够稳定。**
否则它会成为另一层有解释力但没有预测力的中间表示。

---

# 五、我的最终工程判断

如果按“能不能做”来评：

**能做，而且是目前最合理的一版。**

如果按“做出来后能不能稳定达成目标”来评：

**有希望，但成败几乎取决于三件事：**

1. **success fact capture 是否真的补上**
2. **official-eval 到 subtask/edge/card 的信用分配是否不过归因**
3. **CardCompiler + Governance 是否真能压噪，而不是换一层噪声**

---

# 六、我会给这版的总评分

从工程架构角度：**8.5 / 10**
因为：

* 分层清晰
* 复用策略成熟
* sidecar 渐进式很对
* 去冗余意识很强

扣分点在于：

* 接口级规范还没完全写死
* 热/冷路径预算没有完全量化

从目标实现角度：**7.5 / 10**
因为：

* 它第一次真正对准了“跨 session 路径积累”和“成功路径粘住”
* 但 success fact capture 和信用分配这两个最硬的问题，还没有被“文档层面完全闭合”

---

## 一句话结论

**这版最终框架是“工程上可推进、研究上方向正确”的版本；它最大的价值不是已经解决了问题，而是第一次把“如何从阶段6走到能学路径的记忆系统”这条工程路线讲通了。**
