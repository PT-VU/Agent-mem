# 阶段7：AgentMem v2 计划可行性与融合评审

**日期**：2026-03-13  
**结论一句话**：`AgentMem_v2_framework_design.md` 的方向是对的，但它现在把“长期子任务级记忆骨架”说得过于完整，和当前代码基线之间还隔着三个硬前提：`subtask 边界契约`、`高保真事实采集链`、`可落地的存储迁移方案`。最好的工程融合方式不是推倒重来，而是把当前阶段6系统当作 v2 的在线控制层与过渡语义层，在其旁边增量长出 `Episode Ledger -> Subtask Instance -> Path/Prototype -> Compiler`。

## 1. 先过一遍 Linus 三连问

### 1.1 这是真问题，不是想象问题

是。阶段7稿盯住的问题在真实数据里存在，而且已经反复出现：

1. 当前系统确实能改行为，也确实能带来局部成功。
2. 但成功路径没有“粘住”，repeat-10 上出现了“第 2 次成功、第 7 次又成功、后面继续漂”的现象。
3. 长期记忆增长主要体现在 `repair_patterns_v2` 和 workflow/checklist 类对象，而不是 bug-specific invariant。
4. `preventive_rules_v2` 仍然基本不进入主读取闭环。

换句话说，问题不是“记忆系统没用”，而是“记忆系统有用，但学到的对象层次不对，导致成功路径难稳定复用”。

### 1.2 有没有更简单的做法

有。最简单、也是当前最有工程价值的做法不是直接上完整 `Subtask Graph + Path Segment + Prototype + Compiler` 四件套，而是分三层增量：

1. 先补事实层采集，把成功动作、diff、test、touched files 真的写进来。
2. 再把阶段6已有的 `attempt_summary_v1 + subblock_analysis + subproblem_type/strategy_label` 升格成 `Subtask Instance` 的过渡层。
3. 最后才做 `Path Segment / Prototype / Compiler`。

### 1.3 这会破坏什么

如果按阶段7稿原样直推，会破坏三样东西：

1. 破坏当前稳定主链路的低侵入性。当前主链路只有 `plan_generated / action_error / run_done / official_eval_feedback` 四类核心事件，阶段7假设的 `subtask_start / subtask_end / abort / recheck` 并不存在。
2. 破坏当前运行时延迟预算。若把 LLM 提取直接搬到每个 `subtask_end` 在线执行，`bridge_hook` 的超时、circuit breaker、stale fallback 会被频繁触发。
3. 破坏当前数据兼容性。现有 `GraphStore` 只稳定承载 `ObservationKG + BeliefGraph + abstract/failure/repair/attempt_summary/preventive_rule`，还没有给 `Episode / Plan / SubtaskPrototype / PathSegment` 预留迁移路径。

## 2. 当前真实基线，不要被阶段7稿“重新命名”误导

阶段7稿里有一部分内容其实已经在阶段6代码中落地，不应再被视为全新能力。

### 2.1 已经存在的能力

1. `attempt_summary_v1` 已落地，`GraphStore` 已持久化 `attempt_summaries_v1.json`。
2. `trial_overview` 与 `subblock_analysis` 已落地，且由 `ExtractionOrchestrator` 在 `run_done` 生成。
3. `subproblem_type / strategy_label / prefer_actions / avoid_actions` 已落到抽取、存储、检索、注入、runtime guard。
4. `MemoryAgent` 在 planning 检索时已经使用 `subproblem_type / strategy_label` 做召回和重排。
5. `bridge_hook.py` 已能把 `attempt_summary_v1` 的 `avoid_actions` 映射到 `_blocked_action_patterns`，并做软阻断。
6. `official_eval_feedback` 已经参与 promote / suppress，且会回写负向经验。

### 2.2 仍然缺失的能力

真正还没做的是这些：

1. `subtask_start / subtask_end / subtask_abort / subtask_recheck` 事件协议。
2. 成功动作主链路写库。`on_action_executed` 只做统计，不写 `ProblemFile`。
3. 高保真事实层。当前主链路没有持续采集真实 diff/test/touched_files/stdout/stderr。
4. `Episode Ledger / Subtask Instance Graph / Path Segment / Prototype / Compiler`。
5. `preventive_rules_v2` 的稳定读取闭环。

### 2.3 这意味着什么

这意味着阶段7设计稿不能被执行成“从阶段6跳到全新框架”，而应该被执行成“在阶段6在线控制系统旁边长出长期记忆骨架”。

---

## 3. 对阶段7计划的可行性判断

## 3.1 方向可行

方向是成立的，理由有三条：

1. 当前系统的主要短板确实是“事实层不足 + 记忆对象粒度偏 workflow 级”。
2. 子任务级对象比整题级对象更适合承载“局部目标-动作链-结果-复用条件”。
3. 当前 Hook/Controller/official-eval gating 已经是一个很好的在线控制底座，完全值得保留。

## 3.2 按文稿当前表述，直接实施不可行

至少有五个地方，文稿现在写得太“理想架构”，不够“工程架构”：

1. **subtask 边界假设过强**  
   文稿假设 planning 会显式创建 subtasks，且每个 subtask 对应独立 agent dialog turn。当前 SWE-agent 接入链里没有这个契约。

2. **事实层来源未定义**  
   文稿要求 `patch_digest / tests_run / test_outputs / touched_files / state_digest`，但当前 Hook 并不把这些稳定传给 Adapter。

3. **在线/离线职责没有切开**  
   文稿把 `subtask_end` 提取、失败归因、冲突经验分析都放得很近，容易把昂贵分析塞进热路径。

4. **存储迁移没说清**  
   当前 `GraphStore` 是 JSON + NetworkX 的轻量实现。阶段7稿引入的新节点/边种类较多，但没有说明是平铺 JSON、sidecar JSONL、还是直接侵入 ObservationKG。

5. **信用分配层级还不闭合**  
   当前官方评测反馈是 attempt 级，而阶段7想 promote/suppress 到 subtask/path/prototype 级；中间缺少“如何避免过归因”的规则。

## 3.3 最重要的判断

**AgentMem v2 计划可行，但前提是把它改写成“分层投影 + 旁路增量”的工程计划，而不是“新语义直接替换旧主链路”的工程计划。**

---

## 4. 最好的工程融合方式

推荐方案：**保留当前阶段6主链路，新增一个 sidecar 长期记忆层，并让阶段6对象先充当 v2 的过渡语义层。**

## 4.1 推荐融合原则

1. 不动 `bridge_hook -> dispatcher -> agent_mem_main -> SWEAgentAdapter` 主骨架。
2. 不替换 `attempt_summary_v1 / failure_card_v2 / repair_pattern_v2`，先把它们作为 v2 的输入材料。
3. 新对象先 sidecar 落地，不强行塞进 `ObservationKG`。
4. 新增事件先兼容 `v1` payload，采用可选字段，不做硬切换。
5. 一切新 promotion 仍然受 `official_eval_feedback` 约束。

## 4.2 建议的融合架构

```text
现有层（保留）
  bridge_hook
    -> 延迟注入 / runtime guard / cooldown / closure / stale fallback
  agent_mem_main
    -> SWEAgentAdapter
  GraphStore
    -> observation_kg / belief_graph / abstract/failure/repair/attempt_summary

新增 sidecar 层（建议）
  EpisodeLedgerStore
    -> episode_ledger.jsonl
    -> subtask_instances.jsonl
    -> subtask_edges.jsonl
  SubtaskProjector
    -> 从 run_done actions / summary / subblock_analysis 投影出 subtask instances
  PathMiner
    -> 从 subtask instances 生成 path segments
  PrototypeCompiler
    -> 从 subtask instances + path segments 编译 prototype / cards

消费层（沿用现有注入点）
  MemoryAgent / Runtime Controller
    -> 继续在 on_model_query 注入
    -> 逐步读取 compiler cards
```

## 4.3 为什么这是最佳融合点

### 方案 A：直接重写成新的 Subtask Graph 主系统

不推荐。

原因：

1. 现有主链路已能在线工作。
2. 新边界契约还没稳定。
3. 一次性改主链路，问题会出在“线上行为回归”而不是“记忆方法本身”。

### 方案 B：只在现有经验对象上继续补字段

短期可行，长期不够。

原因：

1. 阶段6就是这么做的，已经证明有增益。
2. 但它仍然无法表达 `RETRY_OF / ALTERNATIVE_TO / PRECEDES` 这类跨 session 路径关系。
3. 最终还是会卡在“对象都在，但搜索结构不存在”。

### 方案 C：sidecar 长期层 + 复用现有控制层

推荐。

原因：

1. 风险最低。
2. 最符合当前代码结构。
3. 便于做阶段性 ablation。
4. 出问题时可完全回退到阶段6行为。

## 5. 建议如何把阶段7概念映射到当前代码

| 阶段7概念 | 当前真实状态 | 建议融合动作 |
| --- | --- | --- |
| Runtime Controller | 已存在于 `bridge_hook.py` | 保留，不重写 |
| Attempt Summary | 已存在 | 作为最近一轮 briefing 卡，继续保留 |
| Subtask Instance | 尚不存在 | 先由 `run_done` 投影生成，不要求在线显式 subtask 事件 |
| Episode Ledger | 尚不存在 | 新增 append-only JSONL，不侵入 ObservationKG |
| Path Segment | 尚不存在 | 基于 `subtask_instances.jsonl` 离线/准离线挖掘 |
| Subtask Prototype | 尚不存在 | 从多个 instance 聚类/归并生成，不直接等价于 abstract_experience |
| Compiler Cards | 尚不存在 | 由新的 compiler 输出，但继续走 `on_model_query` 注入 |
| Preventive Rule 读取闭环 | 未闭合 | 不要先强化生成，先把已有对象真正接入读取 |

## 6. 推荐实施顺序

## Phase A：先补事实层，不然 v2 只是更复杂的幻觉

### 必做

1. 给事件协议加可选事实字段：
   - `stdout`
   - `stderr`
   - `diff_content`
   - `test_output`
   - `touched_files`
   - `worktree_digest`
2. 决定成功动作如何入库：
   - 优先方案：从 `on_action_executed` 增量写轻量成功事件
   - 备选方案：从 `run_done.trajectory_steps` 回放补写
3. 统一 `env_signature`，不要再只有 `run_id / attempt_id / instance_id`。

### 为什么这是 P0

没有这一步，后面的 `Episode Ledger / Subtask Instance / Prototype` 只能建立在 action 文本和启发式标签上，还是学不到代码不变量。

## Phase B：做 `Episode Ledger` 和 `Subtask Instance`，但先走投影路线

### 推荐做法

1. 新增 `episode_ledger.jsonl`
   - 一条 event 一行
   - append-only
   - 不参与复杂 merge
2. 新增 `subtask_instances.jsonl`
   - 由 `run_done` 基于 `trial_overview + subblock_analysis + action clusters` 投影生成
3. 新增 `subtask_edges.jsonl`
   - 先只支持：
     - `PRECEDES`
     - `RETRY_OF`
     - `ALTERNATIVE_TO`

### 这里故意不做什么

1. 不要求 planning 立即产生显式 subtasks。
2. 不要求每个 subtask 必须是独立 dialog turn。
3. 不要求在线 LLM 在每个 `subtask_end` 做重分析。

先用 run_done 投影把数据站稳，再决定是否上显式 subtask 协议。

## Phase C：把 `attempt_summary_v1` 升格成“过渡 Compiler 卡”

当前系统已经有最接近 compiler 卡的对象，其实就是：

1. `attempt_summary_v1`
2. `failure_card_v2`
3. `repair_pattern_v2`
4. `negative abstract experience`

建议先定义统一输出模板：

1. `PlanHintCard`
2. `SubtaskRiskCard`
3. `RetryHintCard`
4. `ClosureGuardCard`

然后把旧对象映射成这些 card，而不是等 `SubtaskPrototype` 全部成型后再消费。

## Phase D：再做 `Path Segment` 与 `Prototype`

满足以下条件后再做：

1. 成功动作与关键证据已经稳定采集。
2. `subtask_instances.jsonl` 已有足够样本。
3. 能用评估数据证明“投影出来的 subtask 是稳定的”。

否则现在做 prototype，大概率只是在更高层次上重复阶段6的 workflow 抽象噪声。

## 7. 我认为阶段7文稿里最需要改写的几处

## 7.1 “每个子任务作为独立 agent turn” 不能当实现前提

这可以是**目标实验条件**，但不能写成**默认工程前提**。

建议改成：

> v2 先支持两种子任务来源：  
> 1. `projected_subtask`：从现有轨迹投影；  
> 2. `declared_subtask`：未来由 planner 显式声明。  
> 只有在 declared_subtask 证明收益后，才将其升级为默认主路径。

## 7.2 “子任务结束时提取” 应分成热路径与冷路径

建议拆成：

1. `subtask_end_hotpath`
   - 只记事实
   - 只做轻量 rule-based tagging
2. `subtask_end_coldpath`
   - 可异步或 run_done 后统一做 LLM 归因

否则在线性能会先崩。

## 7.3 “Episode Ledger” 不应先做成大一统图

建议第一版只做 append-only ledger：

1. 易审计
2. 易回放
3. 易回滚
4. 不污染现有 ObservationKG 语义

## 7.4 “Prototype / Skill Compiler” 必须后置

当前系统最大的缺口不是“没有 skill compiler”，而是“事实采集不够、成功语义不够 sharp”。  
在这个前提下过早做 prototype，只会把噪声压缩成更难排查的噪声。

## 8. 需要继续澄清和细化的点

以下问题如果不澄清，阶段7计划很容易写成“架构很美、代码很难落”。

## P0：阻塞级

1. **subtask 的真实来源是什么？**  
   是未来 planner 显式输出，还是先由 run_done 投影生成？  
   这是 v2 工程边界的第一决策点。

2. **事实层证据从哪里来？**  
   是 Hook 实时上传，还是 run_done 回放 `trajectory_steps` 补写，还是两者结合？  
   这决定数据质量和线上延迟。

3. **新对象放在哪里？**  
   是扩展 `GraphStore` 本体，还是以 sidecar JSONL/JSON 并存？  
   这是迁移风险最大的点。

## P1：重要级

1. `official_eval_feedback` 如何分摊到 `subtask_instance / path_segment / prototype`？  
   必须防止“一次 resolved 把整条路径都 promote”。

2. 当前 `attempt_summary_v1` 与未来 `SubtaskRiskCard / PathPriorCard` 的职责边界是什么？  
   不然会产生重复注入对象。

3. `preventive_rules_v2` 是保留、重命名，还是并入 prototype caution layer？  
   现在它名义上存在，实际不闭环。

4. `subtask granularity` 的实验设计怎么做？  
   阶段7稿提到粗/中/细粒度，但没有给可操作的切分规则和指标。

5. `conflict analysis` 的触发条件是什么？  
   不能所有冲突都跑 LLM RCA，否则成本过高。

6. `Memory Compiler` 的缓存与失效策略是什么？  
   如果每次 planning 都现编译，延迟和稳定性都会出问题。

## P2：优化级

1. `Path Segment` 是只做 instance 内，还是跨 instance/repo 泛化？
2. `env_signature` 的字段是否区分“强匹配字段”和“弱相似字段”？
3. 是否需要把 `changed_file_pattern` 和 `test_anchor` 提升为一级检索特征？
4. 是否需要显式定义 `candidate -> promoted -> suppressed` 的统一对象状态机，而不是分散在不同对象里？

---

## 9. 建议的最小交付定义

如果要把阶段7真正落成工程，而不是继续写设计稿，我建议把 DoD 收窄到下面这组最小闭环：

1. 新增 `episode_ledger.jsonl`，记录所有现有事件与补充事实字段。
2. 新增 `subtask_instances.jsonl`，由 `run_done` 投影生成。
3. 新增 `subtask_edges.jsonl`，至少支持 `PRECEDES / RETRY_OF / ALTERNATIVE_TO`。
4. `MemoryAgent` 能读取一个最小版 `SubtaskRiskCard`。
5. `on_model_query` 能消费该 card，但不改变现有注入机制。
6. `official_eval_feedback` 能把 attempt 级结果回写到对应 subtask instances 的状态字段。
7. 有一组 repeat-run 实验能回答：
   - 成功路径是否更稳定
   - 注入噪声是否下降
   - post-success retrieval 是否变 sharp

如果这 7 条做不到，就不该进入 `Path Segment / Prototype / Compiler` 的下一层。

## 10. 最终结论

### 10.1 这份计划值不值得做

值得做。它抓住了当前 AgentMem 最真实的瓶颈：**记忆对象太偏 workflow 提示，事实层和路径层都不够强**。

### 10.2 这份计划现在能不能直接照着做

不能。至少还需要先把以下三件事工程化：

1. `subtask 来源`
2. `事实采集链`
3. `sidecar 存储迁移`

### 10.3 最好的融合姿势

不是“替换当前框架”，而是：

1. **保留阶段6当前主链路作为在线控制面**；
2. **把阶段6已有对象视作 v2 的过渡语义层**；
3. **用 sidecar 方式增量长出长期 episodic search graph**；
4. **在证明数据质量足够前，不要急着上 prototype/skill compiler**。

### 10.4 最关键的一句话

`AgentMem v2` 真正该先解决的不是“怎么设计更漂亮的长期记忆图”，而是“怎么让当前系统第一次稳定记住成功代码路径中的决定性不变量”。  
在这个前提下，`Subtask Graph / Path Segment / Prototype / Compiler` 才是加法；否则它们只是把当前噪声换一种名字再存一遍。
