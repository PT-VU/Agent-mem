# 阶段7：AgentMem v2 综合更新方向与有机结合方案

**日期**：2026-03-13  
**文档目的**：结合 `云端结合意见.md`、阶段7主设计稿、上一版本地工程评审、阶段6真实代码与 repeat-10 证据，给出一版更综合、更工程化的 v2 更新方向。  
**一句话结论**：AgentMem v2 的正确升级方向，不是“继续给当前系统堆更多长期对象”，而是同步做两件事：**一边做减法，收缩当前未闭环和高噪声对象；一边做加法，用 sidecar 方式长出事实层、投影子任务层和 compiler card 层。**

前一版评审已经回答了：

1. 阶段7设计稿方向是否可行；
2. 为什么不能直接 big-bang 落地；

1. **哪些现有模块和对象应该停、应该冻、应该后置**；
2. **哪些现有机制其实非常适合给 v2 新模块复用**。

因此，本文件不再只回答“v2 应该加什么”，而是回答：

> **v2 应该如何在当前工程上做“有机结合”：既增量演进，又主动减复杂度。**

## 2. 综合结论：v2 的正确升级方式是“双轴演进”

阶段7主设计稿强调的是**长期记忆骨架**，上一版本地评审强调的是**工程可落地边界**，云端意见强调的是**复杂度治理与模块复用**。三者合起来后，最合理的方向不是单轴演进，而是双轴演进：

## 2.1 轴 A：做减法，先清掉当前系统的噪声复杂度

这一轴解决的问题是：

1. 当前有哪些对象只写不读；
2. 哪些对象重复表达同一类含义；
3. 哪些对象会持续放大注入噪声；
4. 哪些模块存在于仓库里，但不在真实主链路中。

如果不先做这一步，后面新增的 `Episode Ledger / Subtask Instance / Compiler` 会叠在已有噪声之上，方法不会更清晰，只会更重。

## 2.2 轴 B：做加法，用 sidecar 长出新的长期层

这一轴解决的问题是：

1. 当前缺少高保真事实层；
2. 当前缺少跨 attempt 的路径表达；
3. 当前成功路径缺少“代码级不变量”的稳定承载对象；
4. 当前 `attempt_summary / failure_card / repair_pattern` 还只是过渡语义对象，不是最终长期骨架。

这一步不能推倒现有系统重做，而应该以 sidecar 形式接入：

1. `Episode Ledger`
2. `Projected Subtask Instances`
3. `Subtask Edges`
4. `Compiler Cards`

## 2.3 为什么必须双轴一起做

只做加法，不做减法，会得到一个更复杂但依然 noisy 的 v2。  
只做减法，不做加法，会得到一个更干净但仍然学不到成功路径不变量的阶段6。  
因此，真正合理的更新方向是：

> **先减噪，再补事实，再投影子任务，再编译卡片，最后才考虑 path/prototype。**

## 3. 我建议的项目框架更新方向

我建议把后续框架叙事从“当前系统 + 一堆未来模块”改成下面这五层：

```text
Layer 0: Control Loop（保留）
  bridge_hook
  on_model_query
  runtime guard / cooldown / closure / intervention tracking

Layer 1: Fact Plane（新增，优先级最高）
  success action capture
  diff/test/touched_files/stdout/stderr/state digest
  episode ledger events

Layer 2: Projection Plane（新增，冷路径）
  run_done -> trial_overview / subblock_analysis
  projected_subtask
  subtask edges
  official_eval write-back

Layer 3: Compiler Plane（新增，桥接层）
  attempt_summary_v1 / failure_card_v2 / repair_pattern_v2
  + projected subtasks
  -> PlanHintCard / SubtaskRiskCard / RetryHintCard / ClosureGuardCard

Layer 4: Governance Plane（强化）
  dedup / merge / suppression / budget / candidate-promoted-suppressed
  noise caps / pre-eval success guard / failure-card clustering
```

### 3.1 这五层各自扮演什么角色

`Layer 0` 是现有系统里已经形成闭环、并且最不该重写的部分。  
`Layer 1` 是 v2 真正的 P0，没有它就没有可信长期层。  
`Layer 2` 让当前系统可以在不引入显式 `subtask_*` 在线协议的前提下，先把子任务层跑起来。  
`Layer 3` 负责“让新旧对象有机结合”，它是过渡层，不是最终研究终态。  
`Layer 4` 把云端意见里最重要的“工程减法”和“对象治理”正式纳入方法框架，而不是只作为清理建议存在。

### 3.2 这比原始阶段7稿多了什么

它多了一个关键层：**Governance Plane**。  

原始阶段7稿已经有长期层、短期层、信用层，但还缺少一个明确的“对象治理层”。而当前项目最真实的问题之一恰好就是：

1. 某些对象会无限增殖；
2. 某些对象在 pre-eval 阶段就被抽成 success-like 经验；
3. 某些对象只写不读；
4. 某些对象没有聚类、合并、配额和状态机。

这不是实现细节，而是框架设计的一部分，应该被显式纳入。

## 4. 对当前工程的综合判断：什么该保留，什么该收缩，什么该延后

## 4.1 必须保留并继续复用的部分

这些模块和机制已经形成闭环，应该直接作为 v2 底座：

1. `bridge_hook -> dispatcher -> agent_mem_main -> SWEAgentAdapter`
2. `on_model_query` 延迟注入点
3. runtime guard / cooldown / closure / blocked patterns
4. `run_done` 收尾学习主入口
5. `official_eval_feedback` promote / suppress 闭环
6. `ExtractionOrchestrator + RCAAgent` 冷路径抽取与归因能力
7. `MemoryAgent` 统一检索编排能力
8. `attempt_summary_v1 / failure_card_v2 / repair_pattern_v2` 作为过渡 compiler 输入材料

## 4.2 应该收缩但不必完全删除的部分

这些对象有价值，但当前增长方式或使用方式有问题：

1. `repair_patterns_v2`
   - 保留读取
   - 缩减生成
   - 增加聚类/近重复合并
   - 定位为 `RetryHintCard` 的输入材料，而不是长期终态

2. `failure_card_v2`
   - 保留类型
   - 停止“每次 unresolved 默认新建近似卡”
   - 改成 cluster merge / delta update

3. `attempt_summary_v1`
   - 继续保留
   - 但职责要收敛到“最近一轮 briefing + 控制层输入”
   - 不要再让它承担未来所有长期语义

## 4.3 应该默认停用或降级的部分

这些对象或机制当前主要增加复杂度，不提供核心收益：

1. `preventive_rules_v2` 主生成链  
   当前只写不读，repeat-10 统计为 0，建议默认关闭，只保留离线实验开关。

2. pre-eval success-like abstraction  
   尤其是把 `run_done submitted` 抽成 success-like 经验的路径，应停止进入主经验生成链。

3. `gate_hard_fail` 作为“方法模块”的叙述  
   当前只是日志，不是真正 hard stop。建议降级成 telemetry，不再算主控制层功能。

## 4.4 应该从主工程关注面移出的部分

以下文件当前不在真实主链路，应标记为 `legacy / dormant`，不要继续污染“当前真实架构”的认知：

1. `agent_mem/retrieval/retriever.py`
2. `agent_mem/retrieval/embedder.py`
3. `agent_mem/processing/error_handler.py`

这不一定要求删文件，但应从主架构叙事、主测试矩阵和默认运行路径里移出。

## 4.5 应该明确延后的部分

这些模块是未来研究方向，但不该进入当前默认工程复杂度预算：

1. 显式 `subtask_start / subtask_end / abort / recheck` 在线协议
2. `Path Segment`
3. `Subtask Prototype`
4. 完整 `Skill Compiler`
5. 在线逐子任务 LLM 深分析

## 5. “有机结合”应该怎么做：新旧模块映射表

下面这张表是这次综合评审里最重要的部分。它回答的是：**v2 新模块该如何借现有框架长出来，而不是重新造一个平行系统。**

| v2 目标模块 | 现有可复用部分 | 新增最小模块 | 融合方式 | 当前优先级 |
| --- | --- | --- | --- | --- |
| `Runtime Controller` | `bridge_hook.py` 全部在线控制逻辑 | 无 | 直接继承，不重写 | P0 |
| `Episode Ledger` | 现有事件 payload、`active_tasks.json`、`experience_rw_map.jsonl` | `episode_ledger.jsonl` | 先 append-only sidecar | P0 |
| `SubtaskProjector` | `run_done`、`ExtractionOrchestrator`、`trial_overview`、`subblock_analysis` | `subtask_instances.jsonl` | 先做 `projected_subtask` | P0 |
| `Subtask Edge Builder` | `attempt_summary_v1`、动作顺序、official eval write-back | `subtask_edges.jsonl` | 先只做 `PRECEDES/RETRY_OF/ALTERNATIVE_TO` | P1 |
| `PlanHintCard` | `attempt_summary_v1`、现有 planning retrieval | `card_compiler.py` | 旧对象映射成新卡 | P1 |
| `SubtaskRiskCard` | `failure_card_v2`、negative abstract experience | `card_compiler.py` | 风险对象编译为 caution 卡 | P1 |
| `RetryHintCard` | `repair_pattern_v2` | `card_compiler.py` | 作为执行层 retry 卡，而非终态对象 | P1 |
| `ClosureGuardCard` | `attempt_summary_v1`、runtime guard、closure signals | `card_compiler.py` | 继续走 `on_model_query` 注入 | P1 |
| `PrototypeCompiler` | `abstract_experience`、projected subtasks、official eval states | prototype miner | 后置，等待样本稳定 | P2 |
| `Path Segment Miner` | `subtask_instances.jsonl`、`subtask_edges.jsonl` | path miner | 后置，先同 instance 内验证 | P2 |
| `Governance Layer` | `official_eval_feedback`、suppression、merge、quality gate | object policy / budgets | 将“删减噪声”制度化 | P0 |

## 6. 更新后的工程路线图

## Phase 0：先做减法和治理，不然 v2 会建立在噪声上

### 目标

把当前系统里最明显的“复杂度幻觉”和“污染源”先压下来。

### 建议动作

1. 默认关闭 `preventive_rules_v2` 生成链
2. 停止 pre-eval success-like abstraction 进入主经验流
3. 对 `failure_card_v2` 改成 merge/update，而不是默认新建
4. 对 `repair_patterns_v2` 增加对象预算和聚类收缩
5. 将 `gate_hard_fail` 明确降级为 telemetry
6. 将 `retriever.py/embedder.py/error_handler.py` 标记为 legacy

### 验收标准

1. 主运行路径的活跃对象类型减少
2. post-success retrieval 噪声下降
3. 文档中的“真实架构”与实际运行链一致

## Phase 1：补事实层

### 目标

让 v2 真正有资格学习“成功代码路径中的决定性不变量”。

### 建议动作

1. 事件协议增加可选事实字段：
   - `stdout`
   - `stderr`
   - `diff_content`
   - `test_output`
   - `touched_files`
   - `worktree_digest`
2. 决定 success action 的采集路径：
   - 优先：`on_action_executed` 轻量入库
   - 备选：`run_done` 回放补写
3. 统一 `env_signature`

### 验收标准

1. 成功动作不再大面积缺席
2. diff/test/touched_files 不再只在少数路径出现
3. `run_done` 提取不再主要依赖 action 文本猜语义

## Phase 2：先做 `projected_subtask`，不强推 declared subtask

### 目标

在不改 planner 契约的前提下，先把子任务层建立起来。

### 建议动作

1. `episode_ledger.jsonl`
2. `subtask_instances.jsonl`
3. `subtask_edges.jsonl`
4. `official_eval_feedback` 回写 subtask 状态

### 说明

这一阶段明确只支持：

1. `projected_subtask`
2. 冷路径投影
3. 最小边类型

不要求：

1. 显式 subtask 在线协议
2. 每个 subtask 独立 dialog turn
3. 每个 subtask 在线 LLM 归因

## Phase 3：把旧对象和新投影层编译成统一 cards

### 目标

让 v2 新层能被当前控制层真实消费，而不是另起炉灶。

### 建议动作

1. 定义统一 card schema：
   - `PlanHintCard`
   - `SubtaskRiskCard`
   - `RetryHintCard`
   - `ClosureGuardCard`
2. 把旧对象映射成 cards：
   - `attempt_summary_v1`
   - `failure_card_v2`
   - `repair_pattern_v2`
3. 让 `MemoryAgent` 新增 card source，但仍通过 `on_model_query` 输出

### 验收标准

1. 不新增第二套注入机制
2. 新旧对象都能通过同一个 control plane 消费
3. 注入噪声可测且可控

## Phase 4：最后才上 `Path Segment / Prototype`

### 前提条件

只有满足以下条件后才进入：

1. 事实层稳定
2. projected subtasks 样本足够
3. cards 已能稳定改善行为
4. 对象治理层已能限制噪声扩张

### 说明

这一步不是“下一步自然要做”，而是“满足条件后才做”。  
否则只是在更高一层压缩当前噪声。

## 7. 这套更新方向的关键思想：把旧对象降格为“过渡语义层”

这是“有机结合”的核心。

如果把当前阶段6对象继续当成最终形态，v2 就会被它们绑定住。  
如果把当前阶段6对象全部推翻，v2 又会失去已证明有效的控制面。

正确做法是：

1. **控制机制保留**
2. **过渡对象保留**
3. **最终长期骨架后置**

也就是说：

- `attempt_summary_v1` 不是终态，但它是最好的 briefing/compiler 输入
- `failure_card_v2` 不是终态，但它是最好的风险卡候选
- `repair_pattern_v2` 不是终态，但它是最好的 retry 卡候选
- `abstract_experience` 不是 prototype，但它是 prototype compiler 的输入之一

这就实现了“不是废掉旧工程，而是把旧工程降格成新框架的桥接层”。

## 8. 对阶段7主设计稿的修订建议

如果后续要把 `AgentMem_v2_framework_design.md` 修成更工程化的版本，我建议至少加入下面几条修订：

1. 把“显式 subtasks”从默认前提改为实验条件  
   默认先支持 `projected_subtask`，显式 `declared_subtask` 作为后续实验。

2. 把“热路径 / 冷路径”分离写进主架构  
   `hotpath` 只记事实与轻量 tagging；`coldpath` 做 LLM 归因和对象编译。

3. 增加 `Governance Layer`  
   把去重、配额、merge、suppression、pre-eval success guard、对象状态机写进架构，而不是散落在实现细节中。

4. 把旧对象的定位明确改成“过渡语义层”  
   不要让读者误以为 `attempt_summary/failure_card/repair_pattern` 会被新框架直接替代。

5. 把路线图改成  
   `减噪 -> 事实层 -> projected_subtask -> compiler cards -> path/prototype`

## 9. 当前最推荐的最小闭环

如果只能做一版最稳、最有信息增益的更新，我推荐下面这组最小闭环：

1. 关闭 `preventive_rules_v2` 主生成链
2. 停止 pre-eval success-like abstraction
3. 新增 `episode_ledger.jsonl`
4. 新增 success action 的最小事实采集
5. 新增 `subtask_instances.jsonl`
6. 让 `attempt_summary/failure_card/repair_pattern` 编译成统一 cards
7. 继续使用 `MemoryAgent + on_model_query + runtime guard`
8. 用 repeat-run 实验比较：
   - post-success retrieval 是否变 sharp
   - repair pattern 数量是否下降
   - success path 是否更稳定

如果这一闭环都跑不顺，就不应该进入完整 `Path Segment / Prototype / Skill Compiler`。

## 10. 最终结论

### 10.1 v2 的真正工程主线

不是“再造一个更大的长期记忆系统”，而是：

1. **压缩当前噪声复杂度**
2. **补齐事实层**
3. **投影出子任务层**
4. **用 compiler cards 让新旧系统有机桥接**
5. **最后才上路径原型化**

### 10.2 对当前项目最重要的价值判断

当前项目里最值钱的资产，不是那些“名字好听但未闭环的长期对象”，而是已经证明有效的闭环机制：

1. `on_model_query`
2. runtime guard
3. run_done 学习
4. official eval gating
5. MemoryAgent 检索编排
6. attempt summary 驱动的控制效果

v2 最应该复用这些，而不是从零重写。

### 10.3 这版综合判断和前两份文档的关系

`AgentMem_v2_framework_design.md` 解决了“想去哪”。  
`阶段7_AgentMem_v2计划可行性与融合评审_2026-03-13.md` 解决了“怎么从现在走过去”。  
`云端结合意见.md` 解决了“路上哪些包袱该先扔掉，哪些旧零件可以继续用”。  

三者合并后的最终方向就是：

> **AgentMem v2 应该被实现为一个“减法优先、事实先行、sidecar 增量、控制层复用、长期层后置”的升级框架。**

这才是当前项目最稳、最能持续推进、也最不容易把主链路搞崩的更新方向。
