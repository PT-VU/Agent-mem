# V2.0 SWEAgent侧升级计划

**日期**：2026-03-15  
**状态**：Draft / Pre-Retest Plan  
**目标**：在正式启动 AgentMem v2.1 重测前，明确 SWEAgent 侧是否需要同步升级，哪些已经升级，哪些还需要补，并把 prompt 变更设计成可做消融的独立变量。

---

## 1. 本文档回答什么问题

本文档只回答两件事：

1. AgentMem v2.1 更新后，SWEAgent 和 Hook 侧是否需要同步升级，哪些已经升级，哪些还没升级。
2. 本轮实验设计是否需要改 SWEAgent prompt，如果需要，应该怎么改，才能既体现更新效果，又便于后续消融。

一句话结论：

1. **Hook 接口形态不需要重写，也不需要新增第五类公开事件。**
2. **Hook 代码主体已经升级到能承接 v2.1，但实验启动层还需要把 v2.1 flags 显式暴露出来。**
3. **Prompt 不是 v2.1 生效的前置条件。第一次正式重测应优先保持 prompt 不变，只测 memory 框架升级本身。**
4. **若要加 prompt 升级，必须做成和 v2.1 flags 正交的独立 prompt profile，不能把两者混成一个不可分离的“新版本”。**

---

## 2. 当前 Hook 链路检查结论

## 2.1 当前公开事件主链没有变化

当前 `agent_mem_main.py` 仍只接收四类公开事件：

1. `plan_generated`
2. `action_error`
3. `run_done`
4. `official_eval_feedback`

这意味着：

1. 当前 v2.1 没有破坏阶段6 主链。
2. 不需要为了 success fact 单独新增外部 `action_success` 事件。
3. 当前升级应继续坚持“热路径本地记账 + 冷路径公开事件编排”的做法。

## 2.2 Hook 代码层已经具备的 v2.1 能力

当前 `ExternalToolBridgeHook` 已经具备：

1. `on_actions_generated()`：
   - 继续向 `plan_generated` 路由
   - 保留 runtime guard / proactive trigger / hint 选择机制
2. `on_action_error()`：
   - 继续向 `action_error` 路由
   - 保留失败 streak、干预推进和微模式触发
3. `on_action_executed()`：
   - 已经增加最小 success fact hot-path 记录
   - 采用 `trace_id + step_index` 幂等键
   - sidecar 失败时不会阻塞主链
4. `on_run_done()`：
   - 继续发出 `run_done`
   - 不需要改变公开协议
5. `on_model_query()`：
   - 继续作为统一注入口
   - 已能承接 compiler card 风格的提示对象

所以，对问题 2.1 的直接回答是：

> **Hook 需要同步升级吗？需要，但接口层已经升完了；当前不需要再改 Hook API 形态。**

更准确地说：

1. **需要的升级已经在 Hook 代码里做了。**
2. **还没补的是“启动脚本和实验脚本对这些能力的显式启停控制”。**

---

## 3. 当前还缺的 SWEAgent 侧升级

虽然 Hook 主体已经升级，但实验启动层还有两个空档。

## 3.1 启动脚本还没有显式暴露 v2.1 flags

当前 `start_with_external_tools.sh` 会导出：

1. `SWE_AGENT_EXTERNAL_HOOK_CLASS`
2. `SWE_AGENT_EXT_TOOL_A_CMD`
3. `SWE_AGENT_EXT_TOOL_B_CMD`
4. 阶段6 的 memory gate / timeout / extraction 相关环境变量

但目前还没有显式导出这组 v2.1 开关：

1. `AGENT_MEM_V21_ENABLE_SUCCESS_FACT_HOTPATH`
2. `AGENT_MEM_V21_ENABLE_SIDECAR`
3. `AGENT_MEM_V21_ENABLE_SUBTASK_PROJECTION`
4. `AGENT_MEM_V21_ENABLE_CARD_COMPILER`
5. `AGENT_MEM_V21_ENABLE_GOVERNANCE`
6. `AGENT_MEM_V21_SIDECAR_DIR`
7. `AGENT_MEM_V21_HOTPATH_TIMEOUT_MS`
8. `AGENT_MEM_V21_COLDPATH_TIMEOUT_MS`
9. `AGENT_MEM_V21_MAX_CARDS_PER_QUERY`

这带来的问题是：

1. 代码能力已经存在，但实验入口不够显式。
2. 很难做清晰的 on/off 对照。
3. 实验产物里不容易追溯“这一轮到底开了哪些 v2.1 能力”。

### 建议

在 `start_with_external_tools.sh` 中补一层显式 passthrough/default：

1. 不强行默认打开全部 v2.1 开关。
2. 只负责把 env 接力给 Hook 和 adapter。
3. 把默认值保持为 `0/False`，由具体实验脚本决定开哪些。

## 3.2 实验脚本需要把 v2.1 开关写进 run metadata

当前 repeat-run 脚本已经管理：

1. 模型配置
2. timeout
3. memory extraction
4. storage/evidence 路径
5. official eval feedback 回写

但为了让 v2.1 重测可复盘，建议在脚本里增加两件事：

1. 把本轮启用的 `AGENT_MEM_V21_*` 开关写入 attempt summary 或 run metadata。
2. 把 `prompt_profile` 也一起写入 run metadata。

否则后面做分析时会混淆：

1. 当前收益来自哪组 v2.1 能力
2. 当前收益是否伴随 prompt 变化

---

## 4. Prompt 侧是否必须升级

## 4.1 结论

对问题 2.2 的直接回答是：

> **不是必须。**

原因很简单：

1. AgentMem v2.1 的核心升级点在 memory/control 面，而不在 SWEAgent 基础 prompt 本身。
2. 当前 Hook 已经能通过 `on_model_query()` 注入 compiler cards。
3. 当前 runtime guard、closure、avoid actions 也是通过 Hook 和外部工具链起作用，不依赖改 system prompt 才能生效。

所以：

1. **如果目标是先验证 v2.1 框架升级是否有效，第一次正式重测不应该改 prompt。**
2. **如果一开始就同时改 prompt，就很难区分收益来自 memory 框架还是来自代理行为约束本身。**

---

## 5. 为什么仍然建议准备一个“最小 prompt 升级版”

虽然第一次正式重测不建议立刻改 prompt，但我仍然建议准备一个最小 prompt profile，原因有两个：

1. 后续很可能会发现：
   - Hook 已经给了正确提示
   - 但 agent 没有稳定执行“先局部验证、再扩大范围”的行为
2. 如果没有一个最小 prompt profile，后续我们只能在 Hook 注入上越做越重，最后把控制责任都堆到 memory 层，味道不好。

关键点是：

> **prompt 升级必须很小、很克制，而且必须和 v2.1 flags 正交控制。**

---

## 6. 推荐的 Prompt 升级原则

如果做 prompt 升级，只建议做“行为约束级”的最小增量，不建议把 v2.1 内部对象语言直接塞进 prompt。

### 应该做的

只补这种行为约束：

1. 优先复用已经成功的 reproduction / validation 路径，不轻易创建新的 ad-hoc script。
2. 一旦局部 patch 已经通过 focused validation，先围绕当前 patch 做闭环验证，不要无证据扩大搜索范围。
3. 在没有新增证据前，不要跨模块扩张问题范围。
4. 把注入的 memory hints 视为条件化建议，而不是必须照抄的命令。

### 不应该做的

不要把这些内容直接写进 prompt：

1. `SubtaskInstance`
2. `SubtaskEdge`
3. `CompilerCard`
4. `GovernanceState`
5. `candidate/promoted/suppressed`

原因是：

1. 这些是控制层/长期层内部语义，不是代理必须知道的工作语言。
2. 一旦写进 prompt，后续很难分辨是“模型被术语影响”还是“memory 架构真的有效”。

---

## 7. 推荐的 Prompt 落地方式

## 7.1 不修改现有默认 config，新增独立 prompt profile

建议不要直接改 `SWE-agent/config/deepseek.yaml`。

更稳的方式是新增一个独立配置，例如：

1. `SWE-agent/config/benchmarks/deepseek_agentmem_v20_guard.yaml`

这份配置只做最小模板差异：

1. `system_template` 基本不动，最多补 1 段行为纪律
2. `instance_template` 只加 3 到 5 条工作策略提醒
3. 不改输出格式
4. 不改工具协议

## 7.2 Prompt 差异必须足够小

建议只加一小段：

1. 先复现，再局部修复，再 focused validation
2. 如果 focused validation 已通过，先验证当前 patch 闭环，再决定是否扩范围
3. 避免重复创建新的 repro/test 脚本

这样做的好处是：

1. 不会把实验变成“换了一个新 agent”
2. 仍然能测出 prompt discipline 对结果的边际影响

---

## 8. 便于消融的实验设计

最推荐的是把 prompt 和 v2.1 memory 拆成两个正交开关。

### 开关 A：memory profile

1. `mem_stage6`
2. `mem_v21`

### 开关 B：prompt profile

1. `prompt_base`
2. `prompt_guard`

这样可以直接做 2x2：

1. `prompt_base + mem_stage6`
2. `prompt_base + mem_v21`
3. `prompt_guard + mem_stage6`
4. `prompt_guard + mem_v21`

这个设计有三个优点：

1. 能看出 v2.1 memory 本身的增益
2. 能看出 prompt discipline 本身的增益
3. 能看出两者是否存在协同，而不是把收益混成一团

如果实验预算不够，最小也应该保留 3 组：

1. `prompt_base + mem_stage6`
2. `prompt_base + mem_v21`
3. `prompt_guard + mem_v21`

但这种 3 组设计会损失 prompt-only 的独立解释力。

---

## 9. 推荐实施顺序

### 第一阶段：先不改 prompt，先做正式 v2.1 重测

目标：

1. 验证 memory 框架升级本身是否带来收益
2. 验证 hook 热路径 success fact 和 cold-path projection 在 repeat-run 中是否稳定

这一阶段建议：

1. 使用当前基线 `deepseek.yaml`
2. 显式打开所需 `AGENT_MEM_V21_*` flags
3. 把 flags 写进 run metadata

### 第二阶段：引入最小 prompt profile

目标：

1. 判断 agent discipline 是否进一步提升 memory 提示的利用率
2. 与第一阶段结果做 prompt-only 边际比较

这一阶段建议：

1. 只新增一个 `prompt_guard` 配置
2. 不改 Hook 协议
3. 不改 memory object 设计

### 第三阶段：做 2x2 消融

目标：

1. 定量拆开 memory 贡献和 prompt 贡献
2. 看是否存在强耦合或单边收益

---

## 10. 最终建议

对当前两个问题，我的最终建议是：

### 对 2.1 Hook 是否需要升级

1. 不需要新增 Hook API。
2. 当前 Hook 主体已经升级到能承接 v2.1。
3. 还需要补的是：
   - `start_with_external_tools.sh` 显式导出 `AGENT_MEM_V21_*`
   - 实验脚本把这些 flags 写进 run metadata

### 对 2.2 是否需要改 prompt

1. **第一次正式重测不建议改 prompt。**
2. v2.1 应先在当前 prompt 下证明自己有效。
3. prompt 升级可以做，但要：
   - 单独建 profile
   - 只做最小行为纪律增强
   - 和 memory flags 正交控制
   - 用 2x2 设计做消融

一句话收束：

> **先把 Hook 启动层补齐，先在原 prompt 下重测 v2.1；prompt 升级要做，但必须作为第二变量独立进入实验。**
