**目标读者**：新加入项目的工程师、维护者、二次开发者  
**文档定位**：本文档是 AgentMem 阶段7 的 **最新版框架说明书**。它不再停留在“未来可能如何做”，而是明确：

> 一句话结论：**当前最新版本的 AgentMem v2，是一个“保留阶段6在线主链路 + 新增长期 sidecar 层 + 统一 card 注入 + 显式治理层”的五层记忆框架；其当前可实施轮廓就是 v2.1。**

## 0. 先给最终结论

截至当前阶段7 的确定版本，AgentMem v2 的默认框架不是“推倒重写”，而是：

```text
SWE-agent Lifecycle
  -> ExternalToolBridgeHook
    -> dispatcher.py / agent_mem_main.py
      -> SWEAgentAdapter
        -> Fact Plane
        -> Projection Plane
        -> Compiler Plane
        -> Governance Plane
      -> MemoryAgent recommendations
    -> on_model_query unified injection
```

它由五层组成：

```text
Layer 0: Control Loop
  在线监听、缓冲、统一注入、runtime guard、intervention tracking

Layer 1: Fact Plane
  动作事实、证据引用、run/attempt 账本、成功事实双轨采集

Layer 2: Projection Plane
  run_done 冷路径抽取、projected_subtask、subtask edges

Layer 3: Compiler Plane
  把旧对象和 projected subtasks 编译成统一 cards

Layer 4: Governance Plane
  去重、配额、近重复合并、promotion/suppression、状态机
```

### 0.1 三条总原则

1. **在线主链路不重写**  
   继续保留 `ExternalToolBridgeHook -> dispatcher.py -> agent_mem_main.py -> SWEAgentAdapter`

2. **长期层先走 sidecar，不直接侵入 GraphStore 主语义**  
   sidecar 负责 append-only 事实和 candidate 对象，GraphStore 继续承载 governed curated store

3. **控制层只消费统一 card，不直接消费原始长期对象**  
   任何长期对象都必须先经过 `CardCompiler + MemoryAgent + Hook 注入控制`

### 0.2 v2.1 的当前硬边界

当前默认主线明确包含：

1. 成功事实双轨采集  
2. 三层证据模型  
3. 三层信用分配模型  
4. `projected_subtask` 默认路线  
5. `CardCompiler` 输入白名单  
6. `GraphStore / sidecar` 明确分工  
7. `ObjectGovernancePolicy` 最小状态机

当前默认主线明确不包含：

1. 显式 `declared_subtask` 在线协议
2. `PathSegmentMiner`
3. `PrototypeCompiler`
4. 完整 `Skill Compiler`
5. 在线逐子任务 LLM 深分析

## 1. 框架边界与非目标

## 1.1 当前框架要解决的问题

当前版本要解决的是三个真实工程问题：

1. **系统更擅长记失败，不擅长记成功路径**
2. **系统已有不少有用对象，但层级不对，难以形成跨 attempt 的路径表达**
3. **如果继续加对象而不治理，噪声会比收益增长更快**

因此，当前框架的目标不是“把所有长期对象都做全”，而是：

1. 让成功事实真实进入系统
2. 让 attempt 级、subtask 级、eval 级对象之间的信用不再混写
3. 让控制层只接收低 token、强行动性的 card，而不是一堆原始对象

## 1.2 当前框架的非目标

以下内容在当前主线中视为延后项：

1. Planner 强制声明的 `declared_subtask`
2. 子任务在线生命周期协议：`subtask_start / subtask_end / abort / recheck`
3. Path / Prototype / Skill 完整长期层
4. 在线重型 LLM 分析

## 3.1 Layer 0：Control Loop

这是系统的在线控制面。它负责观察、缓冲、注入和 runtime 风险控制。

### 3.1.1 `ExternalToolBridgeHook`

**状态**：现有复用，v2.1 中继续作为主入口  
**文件**：`source_code/sweagent_external_tools/bridge_hook.py`

**功能定位**：

1. 监听 SWE-agent 生命周期事件
2. 构造统一事件 payload
3. 调用外部工具进程
4. 缓冲 memory hints
5. 在 `on_model_query()` 中统一注入
6. 执行 runtime guard、closure、cooldown、intervention tracking
7. 记录 hook telemetry

**输入**：

1. `StepOutput`
2. `Trajectory`
3. `AgentInfo`
4. 已缓冲的 memory hints

**输出**：

1. `SWE_AGENT_EXT_EVENT_JSON`
2. `_pending_memory_hints`
3. 注入给模型的 `[AgentMem Hints]`
4. hook 级 telemetry 日志

**关键函数**：

1. `on_actions_generated()`  
   触发 `plan_generated` 事件
2. `on_action_error()`  
   触发 `action_error` 事件
3. `on_action_executed()`  
   v2.1 中负责最小成功事实记录，不做重型分析
4. `on_run_done()`  
   触发 `run_done` 冷路径
5. `on_model_query()`  
   从缓冲区选择 hints 并注入到消息
6. `_build_event_payload()`  
   统一构造事件载荷
7. `_select_hints_for_injection()`  
   做 family cooldown、预算控制和去重

**与其他模块的配合**：

1. 通过 `dispatcher.py / agent_mem_main.py` 调 `SWEAgentAdapter`
2. 通过 `_handle_parsed_tool_payload()` 吸收 `MemoryAgent` 返回的建议
3. 通过 `on_model_query()` 把最终 card 消费结果注入模型

**v2.1 特别说明**：

v2.1 不要求新增第五类公开外部事件。  
成功热路径记录可以先走：

1. Hook 内轻量 append-only 记录
2. `run_done` 冷路径补全和校正
3. 可选的 adapter 内部 helper，不强制暴露新公开事件类型

### 3.2.5 Success Fact 统一约束

这是 Fact Plane 的地基。  
如果这里不统一，后面的 reconcile、projection、credit assignment 都会漂。

**v2.1 必须写死的最小 schema**：

1. `instance_id`
2. `run_id`
3. `attempt_id`
4. `trace_id`
5. `step_index`
6. `action_text`
7. `success_like`
8. `timestamp`

**唯一真值入口约束**：

1. `on_action_executed()` 写热路径最小 success fact
2. `handle_run_done()` 负责冷路径补全与 reconcile
3. 最终 truth 以冷路径 reconcile 后结果为准

**幂等规则**：

第一版建议幂等键固定为：

```text
trace_id + step_index
```

如果 `trace_id` 缺失，则只能降级为 telemetry，不允许临时拼装不稳定幂等键进入主事实链。

**`success_like` 的统一判定责任方**：

1. 必须收敛到 adapter 内共享 utility 或等价公共函数
2. 不允许 Hook 和冷路径各自定义一套 success_like 规则

**验收语义**：

1. 同一次运行重复写入不应产生重复 success fact
2. 热路径与冷路径对同一 action 的事实最终一致
3. sidecar 写失败不影响主链运行

### 3.3.4 `SubtaskProjector`

**状态**：v2.1 新增  
**推荐位置**：`agent_mem/processing/subtask_projector.py`

**功能定位**：

从一次 attempt 的：

1. `attempt_summary_v1`
2. `trial_overview`
3. `subblock_analysis`
4. `ProblemFile[]`
5. `run_done_context`

投影出 `SubtaskInstance[]`。

**输入**：

上述 cold-path 中间材料

**输出**：

1. `SubtaskInstance[]`
2. `projection_report`

**关键约束**：

1. 第一版只支持 `projected_subtask`
2. 第一版只在冷路径调用
3. 第一版只生成 candidate，不直接进入主检索默认视图

**稳定性门槛**：

`projected_subtask` 是否进入默认强路径，不能靠主观判断，必须过两类 Gate：

1. **解释性稳定**
   - 相似 attempt 上，intent / boundary / failure type 是否足够一致
2. **决策性稳定**
   - 进入 compiler 后，是否真实改善控制层输出

第一版至少要定义三类阈值：

1. retry 成功率提升阈值
2. post-success retrieval sharpness 提升阈值
3. 注入噪声下降阈值

**不达标时的处理**：

1. 只保留 sidecar candidate
2. 不进入默认 compiler 强路径
3. 不作为在线收益主张依据

### 3.3.6 `run_done_context` 字段表与来源约束

`run_done_context` 是当前框架里的冷路径枢纽。  
它同时服务：

1. success truth 补齐
2. `SubtaskProjector`
3. `SubtaskEdgeBuilder`
4. official eval attach

如果这里不先表格化，它会快速变成新的模糊中心。

| 字段 | 必填性 | 来源模块 | 缺失 fallback | 写入位置 | 存储策略 |
| --- | --- | --- | --- | --- | --- |
| `touched_files` | 应该 | `ActionLogger` 汇总 / patch 分析 | 空列表 | `run_done_context`、sidecar | 摘要值即可 |
| `diff_summary` | 应该 | diff 提取逻辑 / patch 统计 | 空摘要对象 | `run_done_context`、sidecar | 摘要 + 原始证据 ref |
| `validation_summary` | 应该 | test/command 汇总 | `{\"commands\": []}` | `run_done_context`、sidecar | 摘要 + 原始证据 ref |
| `patch_digest` | 可以 | patch 内容哈希 | 空字符串 | `run_done_context` | 摘要值即可 |
| `task_closed_cleanly` | 必须 | `handle_run_done()` 判定 | `False` | `run_done_context` | 摘要值即可 |

**补充约束**：

1. 每个字段都必须能追溯到唯一来源模块
2. projected_subtask 不得依赖未定义字段
3. 允许缺字段降级运行，但必须留下 `skipped_reason`

1. 不提前消费 `Path / Prototype / Skill`
2. 输出必须可去重
3. 输出必须有 family ID 和 source object traceability

**每张 card 的最小字段要求**：

1. `card_id`
2. `card_type`
3. `family_id`
4. `source_object_ids`
5. `confidence`
6. `promotion_state`
7. `evidence_level`

其中：

```text
evidence_level ∈ { local, attempt, official }
```

**明确禁止**：

1. raw subtask 直接注入
2. `Path / Prototype` 提前进入 v1 compiler
3. “见对象就编卡”

**验收语义**：

1. 每张注入卡都能追溯来源对象和证据层级
2. 新对象默认不会自动进入 compiler
3. compiler 关闭时，阶段6 控制层仍可独立运行

---

## 3.5 Layer 4：Governance Plane

这一层的目标是防止系统把噪声越积越多。

### 3.5.1 `EvaluationFeedbackProcessor`

**状态**：现有复用  
**文件**：`source_code/sweagent_external_tools/agent_mem/processing/evaluation_feedback.py`

**功能定位**：

把 official eval 的最终结果回写到现有对象。

**输入**：

1. `instance_id`
2. `outcome`
3. `eval_ref`
4. `patch_text / patch_summary`
5. `changed_files`
6. `validation_summary`
7. `run_id / attempt_id / trace_id`

**输出**：

1. `feedback_report`

**v2.1 角色边界**：

它是最终闸门，不是细粒度因果解释器。

**允许直接推动的状态**：

1. `attempt_summary_v1.final_outcome`
2. candidate 对象的 promotion/suppression
3. `CompilerCard.promotion_state`
4. `SubtaskInstance.eval_context`
5. `SubtaskEdge.eval_support`

**禁止直接做的事**：

1. 直接覆盖 `SubtaskInstance.local_result_status`
2. 直接把 `SubtaskEdge` 定成最终因果边
3. 直接把所有参与 attempt 的对象一把 promote

---

### 3.5.2 `ObjectGovernancePolicy`

**状态**：v2.1 新增  
**推荐位置**：`agent_mem/processing/object_governance_policy.py`

**功能定位**：

为 candidate 对象提供：

1. 去重
2. 近重复合并
3. growth cap
4. pre-eval success guard
5. suppression / deprecation
6. promotion 状态机

**最小状态机**：

1. `candidate`
2. `promoted`
3. `suppressed`
4. `deprecated`

**必须治理的对象**：

1. `abstract_experience`
2. `failure_card_v2`
3. `repair_pattern_v2`
4. `CompilerCard`
5. 进入 curated view 之前的 subtask 派生对象

**状态转移权限表必须写死**：

| 转移 | 允许模块 | 备注 |
| --- | --- | --- |
| `candidate -> promoted` | `EvaluationFeedbackProcessor`、`ObjectGovernancePolicy` | `official_eval` 是最终闸门 |
| `candidate -> suppressed` | `EvaluationFeedbackProcessor`、`ObjectGovernancePolicy` | unresolved / noisy / low value |
| `candidate -> deprecated` | `ObjectGovernancePolicy` | 淘汰态只能由治理层执行 |
| `promoted -> deprecated` | `ObjectGovernancePolicy` | 生命周期收缩 |
| `suppressed -> deprecated` | `ObjectGovernancePolicy` | 生命周期收缩 |

**额外硬约束**：

1. pre-eval success-like object 不得直接进入 `promoted`
2. growth cap / merge / deprecation 规则必须由治理层集中执行
3. suppressed / deprecated 对象不得进入默认在线消费链

## 5. 证据模型、信用模型和状态机

## 5.1 三层证据模型

### Local Evidence

局部 action 级事实：

1. stdout / stderr
2. diff 片段
3. touched files
4. test output
5. action outcome

### Attempt Evidence

一次完整 attempt 的冷路径产物：

1. `attempt_summary_v1`
2. `trial_overview`
3. `subblock_analysis`
4. `run_done_context`

### Official Evidence

外部评测裁决：

1. `official_eval_status`
2. `eval_ref`
3. `changed_files`
4. `validation_summary`

---

## 5.2 三层信用模型

### Local -> Subtask

局部事实只影响：

1. `SubtaskInstance.local_result_status`
2. `SubtaskInstance.failure_type`

### Attempt -> Edge Candidate

attempt 级证据只影响：

1. `SubtaskEdge.effectiveness_candidate`
2. `SubtaskEdge.supporting_attempt_ids`

### Official -> Promotion / Suppression

official eval 只做最终闸门：

1. promotion
2. suppression
3. eval_context attach

---

## 5.3 Attempt 状态机

```text
created
  -> active
  -> run_done_unresolved
  -> run_done_resolved_like
  -> run_done_submitted
  -> official_resolved / official_unresolved / official_infra_failure
```

---

## 5.4 `SubtaskInstance` 状态机

```text
projected_candidate
  -> locally_supported
  -> locally_failed
  -> eval_context_attached
  -> deprecated
```

---

## 5.5 `SubtaskEdge` 状态机

```text
candidate
  -> supported_candidate
  -> suppressed
  -> deprecated
```

第一版没有 `verified_causal`。

---

## 5.6 Governance / Card 状态机

治理对象最小状态机：

```text
candidate
  -> promoted
  -> suppressed
  -> deprecated
```

```text
candidate
  -> injected_once
  -> promoted
  -> suppressed
  -> deprecated
```

## 6. 完整流程：系统如何启动、如何运行、碰到不同情况如何处理

## 6.1 启动流程

1. SWE-agent 启动后，`ExternalToolBridgeHook` 在 `on_init()` 或等价初始化阶段收集：
   - `instance_id`
   - `run_id`
   - `attempt_id`
   - `agent_name`
2. Hook 按当前 step 和事件调用 `_build_event_payload()`
3. `dispatcher.py` 启动外部工具进程
4. `agent_mem_main.py` 读取 `SWE_AGENT_EXT_EVENT_JSON`
5. `setup_agent_mem()` 初始化：
   - `GraphStore`
   - `ActionLogger`
   - `MemoryAgent`
   - `ExtractionOrchestrator`
   - `EvaluationFeedbackProcessor`
   - 未来的 sidecar / projector / compiler / governance
6. `handle_event()` 按事件类型路由到 `SWEAgentAdapter`

---

## 6.2 planning 流程

触发点：`ExternalToolBridgeHook.on_actions_generated()`

### 步骤

1. Hook 扫描 runtime guard / blocked pattern / ad-hoc script 风险
2. Hook 构造 `plan_generated` payload
3. `agent_mem_main.handle_event()` 路由到 `SWEAgentAdapter.handle_plan_generated()`
4. Adapter 先通过 `ActionLogger.log_action()` 记录 planning 动作
5. Adapter 调 `MemoryAgent.retrieve_for_query_type(query_type="planning")`
6. `MemoryAgent` 从当前 governed objects 中召回建议
7. Adapter 返回：
   - `planning_tips`
   - `evidence_refs`
   - `confidence`
   - `retrieval_debug`
8. Hook 解析 payload，把 hints 放入 `_pending_memory_hints`
9. 直到下次 `on_model_query()` 触发，才真正注入模型

### 为什么这样设计

注入与检索解耦，避免“查出来就立刻塞 prompt”，从而保住注入预算和 family cooldown。

---

## 6.3 模型查询前注入流程

触发点：`ExternalToolBridgeHook.on_model_query()`

### 步骤

1. Hook 检查 `_pending_memory_hints`
2. 调 `_select_hints_for_injection()`
3. 根据：
   - `max_hints`
   - `hint_char_budget`
   - family cooldown
   - 去重 fingerprint
   做选择
4. 生成 `[AgentMem Hints]` 用户消息
5. 把 hints 注入 `messages`
6. 记录 `memory_injected` telemetry
7. 触发 `CompilerCard` 的 `injected_once` 状态写回或统计

### 异常处理

1. 没有可用 hints：直接跳过
2. 注入内容超长：截断到预算内
3. trace 缺失：记录 telemetry，但不阻塞推理

---

## 6.4 action_error 流程

触发点：`ExternalToolBridgeHook.on_action_error()`

### 步骤

1. Hook 更新失败计数、触发 marker、记录 intervention
2. Hook 构造 `action_error` payload
3. `handle_event()` 路由到 `SWEAgentAdapter.handle_action_error()`
4. Adapter 使用 `ActionLogger.log_action()` 记录失败动作
5. Adapter 调 `MemoryAgent.retrieve_for_query_type(query_type="repair")`
6. 返回 repair tips
7. Hook 缓冲 hints，等待后续 `on_model_query()` 注入

### 特殊分支

1. 连续失败过多：runtime guard 增强
2. 检索失败：保留错误事实，但不给 suggestions 也继续主代理

---

## 6.5 action_success 流程

触发点：`ExternalToolBridgeHook.on_action_executed()`

### 这是 v2.1 的关键更新点

当前真实代码里，这个入口主要做：

1. error-like observation 统计
2. consecutive failure reset
3. intervention 推进

v2.1 在这里新增的是：

1. **热路径最小成功事实记录**
2. **可选 sidecar append-only 写入**
3. **不强制新增第五类公开事件**

### 热路径只允许做什么

1. 记录：
   - `instance_id`
   - `run_id`
   - `attempt_id`
   - `trace_id`
   - `step_index`
   - `action_text`
   - success-like outcome
2. 写最小 success event 到 sidecar
3. 失败时降级成 telemetry

### 热路径禁止做什么

1. 生成完整 `SubtaskInstance`
2. 调重型 LLM
3. 复杂 merge / cluster
4. 同步 embedding

### 与冷路径的关系

热路径只是先占位。  
真正的 bootstrap 真值源仍然是 `run_done` 冷路径。

---

## 6.6 run_done 冷路径流程

触发点：`ExternalToolBridgeHook.on_run_done()`

这是系统最重要的冷路径学习入口。

### 主流程

1. Hook 构造 `run_done` payload：
   - `trajectory_steps`
   - `exit_status`
   - `has_submission`
2. `handle_event()` 路由到 `SWEAgentAdapter.handle_run_done()`
3. Adapter 关闭或补齐 task context
4. 计算：
   - `submission_success`
   - `resolved_like_success`
   - `task_closed_cleanly`
5. Adapter 构造 `run_done_context`
6. Adapter 收集 `GraphStore` 中的 `task_actions`
7. 先保底写：
   - task end summary
   - fallback attempt summary（如需要）
8. 对 unresolved attempt：
   - 调 `RCAAgent`
   - 调 `FailureCardBuilder`
   - 生成或 patch `failure_card_v2`
   - 生成 `repair_pattern_v2`
9. 调 `ExtractionOrchestrator.process_attempt()`，产出：
   - `trial_overview`
   - `subblock_analysis`
   - `attempt_summary_v1`
   - extra abstractions / repair patterns
10. v2.1 新增：
   - 用 `run_done_context` 补齐成功事实真值
   - 写 `EpisodeLedgerStore`
   - 调 `SubtaskProjector`
   - 调 `SubtaskEdgeBuilder`
   - 调 `CardCompiler`
   - 调 `ObjectGovernancePolicy`
11. 返回：
   - `attempt_summary_info`
   - `failure_card_info`
   - `extraction_pipeline`
   - 未来的 `sidecar_write_report / success_fact_report / projection_report / compiler_report / governance_report`

### 特殊分支

#### 没有 action

1. 不阻塞 `run_done`
2. 仍应尽量生成 fallback summary

#### 已提交但未 official eval

1. 记为 `run_done_submitted`
2. belief 更新可跳过
3. success-like 经验不得直接 promote

#### cold path 超时

1. 必须保住最小 `attempt_summary_v1`
2. 可以跳过 projector / compiler / governance 增强步骤
3. 必须返回 `skipped_reason`

---

## 6.7 official eval 流程

触发点：`official_eval_feedback`

### 主流程

1. 外部评测把：
   - `instance_id`
   - `outcome`
   - `eval_ref`
   - `patch_text / patch_path`
   - `changed_files`
   - `validation_summary`
   送入 AgentMem
2. `handle_event()` 路由到 `SWEAgentAdapter.apply_evaluation_feedback()`
3. Adapter 调 `EvaluationFeedbackProcessor.apply_feedback()`
4. Processor 做：
   - candidate `abstract_experience` promote/suppress
   - unresolved / infra_failure 的 failure 资产写回
5. Adapter 更新 `attempt_summary_v1.final_outcome`
6. v2.1 新增治理写回：
   - `SubtaskInstance.eval_context`
   - `SubtaskEdge.eval_support`
   - `CompilerCard.promotion_state`
7. 返回 `feedback_report`

### 特殊分支

#### resolved

1. promote candidate memories
2. 但仍不能反向证明所有 local subtasks 都是成功因果链

#### unresolved

1. suppress 候选成功对象
2. 写负向经验或 failure asset

#### infra_failure

1. 写环境失败类资产
2. 不直接惩罚局部代码策略

---

## 6.8 sidecar / compiler / governance 失败时怎么处理

### sidecar 写失败

1. 不得影响主代理
2. 记录 telemetry
3. 让 `run_done` 尽量继续

### projector 失败

1. 只跳过 `SubtaskInstance / SubtaskEdge` 生成
2. 不得影响 `attempt_summary_v1`

### compiler 失败

1. 返回空 cards
2. retrieval 继续基于旧对象工作

### governance 失败

1. 保留 candidate
2. 不做 destructive change

---

## 7. 热路径 / 冷路径预算

## 7.1 热路径

包含：

1. `on_model_query`
2. `on_action_error`
3. `on_action_executed`

### 热路径只允许

1. 轻量事实记录
2. telemetry
3. 预算内的 hint 筛选与注入

### 热路径不允许

1. 重型 LLM 分析
2. 复杂 merge / cluster
3. 强依赖 sidecar 成功写入
4. 强依赖同步 embedding

---

## 7.2 冷路径

包含：

1. `handle_run_done`
2. `process_attempt`
3. `SubtaskProjector`
4. `SubtaskEdgeBuilder`
5. `CardCompiler`
6. `ObjectGovernancePolicy`

### 冷路径允许

1. 高密度摘要
2. 结构投影
3. compiler 编译
4. 受时限约束的治理

### 冷路径保底要求

1. 至少保住最小 `attempt_summary_v1`
2. 至少保住最小 sidecar ledger
3. 所有跳过动作都要有 `skipped_reason`

## 7.3 预算必须是硬约束，不是口头原则

### 热路径硬约束

**允许的操作**：

1. 最小事实记录
2. telemetry
3. 预算内 hints 筛选与注入

**禁止的操作**：

1. 重型 LLM
2. embedding
3. merge / cluster
4. 完整 projection

**sidecar 写失败时的降级规则**：

1. 记录 telemetry
2. 保持主代理继续运行
3. 不得因为 sidecar 失败阻断当前 step

### 冷路径硬约束

**允许的操作**：

1. success fact reconcile
2. `run_done_context` 补全
3. projection / compiler / governance

**超时后的 fallback**：

1. 保底写最小 `attempt_summary_v1`
2. 保底写最小 sidecar ledger
3. projector / compiler / governance 可整段跳过
4. 必须输出 `skipped_reason` 和 `error_stage`

## 10. 一句话收束

**当前最新阶段7 框架，不再把 AgentMem 理解成“经验检索外挂”，而是一个由在线控制、事实采集、冷路径投影、统一 card 编译和对象治理共同组成的记忆系统。**
