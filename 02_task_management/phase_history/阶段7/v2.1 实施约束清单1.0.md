# 阶段7：AgentMem v2.1 实施约束清单 1.0

**日期**：2026-03-14  
**状态**：Draft / Normative  
**适用范围**：AgentMem v2.1 第一阶段工程实现  
**文档定位**：本文档不是架构愿景稿，也不是模块说明书，而是 **v2.1 的实现约束规范**。其目标是把阶段7已经收敛出的工程共识写成明确边界，避免后续实现重新发散。

> 一句话结论：**v2.1 的核心不是继续扩模块，而是先把 `success fact capture`、`credit assignment`、`CardCompiler governance` 三个闭环做实。**

## 1. v2.1 的总目标与非目标

## 1.1 v2.1 总目标

v2.1 必须实现下面四件事：

1. **补齐成功事实采集闭环**
2. **建立三层证据 / 三层信用分配协议**
3. **用受治理的 compiler card 替代对象直接注入**
4. **用 sidecar 长出长期层，而不破坏当前在线控制主链**

## 1.2 v2.1 非目标

以下内容 **不属于 v2.1 默认实现范围**：

1. 显式 `declared_subtask` 在线协议
2. `PathSegmentMiner`
3. `PrototypeCompiler`
4. 完整 `Skill Compiler`
5. 在线逐子任务 LLM 深分析
6. 将 sidecar 新对象直接混写进 `GraphStore`

这些能力都可以保留为未来方向，但不得进入 v2.1 默认主线。

## 2. v2.1 的硬边界总表

| 编号 | 约束主题 | 结论 |
| --- | --- | --- |
| C1 | 在线主链路 | 必须保留 `ExternalToolBridgeHook -> dispatcher.py -> agent_mem_main.py -> SWEAgentAdapter` |
| C2 | 注入口 | 必须继续以 `on_model_query` 作为统一消费口 |
| C3 | 成功事实采集 | 必须采用“双轨”：热路径最小记录 + 冷路径真值补全 |
| C4 | 证据模型 | 必须采用三层证据：`Local / Attempt / Official` |
| C5 | 信用模型 | 必须采用三层信用：`subtask / edge-candidate / promotion` |
| C6 | Compiler 输入 | 必须冻结白名单，不得提前引入 `path/prototype/skill` |
| C7 | 存储分工 | `sidecar = append-only ledger`，`GraphStore = governed curated store` |
| C8 | 治理状态机 | 必须至少实现 `candidate / promoted / suppressed / deprecated` |
| C9 | 路径预算 | 必须显式区分热路径与冷路径预算与降级规则 |
| C10 | 延后模块 | `declared_subtask`、`Path/Prototype`、在线逐子任务 LLM 必须后置 |
| C11 | 验证方式 | 必须拆分控制层收益和长期记忆收益，做 ablation |

## 3. 约束 C1：在线主链路不得重写

v2.1 必须复用当前已工作的在线主链路：

```text
ExternalToolBridgeHook
  -> dispatcher.py
    -> agent_mem_main.py
      -> SWEAgentAdapter
```

### 3.1 必须遵守

1. 默认事件主链只允许继续使用当前四类事件：
   - `plan_generated`
   - `action_error`
   - `run_done`
   - `official_eval_feedback`
2. 不得为了引入 v2.1 而重写 Hook 生命周期组织方式。
3. 不得要求 SWE-agent 主代理修改核心回合协议，才能让 v2.1 工作。

### 3.2 原因

当前阶段6 真正已经闭环并验证有效的部分，本质上是：

- 在线提示器
- runtime guard / closure 控制器
- `run_done` 学习器
- official-eval 反馈编译器

v2.1 必须建立在这个现实底座之上，而不是推倒重来。

---

## 4. 约束 C2：统一注入口不得分裂

v2.1 中，所有长期对象最终都必须被编译成统一可消费 card，然后仍然通过 `on_model_query` 注入。

### 4.1 必须遵守

1. `SubtaskInstance`、`SubtaskEdge`、`attempt_summary_v1`、`failure_card_v2`、`repair_pattern_v2` 不得直接进入 prompt。
2. 控制层只消费 `CompilerCard`。
3. `MemoryAgent` 仍是统一的检索与重排编排器。

### 4.2 禁止事项

以下做法在 v2.1 中禁止：

1. 各层自行向 prompt 注入原始对象
2. `SubtaskGraph` 原始节点直接进入 `next_step_template`
3. 单独为 `SubtaskProjector` 再造一个第二注入口

---

## 5. 约束 C3：成功事实采集必须双轨

这是 v2.1 的 P0 约束。

### 5.1 结论

成功事实采集必须采用：

1. **热路径最小记录**
2. **冷路径真值补全**

而且第一版默认把 **`run_done` 冷路径作为 bootstrap 真值源**。

### 5.2 热路径职责

热路径入口是：

- `bridge_hook.py::on_action_executed()`
- 后续打通到 `sweagent_adapter.py::handle_action_success()`

热路径只允许记录最小成功事实，不承担最终语义归纳。

### 5.3 热路径最小必填字段

第一版至少要能稳定记录：

1. `instance_id`
2. `run_id`
3. `attempt_id`
4. `trace_id`
5. `step_index`
6. `action_text`
7. `intent_text` 或等价摘要
8. `tool_call` 摘要
9. `outcome=success_like`
10. `timestamp`

### 5.4 冷路径补全字段

`run_done` 负责补全和校正下列事实：

1. `touched_files`
2. `diff_summary`
3. `tests_run`
4. `validation_summary`
5. `exit_status`
6. `submission_status`
7. `has_submission`
8. `patch_digest`
9. `task_closed_cleanly`

### 5.5 禁止事项

1. 不得把热路径采集失败解释为“该 attempt 没有成功事实”
2. 不得在第一版就要求热路径生成完整 `SubtaskInstance`
3. 不得让热路径直接执行重型 LLM / embedding / merge 逻辑

---

## 6. 约束 C4：必须采用三层证据模型

v2.1 必须显式区分三层证据：

### 6.1 Local Evidence

由单个 action 或局部子步骤产生：

- stdout / stderr
- diff 片段
- touched files
- test output
- action outcome

### 6.2 Attempt Evidence

由一次完整 attempt 的冷路径收尾产出：

- `attempt_summary_v1`
- `subblock_analysis`
- `trial_overview`
- `run_done_context`

### 6.3 Official Evidence

由外部评测或官方裁决提供：

- `official_eval_status`
- `eval_ref`
- patch / changed_files / validation_summary

### 6.4 约束目的

这样做的目的，是防止 `official_eval_feedback` 被迫承担它不该独自承担的细粒度因果解释责任。

---

## 7. 约束 C5：必须采用三层信用分配模型

信用分配不能一把写穿所有对象。

### 7.1 三层信用协议

1. `Local Evidence -> SubtaskInstance.local_result_status`
2. `Attempt Evidence -> SubtaskEdge.effectiveness_candidate`
3. `Official Evidence -> Object promotion / suppression`

### 7.2 v2.1 允许的写回

#### Local 层允许写回

- `SubtaskInstance.local_result_status`
- `SubtaskInstance.failure_type`
- `SubtaskInstance.recommended_next_steps`

#### Attempt 层允许写回

- `SubtaskEdge.effectiveness_candidate`
- `SubtaskEdge.supporting_attempt_ids`
- `SubtaskEdge.confidence_hint`

#### Official 层允许写回

- `attempt_summary_v1.final_outcome`
- `ObjectGovernanceState`
- `CompilerCard.promotion_state`
- `SubtaskInstance.eval_context`
- `SubtaskEdge.eval_support`

### 7.3 v2.1 禁止的写回

1. `official_eval_feedback` 不得直接覆盖 `SubtaskInstance.local_result_status`
2. `official_eval_feedback` 不得直接产出“该 edge 是真实因果路径”的最终断言
3. `official_eval_feedback` 不得直接把所有参与 attempt 的 card 全部标成成功卡

---

## 8. 约束 C6：CardCompiler 输入范围必须冻结

v2.1 中，`CardCompiler` 第一版只允许消费四类输入：

1. `attempt_summary_v1`
2. `failure_card_v2`
3. `repair_pattern_v2`
4. `projected_subtask`

### 8.1 输出类型白名单

第一版只允许输出：

1. `PlanHintCard`
2. `SubtaskRiskCard`
3. `RetryHintCard`
4. `ClosureGuardCard`

### 8.2 明确禁止

以下对象在 v2.1 中不得进入 `CardCompiler` 默认输入白名单：

1. `PathSegment`
2. `Prototype`
3. `Skill`
4. 显式 `declared_subtask` 产物

### 8.3 原因

如果不冻结输入范围，系统会很快重新回到：

- 对象越来越多
- card 越来越多
- 但在线主闭环并没有更强，只是换了一层噪声

---

## 9. 约束 C7：GraphStore 与 sidecar 的分工必须写死

### 9.1 sidecar 的职责

sidecar 只负责：

1. append-only 原始事实记录
2. attempt 级账本
3. projected subtask 临时对象
4. subtask edge 临时对象

建议 sidecar 文件：

1. `episode_ledger.jsonl`
2. `subtask_instances.jsonl`
3. `subtask_edges.jsonl`

### 9.2 GraphStore 的职责

`GraphStore` 继续承担：

1. `ObservationKG`
2. `BeliefGraph`
3. `attempt_summary_v1`
4. `failure_card_v2`
5. `repair_pattern_v2`
6. 经过治理后的稳定对象视图

### 9.3 强制分工

1. sidecar 不做复杂 merge
2. sidecar 不承担最终 curated 语义
3. `GraphStore` 不接受未经治理的新长期对象
4. sidecar 新对象不得直接绕过治理层进入主检索视图

---

## 10. 约束 C8：治理层必须有最小状态机

`ObjectGovernancePolicy` 在 v2.1 中不是附属优化，而是方法正确性的组成部分。

### 10.1 最小状态机

所有 candidate 型对象至少要支持：

1. `candidate`
2. `promoted`
3. `suppressed`
4. `deprecated`

### 10.2 必须治理的对象

1. `abstract_experience`
2. `failure_card_v2`
3. `repair_pattern_v2`
4. `CompilerCard`
5. 后续进入 curated view 的 `Subtask` 派生对象

### 10.3 第一版必须具备的治理动作

1. 去重
2. 近重复合并
3. growth cap
4. pre-eval success guard
5. suppression
6. deprecation

### 10.4 默认约束

1. `preventive_rules_v2` 默认不进入主生成链
2. pre-eval success-like abstraction 不得直接进入 promoted 状态
3. unresolved attempt 不得默认生成无限增殖的近似 `failure_card_v2`

---

## 11. 约束 C9：热路径 / 冷路径预算必须量化

这是实施阶段最容易被忽视，但必须提前写死的部分。

## 11.1 热路径预算

热路径包括：

- `on_model_query`
- `on_action_executed`
- `on_action_error`

### 热路径必须遵守

1. 不允许调用重型 LLM 分析
2. 不允许做复杂 merge / cluster
3. 不允许同步生成 embedding
4. 不允许依赖 sidecar 成功写入才能继续主代理流程

### 热路径默认预算

1. 单次额外处理应维持在 **轻量级附加开销**
2. 第一版实现必须支持 **超时即降级为 telemetry / append-only log**
3. 若 sidecar 写入失败，主代理行为必须不受影响

> 说明：这里先写“轻量级附加开销”而不写死单机毫秒数，是因为运行环境可能变化；但实现上必须提供可配置 timeout，并以“失败可忽略”作为默认降级语义。

## 11.2 冷路径预算

冷路径包括：

- `handle_run_done`
- `ExtractionOrchestrator.process_attempt()`
- `SubtaskProjector`
- `SubtaskEdgeBuilder`
- `CardCompiler`
- `ObjectGovernancePolicy`

### 冷路径必须遵守

1. 允许做较重分析，但必须有总时限
2. 超预算时必须优先保住：
   - `attempt_summary_v1`
   - 最小 sidecar 事实写入
3. 超预算时可以跳过：
   - `projected_subtask`
   - `CompilerCard`
   - 治理增强步骤

### 冷路径默认预算

第一版必须支持：

1. 冷路径整体超时配置
2. 分阶段早停
3. 明确的 `skipped_reason`

---

## 12. 约束 C10：`projected_subtask` 是默认路线，`declared_subtask` 必须后置

### 12.1 v2.1 默认路线

v2.1 只支持：

- `projected_subtask`

其来源必须是冷路径投影，而不是在线协议强依赖。

### 12.2 禁止事项

以下内容在 v2.1 默认路线中禁止：

1. 强依赖 `subtask_start`
2. 强依赖 `subtask_end`
3. 强依赖 `abort / recheck`
4. 默认要求 planner 产出标准化子任务边界

### 12.3 `declared_subtask` 重新进入主线的前提

只有当下列三件事同时成立时，才允许重新讨论：

1. `projected_subtask` 在 repeat-run 上证明具有稳定预测价值
2. `success fact capture` 已经稳定
3. 热/冷路径预算已经量化且验证不破坏主链

---

## 13. 约束 C11：必须做验证门和 ablation

v2.1 不允许只凭“感觉更合理”推进。

## 13.1 三个验证门

### Gate A：Success Fact Capture Gate

至少要验证：

1. 成功 patch 的关键 action 能否被稳定回放
2. `touched_files / diff / tests` 能否在冷路径补全
3. 成功路径相关事实是否不再明显偏失败对象

### Gate B：Projected Subtask Stability Gate

至少要验证两类稳定性：

1. **解释性稳定**
   - 同类 attempt 是否能投影出相似的 subtask intent / boundary / failure type
2. **决策性稳定**
   - 编译成 card 后，是否真的提升：
     - retry 成功率
     - post-success retrieval sharpness
     - 注入噪声下降

### Gate C：Compiler Noise Gate

至少要验证：

1. card 数量是否可控
2. card 重复率是否下降
3. card 对 planning / repair 是否真正有帮助
4. compiler 是否没有把噪声从对象层平移到 card 层

## 13.2 必做 ablation

必须至少拆出下面四组：

1. 仅阶段6 控制层
2. 阶段6 控制层 + success fact capture
3. 上述基础上 + projected_subtask
4. 上述基础上 + compiler/governance

这样才能回答：

> 收益到底来自在线控制增强，还是来自长期记忆结构增强。

## 15. 推荐实施顺序

v2.1 的推荐顺序如下：

### Phase 1：事实层补齐

1. 打通 `on_action_executed -> handle_action_success`
2. 建立 sidecar append-only success fact 记录
3. 在 `run_done` 冷路径补全真值字段

### Phase 2：投影层接入

1. 新增 `EpisodeLedgerStore`
2. 新增 `SubtaskProjector`
3. 新增 `SubtaskEdgeBuilder`
4. 先产出 candidate 对象，不进入主检索默认视图

### Phase 3：Compiler/Governance v1

1. 冻结输入白名单
2. 输出四类 `CompilerCard`
3. 接入最小状态机和去重/配额

### Phase 4：official-eval 写回与实验

1. 接入三层信用协议
2. 写回 promotion/suppression
3. 跑三道 Gate 和 ablation

---

## 16. 一句话实施原则

**v2.1 不是“把长期记忆对象做全”，而是“先把成功事实、信用协议和治理边界做对”。**

如果这三件事没有做实，那么 Path、Prototype、Skill 都应该继续后置，而不是提前进入默认工程路线。
