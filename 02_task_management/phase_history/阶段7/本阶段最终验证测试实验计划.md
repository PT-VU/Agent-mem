# AgentMem v2.1 本阶段最终验证测试实验计划

## 1. 目标

本计划的目标不是再证明“某一次单题跑得不错”，而是更正式地验证下面两件事是否成立：

1. **同题维度**  
   AgentMem v2.1 是否能在解决同一个 SWE-bench Lite 问题的多次重试中：
   - 稳定提高成功率
   - 更早找到第一次成功路径
   - 在第一次成功前推动更多不同解题路径的探索
   - 从而降低首次成功所需的 attempt 数和 token 消耗
   - 在首次成功后增强成功路径复用

2. **跨题维度**  
   AgentMem v2.1 是否能在解决不同 SWE-bench Lite 问题的过程中积累可复用经验，并对后续问题带来正向收益，而不是只累积噪声。

本阶段优先使用 **SWE-bench Lite**，因为它更适合做多轮 repeat、顺序式 warm-start 和官方 eval 对比。

## 2. 本次计划要回答的核心问题

### 2.1 同题价值

我们要回答：

1. 记忆系统是否让 agent 在**首次成功之前**减少重复走旧路径，探索更多不同 patch family。
2. 记忆系统是否让**首次成功更早出现**，从而降低同题求解总 token 消耗。
3. 记忆系统是否让 agent 在同一问题上更容易**重复找到正确 patch family**。
4. 记忆系统是否让“第一次成功之后”的后续 attempts 更容易继续成功，而不是回退。
5. 记忆系统当前帮助的是：
   - 正确代码语义复用
   - workflow / validation discipline
   - 两者都有，但权重不同

### 2.2 跨题价值

我们要回答：

1. 不同问题之间是否存在可迁移经验。
2. 这些经验更像：
   - topic-specific
   - bug-family-specific
   - repo-specific
   - 还是只有泛 workflow 价值
3. 跨题经验积累是否会提高后续任务成功率，还是会引入 retrieval noise 和错误迁移。

## 3. 现阶段假设

基于当前 `astropy__astropy-14182` 单题 repeat10 结果，本计划采用以下工作假设：

### H1

AgentMem v2.1 在**同题重复求解**上已经有正向效果，尤其体现在：

- 成功率提升
- 成功路径重复出现
- repro / validation path 更容易复用
- 更能把 agent 拉回最小修补路径

### H2

AgentMem v2.1 当前的主要收益来源，仍然更偏：

- workflow discipline
- validation planning
- failure avoidance
- confirmed repro path reuse

而不是稳定的 code-level invariant transfer。

### H3

跨题迁移最可能先出现在：

- 同 topic
- 同子系统
- 相近 bug family

因此本阶段跨题验证不追求“所有 Lite 题目上的平均泛化”，而是优先验证**同 topic / 同 repo 序列中的经验积累价值**。

## 4. 总体实验设计原则

### 4.1 固定 prompt，先单独验证记忆增益

正式验证阶段默认使用：

- `prompt_profile = prompt_base`

原因是：

1. 先把 memory 变量和 prompt 变量解耦。
2. 避免出现“提升来自 prompt 还是来自 memory”无法归因。

`prompt_guard` 可以作为下一阶段扩展实验，不进入本阶段主结论。

### 4.2 主对照组必须简单

本阶段主比较对象固定为两个版本：

1. `NoMem`
   - 关闭 AgentMem
2. `v2.1_full`
   - 当前升级后的完整框架

本阶段**不设计消融实验**。

原因：

1. 先验证整体架构相对 `NoMem` 是否有效。
2. 如果整体收益都站不住，消融没有意义。
3. 如果整体收益站住了，再进入第二阶段拆 `compiler / projection / governance` 更合理。

### 4.3 主要结论必须来自官方 eval

所有主结论都必须以 `official_eval` 为准。

辅助指标可以使用：

- 首次成功 attempt index
- token 消耗
- patch family 多样性
- 成功路径复用率
- memory injection sharpness

但这些只能解释原因，不能替代主结果。

## 5. 实验维度 A: 同一个问题上的记忆价值

## 5.1 目标

验证 AgentMem v2.1 是否能在“同题多次重试”中带来稳定增益。

重点不只是看“最后成功几次”，还要看：

1. 首次成功前是否探索了更多不同路径
2. 是否减少了重复尝试同一半正确 patch family
3. 是否更早进入正确 patch family

## 5.2 数据集选择

优先从 SWE-bench Lite 中构造一个 **同题 repeat 集**。

建议样本规模：

- 第一轮正式验证：`12` 个 Lite 问题
- 第二轮扩展验证：`20` 个 Lite 问题
- 每题重复次数：`10` 次

样本选择原则：

1. 优先选择已有 failed-case 历史、适合重复实验的问题
2. 覆盖多个 topic，不只看单一 repo
3. 覆盖不同 bug 类型：
   - parser / formatting
   - API behavior
   - test regression
   - edge-case handling
4. 排除明显不稳定或资源消耗异常的问题

## 5.3 组别设计

每个实例都跑下面两个主组：

### A0: NoMem

- AgentMem 全关
- 每次 attempt 都是 fresh

作用：

- 给出纯 agent 基线

### A1: v2.1_full

- 使用当前完整升级
- 同题内允许 memory 累积

作用：

- 验证当前整体升级的真实收益

## 5.4 同题主指标

### 主指标

1. `Resolved@10`
   - 10 次内至少成功一次的比例
2. `Resolved Count / 10`
   - 10 次中成功次数
3. `First Success Index`
   - 第一次成功出现在第几次
4. `Pre-Success Path Diversity`
   - 首次成功之前，出现过的不同 patch family 数量
5. `Pre-Success Unique Exploration Rate`
   - 首次成功前，非重复路径 attempt 的占比
6. `Mean Tokens to First Success`
   - 从 attempt 1 开始，到第一次 official success 为止的累计 token

### 次指标

7. `Post-Success Reuse Rate`
   - 第一次成功之后，后续 attempts 再次成功的比例
8. `Path Stickiness`
   - 首次成功 patch family 出现后，后续 attempts 继续落在同族 patch 的比例
9. `Mean Steps to Submission`
10. `Mean Steps to First Valid Patch`
11. `Mean Tokens per Resolved Attempt`
12. `Incomplete Rate`

### 解释型指标

13. `Memory Injection Count / attempt`
14. `Injected family diversity`
15. `Compiler card hit rate`
16. `Successful patch family recurrence`

## 5.5 如何定义“同题上有价值”

满足下面条件，才认为 v2.1 在同题维度上通过：

### 必须同时满足

1. `Resolved Count / 10` 明显高于 `NoMem`
2. `First Success Index` 优于 `NoMem`
3. `Pre-Success Path Diversity` 不低于 `NoMem`
4. `Mean Tokens to First Success` 低于 `NoMem`
5. `Post-Success Reuse Rate` 在有首次成功的样本上为正向收益

### 推荐门槛

- `Resolved Count / 10` 相对 `NoMem` 提升至少 `+20%`
- `First Success Index` 相对 `NoMem` 改善至少 `-1`
- `Mean Tokens to First Success` 相对 `NoMem` 下降至少 `10%`
- `Incomplete Rate` 不高于 `NoMem`

## 5.6 同题维度的关键分析输出

每个实例最终都要产出：

1. 10 次 attempt 结果表
2. patch family 聚类结果
3. 首次成功前的路径多样性分析
4. 首次成功前的 token 消耗对比
5. 首次成功前后 memory injection 对比
6. success path 是否复用成功
7. 当前帮助更偏：
   - bug invariant
   - repro reuse
   - validation discipline
   - broad patch suppression

## 6. 实验维度 B: 不同问题之间的经验积累价值

## 6.1 目标

验证 AgentMem v2.1 是否能把前面题目中的经验迁移到后续新题，而不是只会在单题内部反复使用。

## 6.2 核心思路

跨题实验不能用“每题都 fresh”来测。

必须设计成 **顺序式 memory accumulation**：

1. 按预定顺序解决一串 Lite 问题
2. memory store 在问题之间保留
3. 看后面题目的表现是否比 fresh baseline 更好

## 6.3 数据划分

这里的“不同 repo”不是只按仓库名机械分组，而是优先把 **repo 近似当作 topic / 题型容器** 来选题。

原因：

1. 经验迁移最可能先发生在同 topic / 同子系统 / 同类 bug 内。
2. 如果一开始就把 repo 混得太散，容易把真实局部收益稀释掉。

因此本阶段建议用 **两个 repo / 两个 topic-oriented 序列**：

### B1: Repo / Topic 序列 1

- 选择 `1` 个 repo
- 取 `25` 个 SWE-bench Lite 题目
- 尽量集中在同类模块、相近 bug family、相近验证模式

### B2: Repo / Topic 序列 2

- 选择另 `1` 个 repo
- 再取 `25` 个 SWE-bench Lite 题目
- 尽量形成与序列 1 不同的 topic

推荐做法：

- `Repo A`: 偏表格/格式化/解析/IO 类
- `Repo B`: 偏 API 行为/测试回归/业务逻辑类

这样可以回答两个问题：

1. 同 topic / 同 repo 内经验积累是否有效
2. 不同 topic 下，v2.1 的收益强弱是否不同

## 6.4 组别设计

### B0: Fresh Per Instance

- 每个新题开始前清空 memory
- 这是跨题 baseline

### B1: Carry-Over v2.1_full

- 当前记忆框架跨题保留

## 6.5 跨题主指标

### 主指标

1. `Resolved Rate`
   - 后续测试题成功率
2. `Delta vs Fresh`
   - 相对于 fresh baseline 的成功率差
3. `First-Attempt Success Rate`
   - 第一轮就成功的比例
4. `Mean Tokens per Solved Instance`
5. `Time-to-First-Success`

### 次指标

6. `Mean Steps`
7. `Mean Attempts to Success`
8. `Cross-Problem Retrieval Hit Rate`
   - 注入记忆是否真的来自此前题目
9. `Harmful Transfer Rate`
   - 注入经验导致错误方向收敛的比例
10. `Noise Ratio`
   - 注入内容中与当前问题无关的比例

### 迁移诊断指标

11. `Same-Topic Transfer Gain`
12. `Workflow-only Gain`
13. `Bug-Family Transfer Gain`

## 6.6 如何定义“跨题上有价值”

满足下面条件，才认为 v2.1 在跨题维度上通过：

1. `Carry-Over v2.1_full` 在测试题上的 `Resolved Rate` 高于 `Fresh Per Instance`
2. 至少在两个 topic / repo 序列中的一个上有明确正向收益
3. `Harmful Transfer Rate` 可控
4. retrieval sharpness 没有随题目数量上升而明显恶化

建议门槛：

- 同 topic / repo `Resolved Rate` 相对 fresh 提升至少 `+10%`
- `First-Attempt Success Rate` 提升至少 `+10%`
- `Harmful Transfer Rate` 控制在 `<= 10%`

## 7. 统计与显著性

为了让结论更正式，本阶段建议做最小统计约束。

### 7.1 同题维度

使用：

- paired bootstrap CI
- per-instance paired comparison
- `Resolved Count / 10` 的 bootstrap 差值区间
- `First Success Index` 和 `Mean Tokens to First Success` 的 paired 差值分析

重点看：

- `NoMem vs v2.1_full`

### 7.2 跨题维度

使用：

- 分 repo / topic bootstrap
- 整体 bootstrap
- first-attempt success 的二项分布置信区间

### 7.3 通过条件

主结论必须满足：

1. 平均值更高
2. 至少在两个 topic / repo 序列中方向一致或至少一强一弱但整体正向
3. 不是靠单一实例拖起来的平均值

## 8. 本阶段不做消融

本阶段明确不设计：

- `no_compiler`
- `no_projection`
- `no_governance`

这些消融留到下一阶段。

本阶段只回答：

> 当前完整升级架构，相对于 `NoMem`，是否已经整体有效。

## 9. 实验执行顺序

为了控制资源和节奏，建议按三阶段推进。

## 9.1 Phase A: 小规模同题正式验证

规模：

- `12` 个 Lite 问题
- 每题 `10` repeats
- `2` 个主组

目的：

- 快速确认同题维度主结论能否站住
- 重点验证“首次成功前的路径多样性”和“首次成功 token 消耗”

产物：

- `same_problem_formal_report.md`

## 9.2 Phase B: 扩展同题 + 两个跨题序列试运行

规模：

- 同题扩到 `20` 题
- 跨题做 `2` 个 repo / topic 序列
- 每个序列 `25` 题

目的：

- 验证跨题迁移是否有方向性收益

产物：

- `cross_problem_pilot_report.md`

## 9.3 Phase C: 完整跨题正式验证

规模：

- 完成两个 `25` 题序列的正式 carry-over 实验
- 必要时再追加第三个 topic 序列

目的：

- 给出“是否具备更普遍有效性”的正式判断

产物：

- `phase7_final_validation_report.md`

## 10. 运行与记录要求

每次实验必须显式记录：

1. `prompt_profile`
2. `model_config`
3. `memory profile`
4. `v21 flags`
5. `run_tag`
6. `seed / repeat index`
7. `repo`
8. `instance_id`
9. `attempt_count`
10. `official_eval result`
11. `token usage`

额外必须保存：

1. `graph_store`
2. `sidecar_store`
3. `attempt summaries`
4. `attempt feedback`
5. `prediction patch`
6. `memory injection logs`

否则后续无法做解释分析。

## 11. 风险与防偏差设计

## 11.1 主要风险

1. 单次采样波动太大
2. prompt 变化污染 memory 结论
3. 不同 topic 难度差异过大
4. carry-over 实验中噪声累积
5. 某一个 repo 序列拉高或拉低整体结果

## 11.2 缓解方案

1. 使用 repeat，而不是单次运行
2. 主实验固定 `prompt_base`
3. 分 repo / topic 报告结果
4. 记录 harmful transfer
5. 用 fresh baseline 做严格对照

## 12. 本阶段最终想得到的结论形式

本阶段最终报告必须能明确回答下面四句话：

1. `v2.1` 在 SWE-bench Lite 上，对**同题重复求解**是否比 `NoMem` 更有效。
2. `v2.1` 在 SWE-bench Lite 上，对**跨题经验积累**是否比 `Fresh` 更有效。
3. 当前收益主要来自：
   - repro / validation reuse
   - workflow control
   - 还是 code invariant transfer
4. 当前框架下一步应该继续强化：
   - fact plane
   - compiler promotion
   - bug-specific success card
   - 还是跨题治理

## 13. 推荐的最小正式执行版本

如果本阶段资源有限，我推荐先执行下面这个最小正式版：

### 同题正式版

- `12` 个 Lite 问题
- 每题 `10` repeats
- 组别：
  - `NoMem`
  - `v2.1_full`

### 跨题正式版

- `2` 个 repo / topic
- 每个 repo `25` 题
- 每组顺序 carry-over
- 组别：
  - `Fresh`
  - `v2.1 carry-over`

这样已经足够回答：

- 当前升级相对于 `NoMem` 是否更有效
- 有效性更偏同题还是跨题

## 14. 最终判断标准

本阶段只有在以下两条都成立时，才算“更普遍有效性被初步验证”：

1. **同题维度通过**
   - `v2.1_full > NoMem`
   - 且首次成功更早
   - 且首次成功前路径探索更多样
   - 且成功路径复用率更高

2. **跨题维度通过**
   - `v2.1 carry-over > Fresh`
   - 且 harmful transfer 可控

如果只满足第一条，不满足第二条，那么本阶段应得出的诚实结论是：

> 当前 AgentMem v2.1 已经证明了同题重试价值，但跨题知识积累价值仍待验证。

如果两条都满足，才可以说：

> 当前升级不仅改善了同题搜索复用，也开始具备跨题经验迁移的更普遍有效性。
