# 实验设计报告

> 本文档用于辅助学术论文写作，所有内容基于实际执行的实验脚本、配置文件与运行日志，不含推测性内容。

---

## 1. 研究问题

本研究的核心问题是：**跨 attempt 记忆框架能否提升大语言模型（LLM）在代码自动修复任务（SWE-bench）中的解题率？**

具体而言，我们考察以下子问题：
1. 记忆框架在多次独立尝试之间传递知识，能否使后续 attempt 避免重复已知失败路径并复用已知成功路径？
2. 记忆框架的效果是否依赖于模型基础能力（nomem 解出率）？
3. 引入记忆框架后，LLM 的 token 消耗（效率）是否发生变化？
4. 记忆框架的效果是否跨模型泛化？

---

## 2. 实验基准：SWE-bench

### 2.1 数据集选择

实验使用 **SWE-bench Full**（完整集，2,294 个实例），而非 SWE-bench Lite（300 个）或 SWE-bench Verified（500 个）。

选择 Full 集的理由：
- Lite 集为社区高度关注的 benchmark，模型可能存在过拟合污染风险
- Verified 集筛选了"人工确认可解"的实例，不代表真实难度分布
- Full 集提供更宽的实例难度谱，有利于观察记忆框架在不同难度区间的效果

### 2.2 评测方式

每个 attempt 的结果通过 SWE-bench 官方评测脚本（`swebench.harness.run_evaluation`）判定。评测在独立 Docker 容器内执行，通过运行实例对应的测试套件确认 patch 是否真正修复了 bug。结果以 `resolved_ids`（通过）/ `unresolved_ids`（未通过）记录在 `official_eval.json` 中。

### 2.3 实例选择策略

实验分批次扩大实例规模：

**早期探索阶段（F1+F2 前身）**：6 个实例（astropy-11693、astropy-12057、django-11278、sympy-22383、pytest-7231、scikit-learn-26289），用于框架调试与 bug 修复，这批数据因框架版本不一致，不纳入最终分析。

**F1+F2 阶段**：3 个实例（sympy-22383、astropy-11693、astropy-12057），仅跑 with_mem 模式（使用预存的 nomem 基线），验证框架基本流程。

**F3 阶段（核心实验）**：9 个实例，覆盖 3 个主流 Python 开源项目，同时运行 nomem 与 with_mem 两组，构成完整的受控对照实验：

| 实例 | 项目 |
|------|------|
| django\_\_django-12284 | Django |
| django\_\_django-16139 | Django |
| django\_\_django-12497 | Django |
| sympy\_\_sympy-24066 | SymPy |
| sympy\_\_sympy-13031 | SymPy |
| sympy\_\_sympy-13551 | SymPy |
| astropy\_\_astropy-12907 | Astropy |
| astropy\_\_astropy-14995 | Astropy |
| astropy\_\_astropy-13033 | Astropy |

选择这 9 个实例的标准：
- 未在早期阶段使用过（避免记忆库预污染）
- 覆盖三个不同项目（测试跨项目泛化性）
- 预估 nomem 解出率处于 20–60% 区间（基于 phase8 数据估计），使记忆框架有发挥空间

## 3. 实验设计

### 3.1 对照组设计（nomem vs. with_mem）

核心实验为**配对对照设计**：对每个实例，在完全相同的配置下分别运行 nomem 组和 with_mem 组，每组各运行 10 次独立 attempt（repeat=10）。

- **nomem 组**：标准 SWE-agent 运行，无任何记忆注入，每次 attempt 相互独立
- **with_mem 组**：启用记忆框架，attempt 之间通过共享记忆图谱（GraphStore）传递知识；每次 attempt 结束后框架自动抽取并写入记忆卡片，供后续 attempt 检索

两组使用完全相同的：模型、prompt 模板、工具配置、Docker 环境、SWE-bench 数据集分区。

### 3.2 时间公平性控制（Watchdog 机制）

with_mem 组每次 attempt 需要通过 HTTP 调用记忆服务器（bridge overhead），每次调用约 7–9 秒。若不加控制，with_mem 组每次 attempt 的实际可用思考时间将少于 nomem 组，导致不公平对比。

为此，设计并实现了 **Watchdog 计时器**（`bin/watchdog.py`）：

```
agent_time = wall_elapsed - Σ(bridge_overhead)
当 agent_time ≥ budget 时，os.killpg() 杀死整个进程组
```

Watchdog 将每次 bridge 调用的耗时写入 `bridge_overhead.tmp` 文件（每行一个浮点数），实时累加后从总墙钟时间中扣除，确保 nomem 和 with_mem 获得相同的"净 agent 时间"（`budget = 1200s`）。

这一设计解决了此前实验中 with_mem 组因 bridge 调用占用预算而处于劣势的问题。

### 3.3 重复次数与统计考量

每组每实例运行 10 次 attempt，出于以下考量：
- 10 次可计算 95% 置信区间（Wilson/正态近似），足以判断效果方向
- 记忆框架的效果需要多次 attempt 才能积累（attempt 1 无先验记忆，attempt 2+ 开始受益）
- 资源限制下的可行数量（每次 attempt 墙钟时间约 12–35 分钟）

### 3.4 并发控制

实验通过资源槽（resource slot）机制控制并发：

```
GLOBAL_HEAVY_SLOTS = 2   # 全局最多同时运行 2 个重实例
NOMEM_HEAVY_SLOTS  = 1   # nomem 槽位 1
WITHMEM_HEAVY_SLOTS = 1  # with_mem 槽位 1
```

nomem 和 with_mem 并行推进（不同 Docker 容器、不同输出目录），互不干扰。

### 3.5 断点续跑设计

所有实验支持断点续跑（`RESUME_MODE=1, REDO_EXISTING=0`）：框架在每次 attempt 完成后写入独立的结果文件，重启后自动跳过已完成的 attempt。这一设计对于应对 Docker 崩溃、网络中断等实际情况至关重要，本实验中实际发生了多次因 Docker Desktop 停止导致的中断，均通过断点续跑恢复。

## 4. 模型配置

### 4.1 主实验模型：Kimi（kimi-latest / moonshot-v1）

- API：Moonshot AI（`https://api.moonshot.cn/v1`）
- 配置文件：`SWE-agent/config/kimi25_moonshot.yaml`
- 解析方式：`function_calling`（工具调用）
- 温度：默认
- 历史处理：`cache_control`，保留最后 2 条消息的缓存

### 4.2 对比实验模型：DeepSeek V4 Pro（非思考模式）

- API：DeepSeek 官方（`https://api.deepseek.com/v1`）
- 模型名：`deepseek-v4-pro`
- 配置文件：`SWE-agent/config/deepseek_v4_pro.yaml`
- 与 Kimi 实验完全相同的实例和框架配置

DeepSeek 实验目的：验证记忆框架是否跨模型泛化，以及记忆框架效果与模型基础能力的关系。

### 4.3 记忆抽取模型

with_mem 组中，BugInvariantCard 等记忆卡片的抽取由独立 LLM 调用完成（`llm_extractor.py`）：
- Kimi 实验：`kimi-k2.5`（Moonshot AI）
- DeepSeek 实验初版：误用 `kimi-k2.5`（与 agent 模型不一致，后发现并修正）
- DeepSeek 实验修正版：`deepseek-v4-pro`（与 agent 模型保持一致）

## 5. 实验变量

### 5.1 自变量
- **记忆框架启用状态**：nomem（关闭）vs. with_mem（开启所有 v2 模块）
- **模型**：Kimi vs. DeepSeek V4 Pro

### 5.2 因变量
- **解出率**（resolve rate）：10 次 attempt 中成功修复 bug 的比例
- **token 消耗**：per-attempt 的 input token 数（`tokens_sent`）
- **API 调用次数**：per-attempt 的 `api_calls` 数
- **exit_status 分布**：`submitted` / `submitted (exit_format)` / `exit_format` / `None`（Watchdog 杀死）

### 5.3 控制变量
- Docker 镜像：每个实例使用 SWE-bench 官方镜像（`swebench/sweb.eval.x86_64.*`）
- Prompt 模板：所有实验使用相同的 `prompt_base` 配置
- 工具集：`tools/registry` + `tools/edit_anthropic` + `tools/review_on_submit_m`
- 预算：nomem 1200s / with_mem 1200s（净 agent 时间，Watchdog 保证）
- 数据集分区：`subset=full, split=test`

## 6. 计划对比分析

### 6.1 主对比：nomem vs. with_mem（Kimi）
- 9 个实例 × 10 次 × 2 组 = 180 次 attempt
- 分析粒度：per-instance 和 aggregate
- 统计方法：比例差值（pp）、相对提升（%）、95% 置信区间（正态近似）

### 6.2 有效区间分析
将实例按 nomem 解出率分组（0%、0–70%、100%），分析记忆框架在不同能力区间的效果差异。
预期假设：nomem 解出率处于 20–60% 时效果最显著；0% 时无成功轨迹可学习；100% 时记忆引入干扰。

### 6.3 Token 效率对比
- per-attempt 的 input/output token 均值对比
- 分析：记忆引导是否缩短了无效探索轮次，从而降低 token 消耗

### 6.4 跨模型对比（Kimi vs. DeepSeek）
- 相同 9 个实例，对比两个模型的 nomem 解出率
- 验证：DeepSeek nomem 解出率显著高于 Kimi 时，记忆框架是否仍有提升空间

### 6.5 exit_status 分析
- 分析 with_mem 与 nomem 组的 `submitted` 率差异
- 重点关注 `None`（Watchdog 杀死）比例，作为"轨迹失控"的指标
