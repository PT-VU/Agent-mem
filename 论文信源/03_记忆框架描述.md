# 记忆框架架构描述

> 本文档基于对框架源码文件（`bridge_hook.py`、`agent_mem/` 各子模块）的逐行阅读。  
> 所有模块名、类名、环境变量名、参数值均来自实际代码，不含推测。  
> 本文档面向无任何项目内部背景的读者，描述粒度达到可独立还原的程度。

---

## 1. 框架定位

本框架（`sweagent_external_tools_v2`）是 **SWE-agent v1.1.0** 的无侵入外部扩展。它通过 SWE-agent 提供的 Hook 接口（`AbstractAgentHook`）接入 agent 的执行流程，不修改 SWE-agent 核心代码。

**核心功能：** 在同一 bug 实例的多次独立 attempt 之间传递知识——从已完成的 attempt 中抽取结构化记忆卡片，在后续 attempt 开始时将卡片内容注入 agent 的 prompt，引导 agent 复用已知成功路径或规避已知失败路径。

---

## 2. 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                    SWE-agent 执行流程                    │
│                                                         │
│  on_init() → on_run_start() → [on_model_query() +      │
│  on_step_start() + on_actions_generated() +             │
│  on_step_done()] × N 步 → on_run_done()                │
└──────────────┬──────────────────────────────────────────┘
               │ Hook 事件
               ▼
┌─────────────────────────────────────────────────────────┐
│           ExternalToolBridgeHook (bridge_hook.py)       │
│                                                         │
│  ┌─────────────────┐   ┌──────────────────────────────┐ │
│  │   Tool A 调用   │   │    on_model_query() 注入      │ │
│  │ (记忆查询/存储)  │──→│  "[AgentMem Hints]" 追加到  │ │
│  │ 异步 ~45s 超时  │   │  messages 末尾               │ │
│  └─────────────────┘   └──────────────────────────────┘ │
│  ┌─────────────────┐                                     │
│  │   Tool B 调用   │   事件日志写入 hook_events.jsonl    │
│  │ (事件日志记录)  │                                     │
│  │ 同步  ~8s 超时  │                                     │
│  └─────────────────┘                                     │
└──────────────┬──────────────────────────────────────────┘
               │ attempt 结束后（官方评测完成）
               ▼
┌─────────────────────────────────────────────────────────┐
│       EvaluationFeedbackProcessor                       │
│  resolved → 写 SuccessPathCard + BugInvariantCard       │
│  unresolved → 写 BugAntiPatternCard                     │
└──────────────┬──────────────────────────────────────────┘
               │
               ▼
┌─────────────────────────────────────────────────────────┐
│                GraphStore (NetworkX + JSON)              │
│         跨 attempt 持久化，每个实例独立目录              │
└─────────────────────────────────────────────────────────┘
```

**核心组件：**

| 组件 | 文件 | 职责 |
|------|------|------|
| `ExternalToolBridgeHook` | `bridge_hook.py` | Hook 主体，拦截所有 agent 事件，调用 Tool A/B，注入 prompt |
| `GraphStore` | `agent_mem/storage/graph_store.py` | 基于 NetworkX 的持久化图存储，同一实例的多次 attempt 共享 |
| `EvaluationFeedbackProcessor` | `agent_mem/processing/evaluation_feedback.py` | 官方评测后写入/更新记忆卡 |
| `CardCompiler` | `agent_mem/processing/card_compiler.py` | 从图存储检索并编译注入 prompt 的卡片 |
| `LLMExperienceExtractor` | `agent_mem/processing/llm_extractor.py` | 调用独立 LLM 从执行步骤中抽取结构化 CriticalSignal |
| `HierarchicalRetriever` | `agent_mem/retrieval/retriever.py` | 分层检索（任务级 + 动作级），基于 embedding 相似度 |

## 3. 记忆卡类型

卡片类型定义于 `agent_mem/types.py`，`CompilerCardType` 枚举：

| 卡片类型 | 何时写入 | 内容 |
|---------|---------|------|
| `SuccessPathCard` | 官方评测 resolved | 成功修复路径的步骤摘要 |
| `BugInvariantCard` | 官方评测 resolved | bug 不变量特征：`verbatim_diff`（原始 patch，最大 8192 字节）、`anchors`（文件名+行号+函数签名）、`patch_signature_hash`（前 6 行新增代码的 SHA1） |
| `BugAntiPatternCard` | 官方评测 unresolved | 已知错误 patch 的签名（`failed_patch_signature`、`patch_signature_hash`），用于后续检测重复提交 |
| `PlanHintCard` | CardCompiler 从摘要编译 | 规划阶段的高层提示 |
| `RetryHintCard` | CardCompiler 从失败卡编译 | 重试建议 |
| `TimeoutGovernanceCard` | 步骤预算超限 | 催促 agent 尽快提交 |
| `ClosureGuardCard` | 闭包保护激活 | 阻止 agent 重复已失败的探索路径 |

**治理状态机：** 所有卡片初始状态为 `CANDIDATE`，官方评测后：
- resolved → 关联卡片升级为 `PROMOTED`
- unresolved → 关联卡片压制为 `SUPPRESSED`

只有 `PROMOTED` 状态的卡片在后续 attempt 中被检索和注入。

## 4. Tool A / Tool B 的角色

BridgeHook 通过两条外部命令与记忆系统交互，事件 payload 通过环境变量 `SWE_AGENT_EXT_EVENT_JSON` 传递（JSON 序列化）：

**Tool A**（`SWE_AGENT_EXT_TOOL_A_CMD`，默认超时 45s）：
- 处理需要访问 GraphStore 的重量级操作：记忆检索、卡片推送、摘要存储
- 返回 JSON（包含 `planning_tips`、`repair_suggestions`、`recommendations` 等），BridgeHook 解析后缓冲为 hint 队列
- 失败时使用上次成功响应的 stale fallback

**Tool B**（`SWE_AGENT_EXT_TOOL_B_CMD`，默认超时 8s）：
- 轻量级事件日志记录，写入 JSONL 文件（`hook_events.jsonl`）
- 记录 `memory_hint_buffered`、`memory_injected`、`external_tool_result` 等事件

**Overhead 记录：** 每次 Tool A/B 调用完成后，将本次调用耗时（秒，浮点数）追加写入 `SWEAGENT_BRIDGE_OVERHEAD_FILE`（`.bridge_overhead.tmp`），Watchdog 累加读取此文件以扣除记忆调用开销。

## 5. 单次 Attempt 完整执行流程

```
on_init()
  └─ 识别 instance_id（从 agent 属性或 SWE_AGENT_EXT_INSTANCE_ID 环境变量）

on_run_start()
  └─ 初始化步骤预算状态（steps_since_last_edit=0, total_steps=0）

对每步执行：
  on_step_start()
    └─ 步骤预算检查（L1/L2/L3 触发，见第 8 节）
    └─ 调用 Tool A（plan_generated 事件）→ 缓冲 planning_tips
    └─ 更新 _step_index

  on_model_query(messages)
    └─ 模块 D：_v2_decide_strategy()（策略调度器，见第 8.4 节）
    └─ 模块 D：_v2_inject_strategy_header(messages)（注入策略头部）
    └─ _select_hints_for_injection()（按 bucket 优先级+置信度排序）
    └─ 若有可注入 hint：
         messages.append({
           "role": "user",
           "content": "[AgentMem Hints]\n{hint 列表，编号 1-N}"
         })
       截断到 max_hint_chars（默认 900）字符

  on_actions_generated(step)
    └─ 扫描 action_text 中的触发器（before_submit、before_test_run、first_file_access、over_exploration）
    └─ 检测是否创建新的临时脚本（test_/reproduce_/debug_*.py）
    └─ 模块 C：若 action 含 submit 关键字 → _v2_check_consistency_gate(step)（见第 8.3 节）
    └─ 步骤预算更新（is_code_edit / is_patch_submission）

  on_step_done(step, output)
    └─ 更新连续失败计数
    └─ 若 observation 包含 error 关键字：调用 Tool A（action_error 事件）→ 缓冲 repair_suggestions
    └─ 调用 Tool B 记录事件日志
    └─ 写入 bridge_overhead 到 .bridge_overhead.tmp

on_run_done()
  └─ 模块 E：LocalEffectiveFeedback
       统计 active_interventions 的 success_events/error_events 比
       发出 v2_card_feedback_request 事件（供 GraphStore.adjust_card() 调整置信度）
  └─ 触发 EvaluationFeedbackProcessor（在官方评测完成后）
       resolved → _write_success_path_card() + _write_bug_invariant_card()
       unresolved → _write_bug_anti_pattern_card()
```

## 6. 记忆注入机制（Hint 选择与 Prompt 格式）

### 6.1 缓冲队列

Tool A 返回的记忆项目进入 `_pending_memory_hints`（双端队列），每项记录：
- `hint`：注入文本（最大 280 字符/条）
- `card_type`：原始卡片类型
- `family_id`：用于去重和冷却
- `selection_score`：综合评分（`0.45×helpfulness + 0.25×novelty + 0.20×confidence + 0.10×batch_confidence`）
- `signature_hash` / `minimal_patch_signature`：用于 PatchConsistencyGate 比对
- `prefer_actions` / `avoid_actions`：具体行为引导

### 6.2 Hint 桶（Bucket）分类与优先级

```python
bucket_priority = {
    "semantic": 6,   # BugInvariantCard, SuccessPathCard, BugAntiPatternCard
    "closure":  5,   # 闭包信号（步骤超限警告、过度探索警告）
    "repair":   4,   # FailureCardV2, RepairPatternV2
    "validation": 3, # 验证缺失提示
    "general":  2,   # 其他抽象模式
    "workflow":  1,   # 规划提示（belief_tip，仅前 3 步注入）
}
```

每个桶的单次注入上限：
- `semantic`：4 条（BugInvariant 1 + SuccessPath 1 + AntiPattern 最多 2）
- `closure`、`repair`、`validation`、`workflow`：1 条
- 其他：2 条

### 6.3 Hint 选择算法（`_select_hints_for_injection()`）

1. 按 `(bucket_priority, selection_score, confidence)` 降序排列候选池
2. 同一 `family_id` 本次已选过则跳过（去重）
3. `family_cooldown_steps`（默认 4）：同 family 上次注入后未超过 4 步则跳过
4. `max_hints_per_family_per_attempt`（默认 1）：非 semantic 卡同一 family 整个 attempt 最多注入 1 次
5. 总字符预算 `hint_char_budget`（默认 2400）；semantic 卡豁免字符限制

### 6.4 注入格式

```
[AgentMem Hints]
Treat matching hints as high-priority guidance for this attempt.
Avoid over-exploration: reuse validated repro/fix paths first, and once a minimal
plausible patch exists, validate it before broadening the search.
1. <hint 文本>
2. <hint 文本>
...
```

此块以 `{"role": "user", "content": ...}` 形式追加到 `messages` 列表末尾（`on_model_query` 中），即作为 user 消息插入对话历史的最后一条，确保模型在生成下一步 action 前看到记忆内容。

## 7. 五个功能模块

所有模块**默认关闭**，通过环境变量逐项启用（F3 实验全部启用）。

### 模块 A：BugInvariantCard Schema 扩展

**环境变量：** `AGENT_MEM_BUG_INVARIANT_VERBATIM=1`

成功时写入的 BugInvariantCard 附带：
- `verbatim_diff`：原始 patch diff 文本，截断到 `_VERBATIM_DIFF_MAX_BYTES = 8192` 字节
- `anchors`：diff 修改的代码位置（文件名、行号、函数名、参数签名）
- `patch_signature_hash`：从 patch 新增行（`+` 开头，非注释，≥5 字符）取前 6 行计算 SHA1，格式 `sha1:<hex>`

设计目的：原始 BugInvariantCard 仅有文字摘要，VERBATIM_REUSE 策略需要完整 diff 才能精确复现成功 patch。

### 模块 B：BugAntiPatternCard（失败侧对称卡）

**环境变量：** `AGENT_MEM_BUG_ANTI_PATTERN=1`

unresolved 时写入失败模式卡，包含：
- `patch_signature_hash`（与模块 A 相同的哈希算法）
- `error_signature`：错误类型 + 相关代码位置
- `failed_patch_signature`：函数参数签名（用于 Gate 的参数级比对）

同时将 BugAntiPatternCard 加入 `semantic` 桶（最高注入优先级），在 `_buffer_memory_hints()` 中注册到 `_v2_active_anti_patterns` 活跃池供 Gate 比对。

### 模块 C：PatchConsistencyGate（提交前一致性检查）

**环境变量：** `AGENT_MEM_PATCH_CONSISTENCY_GATE = off | advise | enforce`

在 `on_actions_generated()` 检测到 submit/final answer 时触发，决策流程：

```
检测到 submit 动作
  │
  ├─ _v2_gate_pending_pass == True？
  │     └─ 是 → 直接放行（prevent 无限改写循环）
  │
  ├─ 能从 action 文本中提取 inline diff？
  │     └─ 否（submit 无参时 patch 在容器里） →
  │           改写 action 为 git diff 自检命令：
  │             cd /testbed && git add -A && git diff HEAD
  │             + 打印 [INVARIANT] / [ANTI-PATTERN] 提示
  │           设置 _v2_gate_pending_pass = True
  │           返回 "pre_check"
  │
  └─ 计算当前 patch 的 signature_hash
        └─ 与 _v2_active_anti_patterns 中的 hash 匹配？
              ├─ 是（enforce 模式）→ 触发 force_reuse 或 rewrite（返回 "force_reuse"）
              ├─ 是（advise 模式）→ 注入警告提示（返回 "advise"）
              └─ 否 → 放行（返回 "allow"）
```

`advise` 模式不阻断提交，仅在下一步 prompt 中注入警告；`enforce` 模式改写 step.action。

### 模块 D：ReuseExploreScheduler（策略调度器）

**环境变量：** `AGENT_MEM_REUSE_EXPLORE = off | auto`；`AGENT_MEM_FORCE_STRATEGY = auto | reuse | explore`

在 `on_model_query()` 首次调用时（延迟至卡片到达后，最晚在步骤 3）决定本次 attempt 的策略：

**概率计算（`auto` 模式）：**
```python
n_resolved = len(_v2_active_invariants)   # 已有成功卡片数
n_failed   = len(_v2_active_anti_patterns) # 已有失败卡片数

if n_resolved == 0:
    strategy = "explore_fresh";  p_reuse = 0.0
elif n_failed == 0 and n_resolved >= 1:
    p_reuse = min(0.5 + 0.2 * n_resolved, 0.9);  pool = "reuse_dominant"
else:
    p_reuse = max(0.4, min(0.85, 0.6 + 0.1 * (n_resolved - n_failed)));  pool = "mixed"

# 确定性 RNG：seed = sha1("{instance_id}::{attempt_id}::{run_id}")[:12]
draw = Random(seed).random()
strategy = "VERBATIM_REUSE" if draw < p_reuse else "EXPLORE_AROUND_INVARIANT"
```

**三种策略：**
- **VERBATIM_REUSE**：注入 BugInvariantCard 的完整 verbatim_diff，L1 步骤预算从 15 收紧到 8，要求 agent 尽快复现成功 patch
- **EXPLORE_AROUND_INVARIANT**：以 BugInvariantCard 的锚点（文件+行号）为起点，允许在已知区域周围自由探索
- **explore_fresh**：无成功卡片时的默认策略，不注入约束

**`FORCE_STRATEGY` 消融变量：** `reuse` 强制 VERBATIM_REUSE，`explore` 强制 EXPLORE_AROUND_INVARIANT，用于消融实验。

记录事件：`v2_reuse_explore_decision`（含 n_resolved、n_failed、p_reuse、strategy）。

### 模块 E：LocalEffectiveFeedback + L3 强制提交

**环境变量：** `AGENT_MEM_LOCAL_EFFECTIVE_FEEDBACK=1`；`AGENT_MEM_L3_FORCE_SUBMIT = off | dry_run | enforce`

**LocalEffectiveFeedback：**
- 每次记忆注入后，开启一个 `intervention_window`（默认 5 步）的追踪窗口
- 在窗口内统计 `action_error`（error_events）和 `action_success`（success_events）事件
- attempt 结束时，按 per-card 统计发出 `v2_card_feedback_request` 事件，下游 `GraphStore.adjust_card()` 据此提升或降低卡片置信度

**L3 强制提交：**
- `dry_run`（F3 实验）：达到 L3 阈值（总步数 ≥ 50 且无 patch）时记录 `v2_l3_dry_run` 事件，不修改 agent 动作
- `enforce`：将 step.action 改写为强制提交当前最优 patch 候选（F3 实验未使用）

## 8. 步骤预算（Step Budget）系统

BridgeHook 内置基于步骤计数的行为约束，与记忆系统并行运行：

| 阈值 | 环境变量 | 默认值 | 触发行为 |
|------|---------|-------|---------|
| L1 | `AGENT_MEM_STEP_GUARDRAIL_NO_EDIT` | 15 | 超过 N 步未编辑文件，每 5 步注入一条 `[StepBudget]` 警告 hint |
| L2 | `AGENT_MEM_STEP_STRONG_NO_PATCH` | 25 | 超过 N 步无 patch 候选，阻断宽泛回归测试 |
| L3 | `AGENT_MEM_STEP_HARD_STOP_TOTAL` | 50 | 总步数达上限且无 patch，注入强制提交指令 |

VERBATIM_REUSE 策略激活时，L1 自动收紧至 `min(原值, 8)`。

**补充预算：** 若 agent 在 action 中明确确认复现成功（匹配 `repro_confirm|reproduction.*pass` 等模式），额外获得 5 步缓冲。

---

## 9. Proactive Trigger（主动触发）系统

BridgeHook 扫描每步 action 文本，识别以下触发器：
- `before_submit`：检测到 submit/final_answer 关键字
- `before_test_run`：检测到 pytest/unittest 等测试命令
- `first_file_access`：首次出现的 `.py`/`.js` 等代码文件名
- `over_exploration`：创建了 ≥2 个临时脚本（`test_*.py`、`reproduce_*.py`、`debug_*.py`）时激活**闭包保护**

闭包保护激活后：
- 阻断 `workflow` 桶的 hint 注入
- 阻断新建临时脚本的 action（改写为警告 printf 命令）
- 注入 `selection_score=0.98` 的高优先级终止提示

## 10. GraphStore

**文件：** `agent_mem/storage/graph_store.py`  
**实现：** NetworkX DiGraph（内存图）+ JSON 文件序列化到 `AGENT_MEM_STORAGE_DIR/{instance_id}/` 目录

GraphStore 的作用是跨 attempt 持久化：每次 attempt 启动时从磁盘加载，结束后写回。同一 bug 实例的所有 attempt 共享同一 GraphStore 目录。

**存储结构：**

| 字典键 | 类型 | 说明 |
|--------|------|------|
| `abstract_experiences` | dict | 候选经验对象（FailureCardV2、RepairPatternV2、PreventiveRuleV2） |
| `compiler_cards_v21` | dict | 编译后的 prompt 注入卡片（含 BugInvariantCard、SuccessPathCard、BugAntiPatternCard） |
| `attempt_summaries_v1` | dict | 各 attempt 的轻量摘要 |
| `observation_kg` | ObservationKG | 工具调用观测事实图 |
| `belief_graph` | BeliefGraph | agent 对环境的信念（AtomicBelief、AttemptBelief） |

**`adjust_card()` 方法：** 接受 `v2_card_feedback_request` 事件，根据 success_events/error_events 比例小幅调整卡片的 `confidence` 字段（模块 E 闭环）。

## 11. LLM 经验抽取器

**文件：** `agent_mem/processing/llm_extractor.py`，类 `LLMExperienceExtractor`

抽取器通过 OpenAI-compatible API 调用**独立 LLM**（与 agent 运行模型相互独立），分析 agent 执行步骤，生成结构化的 `CriticalSignal`：

```python
@dataclass
class CriticalSignal:
    attempt_id: str
    critical_step: int         # 关键步骤索引
    critical_module: str       # 涉及的代码模块
    error_type: str            # 错误类型
    root_cause: str            # 根因分析
    cascading_effects: list    # 级联影响
    correction_guidance: str   # 修复引导文本
    confidence: float          # 置信度（0–1）
```

**运行模式（`AGENT_MEM_LLM_EXTRACT_MODE`）：**
- `hybrid`（默认）：先运行规则引擎（`ErrorTaxonomy.classify_attempt()`），再调用 LLM 补充，结果合并
- `heuristic`：仅规则引擎，不调用 LLM

**配置环境变量（`from_env()` 读取）：**
- `AGENT_MEM_LLM_MODEL`：模型名称（默认 `deepseek-chat`）
- `AGENT_MEM_LLM_API_URL`：API endpoint
- `AGENT_MEM_LLM_API_KEY`：API 密钥
- `AGENT_MEM_LLM_TIMEOUT_SEC`：单次调用超时，默认 20s

**注意：** 抽取模型与 agent 使用的模型相互独立，需在实验中显式配置一致性（否则可能使用框架默认值）。F3 实验中：Kimi 实验使用 `kimi-k2.5`，DeepSeek 实验使用 `deepseek-v4-pro`。

## 12. Watchdog 计时器

**文件：** `bin/watchdog.py`

**问题背景：** with_mem 每次 attempt 需要调用记忆服务器（每次约 7–9s），若以总墙钟时间作为 agent 运行预算，with_mem 组的"净思考时间"将系统性地少于 nomem 组，导致不公平对比。

**解决方案：** Watchdog 将 agent 进程的运行时间从总墙钟时间中减去记忆调用开销：

```
agent_time = wall_elapsed − Σ(bridge_overhead_per_call)
当 agent_time ≥ budget 时：kill → 返回退出码 124
```

**实现细节：**
```python
proc = subprocess.Popen(cmd, start_new_session=True)
# start_new_session=True → 子进程进入独立进程组
# 超时时：os.killpg(os.getpgid(proc.pid), signal.SIGKILL)
# 覆盖 SWE-agent 及其所有子孙进程（包括 Docker exec）
```

- 每秒轮询：`elapsed = time.monotonic() - t_start`；`overhead = sum(float(line) for line in .bridge_overhead.tmp)`
- 超时后打印诊断信息（elapsed、overhead、agent_time）并退出 124，SWE-agent 轨迹中记录 `exit_status=None`
- F3 实验预算：`budget=1200s`（净 agent 时间）

## 13. 可靠性机制

### 13.1 Circuit Breaker（熔断器）

当 Tool A 或 Tool B 连续失败 `SWE_AGENT_EXT_TOOL_CIRCUIT_THRESHOLD`（默认 8）次后触发熔断：
- 冷却期（默认 30s）内跳过该工具的调用
- 直接使用 **stale fallback**：上一次成功响应的缓存副本（`_last_success_payload_by_event`）
- 冷却期结束后自动恢复，失败计数归零

### 13.2 子进程环境变量继承问题

**问题（来自代码注释）：** `EvaluationFeedbackProcessor` 运行于独立 Python subprocess，可能无法继承 launcher 设置的环境变量，导致模块开关（`AGENT_MEM_BUG_INVARIANT_VERBATIM` 等）失效。

**修复：** `_env_flag()` 函数实现两路读取：
1. 先尝试 `os.environ.get(name)`
2. 若为空，读取 `AGENT_MEM_V2_CONFIG_FILE`（JSON 配置文件路径）中的对应键

Launch 脚本同时将所有模块开关写入 `{RUN_ROOT}/agent_mem_logs/v2_config.json`，并通过 `AGENT_MEM_V2_CONFIG_FILE` 环境变量传递路径，保证子进程也能正确读取。

### 13.3 记忆注入质量门控

BridgeHook 内置门控防止低质量记忆注入：
- `SWE_AGENT_MEM_GATE_MIN_EXTERNAL_RATIO=0.35`：外部记忆覆盖 prompt 预算 ≥35%
- `SWE_AGENT_MEM_GATE_MIN_BUFFER_RATIO=0.15`：保留 ≥15% 缓冲防止 context 溢出
- `SWE_AGENT_MEM_GATE_MIN_ACTION_ERROR_COVERAGE=0.60`：记忆覆盖当前 attempt 已观测错误类型 ≥60%
